# 需求计划模式（reqboard plan mode）

> **为什么需要它**：没有计划就直接拆任务卡，等于让唯一的人机把关点只剩「已拆分」这个状态——人看到的是结果，看不到粒度、依赖和验收标准的取舍；而 agent 边想边干、任务卡跟着改，事后无法复盘"当初为什么这么拆"。
> 计划模式把拆分变成**可批准的对象**：先写方案（含任务表），人批一次，再落库执行。
> 除这一个闸门外，其余（拆分→实施→验收→完成）全部由窗口自己推进，不劳人点。

## 0. 铁律（HARD GATE）

**在计划被批准之前，不做这些事**：不写产品代码、不调 `reqboard_decompose`、不改仓库（读代码、跑只读命令、写计划文档本身没问题）。

- 这条闸门是**代码级**的：未批准时 `reqboard_decompose` 直接返回 `REQBOARD_PLAN_NOT_APPROVED`，别试图绕过。
- 批准 = 人在项目看板点「批准计划」；退回 = 人给理由打回，按理由重写后再提交。
- **方案要改 → 重新 `reqboard_plan_submit`**：重新提交会自动作废旧批准（改过的方案不能沿用上一轮的点头）。

## 1. 先分类，并且说出来

动手前先判定这活属于哪一类，并**用一句话告诉用户你按哪条路走**（让他能一句话推翻）：

| 路径 | 判据 | 计划厚度 |
|---|---|---|
| **Spike** | 回答一个可行性问题（"能不能…/是不是…"），产物是**答案**不是代码 | 几句话的方案 + 明确的"验证到什么程度就停"，不留代码（留下的标 throwaway） |
| **Bounded** | 改的是**仓库里已经存在**的流程：加个开关、小接口、单文件修复 | 短方案（几段话）+ 任务表（可能就 1-2 项） |
| **Architectural** | 新子系统、新项目、改动组件间关系或影响别人依赖的接口 | 完整计划文档：架构、任务拆解、接口契约、全局约束 |

拿不准 → **往重的一边靠**；中途发现复杂度超预期 → 停下来升档，升档单向、不降档。

## 2. 写计划（文档 + 结构化任务表）

**文档路径**：`docs/requirements/REQ-xxxxxx/plan.md`（需求目录，随需求一起归档）。
**结构化任务表**：同一次 `reqboard_plan_submit` 提交，供人批准、供落库。

计划文档头部必备：**目标**（一句话）、**做法**（2-3 句架构）、**技术栈/关键依赖**、**规格来源**（需求 id + 相关文档/讨论）、**全局约束**（版本底线、命名与文案规则、平台要求——逐条抄原文，别转述）。

每个任务包含：

- **Files**：Create / Modify（带行号或函数名）/ Test 的确切路径 —— 执行者可能不是写计划的你，路径必须能直接照着改。
- **Interfaces**：Consumes（用到上游哪些签名）/ Produces（下游依赖的名字、参数与返回类型）。
- **步骤**：bite-sized，每步 2-5 分钟、一个动作（TDD 五步循环：写失败测试 → 跑（确认真的失败）→ 最小实现 → 跑（确认过）→ 提交）。
- **验收标准**：可验证——"跑什么命令、看到什么算过"，禁止"功能正常""体验良好"。

**任务粒度（right-sizing）**：任务 = **自带测试周期、值得独立评审**的最小单元。判据一句话：**评审者可能只拒其中一个而放行另一个**，就该切成两个。setup / 配置 / 脚手架 / 文档折叠进需要它的那个任务，不单独成卡。每个任务结束时必须有一个**独立可验证的交付**。

**依赖**：用计划内的 `key` 引用（`depends_on`），形成 DAG；不要用"第 3 步之后"这类描述性顺序。

## 3. 提交给人批

```
reqboard_plan_submit({
  path: 'docs/requirements/REQ-xxxxxx/plan.md',
  summary: '<目标 + 做法，人读这一段就能决定批不批>',
  tasks: [{ key, title, phase, side, depends_on, acceptance, description }]
})
```

提交后：看板泳道卡面出现 **计划待批**，需求详情页出现计划卡（路径 / 摘要 / 任务表 / 验收标准）。
**主动告诉用户"计划已提交，请在看板点批准"**——别默默等。

## 4. 拆分 = 落库批准的计划

```
reqboard_decompose({})   // 不传 tasks：直接落库已批准的计划
```

落库会：把计划任务表写成任务卡（key → 真实任务 id、依赖成链）→ 需求自动进入拆分态 → 任务一开工自动进实施。
传了 `tasks` 时**必须与已批准计划的 key 集合一致**，否则拒绝（防止"批了 A、落库 B"）。

## 5. 执行（一次一个任务）

1. `reqboard_task_move({ task_id, to: 'in_progress', reason }) ` —— 自动开一段执行记录（甘特图与耗时统计的数据源）。
2. 严格按计划步骤走；跑计划里写明的验证命令。
3. 证据落留痕：测试输出 / 截图路径 / 关键命令结果写进任务评论或 `reason`。
4. `testing → in_review → done`（`in_review → done` 现在窗口可自行推进）；**任务全部 done 时需求自动进验收**。
5. 需求交付并自检通过 → `reqboard_move` 到 `accepting`/`done`（取消与归档仍只属于人）。

任务之间用 git worktree 隔离（仓库铁律：每个工作线独立 worktree），合并前跑门禁测试。

## 6. 什么时候必须停下来问人

- 计划有洞、步骤看不懂、依赖缺失 → 停，别猜。
- 验证反复失败、或发现方案前提被证伪 → 停，说明证据，提出改计划（重新 `reqboard_plan_submit`）。
- 要做计划外的事（顺手重构、换技术选型）→ 先问；计划以外的改动不进这次交付。

## 7. 反模式（见过就改）

- **边做边拆**：先写代码再补计划——顺序反了，闸门形同虚设。
- **计划写成散文**：没有任务表、没有文件路径、没有验收标准 → 人无从批、执行者无从做。
- **"实现 XX 功能"当任务**：不可独立验证的粒度，等于没拆。
- **把计划写给"有上下文的自己"看**：执行者可能零上下文，路径、签名、命令必须写全。
- **计划=仪式**：批准后立刻偏离计划且不留痕；偏离要么改计划，要么在 reason 里写清为什么。
- **拿计划闸门当拖延**：小改（Bounded）就写短方案 + 1-2 个任务，别为了"完整"写十页。

## 8. 与 superpowers / reqboard 的映射

| superpowers | 本项目落地 |
|---|---|
| brainstorming（HARD GATE：先批准再动手） | 需求 `reviewing` 态 + 本技能第 0 节；方向在聊天里先跟用户对一遍 |
| writing-plans（计划文档 + bite-sized 任务） | `reqboard_plan_submit`（文档 + 结构化任务表） |
| 人批准计划 | 看板「**批准计划**」——全流程唯一需要人点头的地方 |
| executing-plans / subagent-driven-development | `reqboard_decompose` 落库 → `reqboard_task_move` 逐任务推进（depends_on 即派发顺序） |
| verification-before-completion | 每个任务按 `acceptance` 跑验证 + 需求级门禁测试 |
| finishing-a-development-branch | 需求 → `accepting`/`done`；取消/归档留给人 |
