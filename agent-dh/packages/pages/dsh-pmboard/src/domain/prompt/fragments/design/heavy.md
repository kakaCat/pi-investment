# 设计（design）· 完整档

> 2026-09-21 用户裁定：**设计阶段只写设计文档，不写计划**——拆分计划（任务表）归拆分阶段
> （vendor 的 writing-plans 纪律随之迁移到 decomposing 档）。本档为自写完整档。
> 设计文档写给"零上下文的执行者"看：拆分阶段的窗口只凭设计文档 + 需求文档就应能写出拆分计划。

## 1. 设计文档集（按类型模板核对，逐份落盘）

- [ ] 写进 docs/requirements/REQ-xxxxxx/design/ 目录；类型决定要交哪几份
      （缺交会在提交拆分计划时被代码级拦下）。
- [ ] 每份聚焦一个视角：架构 / 接口 / 数据模型 / 测试策略 / 风险 / 工作流划分等。
- [ ] 落盘后会被自动登记为 design 产物；若确认时报"没有 kind=design 的产物"，
      先到项目看板打开一次该需求详情触发自动登记，再重试。

## 2. 内容纪律

- [ ] **接口与数据契约先定死**：签名（参数/返回/错误码）、字段（类型/约束）——定不死不许进拆分。
- [ ] **文件结构先定**：哪些文件新建/修改/删除，各自职责一句话；这是拆分阶段做变更盘点的依据。
- [ ] **不写任务表**：任务 DAG、批次、depends_on 是拆分阶段的产物，设计阶段不出现。
- [ ] **验收口径可执行**：跑什么命令、看到什么算过；空话验收打回。
- [ ] **边界写清不做什么**：防范围蔓延；与设计矛盾的拆分诉求应退回本阶段改设计。

## 3. 确认闸门 + 交棒

- [ ] 肯定答复自动落章并推进到 decomposing（看板一键确认同样有效）；
      用户提修改意见 → 就地改设计文档后重新确认。
- [ ] 下一步：decomposing —— 用 reqboard_ask_confirm(target=artifact, kind=design) 交棒；未获批准不得进入。
