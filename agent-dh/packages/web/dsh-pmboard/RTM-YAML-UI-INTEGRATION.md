## 🎯 RTM YAML 集成方案

### 方案A：新增「追溯」Tab（推荐）

**位置**：在现有 4 个 Tab 后新增第 5 个

**内容**：
1. 追溯链可视化（垂直瀑布式）
2. 覆盖度统计卡片（设计/实施/测试）
3. 缺口列表（未覆盖的 FR/设计/任务）

**优点**：
- ✅ 不影响现有 Tab 布局
- ✅ 独立的追溯视图，信息密度合适
- ✅ 适合详细查看追溯关系

### 方案B：增强「执行」Tab（推荐）

**位置**：在执行 Tab 的统计卡片后、DAG 图前

**新增内容**：追溯覆盖度统计卡片

**优点**：
- ✅ 不需要新增 Tab
- ✅ 覆盖度统计与任务统计并列，信息密度高
- ✅ 适合快速查看总体进度

### 方案C：增强「时间线」Tab

**位置**：在条款接收状态后新增追溯详情

**优点**：
- ✅ 条款接收状态 + 追溯链语义相关
- ✅ 时间线 Tab 原本就是查看详细信息的地方

## 🚀 推荐实施方案

### 阶段1：后端 RTM YAML 生成（优先）

**文件**：packages/web/dsh-pmboard/src/application/internal/rtm-generator.ts

**核心函数**：

1. generateRTM() - 生成完整 RTM 文档
2. writeRTM() - 写入 YAML 文件
3. updateRTM() - 任务更新时增量更新

**集成点**：
- 批准计划时生成 (confirm-settle.ts 第 200-260 行)
- 任务状态更新时更新 (ReportTask.ts)

### 阶段2：前端读取 RTM

**API 端点**：GET /api/requirements/:id/rtm

**降级策略**：
- RTM YAML 存在 → 读取并解析
- RTM YAML 不存在 → 实时生成（调用 checkFullTraceability）

### 阶段3：前端展示追溯链

**方案选择**：方案B（增强执行 Tab）+ 方案C（时间线 Tab 详情）

#### 3.1 执行 Tab - 覆盖度卡片

在现有任务统计卡片后新增三个追溯覆盖度卡片：
- 设计覆盖：X/Y FR 有设计
- 实施覆盖：X/Y 设计有任务
- 测试覆盖：X/Y 任务有测试

颜色编码：
- 绿色：100% 覆盖
- 黄色：50-99% 覆盖
- 红色：<50% 覆盖

#### 3.2 时间线 Tab - 追溯链详情

在条款接收状态后新增追溯链详情：
- 需求层（列出所有 FR，标注是否有设计）
- 设计层（列出所有设计章节，标注 serves 和是否有任务）
- 任务层（列出所有任务，标注 implements 和是否有测试）

## 📈 数据流

批准计划
  ↓
confirm-settle.ts (批准后自动生成 rtm.yml)
  ↓
docs/requirements/REQ-xxx/rtm.yml
  ↓
GET /api/requirements/:id/rtm (读取或实时生成)
  ↓
前端 fetch (stage-detail.ts 加载时)
  ↓
渲染追溯链 (执行 Tab 卡片 + 时间线 Tab 详情)

## 🔄 降级策略
