# 正确对比：看板 vs 会话右侧流程图节点

> 分析日期：2026-09-26

---

## 🎯 两个 UI 的区别

### 1. 看板（Board）

**位置**：`/dashboard#pmboard`（独立页面）

**文件**：`packages/web/dsh-pmboard/src/client/views/board.ts`

**作用**：
- 📊 多需求管理（项目级视图）
- 📋 看板泳道（draft/brainstorming/design/...）
- 🔍 需求列表、筛选、搜索
- 📈 进度统计

**数据源**：
- 台账（requirements.json）
- 全部需求列表

**用户**：
- PM 查看全局进度
- 多个 Agent 协作

**典型场景**：
- 查看所有进行中的需求
- 拖动需求卡片到不同泳道
- 点击需求卡 → 进入需求详情页

---

### 2. 会话右侧流程图节点（Node Panel）

**位置**：会话页面右侧（跟随会话上下文）

**文件**：`packages/web/dsh-pmboard/src/client/node-panel.ts`

**作用**：
- 🔍 单需求深入（需求内部视图）
- 📍 8 个节点流程图（draft → archived）
- 📝 每个节点的详细信息
- ⚙️ 实施节点：DAG / 泳道 / 追溯（计划新增）

**数据源**：
- StageOverview（单个需求的 8 个节点详情）
- 当前会话绑定的需求

**用户**：
- Agent 在会话中工作
- 查看当前需求的流程进度

**典型场景**：
- Agent 在会话中处理需求 REQ-xxx
- 右侧自动显示该需求的流程节点
- 点击节点 → 查看该阶段详情（文档/任务/进度）

## 💡 RTM YAML 与两个 UI 的关系

### 1. RTM YAML 的定位

**RTM YAML** = 单需求内部流程的数据记录本

- 📝 从立项开始创建
- 📈 跟随需求全生命周期更新
- 🔗 记录四级追溯链
- 📊 实时反映覆盖度统计

### 2. RTM 与看板的关系

**看板不直接使用 RTM**

看板只需要：
- 需求 ID / 标题
- 当前状态（哪个泳道）
- 简单统计（任务数、完成数）

**原因**：
- 看板是多需求概览，不需要深入每个需求内部
- RTM 数据太详细，看板用不上

### 3. RTM 与会话节点的关系（核心）

**会话节点是 RTM 的主要展示位置** ✅

会话节点的「追溯」Tab 读取 RTM：
- 📋 需求层（从 RTM 读取）
- 🎨 设计层（从 RTM 读取）
- ⚙️ 任务层（从 RTM 读取）
- 📊 覆盖度统计（从 RTM 计算）

**原因**：
- 会话节点聚焦单需求内部
- Agent 在会话中工作，需要看到追溯关系
- RTM 数据粒度与会话节点匹配

## 🔄 完整数据流（修正版）

```
立项（reqboard_create）
  ↓
创建 rtm.yml（骨架）
  ↓
需求全生命周期更新 rtm.yml
  ↓
会话节点读取 rtm.yml
  ↓
实施节点的「追溯」Tab 显示
  ├─ 📋 需求层
  ├─ 🎨 设计层
  ├─ ⚙️ 任务层
  └─ 📊 覆盖度统计

（看板不使用 RTM，直接从台账读取）
```

---

## ✅ 核心结论

### 看板（Board）
- 多需求管理
- 不使用 RTM
- 数据来源：台账

### 会话右侧流程图节点（Node Panel）
- 单需求深入
- **主要使用 RTM** ✅
- 数据来源：StageOverview + RTM YAML

### RTM YAML
- 单需求内部的数据记录本
- **主要展示位置：会话节点的追溯 Tab**
- 从立项开始持续更新

---

## 🎯 RTM 集成的正确理解

**RTM YAML 是为会话右侧流程图节点设计的**

- ✅ Agent 在会话中工作
- ✅ 右侧节点显示当前需求进度
- ✅ 点击「追溯」Tab 看到完整追溯链
- ✅ RTM 提供追溯数据

**看板不需要 RTM**

- ✅ 看板只需要简单的需求列表和状态
- ✅ RTM 的详细追溯数据对看板来说太重了
