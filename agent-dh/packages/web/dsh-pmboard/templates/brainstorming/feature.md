# 需求说明（{{REQ_ID}}）

> 本文档面向：产品、开发、测试、用户——写给人看，不是写给代码看。
> 核心原则：**用户能看懂**——不写技术术语，用场景和结果说话。

## 产品定义 <!-- serves: FR-1 -->

（一句话说清楚这个产品是什么、核心价值是什么——电梯演讲版本。）

**填写示范**：
- ❌ 错误："一个模板系统"（太模糊）
- ✅ 正确："需求文档自动生成系统：PM 新建需求时，系统根据需求类型（feature/bug/refactor...）
  自动生成对应的文档骨架，包含必填章节和填写提示，让 PM 和开发只需填空而非从零写起。
  核心价值：从'记不住要写什么'到'照着模板填'，降低文档门槛、提高质量一致性。"

**三要素检查清单**：
- [ ] 说清楚"是什么"（产品定位）
- [ ] 说清楚"核心价值"（解决什么痛点）
- [ ] 说清楚"与现状的区别"（为什么不用现有方案）


## 目标用户与使用场景 <!-- serves: FR-1 -->

（三问：谁用 / 什么场景用 / 解决什么痛点——具体到岗位/角色，不写"用户"这种空话。）

**填写示范**：
- ❌ 错误："用户使用系统时需要模板"
- ✅ 正确："PM 新建需求时，需要填写需求说明、设计文档、测试用例等 9 类文档。

## 边界（不做什么） <!-- serves: FR-1 -->

（明确说"不做"比说"做"更重要——防止范围蔓延、防止用户期望错位。

**填写要求**：
- 列出**容易被误解为"应该做"的事**
- 每条带理由：为什么不做 / 什么时候再做

**示范**：

- ✅ 正确："暂不支持用户自定义模板格式（如增删章节、改章节名）——
  原因：本期聚焦于『有模板』解决从 0 到 1 问题，定制化留待 P2 需求收集后统一设计"）

- 不做 A：（理由）
- 不做 B：（理由）

## 非功能需求 <!-- serves: FR-1 -->

（性能 / 安全 / 兼容性等指标——有明确数字要求才写，没有就不写。

**填写要求**：
- 指标必须**可测量**：不写"性能好"，写"接口响应 P95 < 200ms"
- 注明**测试方法**：怎么测、用什么工具

**示范**：
- 性能：模板加载时间 < 100ms（浏览器 Network 面板测量）
- 安全：模板内容不含用户隐私数据，不走网络传输（本地文件系统）
- 兼容：支持已有需求（无 artifacts 记录）不受影响，行为与现状一致）

## 验收标准（整体） <!-- serves: FR-1 -->

（全部功能点交付后，整体验收的标准——通常是端到端场景。

**填写要求**：
- 写**完整用户旅程**：从进入到完成的全流程
- 每个关键步骤有**可观测的结果**

**示范**：
1. PM 新建 feature 需求"优化搜索性能"
2. 系统自动生成 requirement.md，包含目标用户/功能点/边界等 7 个章节
3. PM 填写需求后提交，进入设计阶段
4. 系统自动生成 frontend.md / backend.md / interfaces.md 三份设计文档
5. 开发人员打开设计文档，看到章节骨架和接口表格模板
6. 全流程无需手动创建 md 文件，无必填章节遗漏导致的返工）
