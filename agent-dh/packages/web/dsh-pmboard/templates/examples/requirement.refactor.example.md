# 需求说明（REQ-example-refactor）

> 状态：需求分析（brainstorming） · 窗口 w-example · 立据：2026-09-22
> 宣布路径：Architectural（改动跨越 capture-section / H3 / 输入包三处注入点，接口面会被收拢）
> **流程图规范**：一律 ASCII 字符画（svgbob 风格），不用 mermaid。
> **编号规范**：本仓按类型前缀（refactor=RF-x）。

## 项目背景与动机

三个阶段提示词注入点（系统提示词段、闸门后置链 H3、节点输入包）**各自拼一次注入文本**，
同一份「本节点文档（模板地址）」要写三遍、改一处漏两处；上次新增地址段就是三处分别改的。

数据支撑：近 30 天因注入段不一致导致的返工 3 次；三处拼接代码合计 4 份重复字符串常量；
新增一个注入要素的平均改动点 = 3 个文件。

## 产品目标

- G1 （P0）注入段只在一处装配，三处注入点共用同一函数——新增一个注入要素只需改 1 个文件。
- G2 （P1）装配结果可单测：给定 (stage, category, requirement) → 文本可断言，不依赖会话。

## 非目标

- N1 不改注入的**内容口径**（仍是阶段纪律 + 模板地址 + 上游必读三类，不新增要素）。
- N2 不引入运行时读盘（装配器是纯函数，模板索引仍模板清单自动生成）。

## 术语与措辞纪律

| 术语 | 定义（一句话） | 首次出现位置 |
|---|---|---|
| 注入段 | 一次注入里除阶段纪律之外的附加文本（模板地址 / 上游必读） | 项目背景 |
| 装配器 | 把 (stage, category, requirement) 映射为注入段的纯函数 | 产品目标 |

禁用模糊词：不得出现"应该会""大概一致""视情况拼接"；一致/不一致写明确。

## 边界（不做什么）

- 不做「把三处注入点合并成一个」——它们的触发时机不同（系统段求值 / 闸门后置 / 输入包），只统一**装配**，不统一**时机**。
- 不做模板内容改动与落盘（另属模板包需求）。
- 不改门禁、台账协议与客户端渲染。

## 验收标准

- [ ] rg 全仓，注入段字符串常量只剩装配器一处（其余为调用）。
- [ ] 单测：装配器对 (design, feature) 输出与改造前**逐字节一致**（黄金样本对比）。
- [ ] H3 与输入包两路径注入文本相等（同一函数）。

## 用户分析

| 用户角色 | 特点 | 痛点 |
|---|---|---|
| 维护窗口 | 改注入逻辑的人/agent | 三处各一份，改一处漏两处，回归靠人眼比对 |
| 评审人 | 看注入变更的人 | 无法判断三处是否一致，只能逐个读 |

## 用户与角色（用户分析）

维护窗口负责装配器实现与三处接线；评审人只审装配器一处输出（黄金样本 + 单测）。

## 核心场景

### 场景 1：新增一个注入要素

维护窗口在（要给注入段加一类新信息）的情况下，为了（不遗漏任何一个注入点），
做了（只改装配器一处并跑单测），实现了（三处注入点同时生效、输出一致）。

### 场景 2：审查注入变更

评审人在（有人改了注入文案）的情况下，为了（快速确认三处一致），
做了（只读装配器的黄金样本 diff），实现了（无需逐个文件比对）。

## 业务流程

1. 维护窗口改动装配器（一处）。
2. 跑单测：黄金样本对比 + 三路径一致性断言。
3. 不通过 → 回到 1；通过 → 提交。
4. 评审人只审该函数与其黄金样本。
5. 发布（重启后生效）。

## 改动对比（整体 · 修改与删除必须给出原文）

| 项 | 变更类型 | 现状（改前原文） | 改动后（新原文） | 说明 / 影响面 |
|---|---|---|---|---|
| 注入段拼接 | M | 三处各写一份 sectionLines.push(...) | 三处统一调用 buildInjectionSection(...) | 无接口变化；H3/输入包输出必须逐字节一致 |
| 重复字符串常量 | D | （见下"删除内容原文"） | 删除 | 收拢到装配器 |
| 装配器 | A | — | buildInjectionSection(stage, category, requirement) | 新增文件，纯函数 |

删除内容（原文，整段贴）：

~~~
// capture-section.ts
const templateSection = renderTemplateAddressSection(stage, stageReq.category, stageReq)
if (templateSection.length > 0) lines.push('', templateSection)

// h3-inject.ts
scratch.promptText = resolved.text + renderTemplateAddressSection(...)

// node-input-package.ts
text = fmt([... , '## 本节点文档', '{tpl}'].join('\n'), {...})
~~~

删除理由：同一逻辑三份实现（改一处漏两处；近 30 天返工 3 次，证据见背景数据）
替代方案：由 buildInjectionSection 统一产出，三处只调用
回滚方式：git revert <commit>（三处调用点一并回退）

## 功能点明细（原型 + 流程图 + 规则 + 变动对比）

### RF-1 注入段统一装配

**① 原型**：本需求无界面，无原型（备注：无界面功能可省略本项，其余三项不得省）。

**② 流程图（ASCII 字符画 · 本功能点的任务流程图）**

~~~
   [维护窗口改装配器] --> <单测：黄金样本一致?> -- 是 --> [三处生效] --> [提交]
                                   |
                                   +-- 否 --> [回到装配器修改] --> <重跑>
~~~

（先正常态、后异常态；布局从左到右、从上到下。）

**③ 规则与异常**

- 功能逻辑：装配器 = 模板地址段 + 上游必读段；未命中返回空串。
- 交互逻辑：无界面交互（宿主侧）。
- 视觉逻辑：无。
- 技术逻辑：纯函数、零 I/O、不 import node:；单测不落盘。
- 业务逻辑：注入内容口径不变（三类要素）。
- 输入 / 输出：入参 (stage, category, requirement) → 输出 string（可空）。
- 后置条件：三处注入点文本相等，且空集时与改造前逐字节一致。

测试思维自检：正常（有模板）/ 空数据（无模板）/ 错误输入（未知 stage）/ 边界值（类型无该节点模板）/ 超时重试（不适用）/ 并发重复（纯函数，天然幂等）/ 无权限（不适用）/ 中断恢复（无状态）。

交互说明：不适用（无界面）。状态 × 展示枚举：不适用（无界面状态）。列表/表单六项：不适用。
