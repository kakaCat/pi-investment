# 需求说明（REQ-example）

> 状态：需求分析（brainstorming） · 窗口 w-90f10b62 · 立据：用户 2026-09-23
> 宣布路径：**Architectural**——新增模板生成器 + 节点落盘钩子 + 注入机制，
> 涉及多文件与新机制，走完整流程（用户认可）。

## 背景与动机

用户原话：

> 「插件里要有一个默认模版，因为我们是插件，不能让用户自己写模版」
> 「模板下应该按照节点创建文件夹」
> 「类型对应的中文 在立项弹框没展示」

现状缺口（逐条实测，非推测）：

1. 模板只存在于 `docs/requirements/_template/`（仓库 docs 层），**插件内没有任何模板**——
   新部署/新用户拿到的插件是空手的；
2. 写作侧零指引：brainstorming 提示词片段里 grep「边界/必填节/产品定义」**零命中**，
   LLM 写 requirement.md 纯自由发挥；
3. 必填节校验滞后：missingCategoryDocs 首次触发在「提交拆分计划」——
   不合规文档带病走两个节点才被打回返工；
4. 既有 `_template/requirement.md` 还引用已废弃的 plan.md（2026-09-21 裁定后代码已改、文档没跟上）。

## 目标

| 编号 | 目标 | 价值（解决什么问题/对谁的价值） | 衡量指标 | 目标值 |
|---|---|---|---|---|
| G1 | 插件内置全套默认模板（17 类，按产出节点分目录） | 新部署不再空手起步 / 对所有窗口 | 模板文件数 | 17 类全覆盖 |
| G2 | 进入节点时自动落盘骨架（幂等） | 写作侧零指引 → 落笔即合规 / 对窗口 agent | 骨架落盘成功率 | 100% |
| G3 | 注入只给"指针+必填节清单" | 上下文不被模板全文挤占 / 对窗口 agent | 注入字符数 | ≤ 500 字符/次 |
| G4 | 必填节校验前移到提交需求文档时 | 不合规文档不再带病走两节点 / 对审核者 | 一次通过率 | ≥ 80% |


## 非目标

- N1 不改门禁规则本身（必填节清单、转移表不动）
- N2 不改文档放置规范（docs/ 决策树不动）
- N3 不做模板的前端编辑 UI（看板预览走既有文件服务接口即可）

## 产品定义

是：reqboard 流水线的「文档脚手架」能力——让每个需求的每份文档从骨架开始、与门禁同源。
不是：模板市场 / 用户自定义模板系统 / 文档编辑器。

## 用户与角色（用户分析）

| 角色 | 特点 | 痛点 | 核心诉求 |
|---|---|---|---|
| 窗口 agent（主要使用者） | 每会话新开，不携带规范记忆 | 不知道必填节，自由发挥后被门禁打回返工 | 骨架已就位，只填内容 |
| 人类用户（审核者） | 抽审多份需求文档 | 每份结构不一，评审无固定抓手 | 结构一致，必填节/serves 标注可作锚点 |
| 新部署环境 | 只有插件没有宿主仓库 docs | 插件不自带模板，空手起步 | 装上即有模板 |

## 核心场景

- 场景一：**窗口 agent** 在（接手一个 feature 需求、刚进入需求分析节点）的情况下，为了（写出合规的需求文档），（打开已自动落盘的 requirement.md 骨架，逐节填入与用户讨论出的内容），实现了（一次通过必填节校验，无需返工）。

## 功能点明细

### FR-3 节点落盘钩子

- 用例角色：窗口 agent（间接受益：人类审核者）
- 前置条件：需求已立项且 category 已确定；templates/ 对应节点文件夹存在本类型模板
- 交互流程：1. 节点转移事件到达 → 2. 查该节点文件夹有无本类型模板（无→跳过无副作用）→
  3. 目标文件已存在？（是→跳过不覆盖）→ 4. 落盘骨架 → 5. 登记 notes 产物 + 注入指针
- 后置条件：需求目录存在该节点的骨架文档；台账产物区可见；已有内容零改动
- 触发条件：requirement 状态转移成功（transitionRequirement 后置钩子）
- 规则与反馈：模板选择键 = 节点文件夹 + `requirement.<category>.md`；
  落盘幂等（exists 即跳过）；落盘后登记产物供看板可见
- 异常处理：模板缺失 → 记告警日志不阻断转移（骨架是增益不是前置）；
  磁盘写失败 → 响亮报错进 comments，转移本身不回滚

## 非功能需求

- 性能：落盘钩子 < 50ms（同步路径上的文件写，不阻塞转移）
- 兼容：存量需求（无 artifacts）不触发落盘，行为与现状一致
- 安全：骨架只写需求目录内路径；模板常量不含任何凭据/内部地址
- 其他：落盘与跳过都要留审计（notes 产物登记或日志）

## 风险评估

| 编号 | 风险名称 | 场景描述 | 风险级别 | 如何规避 |
|---|---|---|---|---|
| R-1 | 骨架覆盖已写内容 | 落盘逻辑误覆盖人/agent 已写的文档 | 高 | 预防：幂等"不存在才写"硬约束 + 故障注入测试 |
| R-2 | 模板与门禁漂移 | 门禁规则改了、模板没跟上（历史事故重演） | 中 | 预防：check-templates.mjs 门禁，源改未重跑即 exit 1 |
| R-3 | 注入膨胀 | 模板全文进提示词挤占上下文 | 中 | 预防：只注入"指针+必填节清单"，token 预算卡口 |

## 边界（不做什么）

- 不做用户自定义模板上传/覆盖机制（本期模板只有内置一份）
- 不迁移存量需求的既有文档（旧文档保持原样，模板只对新建需求生效）
- 转移层分类感知缺口（跳级转移/人工门走档案）另立项，不在本需求范围

## 验收标准

- [ ] 新立 feature 需求后，`docs/requirements/<REQ>/requirement.md` 自动落盘且
      `missingCategoryDocs` 校验通过（空骨架即合规）——跑 vitest 断言
- [ ] bug 需求进入 design 节点时落盘 `requirement.bug.md` 骨架，含「复现步骤/根因/回归」节
- [ ] 模板源文件改动后 `check-templates.mjs` 未重跑生成器 → exit 1（故障注入实测）
- [ ] 构建后 dist 内含模板常量（grep 命中），profile 重启后新立项自动落盘（线上验证）
