# 需求说明（REQ-example）

## 目标用户与使用场景 <!-- serves: FR-1 -->

**谁用**：PM（产品经理）、前端开发、后端开发、测试工程师

**什么场景用**：
- PM 新建需求后，需要填写需求说明文档、设计文档（frontend/backend/interfaces）、测试用例等 9 类文档
- 开发人员接到需求后，需要填写设计细节、拆分任务、编写测试用例
- 测试人员需要根据设计编写测试用例、执行测试、记录结果

**解决什么痛点**：
1. **当前问题**：每次手动创建空白 md 文件，忘记必填章节导致验收时返工（实测：平均每个需求返工 2 次，浪费 1 小时）
2. **用户期望**：新建需求时，系统自动生成对应阶段的文档模板，打开就能看到章节骨架和填写提示
3. **业务价值**：节省文档准备时间（预计 5 分钟/需求），降低返工率（目标：从 40% 降到 10%）

## 功能点（需求条款） <!-- serves: FR-2 -->

| 编号 | 功能（用户视角场景，禁止技术术语） | 验收标准（可证伪：做什么 → 看到什么） |
|---|---|---|
| FR-1 | 新建需求时，系统根据需求类型（功能/bug/重构等）自动生成对应的文档模板，用户打开文档就能看到章节骨架和填写提示 | 新建 feature 需求 → 进入需求分析阶段 → 打开 requirement.md → 文件包含「目标用户」「功能点」「边界」三个必填章节 + 每个章节下有填写提示 |
| FR-2 | 浏览器端可以预览模板内容（不经过文件系统），方便产品/开发在线查看模板格式 | 在需求详情页点击"预览模板"按钮 → 弹窗展示 requirement.md 模板全文 → 内容与实际落盘的文件一致 |
| FR-3 | 模板落盘具有幂等性：重复进入同一阶段不会覆盖已有文档，避免用户填写的内容丢失 | 用户手写 requirement.md 填充内容后 → 需求退回到 brainstorming 再进入 → 打开 requirement.md → 内容与手写版一致，未被模板覆盖 |
| FR-4 | 节点输入包包含模板文件指针，AI 窗口可以引用模板进行填写指导 | 窗口执行需求分析任务 → 调用节点输入包 API → 返回值包含 template_files 数组（路径+必填章节清单） |
| FR-5 | 提交文档时前移校验必填章节，缺失时拒绝提交并提示缺少哪些章节 | requirement.md 缺「边界」章节 → 点击"提交"按钮 → 弹窗提示"文档缺少必填章节：边界（不做什么）" → 提交失败 |
| FR-6 | CI 门禁检测模板源文件与生成产物是否一致，防止改了源文件忘记重新构建导致线上陈旧 | 修改 templates/brainstorming/feature.md 源文件但未运行 pnpm build → 提交代码触发 CI → check-templates.mjs 检测到漂移 → CI 失败并输出"模板源改动但 dist 未更新" |

## 边界（不做什么） <!-- serves: FR-3 -->

- **不支持用户自定义模板格式**（如增删章节、改章节名）——原因：本期聚焦于『有模板』解决从 0 到 1 问题，定制化留待 P2 需求（3 个月后）收集用户反馈后统一设计
- **不支持模板热更新**（改模板源文件后必须重新构建）——原因：模板是模板清单自动生成为常量，运行时不读文件系统（支持浏览器端预览的技术约束）
- **不支持模板版本管理**（旧需求无法回退到旧版模板）——原因：模板内容变更频率低（预计每季度 1 次），版本管理增加复杂度，ROI 低
- **不支持多语言模板**（仅中文）——原因：用户全部为中文母语者，暂无国际化需求

## 非功能需求 <!-- serves: FR-4 -->

- **性能**：
  - 模板加载时间 < 100ms（浏览器端，测量方式：Network 面板 TTFB）
  - 模板落盘时间 < 200ms（17 个文件并行落盘，测量方式：node-entry 钩子耗时日志）
  - 构建耗时增加 < 5s（inline-templates 生成器，测量方式：pnpm build 总时长对比）

- **安全**：
  - 模板内容不含用户隐私数据（所有模板都是通用骨架，无业务数据）
  - 模板 key 参数校验：拒绝路径遍历字符（../、绝对路径），防止读取任意文件

- **兼容**：
  - 存量需求（无 artifacts 记录）不受影响，行为与现状一致（不自动生成模板，保持空白）
  - 旧版本窗口（未升级代码）仍能正常提交，只是没有模板落盘功能

## 验收标准（整体） <!-- serves: FR-5 -->

完整用户旅程（从新建需求到提交文档）：

1. PM 在项目看板点击"新建需求"，填写标题"优化搜索性能"，类型选择 feature，点击"创建"
2. 系统创建需求 REQ-001，自动进入 brainstorming（需求分析）阶段
3. PM 点击右侧"文档"标签页，看到 requirement.md **已自动生成**（绿色"已生成"标签）
4. PM 点击 requirement.md，编辑器打开文件，看到章节骨架：
   - # 需求说明（REQ-001）
   - ## 目标用户与使用场景（三问：谁用 / 什么场景用 / 解决什么痛点）
   - ## 功能点
   - ## 边界（不做什么）
   - ...（其他章节）
5. PM 在骨架上填写内容，保存后点击"提交"按钮
6. 系统校验通过（必填章节齐全），需求进入 design（设计）阶段
7. 前端开发进入需求详情页，点击"文档"标签页，看到 frontend.md / backend.md / interfaces.md **已自动生成**
8. 开发人员打开设计文档，看到表格模板（编号列已填充 P-1/C-1/S-1/I-1）
9. 开发人员填写设计后提交，需求进入 decomposing（拆分）阶段
10. 全流程无需手动创建 md 文件，无必填章节遗漏导致的返工

## 依赖与约束 <!-- serves: FR-6 -->

**依赖**：
- 需求看板系统已有节点转移钩子机制（强依赖）——本需求监听 node.entered 事件触发模板落盘
- 工作区目录结构遵循 docs/requirements/<REQ>/*.md 规范（强依赖）
- SQLite 数据库已有 artifacts 表（强依赖）——用于登记模板产物，支撑幂等性检查

**约束**：
- 模板文件格式必须是 markdown（已有文档都是 md，不能引入其他格式）
- 模板目录结构遵循现有分类：brainstorming / design / decomposing / implementing / accepting / archived
- 构建工具使用 tsdown（已有 dsh-pmboard 包的构建工具，不引入新工具）
- 浏览器端模板读取不能依赖 fs 模块（浏览器无文件系统 API）
