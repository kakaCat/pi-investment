## 本仓铁律（所有节点共用；与上文任何冲突措辞以此为准；priority=floor，永不裁剪）

- [ ] **批准闸门永不伸缩**：仪式强度可以随任务伸缩，**批准闸门不行**。每一步推进前，
      该阶段产物必须经人确认——调 `reqboard_ask_confirm` 弹框（落章 + 推进原子完成），
      或由人在看板上点确认。未获批准不得进入下一步，不得以"太简单"为由跳过。
- [ ] **产物闸门由代码兜底**：未确认产物时 `reqboard_move` 会被代码级拒绝
      （artifact_not_confirmed）。不要把代码级拒绝当成可以绕过的提示。
- [ ] **清单纪律**：以可勾选清单（`- [ ]` 或编号）逐项执行并逐项确认，禁止散文式步骤；
      清单项未完成不得宣称本节点完成。
- [ ] **交棒唯一**：本节点结束只能按末尾「下一步」行交棒，不得跳级、不得同时开多个下一节点。
- [ ] **失败要响亮**：证据缺失 / 预算超限 / 边界不平衡一律结构化报出，
      禁止静默降级或以"应该没问题"收尾。
- [ ] **确认门对话优先（REQ-260922213356-4a45 FR-9/FR-11）**：用户的提问先在对话里回答；只有需要人裁决的
      产物/计划才发起确认门，弹框里只放结论、链接与推进目标，一个节点只在该闸门弹一次。
- [ ] **文字确认走 evidence**：用户在对话里明确说"确认"，用 `reqboard_ask_confirm` 的 evidence 路径把
      答复原文落章推进（不弹框）；答复是"需修改"则返工，不推进、也不注入下一节点纪律。
- [ ] **同一产物不重复弹框**：目标产物已确认（或计划已批准）时直接返回，不再弹框；弹框超时/中断也不自动重弹。
- [ ] **人工门反馈处理**：人工门（`reqboard_ask_confirm` / `reqboard_accept_sheet`）返回用户反馈时
      （`confirmed=false` + `user_feedback`，或验收单 `failed > 0` + 返工卡），**必须先处理反馈**：
      ① 回答用户提出的问题或疑虑；② 根据反馈意见修改产物/代码；③ 修改完成并验证通过后，
      再考虑重新提交确认/验收。**禁止立即重新调用人工门工具**——反复弹框是最差体验；
      把用户反馈当作普通对话处理，正常沟通、修改、验证，完成后自然进入下一轮确认流程。
      验收返工时，先调 `reqboard_status` 查看返工卡及用户意见，再按意见逐项修改。
