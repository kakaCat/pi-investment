# quantsys-v2 能力诚实评估：真能解决问题吗？

> 调查：investor @ w-ac60b8e8，2026-09-02
> 背景：工具补齐过程中对 v2 后端做了全链路实测（curl + 数据库直查 + 任务清单审计），不停留在"接口通"，验证"数据链路是否真活"。

## 结论先行

**v2 的"零部件"大多能工作，但"整车"不可靠。** 功能模块代码存在、接口能调通、算法正确；但维持数据新鲜的日常任务大面积停用/无可靠宿主，模型质量是弱信号，且"写出来但从未被真实调用"的路径密度高。最有效的改进方向不是加新功能，而是**把数据管道挂到可靠宿主 + 清理死模型/死路径**。

## ✅ 真正可用的（本轮实测验证）

| 能力 | 验证方式 | 结论 |
|------|---------|------|
| 数据查询层（行情/K线/财务/筹码/板块） | curl 多接口 | 稳定可用 |
| swing_points ZigZag | 601857 实调 46 拐点/22 笔 | 算法正确（修 DI 后） |
| 决策审计闭环 | record→history→evaluate 全链路 | 真实回填 outcome + 提炼 lesson |
| 盘前挂单撮合 | 挂单 3 笔实测 + orchestrator 代码审计 | 可靠：宿主=FastAPI 进程内 60s tick（8:00-17:59 工作日），不依赖被禁用的 Agent OS 任务 |
| watch 引擎 | conditions.py 代码审计 + 规则创建实测 | 5 种条件真实求值、冷却、自适应频率 |
| ML 管线（lightgbm） | 4 只标的实调 | 特征与 DB 因子同源、每日重训（cron 周一 3:00+每月强训）、输出有区分度（0.52~0.67）、有上线门禁 |

## ⚠️ 半可用 / 弱信号

| 问题 | 实测证据 | 影响 |
|------|---------|------|
| **ML 模型弱信号** | lightgbm_20260901：test_acc 0.569 / test_roc_auc 0.582 / recall 0.284 | 只能当第 4 辅助维度，不能驱动决策；需要更好的标签/特征才能升级 |
| **xgboost 旧模型是死的** | 任意标的输出恒定 0.4659；特征名与 DB 因子不匹配 | model_predict 误默认 xgboost 时输出垃圾（已修默认值为 lightgbm）；建议下线或重训 |
| **因子新鲜度不均** | factor_values：8-31 仅 10 只有新因子、8-28 4538 只、9-01 因子缺失 | ML 特征日期滞后（预测返回 date=8-27/8-31 混杂） |
| **K线新鲜度不均** | 601857/002241/300750 停在 8-27，600519 到 8-31 | swing_points/技术分析对滞后标的失真 |
| 财务数据源脆弱 | agent-ts 会话实测"所有财务数据源均不可用"（8-30） | 基本面维度偶发缺位 |

## ❌ 结构性风险（同一事故模式反复出现）

1. **"进程死了没人知道"**：orchestrator/watch engine 都曾静默死亡多天（v2 代码注释自认两次事故：08-05 后 orchestrator 死 8 天致 T+1 不结转；WatchEngine 08-02~12 静默消失）。当前解法（关键循环寄生 FastAPI 进程）方向正确，但数据同步类任务没有这个待遇。
2. **Agent OS 调度器名存实亡**：43 个任务中核心数据任务（kline_update/factor_compute_daily/data_pipeline_daily/chip_distribution_update/data_quality_check）**全部禁用**，启用的多为 /bin/true 占位壳——数据新鲜度没有系统级保障，实际依赖 agent 盘后例程自觉驱动。
3. **"未被真实调用过"的代码密度高**：本周修掉的 3 个必炸 bug（swing DI 未注入、decision_service getter 未调用、ctx.tools.call 不存在）全是"写出来但从没跑通过"的路径。教训（已入 genome）：字段假设必须用真实数据验证，故障路径必须故障注入实测。

## 建议（按杠杆排序）

1. **数据管道挂靠可靠宿主**（最高杠杆）：把 kline 每日同步 + 因子每日计算并入 FastAPI 进程内 orchestrator tick（与挂单撮合同宿主），或由 agent-dh 盘后例程显式承担（kline_daily_sync 工具已存在）——二选一，但必须有一个明确 owner。
2. **下线 xgboost 旧模型**（或加路由层拒绝）：避免任何调用方误用死模型。
3. **决策评估积压清理**：180 条 pending（agent-ts 时代）用新 /api/decisions/evaluate 低峰期批量清理。
4. **ML 模型升级**：当前特征集（34 个技术因子）info 含量有限，recall 0.28 说明漏掉大部分上涨——考虑加入资金流/主线/regime 特征，或调整标签 horizon。
5. **新鲜度监控进告警**：factor/kline 最新日期滞后 >1 交易日时自动告警（现有 data_quality_report 可扩展）。
