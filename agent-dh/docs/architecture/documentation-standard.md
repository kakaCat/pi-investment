# 项目文档规范

**唯一事实源**：本文件是项目文档体系的权威定义。所有需求、设计、实施文档必须遵循此规范。

## 核心原则：文档是一条问答链

**每份文档回答一个问题，下一份文档承接它的答案。**

| # | 文档 | 回答的问题 | 承接自 | 产出 |
|---|------|-----------|--------|------|
| 1 | **需求文档** | **做什么** | 用户意图 / 问题现象 | 功能点清单（编号）+ 边界 + 成功标准 |
| 2 | **技术设计文档集** | **怎么做** | 做什么 | 架构 / 数据 / 接口（含前后端）/ UI / 迁移 / 测试用例 |
| 3 | **拆分文档** | **分几步，每步完成什么** | 怎么做 | 步骤清单（编号）+ 每步产出 + 覆盖对照 |
| 4 | **实施文档** | **照着做** | 分几步 | agent 的指令：改哪些文件、什么顺序、怎么验证 |
| 5 | **验收** | **做的，和「说的」「设计的」一致吗** | 上面全部 | 三方一致性报告 |

**层级归属（用户确认）**：第 2 层「技术设计文档集」= 架构 / 数据 / 接口（**前后端文档在此**）/ UI / 迁移 / **测试用例**。
即：**前后端与测试用例不是独立的层，而是「怎么做」的组成部分**——它们是方案，不是步骤。

### 语言强度按层（用户确认：不是所有层都要"全业务"）

| 层 | 语言 | 理由 |
|----|------|------|
| 1 **需求** | **全业务** | 用户要认 |
| 2 **技术设计** | **技术为主** + 每节标"服务哪条需求" | 工程 / agent 执行；硬套业务语言会让方案失真 |
| 3 **拆分** | **业务标题 + 技术细节下沉** | **用户看不懂的重灾区** |
| 4 **实施** | **技术为主** + 业务三要素 | 给 agent 执行 |
| 5 **验收** | **全业务 + 可执行操作** | 用户要独立复核 |

**判据**：这一层的**读者是谁，就用谁的语言**。业务化 ≠ 把技术文档写成散文。

### 三条铁律

1. **层层引用，不许凭空新增** —— 每层只能引用上一层的编号：
   - 第 4 层做了第 1 层没写的东西 → **超范围**；
   - 第 1 层的编号找不到任何下游 → **漏做**。
2. **每层都要说人话** —— 五个层级的产物都是给人看的（也包括给下一个 agent 看）。
3. **验收 = 一致性** —— 不是问"做完了吗"，是问「**做的是否和「做什么」+「怎么做」一致**」。

### 为什么这样切

编号串联（§八）让"一致"从主观感觉变成**可机械核对的比对**。
R9 之所以能溜过四个节点，正是因为**链条上没有一处问过「这条和那条对得上吗」**。

### 支撑性约定

- **单一职责**：每类文档只有一个用途，不重叠；
- **格式双层**：人读用 Markdown 表格，机器读用 YAML front-matter；
- **推断显式化**：所有推断标 `[TBD]` 并汇总，**进入实施前必须清零**。

## 零、立项类型决定文档集（先选类型，再选文档）

**原则**：**四件事跨所有类型不可省**——① 问题/目标是什么（可观察）② 做什么（编号 + 业务语言）
③ 怎么验（可执行操作 + 预期）④ 证据（可定位到编号）。
其余文档**按立项类型裁剪**：类型决定「要哪些文档」+「每份写什么」，**不搞一刀切六套全写**。

### 0.1 根编号按类型前缀（一眼识别类型，且全局唯一）

| 立项类型 | 根编号前缀 | 根编号语义 | 例 |
|---------|-----------|-----------|-----|
| feature | `FR-` | 功能点（验收标准挂其下 `AC#`） | FR-1、FR-1/AC2 |
| bug | `BUG-` | 缺陷项 | BUG-3 |
| refactor | `RF-` | 非功能目标 / 行为不变式 | RF-1 |
| spike | `SP-` | 待答问题 | SP-2 |
| doc | `DOC-` | 文档目标 | DOC-1 |
| chore | `CH-` | 任务项 | CH-4 |

下游编号（`T-` / `D-` / `BE-` / `FE-` / `TC-` / `E-`）**全类型统一**，链路不变：

```
FR-1 ← T-1 ← D-ARCH-2 ← BE-3 ← TC-007 ← E-1
```

### 0.2 文档集矩阵（✅ 必填 / ⚪ 按需 / ❌ 不要求）

| 文档 | feature | bug | refactor | spike | doc | chore |
|------|:---:|:---:|:---:|:---:|:---:|:---:|
| 根文档 | ✅ 全量 | ✅ 精简 | ✅ 精简 | ✅ 问题清单 | ✅ 目标 | ⚪ 一句话 |
| 技术设计 `design/*` | ✅ 全 6 份 | ⚪ 根因 + 修复 | ✅ ARCH + MIG | ⚪ 结论报告 | ❌ | ❌ |
| 拆分文档 `decomposition` | ✅ | ✅ | ✅ | ⚪ ≤3 任务免 | ⚪ | ⚪ |
| 任务卡 `tasks/T-#` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 测试用例 `test-cases` | ✅ 含 E2E | ✅ 含回归用例 | ✅ 含不变式证明 | ⚪ 验证记录 | ❌ | ❌ |
| 前后端协作 | ✅ 有 UI/API 时 | ⚪ 按需 | ⚪ 按需 | ❌ | ❌ | ❌ |
| 验收 `verification` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| 归档 `archive` | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |
| front-matter | ✅ | ✅ | ✅ | ✅ | ✅ | ✅ |

### 0.3 每类写什么（差异集中在根文档与验收核心）

| 类型 | 根文档必填节 | 验收核心 |
|------|-------------|---------|
| **feature** | **§一 全 11 节**：产品定义 / 用户与角色 / 目标与度量 / 要解决的问题 / 用户场景 / 功能点 / 非功能 / 边界 / 优先级与版本切分 / 测试策略 / [TBD] | 功能点逐条可验 |
| **bug** | 现象 / 复现步骤 / 期望 vs 实际 / 影响面 / 根因（实施后回填） / 回归验证 | **复现步骤不再成立**的可执行证明 |
| **refactor** | 现状问题 / 目标结构 / **行为不变式** / 迁移回滚 / 性能基线 | **行为不变证明**（既有测试全绿 + 关键路径对比） |
| **spike** | 待答问题 / 验证方法 / 结论与证据 / 建议（采纳或放弃） | 问题被回答（**允许结论是"不做"**） |
| **doc** | 目标读者 / 认知缺口 / 内容大纲 / 落点 / wiki 挂接 | 大纲逐节可查 + `wiki_probe.py` 无死链 |
| **chore** | 做什么 / 为什么 / 完成判据 | 完成判据可执行 |

### 0.4 不可裁剪的底线

- 根编号 + 验收 + 证据 **三件套必须齐**；
- 类型只能**减少文档数量**，不能**取消追溯**；
- **任务卡 `tasks/T-#.md` 所有类型都要**——它是 agent 的指令，不是文档负担；
- **只有 feature 需要完整 PRD**；bug/refactor/spike 用各自的根文档体例，**不套 PRD 会注水**。

### 0.5 下游文档也分类型：共同骨架 + 类型专属增量

**不能每类抄一份完整规范**（6 份副本必然漂移）。结构应是**两层**：

- **共同骨架 BASE**：所有类型都要有的节，**只定义一次**；
- **类型增量 DELTA**：只有该类型才有的节，定义在 profile 里。

**门禁校验 = BASE + DELTA[类型]**。

**① 任务卡（§四 · agent 的提示词）**

BASE：front-matter（id/serves/type/status）／业务三要素／实施步骤（文件路径 + 编号）／验收（可执行命令 + 预期）／证据

| 类型 | DELTA（专属必填节） | 为什么 |
|------|-------------------|--------|
| feature | 上游依赖编号 / 影响面 | 新能力要接进现有系统 |
| **bug** | **复现步骤（先复现并贴失败输出）／根因／防复发** | 不先复现就无法证明修好了 |
| **refactor** | **行为不变式（改前固化当前行为）／前后对比证据** | 重构的正确性 = 行为没变 |
| **spike** | **待答问题／验证方法／结论回填位置** | 产出是知识不是代码 |
| doc | 目标读者 / 内容大纲 | — |
| chore | 完成判据 | — |

**② 测试用例（§六）**

| 类型 | DELTA（层级要求） |
|------|-----------------|
| feature | 单元 + 集成 + **E2E 必含** |
| **bug** | **回归用例必含**（把复现步骤固化成测试，防再犯） |
| **refactor** | **不变式用例必含**（断言外部行为与基线一致） |
| spike | 验证记录（可复现实验），不要求自动化 |
| doc / chore | ❌ 不要求 |

**③ 技术设计（§二）**

| 类型 | DELTA（必写） |
|------|--------------|
| feature | 全 6 份 |
| **bug** | **根因分析** + 修复方案 + 影响面 |
| **refactor** | **目标结构** + **不变式清单** + 迁移回滚 |
| **spike** | **结论报告**（问题 / 方法 / 结论 / 建议） |
| doc / chore | ❌ |

**④ 拆分文档（§三）**

BASE：覆盖对照表（编号串联）。DELTA：

| 类型 | DELTA |
|------|-------|
| feature / bug / refactor | 全量逐条对照 |
| spike | ≤3 任务免拆分文档 |
| doc | 按大纲章节拆 |
| chore | 单任务免 |

**⑤ 验收（§七）** — DELTA 见 7.3。

**⑥ 前后端协作（§五）**

| 类型 | DELTA |
|------|-------|
| feature | 有 UI/API 时必须（mock + 联调清单） |
| bug | 仅当缺陷出在接口层 |
| refactor | 仅当动了接口 |
| 其他 | ❌ |

**⑦ 落地（两层 profile）**

```ts
const BASE = { taskCard: ['business-triad','steps','acceptance','evidence'], ... }
const PROFILES = {
  bug: {
    rootPrefix: 'BUG-',
    rootDocDelta: ['repro','expected-vs-actual','impact','root-cause','regression'],
    taskCardDelta: ['repro','root-cause','prevent-recurrence'],
    testDelta: ['regression'],
  },
  // ...
}
```

共同骨架只定义一次；门禁读 BASE + PROFILES[type]，**新增类型只加一条 profile**。

### 0.6 阶段 ↔ 产物映射（不许越层）

**reqboard 的每个阶段只产出一类文档**，越层会制造"这到底是设计还是计划"的不可回答问题：

| 阶段 | 唯一产物 | 回答 | **不产出** |
|------|---------|------|-----------|
| brainstorming | 需求文档（PRD） | 做什么 | 技术方案、任务清单 |
| **planning** | **技术设计文档集**（design/*.md） | **怎么做** | **任务 DAG / 工序 / "分几步"** |
| **decomposing** | **拆分文档**（decomposition.md） | **分几步，每步完成什么** | **重复技术方案** |
| implementing | 实施文档（tasks/） | 照着做 | 需求重述、方案重设计 |
| accepting | 验收文档 | 做的是否与说的/设计的一致 | 新需求、新设计 |

**三条判据（门禁可依此报警）**：

1. **技术设计里出现任务编号表 / 依赖 DAG** → 越层（那是拆分文档的内容）；
2. **拆分文档里重复架构/接口设计** → 越层（引用编号即可，不复述）；
3. **实施文档里重新设计接口** → 越层（应回到 planning 改设计，再走拆分）。

**为什么**：五层是"每层引用上层编号"的链（§八）。越层就等于**在两层各写一份事实**——
必然漂移，且让"缺失在哪一层"无法判定（R9 这类缺口会变成"两层都写了但都不全"）。

### 0.7 插件落地

`CATEGORY_FLOW_PROFILES` 从「stage 单维」扩展到「**文档集 + 门禁 + 提示词分片 + 根编号前缀**」四维：

```ts
{ feature: { requiredDocs: [...], gates: [...], fragments: [...], rootPrefix: 'FR-' }, ... }
```

门禁与提示词读**同一份 profile** —— 新增/调整立项类型只改一处。

## 一、需求文档（requirement.md）

**用途**：定义"要做什么、为什么做、怎么算做完"——面向人的业务规格

**位置**：`docs/requirements/REQ-{id}/requirement.md`

### 1.1 Front Matter（YAML，必填）

```yaml
---
req_id: REQ-xxxxxx
title: 需求标题（≤120字符）
category: feature | bug | refactor | spike | doc | chore
status: draft | brainstorming | planning | decomposing | implementing | accepting | done
owner: 窗口ID（如 w-e1fc9bb5）
created: YYYY-MM-DD
business_value: 业务价值/优先级（一句话）
risk_level: low | medium | high
---
```

### 1.2 正文结构（PRD 体例 · 11 个必填节）

> **其他立项类型**（bug / refactor / spike / doc / chore）的根文档必填节见 **§0.3**——
> **不套 PRD**（硬套会注水：bug 缺的是"复现步骤"，refactor 缺的是"行为不变式"）。

#### §1 产品定义（必填）

**两件事**：① **产品是什么**（一句话，含边界）；② **为什么现在做**（实证触发，不是"应该做")。

**并列出交付物清单**——本需求产出什么、谁消费：

| # | 交付物 | 是什么 | 谁消费 |
|---|--------|--------|--------|
| 1 | … | … | … |

#### §2 用户与角色（必填）

| 角色 | 是谁 | 他要什么 | 今天被什么卡住 |
|------|------|----------|---------------|
| 需求方 / 验收人 | … | … | … |
| 执行窗口（agent） | … | … | … |

**要求**：至少 1 个角色，且"今天被什么卡住"必须具体（含糊等于没写）。

#### §3 目标与度量（必填）

| 目标 | 度量口径 | 今天（实测） | 目标值 |
|------|---------|-------------|--------|
| … | … | … | … |

**禁止**：只写"更好 / 更快"——必须给**今天值**与**目标值**，否则不可度量。

#### §4 要解决的问题（必填）

**问题陈述三要素**（缺一不可）：
- **痛点**：可观察现象（数据/截图/日志）
- **受影响用户**：谁被坑了
- **证据**：实测数据/案例/复现步骤

**示例**：
> REQ-c9f899 的 R9「表达能力扩展（指标/板块/事件）」在需求里写明"全部纳入本轮"，却在计划阶段 0 次出现（取证：plan.md grep "指标|板块|事件" → 0 次、拆分盘点未列、验收材料 0 次提及）。受影响：验收时看不出这条需求没做。

**禁止**：推断、假设、"应该会"——必须是**已观察到**的现象。

#### §5 用户场景（必填）

**"谁在什么场景走这条路"**——至少覆盖四类场景：

| 场景 | 要写清楚 |
|------|---------|
| 正常流程 | 用户怎么触发、看到什么、确认什么 |
| **今天翻车的地方** | 哪一步出问题、后果是什么（这是最有价值的一节） |
| 验收 | 谁来验、怎么验、看哪个界面 |
| 复盘 / 换人接手 | 半年后或换窗口，靠什么看懂 |

#### §6 功能点（FR-# + AC#，必填）

每条功能点 = **编号 + 标题 + 一句话目标 + AC（可证伪的验收标准）**

**格式**：
```markdown
**FR-1 覆盖门禁**：拆分时逐条核对，每条功能点必须有落点。
- AC1：构造"需求里有、卡上没有"的样例 → 提交被**拒绝**并指出缺失编号。
- AC2：同一样例改为显式标"本轮不做 + 理由" → 提交**通过**。
```

**编号**（§0.1 / §八）：feature 用 `FR-<n>`，验收标准用 `AC<n>`；
bug/refactor/spike/doc/chore 用各自根前缀。

**追溯要求**：每条功能点必须被 ≥1 张任务卡引用，或显式标"本轮不做"并写明理由。

**粒度**：功能点回答"做什么"；**实现细节（改哪些文件、字段、接口）不写在这里**——那是技术设计（§二）。

#### §7 非功能需求（必填）

| 项 | 要求 |
|----|------|
| 向后兼容 | 存量怎么办（是否豁免、是否只警告） |
| 不改动什么 | 哪些既有语义/状态机明确不动 |
| 可回滚 | 出问题怎么退回今天的行为 |
| 规模 / 性能 | 可量化的开销上限 |

#### §8 边界（本轮不做，必填）

显式列出**不做什么、为什么不做**。防止范围蔓延。

**示例**：
- 不做"需求质量"评判（如需求本身写得含糊）——只做覆盖可追溯与措辞形态
- 不改 reqboard 状态机（只新增门禁）

#### §9 优先级与版本切分（必填）

| 版本 | 内容 | 理由 |
|------|------|------|
| **MVP（必须先上）** | … | 没有它其余都是纸面 |
| V2 / V3 / V4 | … | … |

**实施前置**：列出"不满足就不开工"的条件（如依赖的并行改动、需清零的 [TBD]）。

**要求**：MVP 必须给出"为什么是这几项先上"——否则切分没有依据。

#### §10 测试策略（必填）

**格式**（表格）：
| 层级 | 用例数 | 覆盖路径 | 不覆盖（显式） |
|------|--------|----------|----------------|
| 单元 | 10 | 纯函数边界/异常 | 不测 I/O |
| 集成 | 5 | 单组件 + 真库 | 不测跨服务 |
| E2E | 2 | 触发→待办→晋升→关闭 | 不测异常回滚（留集成） |

**要求**：必须有 E2E；每层写清"不覆盖什么"（防止过度测试）。

#### §11 [TBD] 待确认清单（必填）

所有**推断而未验证**的内容：接口路径/参数名/依赖版本/性能指标——标原因、留到执行前验证。

**示例**：

## 四、任务实施文档（tasks/{task_id}.md）

**用途**：= **agent 的工作提示词**——自足、可执行、带验收标准

**位置**：`docs/requirements/REQ-{id}/tasks/{task_id}.md`

### 4.1 Front Matter

```yaml
---
task_id: t-xxxxxx
title: 业务标题（三要素）
requirement_refs: [FR-1, FR-3]  # 必填（本卡交付的根编号）
depends_on: [t-yyy]
phase: implement
side: backend | frontend | fullstack
status: todo | in_progress | testing | in_review | done
---
```

### 4.2 正文结构（5个必填节）

#### §1 业务三要素（= agent 的上下文）

- **在做什么**：一句话业务动作
- **解决什么问题**：痛点 + 受影响用户 + 证据
- **得到什么结果**：可观察变化

#### §2 需求背景（= agent 的决策依据）

从 requirement.md 提取的相关条款（R# 引用）+ 成功标准。

#### §3 实施方案（= agent 的执行指令）

**必填内容**（步骤清单）：
1. 改哪些文件（精确路径，如 `packages/dsh-pmboard/src/gates/coverage-gate.ts`）
2. 新增哪些文件（模板/骨架）
3. 调用哪些接口（from design/interfaces.md）
4. 依赖哪些前置（`depends_on` 的产出）
5. 预期产出（文件/表/端点清单）

**示例**：
```markdown
### 步骤 1：新增覆盖门禁模块
- 文件：`packages/dsh-pmboard/src/gates/coverage-gate.ts`
- 内容：导出 `checkCoverage(requirement, tasks) => { gaps: string[] }`
- 输入：requirement.md 的 R 列表、tasks 列表
- 输出：缺失条款号数组
- 验证：单元测试 `tests/gates/coverage-gate.test.ts`

### 步骤 2：集成到 reqboard_submit
- 文件：`packages/dsh-pmboard/src/tools/reqboard-submit.ts`
- 修改：`kind=plan` 分支调用 `checkCoverage`，gaps 非空则 reject
- 验证：集成测试构造缺失样例 → 返回 409
```

#### §4 验收标准（= agent 的自检清单）

**格式**（checkbox + 具体命令）：
```markdown
- [ ] 单元测试通过：`pytest tests/gates/coverage-gate.test.ts`
- [ ] 集成测试通过：`curl -X POST .../reqboard/submit -d @缺失样例.json` → 返回 409
- [ ] 门槛回归：`pnpm test` → 311 passed
```

**禁止**："测试通过"这类空话——必须是可机器执行的命令。

#### §5 [TBD] 待确认

实施时遇到的未决问题（接口未定/依赖版本冲突/性能指标待测）。

### 4.3 Prompt Injection 规则

1. **实施文档 = 完整提示词**：agent 只读此文件 + repo 代码，不依赖会话历史
2. **§3 实施方案必须自足**：精确路径、完整步骤、可复现
3. **§4 验收标准必须可机器执行**：禁止"测试通过"，要 `pytest tests/abc.py::test_xyz`
4. **[TBD] 必须汇总**到 `confirmation_report.md`，实施前清零

**M 类**：
- [ ] Front-matter 完整
- [ ] `requirement_refs` 非空
- [ ] 验收标准可执行（含命令）
- [ ] 实施方案有文件路径

**S 类**：
- [ ] 方案是否可行
- [ ] 步骤是否遗漏

## 七、验收文档（verification.md）

**位置**：`docs/requirements/<REQ>/verification.md`
**编号**：验收项**不单独编号**——直接以它验证的**根编号**为行键（这就是 FR-10「对应哪条」的落点）。

### 7.1 验收是什么：三方一致性比对

**验收不是"做完了吗"，而是「做的，和说的、设计的，一致吗」**——三方比对：

| 方 | 来自 |
|----|------|
| **做什么** | 需求文档（根编号） |
| **怎么做** | 技术设计文档集（设计编号） |
| **实际做了什么** | 实施文档 + 证据 |

比对**必然只有四种结果**，每一种都必须**显式出现**（不能沉默）：

| 结果 | 表现 | 含义 | 处置 |
|------|------|------|------|
| ✅ **一致** | 三方齐全且对得上 | 正常 | 通过 |
| 🔴 **设计缺失** | 有根编号，无设计编号 | 知道要做什么，不知道怎么做的 | 打回补设计 |
| 🔴 **实施缺失** | 有设计编号，无实施/证据 | 设计好了没做 | 打回补实施 |
| ⚠️ **超范围** | 有实施，无需求/设计编号 | 做了没说要做的 | 补需求，或撤掉 |
| ⚠️ **不一致** | 三方都有但内容对不上 | 说 A 做 B | 打回澄清 |

**这张表就是 R9 的解药**：R9 的形态是「有根编号、无设计编号、无实施」→
落在**第二/第三行，当场可见**，不需要有人事后去问。

### 7.2 一致性对照表（人可见 + 机器可解析）

| 需求编号 | 做什么 | 设计编号 | 怎么做 | 实施 + 证据 | 怎么验（可执行） | 预期 | 一致 |
|---------|--------|---------|--------|------------|----------------|------|------|
| FR-1 | 拆分漏条款会被拦下 | D-ARCH-2 | 覆盖门禁模块 | T-1 已交付；E-1: 3 passed | `pytest tests/gates/test_coverage_gate.py -q` | 3 passed | ✅ |
| FR-7 | 缺"怎么验"的验收项不放行 | — | — | — | — | — | 🔴 设计缺失 |

**四件套缺一不可**（FR-10）：验什么 / 对应编号 / 怎么验 / 预期。
缺"怎么验"（无可执行命令、无可达界面路径、无可查数据）→ **验收单不生成**，并结构化指出缺项。

### 7.3 验收项从哪来（FR-9）

**必须双向齐全，两边都进同一张表**：

| 来源 | 生成方式 | 作用 |
|------|---------|------|
| **需求级** | 每条根编号 + 每条验收标准 → 各一项 | 让"需求里有、卡上没有"的东西**在验收阶段可见** |
| **任务级** | 每张卡的验收标准 → 一项 | 定位是哪一步没做到 |

两张来源靠**「对应编号」列对齐**——这是 R9 那类缺口无法再藏身的原因。

### 7.4 类型专属的验收核心

| 类型 | 验收核心（必须出现在验收项里） |
|------|------------------------------|
| feature | 功能点逐条可验 |
| **bug** | **复现步骤不再成立**的可执行证明（贴修复前后输出对比） |
| **refactor** | **行为不变证明**（既有测试全绿 + 关键路径输出对比） |
| **spike** | 问题被回答（**允许结论是"不做"**，但必须给依据） |
| **doc** | 大纲逐节可查 + `wiki_probe.py` 无死链 |
| chore | 完成判据通过 |

### 7.5 质量门禁

**M 类（机器拦截）**：
- [ ] 每个验收项都有「对应编号」，且该编号真实存在
- [ ] 每个验收项都有「怎么验」（可执行形态）
- [ ] 每条根编号至少有一项验收（否则该项显示 🔴 未覆盖）

**S 类（人判）**：
- [ ] 「怎么验」的操作人按步骤能独立跑通（真能复现，不是"应该能"）
- [ ] 预期写的是**可观察结果**，不是"功能正常"

## 八、统一编号体系（文档串联的载体）

**为什么需要**：追溯不能靠人肉维护对照表——必须**每个文档项自带编号**，编号互相引用，
机器才能串联。本规范所有追溯（§一接收标记、§三覆盖表、§四证据、§八 RTM）读的都是**同一套编号**，
不再各自维护映射表（避免"两份真相"漂移）。

### 8.1 编号格式

| 文档 | 编号 | 例 | 谁分配 |
|------|------|----|--------|
| 需求文档 | `R<n>` 功能点/条款（**根编号**） | R1、R9 | 需求分析 |
| 拆分文档 | `T-<n>`（卡文档 = `tasks/T-<n>.md`） | T-1、T-4 | 拆分 |
| 技术文档 | `D-<域>-<n>`：ARCH / DATA / IF / MIG | D-ARCH-2、D-DATA-1 | 计划 |
| 前后端文档 | `BE-<n>` / `FE-<n>`（UI 部件归 FE） | BE-3、FE-2 | 计划 |
| 测试用例文档 | `TC-<n>`（三位补零） | TC-007 | 计划 / 实施 |
| 实施文档 | 卡 `T-<n>.md` 完工段 + 证据 `E-<n>` | E-1 | 实施 |

### 8.2 串联字段（每个编号必带）

| 字段 | 说明 | 必填 |
|------|------|------|
| `id` | 本编号 | ✅ |
| `serves` | **上游编号**，必须指向真实存在者 | ✅ |

串联链示例：

```
FR-4 ← T-1 ← D-DATA-1 ← BE-3 ← TC-007 ← E-1
```

### 8.3 三条硬约束

| 约束 | 含义 | 违反后果 |
|------|------|---------|
| **不复用** | 编号作废后不得回收再用 | 历史引用会指向新对象 |
| **不悬空** | `serves` 必须指向存在的编号 | 提交被拒（`dangling_reference`，指出悬空方与目标） |
| **不孤儿** | 根编号必须有下游指向 | 需求文档与看板**显眼标红**（**R9 蒸发时的形态就是这个**） |

### 8.4 双向可查

| 方向 | 问法 | 用途 |
|------|------|------|
| **向下** forward | 给一个编号 → 列出全部子孙编号 | 这条功能由哪些文档承载 |
| **向上** backward | 给任一下游编号 → 一路反查到根 `R#` | 这份文档在服务哪条功能 |

### 8.5 表格写法（人可见 + 机器可解析）

拆分文档的覆盖对照表，每行一个 `T-`：

| 本项编号 | serves | 名称（业务语言） | 状态 | 下游编号 |
|---------|--------|----------------|------|---------|
| T-1 | FR-1, FR-4 | 覆盖门禁：拆分时不许漏条款 | done | D-ARCH-2, TC-001, E-1 |

## 九、RTM 需求追溯矩阵（核心）

**用途**：保证 100% 覆盖 + 100% 来源可追溯 + 影响分析

### 9.1 追溯维度

**前向追溯**：
```
需求条款 FR-# → 任务卡 T-# → 设计章节 D-域-# → 接口 BE-# / FE-# → 代码文件 → 测试用例 TC-### → 证据 E-#
```

**后向追溯**：
```
测试结果 → 代码提交 → 设计文档 → 任务卡 → 需求条款 FR-# → 业务价值
```

### 9.2 存储方式

- **Option 1**：手工表格（decomposition.md 的覆盖对照表）——**当前采用**
- **Option 2**：SQLite + 前端视图（轻量工具）——未来考虑
- **Option 3**：Jira/DOORS（重量级）——本仓不推荐

### 9.3 门禁规则

- [ ] 每条 FR- 必须有 ≥1 行（任务卡）
- [ ] 每张任务卡必须有 `requirement_refs`（根编号）
- [ ] 每个设计章节必须有 `serves: FR-#`
- [ ] 每个测试用例必须有 `serves: FR-#`
- [ ] **孤儿检测**：没有根编号引用的卡/章节/用例 → 标红

### 9.4 覆盖报告

**格式**（表格）：
| 条款 | 任务数 | 设计章节 | 测试用例 | 状态 |
|------|--------|----------|----------|------|
| FR-1 | 2 | D-ARCH-2, D-ARCH-3 | TC-001, TC-002 | ✅ 已覆盖 |
| FR-7 | 0 | — | — | 🔴 未覆盖（缺失） |

## 十、反模式（禁止）

❌ **只有需求文档没有实施文档** → agent 不知道怎么做

❌ **实施文档是散文而非步骤清单** → agent 无法执行

❌ **验收标准是"测试通过"而非具体命令** → 无法机器验证

❌ **设计文档没有 `serves: FR-#`** → 无法追溯，孤儿章节

❌ **测试用例不写 `serves: FR-#`** → 不知道在测什么需求

❌ **[TBD] 散落各处未汇总** → 执行时踩坑

## 十一、规范演进规则

本规范本身如何演进：

1. **修改提案**：需求 REQ-xxxx 提出规范变更
2. **影响分析**：列出需要同步修改的地方（提示词分片/门禁代码/文档模板）
3. **批准门槛**：规范变更需人工批准（不可 agent 自行修改）
4. **版本号**：规范变更后版本号 +1（front-matter 的 `version`）
5. **回溯迁移**：既有需求不强制回溯，但新需求必须遵循新版
