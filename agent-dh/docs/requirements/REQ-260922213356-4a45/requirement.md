## 项目背景与动机

文档模板包（templates/ 下 23 份）**早就写好了，但全仓代码引用为 0**——只有人知道它在哪。
窗口写文档时凭记忆写章节名/编号，常与门禁要求对不上，提交被打回返工；把模板全文塞进提示词又太贵，
且节点压缩后仍要重放。

数据支撑（实测）：模板包 107KB；模板全文若进提示词，design 节点单次约 65KB（≈2 万 token）；
近一轮会话中因"看不懂/口径不符"的返工与追问 6 次（含本需求自身的 v1→v14 迭代）。

## 产品目标

- G1 （P0）窗口进入任一节点，提示词里给出该节点该产出文档的**模板地址**（= 配置的模板根 + 静态映射表里的相对名，绝对路径），窗口自己打开照写。
- G2 （P0）实施节点给出**上游必读文档地址**（拆分计划 / 当前任务卡 / 该卡引用的设计文档），并写明"先读再动手"。
- G3 （P0）节点压缩前后、以及压缩后重注入，地址都不丢，且成本可记账。
- G4 （P1）确认门回到对话：提问先答、文字确认落章、弹框只在节点闸门出现一次。

## 产品定义

把「文档模板」从**只有人知道位置**的磁盘文件，变成**节点入口可发现、可打开**的格式事实源：
窗口进入任一节点时，注入的提示词直接给出「本节点要产什么（模板地址）」+「开工前要读什么（上游文档地址）」；
常驻的只是**指针**（名称 + 一句话用途 + 地址），模板正文按需打开（按 skill 的方式），因此**压缩再注入的成本恒定**。
同时把确认门从「弹框当问答通道」改回**对话优先**：提问先答、文字确认落章、弹框只在节点闸门出现一次。

### 设计取舍：为什么**不需要**"模板清单生成器"（v16 简化）

原方案想加一个构建期脚本（扫 templates/ 生成路径索引）+ 同步门禁。它对**本需求的目标（把地址和节点提示词一起注入）不是必需的**：

- 注入时用的是**地址字符串**，不需要跑任何脚本；一张静态表就能产出。
- 生成器的唯一价值是"防死链 / 防漏配"，而这两点用**一个单测**就能覆盖（见 FR-1）：断言①表里每条路径存在 ②表与门禁文档集一致 ③目录里有未被表引用的模板时报警。

故本版**砍掉生成器与 check 脚本**，只保留：**静态映射表 + 一个守护单测 + 配置的模板根**。
代价（如实写明）：模板文件改名/新增时**必须同时改映射表**，否则单测变红——用红灯替代构建期脚本，复杂度更低。

## 非目标

- N1 不做「模板全文进提示词」（token 昂贵、压缩后仍需重放，成本不恒定）。
- N2 不做「模板落盘到需求目录」（属另一窗口在途工作，本需求不碰）。
- N3 不做「强制读取门禁」（窗口是否真打开过文件无法机械证伪，不造假门禁）。

## 边界（不做什么）

- 不做模板全文注入、不做模板落盘、不做强制读取门禁（理由见「非目标」N1~N3）。
- 不新增注入通道（不改 HANDLER_ORDER、不加系统提示词段之外的新面）。
- 不改模板正文、不改门禁判定规则、不改台账协议与客户端渲染；不引入运行时读盘。

## 验收标准

- [ ] 单测：映射表每条路径 existsSync 为真；映射与门禁文档集逐项一致；templates/ 下有未被映射引用的文件时报警（漏配检测）。
- [ ] 注入段里每条模板地址用 read **实读成功**；把路径根改成仓库根相对 → 验收必红。
- [ ] 压缩关 / 压缩开两条路径下，模型可见面都含同一份地址段；留痕字符数含地址段。
- [ ] 非肯定答复：取词被跳过、回灌消息不含下一节点纪律特征串；肯定答复仍正常注入。
- [ ] 用户提问 3 次 → 弹框 0 次；用户文字说「确认」→ 落章推进且零弹框。

## 用户与角色（用户分析）

执行窗口是主要使用者（进节点即取模板地址、实施前取上游地址）；看板用户只做节点裁决（其余在对话里完成）；
维护者负责模板源与代码里的地址映射表保持一致，并保证注入映射与门禁同源。

## 业务流程

1. 维护者维护模板文件（templates/ 下）。
2. 维护者同步代码里的地址映射表（节点×类型 → 模板相对名）——漏改会被守护单测拦下。
3. 窗口进入节点 → 注入 = 阶段纪律 + 模板地址 + 上游必读地址。
4. 窗口打开模板与上游文档，产出文档。
5. 提交时校验必填章节；守护单测校验"映射表与模板目录一致"（漏改即红）。
6. 节点边界触发压缩 → 会话面替换为节点输入包（含同一份地址）。
7. 需人裁决 → 只在该节点闸门弹一次确认框（结论/链接/推进目标/3 选项）。
8. 用户文字确认 → 用 evidence 落章推进（不弹框）；答复为"需修改" → 不推进、不注入下一节点纪律。

## 功能点明细（原型 + 流程图 + 规则 + 变动对比）

### FR-1: 模板地址映射集中在一处（P0）

**① 原型**：无界面（代码常量），不适用。

**② 流程图（ASCII 字符画 · 任务流程图）**

~~~
   [改/新增模板文件] --> <同步改映射表?> -- 是 --> [单测绿] --> [可注入]
                              |
                              +-- 否 --> [单测红：路径不存在 / 与门禁不一致 / 漏配]
~~~

**③ 规则与异常**：功能逻辑=一张按节点×类型组织的静态表（相对名 + 人读名）；技术逻辑=纯常量，零 I/O、不引入脚本；

## 非功能需求

- 性能：单次注入增量 < 2KB（不随模板体量增长）；解析/渲染为纯函数，单次 < 1ms。
- 兼容：空集时注入文本与改造前逐字节一致；不改台账 schema。
- 可测试：解析/装配/渲染均为纯函数（domain 层禁 node:/@deepseek-ai/、不碰时间与随机数）。
- 响亮失败：映射表引用了不存在的模板 → 守护单测直接红；注入段渲染失败沿用既有降级留痕，不静默。
