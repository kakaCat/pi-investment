## 场景详细描述 <!-- serves: FR-3, FR-5, FR-8, FR-9, FR-10, FR-11, FR-12 -->

### UC-1 设计节点窗口拿到模板地址并照写 <!-- serves: FR-2, FR-3 -->

**角色**：执行窗口（agent）

**前置条件**：
- 需求处于 `design` 状态且 `stageEnabledFor(category, 'design')` 为真（feature/refactor/bug 走此节点）；
- 插件配置已解析出可用的 `templateRoot`（绝对路径）。

**主流程**：
1. 节点推进到 design → 下一回合系统提示词段 `reqboard:capture` 求值；
2. 窗口看到阶段纪律之后跟着一段「本节点文档（模板地址 · 先读再动手）」：
   列出 feature 在该节点的 5 份设计模板绝对地址（sides=backend 时另有 backend.md）；
3. 窗口对每条地址执行 `read`（绝对路径，直接打开成功）；
4. 窗口按模板的章节名产出文档，落到 `docs/requirements/<REQ>/design/`；
5. 产出后调 `reqboard_ask_confirm(target=artifact, kind=design)` 请人确认。

**预期结果**：
- 窗口不再凭记忆写章节名；文档一次通过门禁（节名/编号合规）；
- 注入增量 < 2KB，且**不随模板包体量增长**。

**异常分支**：
- **分支 A：类型无该节点模板**（bug 的 design）→ 地址段为空串，注入文本与改造前逐字一致；
- **分支 B：`templateRoot` 不可用** → 地址段整体不注入，并写 `address_section_disabled` 留痕（不静默）；
- **分支 C：映射表指向的文件不存在** → 开发期守护单测已红；运行时窗口 read 失败，地址不做兜底（暴露而非掩盖）。

**时长估计**：正常路径 = 注入即得，无额外等待（纯函数 < 1ms）。

### UC-2 实施节点先读上游再动手 <!-- serves: FR-5 -->

**角色**：执行窗口

**前置条件**：需求处于 `implementing`；台账存在已登记的上游产物（requirement/design/decomposition）与当前任务卡。

**主流程**：
1. 窗口进入 implementing 节点，注入段给出：
   「产出模板」= 任务卡/评审/测试证据模板地址；「上游必读」= 上游节点产物地址 + 当前任务卡 + 该卡引用的设计文档；
2. 纪律句明写「先读再动手」；
3. 窗口按顺序打开上游地址，再动代码；
4. 完成后按任务卡推进状态（`reqboard_task_move`）。

**预期结果**：改动与设计/需求编号对得上；任务卡汇报可引用设计落点。

**异常分支**：
- **分支 A：任务卡未登记 cardDoc** → 不列出该地址（不臆造），其余上游照列；
- **分支 B：台账无任何产物** → 上游清单为空，只给模板地址（若也没有 → 空串）；
- **分支 C：节点压缩发生** → 输入包仍含同一份上游地址（否则实施窗口就看不到该读什么）。

### UC-3 节点中途压缩后地址仍在 <!-- serves: FR-8, FR-12 -->

**角色**：执行窗口

**前置条件**：节点隔离/压缩开启（`nodeIsolation=true`）；当前节点进行中。

**主流程**：
1. 节点边界触发压缩 → 会话可见面被替换为「节点输入包」；
2. 输入包内含「## 本节点文档」小节（与压缩前系统段**同一函数**产出）；
3. 下一回合系统提示词段重装 → 再次含同一份地址段；
4. 留痕（`prompt-injection-log.json`）记录的 `charCount` 含地址段。

**预期结果**：地址**不丢**；窗口可在压缩后的任一回合继续按模板写。

**异常分支**：
- **分支 A：系统提示词段不可得** → 输入包仍带地址（两条路径互为兜底）；
- **分支 B：只把地址挂在 H3 scratch、不挂输入包** → 压缩路径断言必红（测试设计即为此）。

**时长估计**：无额外耗时。

### UC-4 用户提问不被弹框打断 <!-- serves: FR-9, FR-11 -->

**角色**：看板用户（人）

**前置条件**：窗口有进行中需求；产物尚未定稿。

**主流程**：
1. 用户在对话里连问 3 个问题（"这版设计为什么砍掉生成器？""验收怎么跑？""能不能顺便改模板名？"）；
2. 窗口**逐条在对话里回答**，全程不弹框；
3. 产物定稿且无未答问题 → 窗口调 `reqboard_ask_confirm` 弹**一次**确认框（框里只放结论/链接/推进目标/3 选项）；
4. 用户文字回复「确认，进入下一步」→ 窗口带 `evidence=<用户原文>` 调 `reqboard_ask_confirm` 落章推进，**零弹框**。

**预期结果**：用户提问 3 次 → 弹框 0 次；文字确认 → 落章推进且零弹框（= 需求验收标准原句）。

**异常分支**：
- **分支 A：同一产物已有未答确认框** → 不再重复弹（守卫：同产物未变更不重弹）；
- **分支 B：弹框超时/中断** → 不自动重弹；等用户新消息或状态变更再发起；
- **分支 C：弹框通道不可用** → 返回 `fallback=board`，提示用户走看板确认（不伪造确认）。

### UC-5 答复"需修改"不被推着走 <!-- serves: FR-10 -->

**角色**：看板用户

**前置条件**：闸门已弹出；用户选择"需修改"并写了意见。

**主流程**：
1. 用户作答"需修改：第 3 节缺少端侧条件说明"；
2. H1 以台账实时状态判 `verdict=negative`（需求 status 未推进到 `ctx.to`）；
3. H3 直接 `skip(negative_verdict)`——**不取下一节点纪律**；
4. H4 只发作答摘要 + 用户意见（不附任何纪律块）；
5. 窗口按意见返工，改完再确认一次。

**预期结果**：节点不推进；回灌消息**不含下一节点纪律特征串**（可机械断言）。

**异常分支**：
- **分支 A：并发把状态改了** → H1 依然以实时台账为准，判 negative（保守）；
- **分支 B：用户先说"需修改"又改口"确认"** → 第二次作答走 evidence 路径，正常落章推进（不因上一次 negative 卡死）。

### UC-6 维护者改名模板被单测拦下 <!-- serves: FR-1, FR-6, FR-7 -->

**角色**：维护者

**前置条件**：模板包 `templates/` 与代码内地址映射表同仓维护。

**主流程**：
1. 维护者把 `templates/design/architecture.md` 改名为 `templates/design/arch.md`（或新增一份模板）；
2. 未同步地址映射表 → 运行守护单测；
3. 单测报红：① `relPath` 指向不存在（死链）；② `templates/` 下出现未被任何条目引用的文件（漏配）；
4. 维护者同步映射表 → 单测转绿。

**预期结果**：地址漂移在**开发期**暴露，而不是等窗口 read 失败。

**异常分支**：
- **分支 A：门禁文档集变了**（如 feature 新增一份必交文档）但映射表没跟 → 同源校验失败（FR-7）；
- **分支 B：模板文件存在但文档画的流程图与代码不一致** → 对照校验失败（FR-6）。

**时长估计**：单测毫秒级。

### UC-7 该类型没有模板时不产生噪音 <!-- serves: FR-4 -->

**角色**：执行窗口

**前置条件**：需求类型在该节点无必交文档（如 bug 的 design 节点、spike 的 design 节点）。

**主流程**：
1. 节点注入照常发生（节点纪律还在）；
2. 地址解析返回空集 → 渲染返回空串 → 注入文本与改造前**逐字节一致**；
3. 窗口看不到任何空表头、"（无）"占位或多余空行。

**预期结果**：老行为不被扰动（基线测试逐字节比对通过）。

**异常分支**：
- **分支 A：人为在映射表里给 bug 的 design 塞条目** → 单测的"与门禁文档集一致"断言变红（防臆造）。
