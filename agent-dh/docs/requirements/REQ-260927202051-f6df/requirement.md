## 产品定义

**DAG 任务队列机制**：任务卡与依赖关系（DAG）从台账 `dsh-reqboard.json` 迁出，改存到每个需求各自的
队列文件 `docs/requirements/<REQ>/queue.json`。拆分时任务写入队列，执行时从队列取父卡信息，
状态流转也写回队列——**队列是任务数据的唯一存储，台账不再记录任务**。

**核心价值**：
- 任务数据按需求分片落盘：单个需求的任务可独立读写、独立查看、独立备份，不必在 7.8MB 的单体台账里翻找
- 队列文件即 DAG：依赖层级、ready 队列、批次肉眼可读，可被脚本与页面直接消费
- 台账瘦身：82 个需求共 587 条任务从单体文件移出，写放大与并发冲突面同步下降

**与现状的区别**：
- 现状：任务存在 `dsh-reqboard.json` 的 `tasks[]`（587 条、单体、7.8MB），队列不存在
- 改进后：任务存在各需求的 `queue.json`；台账 `tasks[]` 字段移除（schema v8→v9），仅保留需求与分诊记录

## 一句话目标

把任务数据从台账迁到按需求分片的 `queue.json`（含 DAG 层级与 ready 队列），
拆分生成、执行读取、状态更新三处均以队列为准，台账不再记录任务。

## 功能点

- **FR-1: 队列作为任务主存储**：`reqboard_decompose` 拆分时把任务卡写入 `docs/requirements/<REQ>/queue.json`（含 DAG 拓扑与层级），不再写入台账 `tasks[]`
- **FR-2: 执行从队列读取父卡**：`reqboard_task_run` 从 `queue.json` 读取父卡信息、依赖关系与 ready 队列
- **FR-3: 状态更新在队列实现**：`reqboard_task_move` 的状态流转写回 `queue.json`，并在依赖满足时解锁下游任务
- **FR-4: 原子写入**：队列文件写入使用临时文件 + fsync + rename，保证并发下不产生半截 JSON
- **FR-5: 数据校验与版本兼容**：队列文件带 `version` 字段；写入前/读取后/更新前按 V-1~V-6 校验（必填字段、标识唯一、引用完整、层级一致、ready 双向一致、无环）
- **FR-6: 台账 schema 升级 v8→v9**：从台账移除 `tasks` 字段、`schemaVersion` 升为 9，并在 `migrations[]` 写入迁移留痕
- **FR-7: 历史任务迁移**：把台账中存量 587 条任务（含 465 条 dependsOn）按 `requirementId` 分片迁移到各自需求的 `queue.json`，依赖 id 重映射为计划键
- **FR-8: 读方改造**：原先读台账 `tasks` 的模块（看板任务页与甘特、任务/需求/验收路由、执行链与状态工具、RTM 与覆盖门禁）全部改读队列

## 边界（不做什么）

本需求**不包含**以下内容：

1. ❌ **不改任务状态机语义**：状态枚举与合法转移表（`todo→in_progress→…→done`）保持不变，只换存储位置
2. ❌ **不做队列文件的可视化 UI**：DAG 图渲染留待后续（本期保证看板任务页/甘特功能不回归，但不新增图形视图）
3. ❌ **不实现并行调度引擎**：同一 layer 任务的并行执行仍由人工/窗口决定，队列只负责表达依赖
4. ❌ **不实现断点续传**：任务中断后的自动恢复留待后续
5. ❌ **不跨需求依赖**：任务只依赖同需求内的任务；跨需求依赖不支持
6. ❌ **不取消台账**：需求记录、分诊记录、评论、revision 仍存台账，只移走 `tasks`
7. ❌ **不保留双写**：迁移后**不再**向台账 `tasks` 写任何数据（用户明确要求），亦不做读写双轨兼容
8. ❌ **不引入分布式锁**：并发写同一队列由原子 rename + last-write-wins 兜底

**明确做的事情**：
- ✅ 队列文件成为任务主存储（生成/读取/更新/校验）
- ✅ 台账 schema v8→v9，`tasks` 移除 + 迁移留痕
- ✅ **存量全量**历史任务分片迁移（含 dependsOn 重映射）；条数由迁移脚本现算，**不写死**
- ✅ 36 处读方改造为读队列
- ✅ 迁移脚本带 `--dry-run` / `--apply` / `--verify` 与白名单校验

## 非功能需求

- **性能**：单需求队列文件 <100KB（任务数 <100）；生成 <50ms、读取 <10ms、更新 <20ms
- **可靠性**：原子写入（temp+fsync+rename）；台账 `tasks` 移除前必须有可回滚备份
- **兼容性**：迁移脚本幂等（重复 `--apply` 无操作）；迁移前自动备份台账
- **可回滚**：备份文件保留，出现异常可整册还原
- **安全**：迁移脚本逐路径白名单校验，出现白名单外差异即中止且不落盘

## 风险与不做项

**已知风险**：
1. **看板回归风险（最高）**：本 GUI 的任务页/甘特经 `http/routers/stages.ts` 从台账 `tasks` 渲染；
   若只移数据不改读方，界面立即空白。故 FR-8 与 FR-6/FR-7 必须同批交付，且以看板实测为准。
2. **自举顺序**：本需求自身已过 decompose 环节，其 8 张在制卡不会自动进入新队列，
   需由迁移脚本一并迁入（依赖 t 卡在 FR-7 覆盖范围内）。
3. **并发写**：同需求多窗口并发写队列由 last-write-wins 兜底；不一致以备份台账为准。

**不做**：UI 图形视图、并行调度、断点续传、跨需求依赖、双写兼容、分布式锁（见「边界」）。
