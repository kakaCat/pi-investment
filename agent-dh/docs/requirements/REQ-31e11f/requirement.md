> 会导致后面越来越难推进，llm智能降级问题。需求拆分也是这样尽量用不同窗口或subagent分担上下文压力」

> 人机回路的方式，咱们没有深度的交流，这样不好」

## 2. 问题现状（调查证据）

会话框顶部进度流程条与项目看板**走两条数据通路、两套口径**：

| 事实 | 证据 |
|---|---|
| 看板读全量台账（plan/verification/archive/executions/dependsOn） | `GET /reqboard/state`（dsh-pmboard host/routes.ts） |
| 进度条读窄投影：无 executions / dependsOn / verification / archive | `GET /session/:sid/progress`（routes.ts:730-799） |
| FLOW 节点止于 done，**没有归档节点** | conversation-progress.ts:22-30 |
| 阶段→任务过滤引用不存在的 phase 值，点"拆分"等节点永远空白 | conversation-progress.ts:239-247 stageTasksMap |

结果：点节点要么没内容、要么内容与看板对不上；拆分结果、执行人、验收证据、归档逻辑
在看板里有、在会话框里不可见。

## 3. 需求目标

会话框进度流程条的**每个节点可点击**，展示该节点的完整内容，且与项目看板**同源同口径**
——进度条是同一台账的投影 + 深链入口，不是第二套看板。

**节点完成 = 节点产物就位**（2026-09-14 用户补充）：每个阶段必须产出对应的文档产物才算
完成，产物串成追溯链，任一节点可向上追到源头——保证项目完成不跑偏。

## 4. 功能需求（节点内容清单）

| 节点 | 点击后必须展示 |
|---|---|
| 立项 | 需求卡（标题/分类/描述）+ 立项窗口 + 时间 |
| 需求分析 | **需求文档**（超链接点击打开全文）+ 共创留痕（评论/会话锚点）+ 该阶段时间线 |
| 技术设计 | **技术设计/实施计划内容**（plan.md 超链接点击打开全文）+ 计划任务表 + 批准人/时间 |
| 拆分 | 落库任务 DAG（标题/阶段/端侧/依赖/**验收标准与测试内容：怎么验**）+ 与计划任务表对照 + 拆分操作者 |
| 实施 | 每任务执行记录：**哪个窗口或 subagent 完成**、手动/编排派发、起止、结果、证据；按窗口分组 |
| 验收 | 验收内容列表：结论 + 证据清单 + 人工审核 pass/rework + 意见 |
| 完成 | 里程碑时间 + 验收结论摘要 |
| 归档 | **归档逻辑**：目录/保留文档清单/合并去向/索引条目/说明书更新点/归档人 |

### 节点产物与追溯链（用户指定，2026-09-14）

| 节点 | 产物 | 落点 | 登记时机 |
|---|---|---|---|
| 需求分析 | 需求文档 requirement.md | docs/requirements/REQ-xxx/ | brainstorming 阶段窗口写出并登记 |
| 技术设计 | 技术/计划文档 plan.md | plan.path | reqboard_plan_submit（已有闸门基础） |
| 拆分 | 拆分清单 decomposition.md（计划任务表 ↔ 落库任务 id 对照）+ **每任务自足任务卡骨架 tasks/t-xxx.md** | docs/requirements/REQ-xxx/ | reqboard_decompose 落库时自动生成 |
| 实施 | 每任务详情文档 tasks/t-xxx.md：**拆分时的任务卡骨架**（目标/背景/范围/验收标准/上游产出摘要/executorHint）**+ 完成时的结构化汇报**（执行窗口/subagent、起止、结果、做了什么/改了哪些文件/下一步） | docs/requirements/REQ-xxx/tasks/ | 骨架 decompose 生成；汇报经 reqboard_task_report 追加 |
| 验收 | 验收文档 verification.md（结论 + 证据清单 + 审核意见） | docs/requirements/REQ-xxx/ | reqboard_verify_submit 时落盘 |
| 归档 | 归档材料（dir/docs/mergedInto/indexEntry，已有 ArchiveRecord） | archive.dir | reqboard_archive_submit |

规则：
1. 台账增加 artifacts 登记（节点 → 产物路径/登记人/时间）；产物文档即节点面板"文档超链接"的展示对象；
2. **闸门**：推进到下一主态时校验当前节点产物已登记——缺失则拒绝并明确提示缺哪份文档
   （对本特性落地后新建的需求硬拦；存量在途需求标红提醒不硬拦，避免锁死历史工作）；
3. **追溯**：每份产物头部带 REQ id 与上游产物链接；节点面板底部渲染产物链
   （需求 → 计划 → 拆分 → 实施 → 验收 → 归档）；
4. **阶段通知（简版）**：产物登记与闸门拦截时经 feishu_notify 发飞书通知（复用现有通道）；
5. **五道人工确认门（2026-09-14 用户裁定，部分回调 2026-09-11 放权）**：

   | 转移 | 确认对象 | 确认方式 |
   |---|---|---|
   | brainstorming→planning | 需求文档 requirement.md | 看板一键确认（新增硬门） |
   | planning→decomposing | 技术设计文档（须含 UI/前端/后端/测试用例四视角） | 批准计划（既有门，内容增强） |
   | decomposing→implementing | 拆分清单 decomposition.md | 看板一键确认（新增硬门） |
   | accepting→done | 验收清单 verification.md | 验收通过（既有门） |
   | done→archived | 归档方案（目录/文档/合并去向） | 归档（既有门） |

   语义：产物存在 ≠ 人已审阅——产物登记即发飞书通知请人审阅；人看文档 → 对话交流改进
   → agent 修订产物 → 人在看板一键确认 → 才放行对应转移（未确认代码级拒绝，
   code=artifact_not_confirmed）。流速保障：确认是一键动作 + 通知即时触达，
   而非 2026-09-11 前那种多重表单。
   **确认入口外置**（2026-09-15 用户反馈）：批准/确认按钮必须在需求**卡面**直接可达，
   不埋在详情抽屉里——人不该为了点一个确认先开抽屉。

## 5. 实现约束（用户指定）

1. **DDD 分层**：domain / application / infrastructure / presentation 职责分离。
2. **模板模式**：节点详情"骨架固定、内容可变"，用 Template Method 落地（双端各一处）。
3. **预留"一个项目几个需求"**：LLM 上下文有限，需求拖久会智能降级、越来越难推进——
   数据模型现在预留项目分组（projectId）与需求谱系（parentId）字段，
   支持将来"大需求拆成多个子需求"零迁移。
4. **多窗口/subagent 分担上下文**：拆分与执行尽量派给不同窗口或 subagent；
   执行意图（executorHint）落成数据，分担结果在实施节点面板可见可审计。
5. **阶段提示词钩子（借鉴 superpowers hook 机制）**：需求进入各阶段时，自动向绑定会话
   注入该阶段的流程纪律提示词——brainstorming=一次一个问题/2-3 方案对比/分节逐段确认/
   设计未批准禁止实现；planning=计划含任务表+验收标准+提交前自查；implementing=按任务卡
   执行不二次创作/完成即汇报/优先新窗口或 subagent；accepting=证据先行禁止空话。
   复用既有注入点（capture.ts systemPrompt 组装注入 + capture-hook 事件注入），不新造机制。
   **提示词写在插件里，不走 skill**（2026-09-14 用户指定）：内容为 dsh-pmboard 包内
   stage-prompts.ts 模块常量（与 capture.ts 字面量提示词同风格）——skill 是模型自主
   决定调不调，纪律强制必须确定性注入；且提示词与状态机同仓同版本、可单测覆盖，
   不会出现 skill 文件与插件版本漂移。
6. **文档即接力棒（handoff，2026-09-14 用户指定）**：产物链 + 任务卡的目的是让任何
   新窗口/subagent **零会话历史**即可接续实施——借鉴 Claude Code Task 模式：每个拆分项落为
   一张自足任务卡（目标/背景/验收/范围/上游产出摘要/执行方式提示），分而治之，
   摊薄单窗口上下文，对抗 LLM 上下文用满后的智能降级。

## 6. 范围边界

**In scope**：节点内容契约（domain）+ 节点详情接口 + 会话框节点面板 + 看板同源化 +
预留字段 + executorHint 透传 + stageTasksMap 错误过滤修复 + FLOW 补归档节点。

**Out of scope**：编排器"自动开新窗口派发任务"的行为改造（若现状缺失，验证后另立需求）；
项目分组/子需求拆分的业务流程（本需求只预留数据结构）；
reqboard_notify_human 多渠道通知框架与飞书卡片动作按钮（人机回路工程，另立需求）；
Goal 独立工具三件套（被产物模型吸收，无需独立存储）。

## 7. 验收标准（需求级）

1. 8 个节点（含归档）点击均展示第 4 节对应内容，与看板数据一致。
2. "实施"节点能看出每个任务由哪个窗口/subagent 完成。
3. "验收"节点展示验收内容列表与人工审核结论；"归档"节点展示归档逻辑。
4. 预留字段就位且老台账兼容加载。
5. 双端共享同一契约：新增/修改节点只改 domain + 一个装配器 + 一个渲染器。
6. 每个节点产物登记可查、可在节点面板点击打开；缺产物的节点在看板/进度条标红。
7. 新需求缺产物推进被代码级拦截并提示缺哪份；任意节点可沿产物链向上追溯到需求文档。
8. 任务完成汇报（做了什么/改了哪些文件/下一步）自动渲染为该任务的实施产物文档并可追溯。
9. 需求进入各阶段时绑定会话自动收到该阶段纪律提示词（brainstorming 阶段含
   "一次一个问题/方案对比/分节确认"要点），注入时点与内容可单测验证。
10. 五道人工确认门代码级生效：五类产物未经人确认，对应转移被拒并提示待确认产物；
    看板每道门有一键确认按钮与「待确认」标识；产物登记即发飞书审阅通知。
11. 接力实测：开一个全新窗口/subagent，不读会话历史、仅凭任务卡 + 产物链
    即可正确接续执行某个任务并提交 task_report（handoff 契约真实可用）。
12. 分类流程生效：bug 分类需求不经需求分析硬门即可推进到技术设计；各分类的
    阶段/产物/闸门与 CATEGORY_FLOW_PROFILES 表一致；流程图按分类渲染跳过节点。
