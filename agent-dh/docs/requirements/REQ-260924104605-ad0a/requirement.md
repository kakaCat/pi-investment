# REQ-260924104605-ad0a 盯盘通知改版：专用 webhook 分群 + 消息格式重设计

> 状态：brainstorming（需求分析）｜ 类型：feature ｜ 难度：expert
> 立项来源：用户原话「我发现v2系统的盯盘发消息特别混乱，1、给盯盘专门一个webhook地址，
> 系统现在支持吗，2、…输出的内容看不懂 还不如 [旧版 🔔 需决策 格式] 这个之前的方式，需要你再设计一下」

## 1. 需求概述

### 1.1 一句话目标

让盯盘类通知**全部进专用「盯盘」群**（不再与系统告警混居），且每张卡都按
**意图驱动骨架**呈现（意图/触发/现价/为什么提醒/预案/风控/下一步），
用户只看飞书消息就能读懂"是什么、为什么、该怎么办"。

### 1.2 可证伪判定标准

1. 造一条 L1 规则触发 → 消息落在「盯盘」群，alerts 群无此消息（看群 + 投递日志双验）。
2. `pytest quantsys-v2/tests/notification/` 全绿；新增用例断言：N=1 P1 卡无重复行；
   超时回执文本不含微秒、不含「| 周期 |」；「频道：」不出现在任何用户可见文案。
3. 同一巡检周期造 3 条超时待办 → 只收到 1 张聚合卡，含 3 行待办清单。
4. 用户对照旧版样例消息目检一张 P1 完整卡：意图标签/这条提醒为了/预案/风控/下一步齐全。
5. 回滚演练：把 10 行 webhook 改回原值 → 消息回到原群（配置级回滚成立）。

### 1.3 背景

用户 2026-09-24 反馈 v2 盯盘通知「特别混乱」，并给出两条具体线索：
① 希望盯盘有专用 webhook；② 现有的「🟠 P1 待决策」卡与「📋 盯盘回执 · 超时回执」
看不懂，明确不如旧版「🔔 需决策」意图驱动格式，要求重新设计。

### 2.2 调查结论

- **架构即支持分群**：`public.notification_channels` 已有 13 行（3 物理群 + 10 盯盘逻辑
  频道），每行独立 webhook；设计上「渠道码与 webhook 多对一可配，只改配置」
  （`domain/notification/policies/watch_channel_policy.py:8`）。
- **现状未生效**：13 行 webhook 全指向同一机器人（尾号 …172829）。
- **三条旁路**（只改配置治不好，需接线）：
  1. L0/L1 direct 直飞书（`notifier.py:163` → `notification_facade.py:243`），
     FeishuChannel 单 webhook，盯盘触发主力路径不过渠道表；
  2. 回执走 `facade.send_card` 不带 os_channel（`watch_channels.py:68`）；
  3. 超时回执一律 alerts（`receipt_service.py:55`）。
- **格式根因**：
  - 「🟠 P1 待决策」（`watch_level_templates.py:152 render_p1`）：N=1 时首行与
    条目逐字重复；rule_id 缺失渲染「规则#-」；新模板只消费 symbol/price/action
    少数字段，丢失旧版的意图标签/「这条提醒为了」/预案评分依据/风控/有效期/来源；
    标的显示为「601888 中国中免」代码在前，且回执里只有裸代码「601888.SH」
    （`quant.watch_todos` 无名称列，未联查 `quant.stocks`）——用户反馈
    「股票编码太难理解是那个公司」。
  - 「📋 超时回执」（`receipt_service.py:107-112`）：ISO 微秒原文直出；
    「due X | 周期 |X」同一时刻印两遍且双竖线（`receipt_period(todo,'')` 返回
    `'|<due>'`，渲染时又单独印 due——真 bug）；「频道：alerts」内部信息外露；
    一条待办一张卡刷屏。
  - 用户认可的旧版意图驱动格式仍在 `feishu_formatters.py:52` 无级别分支存活——
    REQ-c9f899 分级模板上线后带级别通知改走新模板，信息密度倒退。
- **闭环断在最后一段**（用户 2026-09-24 追问核实）：触发→发飞书 ✅、触发→wake
  归属 agent 判断 ✅（仅 L2，facade.py:209）、处置→收敛入库 ✅（close API 含
  close_reason/next_condition 校验），但**处置后回执未接线**——close 路由返回
  receipt=None（watch_todo_async.py:139-141 注释「留待接入后填充」），且现有 result
  文案只写「已出处置结论」不带原因与后续意见。agent 建仓/不建仓的判断结果
  永远不会发回给用户。

## 3. 目标方案

### 3.1 用户已拍板的决策（2026-09-24 弹框确认）

1. **分群方式**：10 个盯盘逻辑频道全部进新建「盯盘」群（一个专用 webhook），
   与 alerts/reports/trading 彻底隔离；风控/待决策靠红卡 + @你 保证可见。
2. **P1 密度**：多项时首项完整（意图/预案/风控全字段）+ 其余每项一行摘要（含待办#）。
3. **回执形态**：同一巡检周期的多条超时/升级回执聚合成一张清单卡，不再一条一卡。

## 4. 产品定义

盯盘通知是 WatchEngine 面向**人**的唯一界面：规则触发、待办升级、超时回执都经它触达。
本需求把它从「机器台账的副产物」重新定位为「给人看的决策入口」：
分群让噪音可隔离（不想看时静音盯盘群即可，风控靠红卡 @你 穿透）；
意图驱动骨架让每条消息自足回答「是什么、为什么提醒、该怎么办」。

## 5. 用户与角色

- **用户本人（唯一读者）**：接收飞书卡片，按「处置入口」去待办看板或会话处置；
  对 P0/超时类需要被强提醒，对 P2/P3 只需扫一眼。
- **agent（investor 等）**：触发通知的另一消费者（L2 wake 通道），
  本需求不改变 wake 载荷契约，只改给人看的飞书侧。
- **运维者（未来的用户本人）**：通过 SQL 即可调整频道→群映射，无需改代码。

## 6. 边界

**做**：盯盘类通知（触发卡 P0-P3 + 三类回执 + 心跳告警）的格式与分群；
direct/回执两条旁路的渠道路由接线。
**不做**：① 不动 WatchChannelPolicy 的 10 频道划分与路由语义本身；
② 不动待办/SLA/晋升机制（只改它的呈现）；③ 不改 alerts/reports/trading
三群承载的其他系统消息格式。

## 7. 功能点

### FR-1: 盯盘频道 webhook 切换到专用群

**功能描述**：新建飞书「盯盘」群与机器人，把 notification_channels 表中 10 个盯盘
逻辑频道行（risk_stop / decision_inbox / entry_signal / exit_manage / position_ops /
watch_symbol / watch_market / market_state / rule_governance / system_ops）的
webhook 更新为新地址；alerts/reports/trading 三行保持不变。

**落地状态**：✅ 已于 2026-09-24 完成——用户提供盯盘机器人地址（尾号 …60d879，
完整值只存 DB 不进 git），10 行已 UPDATE 切换，并经 Agent OS 实测投递成功
（watch_symbol 测试卡「✅ 盯盘群接线测试」已送达，log_id fe494f41）。
**注意过渡态**：在 FR-2/FR-3 接线完成前，只有走 Agent OS 网关的路径（L2 等）
会进盯盘群；L0/L1 direct 与回执仍落旧群。

**验收标准**：
- AC-1.1: `SELECT code, config->>'webhook' FROM notification_channels` 显示
  10 个盯盘频道 = 新 webhook（…60d879），3 个物理群 = 原 webhook（…172829）
- AC-1.2: 经 Agent OS 向任一盯盘频道发测试消息，投递日志 status=sent 且落入盯盘群
- AC-1.3: 回滚演练：改回原 webhook 后消息回到原群

### FR-2: L0/L1 direct 路径接入渠道路由

**功能描述**：盯盘触发不再以单 webhook 直飞书旁路分群。direct 模式也按
`variables["os_channel"]`（逻辑频道码）路由到对应物理群。实现二选一
（设计阶段定死，对外行为一致）：
- 方案 A：direct 模式改走 `send_with_fallback(notification, 'agent', 'feishu')`，
  与 L2 之外的 agent 模式同路径；
- 方案 B：FeishuChannel 支持按频道码从渠道表选 webhook（渠道层多 webhook 化）。

**约束**：无论哪个方案，Agent OS 网关不可用时必须降级直飞书（既有
send_with_fallback 机制），**不丢消息**；降级须在结果 metadata 如实标注。

**验收标准**：
- AC-2.1: 造一条 L1 规则触发（direct 模式）→ 消息落盯盘群，alerts 群无此消息
- AC-2.2: 停掉 Agent OS（:8080）后触发同规则 → 消息降级直飞书送达，
  结果 metadata 含降级标注，触发记录 notified=True
- AC-2.3: 既有测试 `tests/notification/` 全绿（无回归）

### FR-3: 回执路径携带逻辑频道

**功能描述**：`send_watch_receipt` / `send_watch_alert` 经门面发送时携带逻辑频道码
（回执按 resolve_channel 的既有口径：超时/P0→alerts 语义改为→盯盘群内高优先级；
其余→盯盘群普通优先级），不再落入 alerts/reports 群。

**验收标准**：
- AC-3.1: 造一条超时回执 → 落入盯盘群，alerts 群无此消息
- AC-3.2: 回执投递失败仍如实记 delivery_status=failed（不吞错，保持既有纪律）

### FR-4: 统一意图驱动消息骨架

**功能描述**：所有盯盘触发卡统一按「意图标签｜标的（名称+代码）→ 阶段/归属 →
触发事实 → 现价/涨跌/盈亏 → 这条提醒为了 → 预案（含评分依据原文）→
风控（止损/止盈）→ 有效期/来源 → 下一步/处置入口」组织。字段从
Notification.variables 结构化直取，禁止解析已拼好的文案（沿用 REQ-c9f899 纪律）；
缺字段时隐藏该行或如实留空，绝不臆造（R-013）。

**多账户规则**：归属账户是骨架**必备字段**，任何级别（含 P1 摘要行、P2 单行、
回执聚合卡每行）都必须显示；同一标的属于多个账户时按账户分别成项/分行，
**绝不跨账户合并**（聚合键含账户，与既有聚合器 account×symbol×时段 口径一致，
作为不变式守住）。

**验收标准**：
- AC-4.1: 模板单测断言骨架各段顺序与缺失字段的隐藏行为
- AC-4.2: 用户目检一张真实 P1 卡：意图标签/这条提醒为了/预案/风控/下一步齐全
- AC-4.3: 同一标的在两个账户各有一条触发 → 消息中出现两行/两项，各自带归属账户，不被合并
- AC-4.4: 任何级别的渲染结果中每项都含归属账户（无账户时显示「通用观察」，不留空）

### FR-5: P0 红卡

**功能描述**：全字段骨架 + @你 + 「不可静默」标注 + 处置回执位；
保持现有 P0 语义（红卡/必达/不聚合），只换骨架。

**验收标准**：
- AC-5.1: P0 卡含 @所有人、intent 标签、止损止盈、处置入口
- AC-5.2: P0 不进任何聚合，逐条必达（既有语义回归）

### FR-6: P1 橙卡

**功能描述**：1 项 = 一张完整卡（首行与条目不得重复）；N 项 = 首项完整 +
其余每项一行「emoji意图 标的 现价 → 一句动作 · 待办#」；首行为汇总「N 项等你拍板」。

**验收标准**：
- AC-6.1: N=1 时全文搜索 action 文本只出现一次（修 FR-9 的判重断言）
- AC-6.2: N=3 时卡片含 1 段完整卡 + 2 行摘要，摘要行含待办# 与归属账户
- AC-6.3: 处置入口文案保留（待办看板 / 「处置 #<待办号>」）

### FR-7: P2/P3 语义不变，补意图 emoji

**功能描述**：P2 一行知悉（行首补意图 emoji）；P3 仍只进日终汇总、不单独推送；
聚合器（账户×标的×时段）行为不变。

**验收标准**：
- AC-7.1: P2 卡每行以意图 emoji 开头
- AC-7.2: P3 standalone_push=False 语义不变（单测回归）

### FR-8: 回执聚合卡

**功能描述**：同一巡检周期（WatchSlaJob 一轮）的同类回执合成一张清单卡
「⏰ N 项超时未处置 / N 项升级」：每行 = 待办# + 标的 + 级别 +
已超时时长（人性化，如「已超时 2h14m · 截止 10:00」）+ 账户。
幂等键从单条 (todo_id, kind, digest) 扩展为周期级聚合键
（digest 输入 = kind + period + 桶内 todo_id 有序集合），保证不重发、不漏发；
watch_receipts 表结构不变（payload_digest 列复用）。

**验收标准**：
- AC-8.1: 同一周期造 3 条超时待办 → 只收到 1 张聚合卡，含 3 行清单，每行带归属账户
- AC-8.2: 重复巡检同一周期 → 不重复发送（幂等，delivery 记录无新增）
- AC-8.3: 周期内 0 条回执 → 不发空卡

### FR-9: 修复 P1 卡 N=1 首行与条目重复

**功能描述**：render_p1 在 total=1 时不重复输出摘要行与条目行（并入 FR-6 实现，
单独成条是因为它会被拆成独立任务验收）。

**验收标准**：
- AC-9.1: 单测：N=1 渲染结果中 action 文本出现次数 = 1

### FR-10: 修复「规则#-」

**功能描述**：rule_id 沿 TriggerPayload → facade → 模板链路传到卡片；
确实无规则的场景（如手工待办）显示「手工」而非「-」。

**验收标准**：
- AC-10.1: 有规则的触发卡显示真实规则号；无规则场景显示「手工」，
  任何情况下不出现「规则#-」

### FR-11: 修复回执时间格式与双竖线

**功能描述**：时间不印 ISO 微秒原文；due 与周期只印一次；
receipt_period 的空 tag 不再产出「|<due>」形态。

**验收标准**：
- AC-11.1: 回执文本不含「T..:..:........+08:00」微秒形态、不含「| 周期 |」

### FR-12: 清除内部信息外露

**功能描述**：用户可见卡片不再出现「频道：alerts」等路由内部字段；
内部路由信息只进日志与投递记录。

**验收标准**：
- AC-12.1: 全部模板渲染结果中不出现「频道：」字样（单测断言）

### FR-13: 标的名称优先展示

**功能描述**：所有用户可见消息以「名称（代码）」呈现标的（对齐用户认可的旧版格式
「深南电路（002916）」），不再出现「601888 中国中免」这种代码在前的形态，
更不允许只有代码没有名称。现状缺口已核实：`quant.watch_todos` 无名称列
（回执只能渲染「601888.SH」），名称需经 symbol 联查 `quant.stocks.name` 补齐。

**细节**：
- WatchCardItem.display 从「代码 名称」改为「名称（代码）」；
- 回执渲染（render_receipt / 聚合卡）在渲染前批量解析名称（todo.symbol → stocks.name），
  一轮巡检一次联查，不逐条打 DB；
- 名称缺失（stocks 表查不到）时如实只显示代码，并在卡尾注「名称缺失」——不臆造（R-013）。

**验收标准**：
- AC-13.1: 超时回执/聚合卡每行显示「名称（代码）」，不出现裸代码行
- AC-13.2: 触发卡标题与首行均为「名称（代码）」形态
- AC-13.3: stocks 表无记录时降级为纯代码 + 「名称缺失」标注，不抛错、不臆造

### FR-14: 处置结论回执（闭环最后一段接线）

**功能描述**：待办收敛（close）后必须把处置结论回发用户——这是「触发→agent 判断→
处置→**回发结论**」闭环缺失的最后一段。现状：close 路由返回 receipt=None
（watch_todo_async.py:139-141），render_receipt 的 result 分支不含结论内容。

**细节**：
- 接线：todo_service.close 成功收敛后触发 ReceiptService.result（幂等键沿用
  (todo_id, 'result', digest)），失败如实记 delivery_status=failed；
- 文案：结论（动作：建仓/减仓/不动 + action_kind）+ **原因**（close_reason）+
  **后续处理意见**（next_condition，「不动」必填——既有 I4 校验保证有值）+
  待办#/标的（名称（代码））/归属账户；
- 形态：单张卡（处置是人/agent 的主动动作，即时性优先，不入聚合）；
- 落盯盘群（FR-3 口径）。

**为什么程序化而非提示词**（2026-09-24 用户追问后的裁定）：
① 处置入口不止 agent——人在待办看板勾选处置时无 agent 在场，提示词无从生效；
② 回执价值在于必定到达，提示词是软约束（会忘/上下文被裁/模型漂移）；
③ 字段完整性由结构保证——「不动必须给 NEXT 条件」是 I4 硬校验，程序渲染天然带出；
④ 升级/超时回执本来就是程序化的，result 未发是 t12 欠账而非设计选择。
**提示词的补充位**（管质量不管发不发）：wake agent 时提示「处置后系统自动回发
close_reason 给用户，请写得人读得懂」。

**验收标准**：
- AC-14.1: 调用 close API 收敛一条待办 → 盯盘群收到处置后回执卡，
  含结论/原因/后续意见三要素
- AC-14.2: 「不动」处置的回执必含 NEXT 条件原文
- AC-14.3: 重复收敛同一待办 → 不重复发（幂等）；回执发送失败记 failed 不吞错

## 8. 接口与数据契约

- **对外签名不变**：`NotificationFacade.send_watch_triggered` 参数列表与返回
  （ChannelResult）保持兼容；调用方（notifier.py、watch_sla_job.py）不改签名。
- **WatchCardItem 扩展**（可选字段，向后兼容）：intent / stage / purpose /
  plan_full / stop_loss / take_profit / validity_days / source / todo_id；
  缺字段隐藏该行或留空，绝不臆造（R-013）。
- **notification_channels 表**：仅 UPDATE 10 行 webhook 字段（已于 2026-09-24 执行，
  新值尾号 …60d879，原值尾号 …172829）；无 schema 变更；回滚 = 改回原 webhook。
- **回执幂等键**：聚合卡 digest 输入从 (kind, todo_id, period) 调整为
  (kind, period, 桶内 todo_id 有序集合)；watch_receipts 表结构不变。
- **wake 载荷契约不变**：L2 经 wake 通道投递给 agent 的载荷字段不增不减。
