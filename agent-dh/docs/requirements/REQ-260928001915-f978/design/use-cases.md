# 用户场景设计（REQ-260928001915-f978）

> 每章标题行必须带 `serves: FR-x` 标注（缺标注 = 孤儿章节被门禁拦）。

## 场景 1：理解任务类型分布 `serves: FR-1`

**角色**：项目管理者（PM）

**目标**：快速了解一个需求的任务组成（多少实施任务、多少测试任务、前后端比例）

**前置条件**：
- 需求已完成拆分（decomposing 阶段）
- 队列文件已生成

**操作步骤**：
1. 打开项目看板，点击需求卡片
2. 节点详情面板展开，显示"📊 DAG 层级"区域
3. 目视扫描 DAG 中的卡片

**预期结果**：
- 七类任务类型彩色徽标一目了然（蓝色=实施、橙色=测试、紫色=文档等）
- 端侧徽标显示前后端分布（紫色=backend、粉色=frontend）
- 快速判断：这个需求是重实施（蓝色多）还是重测试（橙色多）

**设计元素**：
- FR-1：卡片类型系统（phase 七色 + side 四色）
- 视觉编码优于文字标签（颜色比"实施"二字更快被识别）

## 场景 2：识别关键路径与瓶颈 `serves: FR-6`

**角色**：技术负责人（TL）

**目标**：找出影响整个需求交付进度的关键任务链

**前置条件**：
- 需求进入实施阶段（implementing）
- DAG 包含 >20 个任务

**操作步骤**：
1. 打开节点详情面板，查看 DAG
2. 点击「关键路径」按钮
3. 观察被虚线轮廓标记的节点

**预期结果**：
- 关键路径节点高亮显示（虚线蓝色轮廓）
- 关键路径边线加粗蓝色
- 图例显示"关键路径 8 步"
- TL 识别出：这 8 个任务是瓶颈，必须串行完成

**决策依据**：
- 关键路径上的任务延期 → 整个需求延期
- 非关键路径任务有松弛时间，可以后置或并行

**设计元素**：
- FR-6：computeCriticalPath 算法
- 视觉强调（虚线轮廓 + 边线加粗）

## 场景 3：理解任务依赖关系 `serves: FR-2, FR-4`

**角色**：开发工程师

**目标**：了解某个任务的前置依赖和后续影响

**前置条件**：
- 工程师被分配任务 B
- 需要了解："我完成 B 之后，谁会被解锁？"

**操作步骤**：
1. 在 DAG 中找到任务 B 卡片
2. 鼠标悬停在 B 上
3. 观察高亮变化

**预期结果**：
- B 卡片：黑色轮廓（高亮自己）
- 上游依赖 A：橙色轮廓 + 橙色边线
- 下游后继 C、D：蓝色轮廓 + 蓝色边线
- 其他节点：半透明
- 工程师理解：我依赖 A，完成后会解锁 C 和 D

**交互细节**：
- 悬停即触发（无需点击）
- 移开鼠标自动恢复
- 支持点击钉住（持续观察依赖关系）

**设计元素**：
- FR-2：真实 DAG 连线
- FR-4：悬停高亮上下游
- 颜色语义：橙色=我依赖谁（输入）、蓝色=谁依赖我（输出）

## 场景 4：大图导航（主线折叠）`serves: FR-7`

**角色**：技术负责人（TL）

**目标**：快速定位关键任务，不被 65 张卡片淹没

**前置条件**：
- 需求包含 65 个任务、12 层、83 条边（如压力图数据集）
- DAG 渲染后高度约 3000px

**操作步骤**：
1. 打开节点详情面板
2. 点击「只看主线」按钮
3. 观察节点数量变化

**预期结果**：
- 只显示关键路径上的 12 个任务（从 65 降到 12）
- 有支线的节点卡角显示 `+5 支线` 徽标
- 画布高度从 3000px 降到约 800px
- TL 快速浏览主线，确认核心流程

**展开操作**：
- 点击「展开全图」恢复全部节点
- 或点击卡角的 `+N 支线` 徽标展开该处支线（未来扩展）

**设计元素**：
- FR-7：主线折叠
- FR-6：关键路径算法（决定哪些节点留下）
- 信息层次：默认显示主线，细节按需展开

## 场景 5：识别父子卡结构 `serves: FR-1`

**角色**：项目管理者（PM）

**目标**：了解哪些任务有子卡链，子卡执行进度如何

**前置条件**：
- 需求包含父子卡（如父卡"实现后端 API"，含 4 个子卡：dev/integrate/review/test）

**操作步骤**：
1. 在 DAG 中浏览卡片
2. 识别左侧有蓝条的卡片（父卡）
3. 查看卡片底部的子卡链进度条

**预期结果**：
- 父卡左侧蓝条标识（与普通卡区分）
- 底部进度条显示：4 个竖条 + `2/4` 文本
  - 绿色竖条 = 已完成子卡
  - 蓝色竖条 = 进行中子卡
  - 灰色竖条 = 未开始子卡
- PM 快速判断：这个父任务的 4 步流程走到了哪里

**子卡呈现**：
- 子卡在 DAG 中左缩进 18px + 左侧灰色竖线
- 子卡按 `stageKind` 顺序排列（dev → integrate → review → test）

**设计元素**：
- FR-1：三角色结构（父/子/普通）
- 视觉层次：父卡蓝条醒目，子卡缩进从属

## 场景 6：识别可执行任务 `serves: FR-3`

**角色**：开发工程师

**目标**：找出"现在可以开始做"的任务

**前置条件**：
- 需求进入实施阶段
- 部分任务已完成，部分依赖已解锁

**操作步骤**：
1. 打开节点详情面板
2. 扫描 DAG，寻找右上角有绿点的卡片

**预期结果**：
- `ready` 数组中的任务右上角显示绿点 + 光晕
- 工程师快速定位：这 3 张卡现在可以并行开工
- 点击卡片打开任务卡文档，查看详细实施方案

**数据来源**：
- `QueueFile.ready[]` 由后端计算（依赖已全部 done 且自身 todo）
- 前端只负责标记显示

**设计元素**：
- FR-3：ready 标记（绿点）
- 位置选择：右上角（不遮挡标题，且与左上角 id 对称）

## 场景 7：纵向/横向布局切换 `serves: FR-3`

**角色**：所有用户

**目标**：适配不同屏幕尺寸与浏览偏好

**前置条件**：
- 宽屏显示器（≥1920px 宽）
- 或窄屏笔记本（≤1440px 宽）

**操作步骤**：
1. 在宽屏上，默认纵向布局（瀑布流）
2. 点击「横向」按钮
3. 观察布局变化

**预期结果**：
- 纵向模式：层级从上到下排列，同层按画布宽度分列（适合宽屏）
- 横向模式：层级从左到右排列，同层限高 8 行分列（适合窄屏滚动）
- 用户选择偏好的浏览方式

**设计元素**：
- FR-3：layoutDag 算法支持双向
- 用户控制：按钮切换，状态保持在 `DagRenderState`

## 场景 8：点击钉住（持续观察依赖）`serves: FR-5`

**角色**：开发工程师

**目标**：持续观察某个任务的依赖关系，不被鼠标移开打断

**前置条件**：
- 工程师需要对比任务 B 和任务 E 的依赖关系

**操作步骤**：
1. 点击任务 B，观察其依赖高亮
2. 保持高亮，移动鼠标到任务 E
3. 点击空白区域清除高亮

**预期结果**：
- 第 1 次点击 B：B 及其上下游高亮，移开鼠标**高亮保持**
- 移动到 E 时，B 的高亮仍在（不被鼠标悬停干扰）
- 点击空白：清除高亮
- 工程师完成对比分析

**与悬停的区别**：
- 悬停：临时预览，移开即消失
- 钉住：持久显示，需显式取消

**设计元素**：
- FR-5：点击钉住机制
- 状态管理：`state.pinned` 记录钉住的节点 id

## 场景 9：发现数据异常 `serves: FR-2`

**角色**：开发工程师（排查问题）

**目标**：发现队列数据中的异常（如边线引用不存在的任务）

**前置条件**：
- 队列文件被手工编辑，引入错误

**操作步骤**：
1. 打开节点详情面板
2. 浏览器控制台显示警告："边 t-1 → t-999 引用了不存在的任务"
3. DAG 正常渲染，但该边缺失

**预期结果**：
- 控制台警告提供精确错误位置（`edges[2]`）
- 渲染降级：跳过错误边，其他正常显示
- 工程师修复 queue.json，刷新页面恢复

**设计元素**：
- FR-2：数据校验（validateQueueFile）
- 错误处理策略：降级渲染 > 崩溃

## 非功能场景：性能与可读性 `serves: FR-2, FR-3`

**场景 A：大图渲染性能**

**输入**：65 个节点、83 条边的 DAG

**预期**：
- 渲染时间 <500ms（前端计算 + DOM 插入）
- 交互响应 <100ms（悬停/点击）
- 不卡顿、不闪烁

**场景 B：可读性**

**输入**：12 层 DAG，画布高度 2400px

**预期**：
- 层级间距足够（30px），不拥挤
- 卡片内文字可读（11.5px 字体 + 2 行标题截断）
- 边线不遮挡节点（透明度 + 箭头标记）
