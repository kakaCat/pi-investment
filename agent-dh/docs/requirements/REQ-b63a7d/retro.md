# REQ-b63a7d 复盘：reqboard 文档路径口径统一

## 一、事故与根因

控制台报 `GET /dashboard/api/reqboard/file?path=agent-dh/docs/... 403`。用户第一反应是「插件页面没加 token」——**实测证伪**：同端点不带任何 token、只把 path 换成 `docs/...` 就 200；403 响应体明确是白名单守卫的 `code=forbidden`。

真根因是**两端口径不一致**，不是单条脏数据：

- 登记端 `ReportTask` 把窗口汇报的 `files_changed` **原样**上浮成 `task_output` 产物；
- 读取端只认 `<cwd>/docs/**` 且**先判白名单后读文件**；
- 而「改动文件上浮」（REQ-2e9473 t12）引入的**全是源码文件** → 每个源码类产物必然 403 + 被判「缺失」。台账全量扫描 **142 条**非合规路径（工作区名前缀 / 绝对路径 / 跨仓 / brace 伪路径）。

## 二、过程教训

1. **症状指向的位置往往不是根因位置**：用户给的是一条 403，但真正的问题在「写入侧」与「读取侧」的口径裂缝。只看报错点（文件接口）会修成「放宽白名单」，而源码类产物仍会因别的写法复发——所以必须扫台账全量，先量化范围再定方案。
2. **「有没有 token」这类假设必须用一次对照实验打掉**：同一端点、同一文件、只改 path 前缀 → 200 vs 403，一次 curl 就排除鉴权。省下了改鉴权的整条弯路。
3. **自己的工具也会骗自己**：t5 清理脚本首版用 `process.cwd()` 当工作区根（脚本从包目录跑），会把 `<workspace>/packages/...` 错剥成 `src/...`。是 dry-run 的全量 diff 暴露的——**破坏性脚本必须先 dry-run 打印全量变更**，而不是只看「总结数字」。
4. **运行中的缓存型存储不能外部改文件**：`JsonLedgerRepository` 把台账缓存在内存，运行中改盘会被下一次 mutate 静默覆盖。故清理必须挑停服窗口（脚本内置 120s 护栏），本次先 apply 再立刻 self_restart，重启后 verify 复跑确认存活。
5. **门禁确实在起作用**：t4 的验收标准最初只写了断言词、没有可执行操作，被验收提交门禁打回（`REQBOARD_ACCEPTANCE_NOT_EXECUTABLE`）——「只能靠相信」的验收等于没验。这说明门禁不是形式。

## 三、可复用的判据

- 路径类 bug 的通用形状：**写入侧口径 ≠ 读取侧口径**。修复要同时钉两端（写入归一 + 读取容忍 + 单点判定 openable），只钉一端必然残留。
- 归一层必须是**纯函数且唯一实现**，纯字符串层无法判定的（是否跨仓、是否存在）交 fs，且 fs 判定只在一处（host）做——两端各判一次就是下一次 drift。
- 「403 vs 404」是语义：安全拒绝（穿越）用 403；「不在我的服务范围」用 404 + 明确 code，别让路径写错误冒充权限问题。

## 四、结论

用户报的那条 403 已消失（同路径现 200）；源码类产物可读；跨仓/伪路径从「403 含糊拒绝」变成「404 + 明确原因」；前端预检从 N 条失败请求收敛为 1 条恒 200 的批量请求。相关 57 例测试全绿，防回归含真实台账扫描。
