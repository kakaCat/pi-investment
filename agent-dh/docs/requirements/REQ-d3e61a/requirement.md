## 1. 产品定义

**产品**：项目的**文档标准 + 把它落地到插件里的文档校验能力**。三件事必须串成一串：

| 环节 | 是什么 | 谁消费 |
|------|--------|--------|
| **① 文档标准** | 人类可读的唯一事实源：六类文档各自「回答什么问题、写什么、什么格式」，含编号体系与分类文档集 | 人读；被 ③ 引用 |
| **② 在插件里实现** | 标准**不是纸面规范**——它的每条 M 类要求都落成插件代码里的校验逻辑 | 运行时自动执行 |
| **③ 文档校验** | 插件在每个节点完成时**按标准核对文档内容**，不达标代码级拦截 | 拦在执行链上 |

**一句话**：**标准说"该写成什么样"，插件负责"没写成这样就别想过"。**

**为什么现在做**：R9 证明了两件事——
① 流水线会在**无人报警**的情况下丢掉整条需求（68 文件、12314 行、验收全绿，而需求里提了 3 次的能力一行没做）；
② **只写在规范里、不设卡＝没有规范**（本需求自己的 requirement.md 一度连 front-matter 都没有，
而规范写了 front-matter 必填）。

### 1.1 五层文档链与阶段产物（本需求的立足点）

**五份文档不是五个产物，是一条问答链**——每份回答一个问题，下一份承接它的答案：

| # | 阶段 | 产物 | 回答的问题 | 承接自 |
|---|------|------|-----------|--------|
| 1 | brainstorming | **需求文档**（PRD） | **做什么** | 用户意图 / 问题现象 |
| 2 | planning | **技术设计文档集**（design/*.md） | **怎么做** | 做什么 |
| 3 | decomposing | **拆分文档**（decomposition.md） | **分几步，每步完成什么** | 怎么做 |
| 4 | implementing | **实施文档**（任务卡 tasks/） | **照着做** | 分几步 |
| 5 | accepting | **验收文档**（verification.md） | **做的与「说的」「设计的」一致吗** | 上面全部 |

**三条铁律**（对应 FR-1 / FR-2 / FR-12）：

1. **层层引用，不许凭空新增**——每层只能引用上一层编号：凭空新增 = 超范围；无下游 = 漏做。
2. **不许越层**——**技术设计只回答"怎么做"**（不写任务 DAG 与工序）；
   **拆分文档只回答"分几步、每步完成什么"**（不重复技术方案）。
   混层会让"这到底是设计还是计划"无法回答，也会让两道门禁互相覆盖。
3. **验收 = 一致性**——不是"做完了吗"，是三方比对（FR-9）。

**本需求要求**：planning 阶段的产物**正名为「技术设计文档集」**，不叫"实施计划"；
任务 DAG 与"分几步"属 **decomposing 阶段**的拆分文档。

## 2. 用户与角色

| 角色 | 是谁 | 他要什么 | 今天被什么卡住 |
|------|------|----------|---------------|
| **需求方 / 验收人** | 用户 | 看得懂要做什么；能**独立复核**做没做到 | 卡看不懂（「判据 metric 化」）；验收单没有"怎么验" |
| **执行窗口** | agent（如本窗口） | 拿到**自足指令**；知道写到什么程度算覆盖 | 不知道"拆到什么程度算没漏"；提示词按缺省难度注入 |
| **下游窗口 / 未来的自己** | 其他 agent 窗口 | 接手时看懂上下文与来源 | 只有工程标题，看不出交付了什么业务能力 |

## 3. 目标与度量

| 目标 | 度量口径 | 今天（实测） | 目标 |
|------|---------|-------------|------|
| **不丢** | 需求功能点的下游覆盖率 | R9 一条漏过 4 个节点、无人报警 | **100%**；缺口在**拆分那一刻**被拦下 |
| **看得懂** | 非工程读者能否复述"解决什么、做完看到什么" | 用户自述"我不知道这张卡在解决什么" | 能复述；复述不出 → 卡不合格 |
| **验得了** | 验收项含「可执行怎么验」的比例 | 0%（验收单只写"确认什么"） | **100%** |
| **不出格** | 超范围交付（做了没说要做的） | 无检测手段 | 验收时显式标 ⚠️ |
| **标准可执行** | 标准条目被插件校验覆盖的比例 | 0%（标准是纯文本，无任何校验） | 100%（每条 M 类要求都有对应校验） |

## 4. 要解决的问题

### P1 条款静默丢失（主问题）

需求条款与成功标准**没有任何机制保证被翻成任务卡**。R9 实证：

| 检查 | 实测 |
|------|------|
| 需求里 指标/板块/事件 出现次数 | **3 次** |
| `plan.md` 里出现次数 | **0 次** |
| 任务卡里相关卡 | **0 张** |
| 任务卡带 `requirement_refs` 的 | **0 张**（该字段根本不存在） |
| 验收材料是否提及 | 否（而需求 §4 第 10 条正是"每阶段新增条件类型上线"） |
| 线上是否实现 | 否 |

**关键**：R9 既没进任务卡，也没被写成"本轮裁剪"——**没有记录 = 后来看起来像已包含**。

### P2 验收阶段结构上看不见

验收项从**任务卡的验收标准**生成，不从**需求条款**生成。所以"需求里有、卡上没有"的东西在验收阶段
**结构上不可见**——这与"12/12 全绿"可以同时成立。

### P3 拆分 / 实施 / 验收的内容太技术化

现卡如「规则自愈」「判据 metric 化」「新增四张表与两表加列」——是实现视角。
用户看不懂、下游窗口看不懂、未来复盘也看不出交付了什么业务能力。

### P4 验收项不可操作

验收单每项只写"确认什么"，**不写"怎么验"**。人拿到验收单无法独立复核，只能选择相信 → **验收退化为盖章**。

### P5 校验靠自觉，插件不设卡（元问题）

P1–P4 的共同放大项：这些要求**全部只写在规范里、靠执行者自觉**。
插件在节点完成时只校验"产物登记了没有 + 人确认了没有"，**不校验产物内容是否达标**。
**R9 能溜过四个节点，正是因为每一站都没有设卡。**

## 5. 用户场景

### 场景 1｜提一条需求
用户口述意图 → 窗口产出需求文档 → **用户能看懂"要做什么"**并在看板上确认 → 进入计划。

### 场景 2｜拆分（今天翻车的地方）
窗口把需求拆成任务卡 → **插件在提交前逐条核对**：
每条功能点要么落到卡上、要么显式写"本轮不做 + 理由" → 有落不下的 → **提交被拒，列出缺哪几条**。
用户看到的是"**分几步、每步做完什么变了**"，而不是服务名和字段名。

### 场景 3｜验收
窗口交付 → 验收单列的是**三方对照**：做什么（需求）× 怎么做（设计）× 实际做了什么（实施+证据）。
**每项都写"怎么验"**（命令 / 界面路径 / 数据查询 + 预期）→ 用户照着做，**独立复核**，不需要相信任何人。

### 场景 4｜半年后复盘 / 换窗口接手
给定任一条功能点 → **一次列出**它对应的「任务 → 设计章节 → 接口 → 测试用例 → 证据」，
以及"做的和说的是否一致"。不依赖任何人的记忆。

## 6. 功能点

> 编号规则：根编号 = `FR-<n>`（功能点），验收标准 = `AC<n>`。
> 每条 AC 都是可证伪的（跑什么、看到什么算过）。

### 模块 A｜不丢（可追溯）

**FR-1 覆盖门禁**：拆分时逐条核对，每条功能点必须有落点（落到卡上，或显式登记"本轮不做 + 理由"）。
- AC1：构造"需求里有、卡上没有"的样例 → 提交被**拒绝**并指出缺失编号。
- AC2：同一样例改为显式标"本轮不做 + 理由" → 提交**通过**（拦的是"无记录"，不是"不许多做少做"）。

**FR-2 编号串联**：六类文档的每一项都带编号，编号互相引用，可双向查询（向下=这条功能由谁承载；向上=这份文档服务哪条）。
- AC1：给定任一测试用例编号 → 能向上反查到根编号 `FR-#`。
- AC2：给定任一 `FR-#` → 能向下列出全部下游编号。
- AC3：`serves` 指向不存在的编号 → 提交被拒（悬空引用）。
- AC4：根编号无任何下游 → 需求文档与看板**显眼标红**。

**FR-3 需求侧接收标记**：需求功能点自身带接收状态（已被任务接收 / 已完成+证据 / 本轮不做 / **未被接收（红）**），随卡的生命周期自动更新。
- AC1：每条功能点都有接收状态；取消某张卡的交付后，该功能点回落为"未被接收（红）"。

**FR-4 三段可追溯**：从一条功能点点开，能看到**哪张卡交付了它、证据是什么**。
- AC1：给定任一功能点，能定位到「交付它的卡 + 证据」。
- AC2：清空某张卡的证据后重新结单 → **被凭证门拒绝**。

**FR-5 全链路交付物映射**：设计章节、接口、UI、测试用例都必须声明**服务哪条功能点**。
- AC1：设计章节缺映射 → 提交计划被拒（硬）。
- AC2：测试文件缺映射 → 验收单出现"孤儿用例"项（警告级，不阻断）。

### 模块 B｜看得懂

**FR-6 任务卡业务三要素**：每张卡必须让**非工程读者**看懂三件事——在做什么 / 解决什么问题 / 得到什么结果。
- AC1：旧写法（如 title=「规则自愈」、无问题、无结果）→ 被拦或强制改写。
- AC2：**人工判据**——把卡给不懂代码的人看，他能说出"解决什么、做完看到什么变化"；答不出即不合格。

**FR-7 面向人的每个面都要业务化**：需求 / 计划 / 任务卡 / 验收单 / 看板卡片，凡需人读的面都用业务语言。
- AC1：把当前真实的验收单给不懂代码的人看，他能说出每项在确认什么业务结果。

**FR-8 语言强度按层**：不是所有层都"全业务"——**按读者定语言**（需求与验收全业务；设计与实施技术为主、
但每节须标服务哪条功能点；拆分=业务标题 + 技术细节下沉）。
- AC1：技术设计文档不需要写成散文，但每节都能回答"服务哪条功能点"。

### 模块 C｜验得了

**FR-9 验收 = 三方一致性比对**：验收不是"做完了吗"，是"**做的，和说的、设计的，一致吗**"。
- AC1：用 R9 做回归——需求有编号、无设计、无实施 → 验收单**直接显示「设计缺失 / 实施缺失」**，不需人工追问。
- AC2：构造"有实施、无需求编号" → 显示「超范围」。
- AC3：构造"三方都有但实施与设计矛盾" → 显示「不一致」。

**FR-10 验收项必须可操作**：每项四件套缺一不可——验什么（业务语言）/ 对应编号 / **怎么验（可执行）** / 预期。
- AC1：构造只写"确认可用"、无"怎么验"的验收项 → **验收单不生成**并指出缺项。
- AC2：取本需求之前任一真实验收项做回归 → 判不合格。

**FR-11 测试分层与 E2E**：需求与卡必须声明测试层级；**只有单元测试不算交付完成**。
- AC1：用盯盘闭环做回归——只交单元/集成测试时，验收单显示「E2E 覆盖：无（缺口）」；补一条链路 e2e 后变「有」。

### 模块 D｜强制力与规范

**FR-12 文档校验**（插件的核心能力）：插件**按文档标准核对文档正文**，在每个节点
（需求/计划/拆分/实施/验收）放行前校验，**不达标代码级拦截**。
校验对象是**文档内容**——不只是"产物登记了没有、人确认了没有"（现状只查这两项，不读正文）。
- AC1：逐节点故障注入——五个节点各构造"条款无着落"样例，**每个节点都必须拦下**（不得带病流转）。
- AC2：构造缺"怎么验"的验收项 → 验收单不生成（证明校验的是**内容**，不是登记状态）。
- AC3：存量需求（无编号字段）**不被拦**（豁免语义生效）。

**FR-13 文档标准（本需求的产出物之一）**：产出并确立**唯一事实源**
`docs/architecture/documentation-standard.md`，内容含：
① 五层文档问答链与语言强度按层；② 六类文档各自「写什么 / 什么格式 / 必填节」；
③ 编号体系与串联规则；④ 按立项类型的文档集（含下游「共同骨架 + 类型增量」两层结构）；
⑤ 质量门禁（M 类机器拦截 / S 类人判）；⑥ 反模式与演进规则。
- AC1：该文档存在且**自洽**——本需求自己的 requirement.md 必须满足它（含 front-matter、必填节）。
- AC2：各阶段提示词与门禁**引用**该文档而非复制其内容；删掉该文档里一个面的定义后，对应门禁测试变红。
- AC3：标准可演进，且演进需人工批准、版本号 +1、不强制回溯老需求。

**FR-14 标记载体选择**：标记必须同时满足**渲染后人能看见**与**机器可解析**；同一条状态只写一处。
- AC1：HTML 注释不得承载任何状态；逐条状态只存在于表格行。

**FR-15 分类文档集**：按立项类型（feature/bug/refactor/spike/doc/chore）决定**要哪些文档**、每份写什么；
下游文档用「共同骨架 + 类型增量」两层结构，**不抄副本**。
- AC1：六类各建样例——只提交该类型必需文档即通过；多交或少交必填 → 被拒并指出缺哪份。
- AC2：bug 免 PRD 的"用户角色/场景"节，**但缺"复现步骤"必须被拒**（证明裁的是数量，不是追溯）。
- AC3：删掉 BASE 里某个公共节（如"验收"）→ **所有类型**的卡都被拒（证明 BASE 只定义一次、无副本漂移）。

**FR-16 提示词注入要"聪明"**：难度由**需求实质**推断（动架构 / 多子系统 / 改数据模型 → heavy），
推断依据写进注入留痕；注入与需求实质不一致时**响亮提示**，不静默按缺省走。
- AC1：给一条"动架构"的需求 → 注入难度判定必须是 heavy（而非缺省的 light）；留痕里能读到推断依据。
- AC2：把推断改坏成"永远 light" → 该用例变红。

## 7. 非功能需求

| 项 | 要求 |
|----|------|
| **向后兼容** | 存量需求（无编号字段）**只警告不拦**，避免门禁上线即全红 |
| **不改状态机** | reqboard 的六个状态与既有闸门语义（approval / artifact / 人工确认）**不变**，只**新增**校验 |
| **可回滚** | 新门禁可单独关闭；关闭后行为回到今天 |
| **规模** | 校验为文档解析，单次提交开销应 < 1s |
| **范围外** | 不评判"需求本身写得好不好"；不做文档模板层与 Dashboard（见 §9） |

## 8. 边界（本轮不做）

- ❌ 不给存量老需求做大规模回溯迁移（只警告不拦）。
- ❌ 暂不做文档模板层、Dashboard/追溯视图（等闸门跑 1–2 周看清真实卡点再说）。

## 附录 A 任务卡样例（前后对比，以本项目真实卡为例）

### A.1 旧写法（用户看不懂："我不知道这张卡在解决什么"）

| 字段 | 内容 |
|------|------|
| title | 规则自愈 |
| description | （空） |
| acceptance | 运行 pytest tests/application/test_self_heal.py 通过；断言超阈值后新触发 suppressed=true 且不建 todo |
| implementation | NoiseSelfHealService：按日聚合统计→抑噪（suppress_until + P3）→建修规则 todo；写 watch_rule_changes 审计 |

> 问题：主语是**实现**（服务/字段/断言），读者看不出"业务上发生了什么变化、我作为用户会感知到什么"。

### A.2 新写法（业务三要素，非工程读者能复述）

**在做什么**
盯盘噪音治理：让"反复触发"的规则自动收敛成一条「修规则」待办。

**解决什么问题**
同一批规则连续 4-5 天、日均 5-7 次触发（#57 日均 6.8 次、#92 5.4 次、#137 5.0 次）。
你收到的通知里同类重复占多数，**真正该看的买卖信号被淹没**。
根因不是"该多叫几次 agent"，而是**规则本身配置不当**（阈值贴着市价、冷却窗口与阈值不匹配）。

**得到什么结果（可观察）**
1. 该规则自动进入抑噪：**不再逐条推送，一天最多打扰你一次**；
2. 系统生成一条待办，讲清「为什么反复触发 + 建议延长冷却 / 改阈值 / 退役」；
3. 你处置后规则恢复正常级别。
   **上线首日实测命中 5 条规则**（#57 / #92 / #137 / #162 / #180），当天即生效。

**怎么算完成（acceptance｜工程可验，保留）**
抑噪期新触发落库 suppressed=true 且不建待办；把该分支改坏可复现失败；回归门槛 311 passed。

**工程怎么做（implementation｜下沉细节）**
NoiseSelfHealService + noise_policy 纯函数 + 10 分钟定时扫描；变更写 watch_rule_changes 审计。

### A.3 人工可读性判据（本需求 FR-6 的验收方式）

## 附录 B 参考流程吸收（VAF 流水线纪律，用户供图）

> 用户给出了一套比我们更严的参考流水线（P 阶段需求分析 → S 阶段开发实现 → T 阶段 E2E 验收，
> 阶段解锁靠「前置阶段 approved」）。它不是要照抄，而是吸收其纪律。以下是它有三处
> 比我们现在的需求更硬、且直接指向我们还没堵上的洞。网上取证（Definition of Done & Project
> Handoff Template 等）只拿到标题、正文抓取超时——标注「待确认」；以下吸收全部基于用户供图。

### B.1 产物模板化：每类产物由模板定义「写什么」

我们的产物（requirement.md / design/*.md / 任务卡 / 验收单）目前是自由文本——
这正是「任务卡说好模糊」的根因。参考流程的做法是模板文件（prd_template.md、
testcase_schema.yaml）先把"写什么、每个字段的格式"锁死，再让产物去填它。

吸收为「分类文档集 + 模板校验」（FR-15；模板层本轮不做，见 §8）：每类交付物都必须有模板（template/schema），模板里写清
必填块、格式、禁止项（如断言禁止只写 json_path 不写人话）；产物提交时按模板校验，
缺必填块即拒。

### B.2 DoD 清单 + 机器门禁：达标线是客观的，两条核心

参考流程的「合格」判定拆成两条核心 + 机械校验：
- 100% 覆盖（每个测试点至少 1 用例、每个功能点有验收标准）
- 100% 来源可追溯（反幻觉：每个功能点必须引用 PRD 具体章节序号，缺一个都 block）

这正是我们 FR-1 / FR-4 的更严形态：不只是「条款被卡接收」，而是引用必须精确到章节序号，
且由机器门禁自动 block。

吸收：R1 的追溯精度从「条款号」收紧到「章节序号」；验收单的每项校验拆成两类：
- M 类（机器机械比对，可自动判/自动修）：格式、字段、覆盖率、来源标注——缺即拒；
- S 类（语义，机器不判）：只标 ⚠️ 待人工确认，不假装判了。

### B.3 「待确认」机制：先设计后验证的容错，不是放任幻觉

参考流程允许用例里存在没和代码核对过的部分（接口路径、参数名），但必须显式标
「待确认」并写原因，汇总进 confirmation_report.md 留到执行前验证。

这和我们之前"评判不准就停手"的做法（R-016 样本门槛 / 宪法第 5 条）同向，但更强：
它不是停下来，而是显式标记 + 汇总 + 执行前必须清空。

吸收：任何产物里凡「推断而非验证」的内容，必须标「待确认」+ 原因，汇总进
confirmation_report.md；执行（implementing）开始前该文件必须为空。

### B.4 断言双层：semantic（人读）+ action（机器执行）

参考流程要求断言必须是 semantic + action 双层结构——semantic 是人读的自然语言（禁止留空），
action 是机器可执行断言。这正好回应你"验收列表也看不懂"：验收项的「该看什么」用人话，
「机器怎么判」用动作。

吸收进 FR-7：面向人的面（含验收单）用 semantic 自然语言；机器校验用 action 枚举；
两者一一对应，禁止只有 action 没有人话。

### B.5 对我们的提示词注入的加固（回应「注入强提示词」）

参考流程的「合格」是三层判定叠加（前置门禁 → 机器质量门禁 → 人工放行）。
我们的 FR-16 是注入侧。合并后注入提示词必须把这三类约束作为不可裁剪的 floor 件注入：
模板校验 / DoD 清单 / M-S 分类与「待确认」汇总——不得因预算被裁掉（对齐本仓
"priority=floor 永不裁剪"）。
