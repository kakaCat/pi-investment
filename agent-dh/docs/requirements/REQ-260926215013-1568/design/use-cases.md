# 用例设计 · Dive 对齐 Goal driver

**需求**: REQ-260926215013-1568

读者：维护 Dive 自动续跑的工程师与产品负责人。这里回答「对齐之后，谁在什么时刻会看到什么」。

## 角色与前提 «serves: FR-6»

- **窗口 agent（Dive armed 需求）**：需求被 `armed` 且 `phase==='active'` 时，才会收到自动续跑回合。
- **人类使用者**：随时可在同一个窗口插话；插话优先于自动工作。
- **前提**：本轮只改「怎么起回合」，不改「谁来把需求置为 armed/active」（那仍是既存流程的空白，不在本需求范围）。

## UC-1 空闲续跑（主路径） «serves: FR-6, FR-7»

1. 需求处于 `armed + active`，绑定窗口 agent 完成一次对话，状态回到 **整 agent 空闲**。
2. 驱动器先兑现**耐久检查点**（台账写队列排空），复查需求仍是同 revision 的 `armed + active`。
3. 起一轮：全局唯一的回合消息（带 `source:{kind:'dive',requirementId,revision,round}`）进入会话，回合号 = `roundsInStage + 1`。
4. 该消息**真正进入模型历史**（`user/message` 身份匹配）后，`roundsInStage` 才 +1。

**结果**：人会看到「第 N/M 回合」的续跑消息；台账里回合数只在真实消耗后增加。

## UC-2 人类插话让位 «serves: FR-2»

1. 驱动器刚排入一轮（`queued`），或在第 2 步等待检查点时；
2. 人类在该窗口发来一条消息（或任何非本回合的入队输入）；
3. 驱动器把预留标为 `stale`、置「有竞争输入」，本拍**不起轮**；
4. 人类那一轮跑完、agent 再次空闲后，竞争标志复位，续跑继续（用同一个回合号）。

**结果**：对话中人类永远优先，自动续跑不会打断正在进行的回合。

## UC-3 陈旧/伪造回合被拒 «serves: FR-1, FR-10»

1. 一轮已认领（`claimed`）但尚未进入 step；
2. 期间需求被推进（`version` 变）或 `phase` 不再是 `active`，或消息内容/来源与登记不一致；
3. `agent/pre-step` 在进入 step **前**判定不成立 → 返回 `reject`，并把同批其它已认领的人类消息按原顺序放回；
4. 进入 step **后**再校验一次（防 await 期间变化）；仍不成立同样拒。

**结果**：旧 revision 的回合混不进来；被拒不留痕为零（`warn` 写明是哪一条不变量不成立）。

## UC-4 回合耗尽终态 «serves: FR-8»

1. `roundsInStage` 达到该阶段上限（`stage-configs.ts` 的 `maxRounds`）；
2. 驱动器写**终态**：`dive.phase='paused'`、`pausedReason='round-limit'`（含上限值与阶段），追加一条台账 comment，并 `warn` 一次；
3. 此后该需求不再判定上限、不再起轮；要恢复只能人工 `reqboard_clear_pause`。

**结果**：不再出现「日志里刷一行 warn 然后静默停跑」；看板/台账能看到终态与原因。

## UC-5 异常收尾与插件卸载 «serves: FR-5, FR-9»

- **max-tokens 收尾**：回合因 max tokens 结束 → 解除武装（不再自动续跑）。
- **被中止（aborted）**：若该轮已认领/已进入 → 标 `cancelled`，下一次空闲时把需求终态暂停（`pausedReason='aborted'`）；否则直接解除武装。
- **agent 报错**：解除武装；**agent 销毁**：清理其驱动状态。
- **插件卸载/驱动停用**：先关闭准入（拒绝新排队），再逐个解除武装、以 `parent` 原因取消在飞回合，最后等驱动链与 agent 静默；teardown 期间到达的触发一律丢弃。

**结果**：卸载/异常不会留下半开的续跑；也绝不会偷偷重启一轮。

## 什么时候仍会跑 / 不会跑 «serves: FR-6»

**仍会跑**：agent 处于 `idle`、无竞争输入、绑定需求 `armed + active`、回合数未达上限、检查点可兑现时——**下一次空闲即起轮**。

**不会跑**：
- agent 正在 `running`（哪怕需求刚被推进）——等它空闲；
- 有竞争输入未消费（人类消息/其它插件注入在队列里）——让位到下一次空闲；
- 需求不是 `armed + active`，或已到回合上限（终态暂停）；
- 检查点失败（此时解除武装并告警）；
- 驱动已 teardown。

**刻意不为「窗口长期不空闲」加兜底**：让位是目标行为，任何兜底都会重新引入「打断正在跑的工作」这一类故障。
