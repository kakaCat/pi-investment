## 2. 目标

让"按插件设计的流程完成项目"不再依赖 agent 自觉：确认即推进、完工有凭证、拆分不重复、产物自登记、实施照设计、验收逐项过、**阶段职责有明确规范、文档演进全程留痕**。

## 3. 方案（八个工作流）

### W1 确认弹框原子化（解决 A）

**设计原则（用户裁定 2026-09-17，经死锁质疑修订）：关键确认 = 系统能直接见证用户意志的确认。** 节点推进、计划批准、验收通过、产物确认的落章依据必须是**系统可独立证实**的用户行为，agent 转述"用户同意了"不构成有效确认。三通道并存、永不死锁：①弹框（首选，结构化答复直接落章）；②看板确认按钮（永久兜底，agent 未弹框时用户主动点）；③文字确认（核验后有效——confirm_artifact 的 evidence 必须引用最近一段时间内真实存在的用户消息原文，由 capture-hook 校验会话事件流，编造/曲解/找不到原文 → 拒绝落章）。**防卡死**：看板通道永远可用 + 产物登记超时未确认 hook 主动提醒弹框（W1.5）+ 详情页"⏳ 等待确认"状态可见。

1. 新工具 `reqboard_ask_confirm`：弹框（复用 ask_user_question UI 通道，经 `ctx.userQuestions` 服务接缝，已查证可用）→ 用户确认 → 自动 reqboard_confirm_artifact 落章 → 自动 reqboard_move 推进，一次调用原子完成；用户选"需修改/暂停"则不推进并记录。
2. `reqboard_move` 被人工闸门拒绝时，返回体带结构化问题卡（gate_question），可直接传给 reqboard_ask_confirm。
3. `reqboard_requirement_submit / plan_submit / verify_submit` 返回 note 写明"下一步：调 reqboard_ask_confirm 请人确认"。
4. stage-prompts.ts 各阶段纪律中"节点推进确认"改指 reqboard_ask_confirm（普通征询仍用 ask_user_question）。
5. **里程碑主动提醒**：capture-hook 检测"阶段产物已登记但超 30 分钟未确认"时，向绑定窗口注入"你现在必须调 reqboard_ask_confirm 请人确认"——从软纪律升级为到时触发，解决"agent 不主动弹框"。
6. **注入韧性说明**（复盘结论，非新增机制）：上下文压缩会删历史注入副本，但 capture-hook 事件驱动重注保证关键节点提示词在场（REQ-6f39b5 实证：假完成时刻纪律在场仍被无视）——故纪律兜底靠硬门而非更多注入。

### W2 实施防假完成（解决 C/D）

1. **done 凭证门**：task_move→done 前置条件 = 该任务已有 reqboard_task_report 且证据非空 + 开工以来本窗口存在真实工具动作（edit/write/bash 痕迹）。
2. **验收标准可证伪**：plan_submit 校验 acceptance 含可验证锚点（命令/路径/断言），"功能正常"类空话打回。
3. **开工说明书送达**：task_move→in_progress 返回任务卡全文（验收标准/范围/背景/实施方案，实施方案见 W5）。
4. **禁止批量关闭**：同一窗口在一次调用/一分钟内关闭多个任务 → 拒绝并提示逐任务验收。
5. **构建新鲜度门**：页面插件任务（packages/pages/*）转 done 前检查 lib/client.js mtime 新于 src 最新改动。

### W3 拆分幂等与阻塞告警（解决 B）

1. decompose 守卫补 decomposing/implementing 状态拒绝 + "该需求已存在任务"检查。
2. rollup 被阻塞时（如存在非 done 任务），verify_submit/task_move 返回体加显式 blockers 字段（阻塞任务清单），不再静默。

### W4 过程产物三层登记（解决 E）

1. **REQ 目录自动发现**：docs/requirements/<REQ>/ 落盘即产物——渲染详情页前 syncReqArtifacts() 扫描目录，未登记文件自动补登（auto_discovered 标记 + mtime + 大小），文档记录区从登记表渲染。
2. **任务文件上浮**：task_report 的 files_changed 自动登记到需求级产物清单（kind=task_output，关联 task_id），覆盖 packages/ 代码文件。
3. **闸门校验**：verify_submit evidence 路径存在性校验；archive_submit 漏登警告（目录内有未列入清单的文件）。

### W5 实施卡：拆分方案 ≠ 实施方案（解决 F）

核心原则：**拆分卡回答"做什么"，实施卡回答"怎么做"——卡随人走，实施照卡执行。**

1. 拆分阶段任务卡每项必须含 `implementation` 字段（实施方案：改哪些文件、步骤、验证方式），拆分确认 = 同时确认做什么与怎么做。
2. decompose 落库时任务卡必须携带实施方案段（不允许只有 title+acceptance 的薄卡）；实施方案缺失的任务拒绝落库。
3. task_move→in_progress 送达完整任务卡（含实施方案）——agent 开工即拿到"怎么做"，不需要凭记忆回读技术设计文档。
4. done 凭证门联动：task_report 的 files_changed 应落在实施方案声明的文件范围内，超出范围 → 范围蔓延警告（不硬拦，但写进验收单提示验收人）。

### W6 验收单机制：逐项确认 + 断点续验 + 返工回路

核心原则：**实施完直接进验收（R2 已有，W3 修复阻塞后生效）；验收不是一句话总结，是逐项打勾的验收单；验收可以被问题打断，修好接着验。**

1. 全部任务 done → agent 生成验收文档（逐项验收标准+证据）→ 自动进入 accepting（现有 rollup R2）。
2. `reqboard_verify_submit` 升级为生成**结构化验收单**：验收项 = 每个任务的验收标准 + 需求级验收标准，逐项列出，每项带证据（产物路径/命令输出/截图）。
3. 用户**逐项确认**（首选 ask_user_question 逐条弹框；看板勾选为并行通道）：每项可 通过 / 不通过（可填修改意见）。
4. **断点续验**（用户 2026-09-17 提出的细节场景）：验收中发现问题 → 验收单**挂起**（各项 pending/passed/failed 状态持久化，列表"断"在那里）→ 先修复：
   - 小修：accepting 阶段内直接修复（改动留痕到对应验收项）；
   - 大修：打回 implementing，生成返工任务（关联原任务 + 验收意见）；
   - 修复完成 → **从断点继续弹框验收**，已通过的项不重弹、保留结论。
5. 验收单版本化留痕：v1/v2/v3… 每轮各项结论、意见、挂起/续验记录进需求时间线，供复盘与归档引用。

### W7 阶段职责规范：每个阶段做什么的明确约定（用户 2026-09-17 提出并逐段裁定）

**问题**：各阶段"要完成什么"从未明确定义——技术设计吞掉拆分的活、拆分退化为落库、实施无卡可依、需求分析只有纪律没有方法论。本工作流把七阶段职责写成规范（落地到 workflow-stages.md + STAGE_PROMPTS），并配套工具调整。

#### 立项 draft
- 目标：确认"这件事值得做"。活动：两问弹框（名称+类型）。产物：REQ 台账卡片。出口：窗口接手自动进需求分析（R1）。禁止：不谈方案、不动代码。

#### 需求分析 brainstorming（参考 superpowers brainstorming 方法论重新设计，用户裁定）
- 入口：两问弹框立项确认后**自动注入需求分析提示词**（机制已有：capture-hook 即时注入 + systemPrompt 每回合组装，双层）。
- **方法论（superpowers 式检查表，按序执行）**：
  1. **探索项目上下文**：读相关文件/文档/最近变更，先建立事实基础；
  2. **范围评估先行**：请求涉及多个独立子系统时，先帮用户拆子项目，不急着问细节；
  3. **澄清提问**：一次一个问题（弹框），理解目的/约束/成功标准；
  4. **提 2-3 个方案**：带取舍对比与明确推荐；
  5. **分节呈现设计**：每节弹框确认后再写下一节；
  6. **写需求文档** requirement.md；
  7. **文档自查**：占位符/矛盾/模糊/范围蔓延，逐项过完再提交；
  8. **用户审阅文档**（弹框确认）→ 人工门放行。
- **HARD-GATE**：需求文档未经用户批准，不得进入任何技术设计/实现动作——"太简单不需要走流程"是反模式，简单的文档可以短，但不能跳。
- 产物：requirement.md（过程产物自动登记 W4）。

#### 技术设计 planning（用户裁定：代码层面的设计，产物是一套文档）
- 目标：在**代码层面**回答"怎么做"：
  ① 数据层——是否需要改表/改 schema；
  ② 设计模式选择（说明理由）；
  ③ **框架/库选型**——优先现成框架减少自研（框架质量优于自写），给选型对比；
  ④ 代码规范约束；
  ⑤ UI 设计 + 前端实现方式/框架 + 排版 + 样式设计；
  ⑥ **测试用例内容**（测什么、怎么测）。
- 产物：**一套技术文档**（不是单个文件——按主题分，如 design/architecture.md、design/ui.md、design/test-cases.md，规模小可合一）。
- **不做**：工作流划分与工作量预估（属拆分阶段）；不写实现代码。
- 出口：人工门——技术设计批准（三通道）。

#### 拆分 decomposing（用户裁定：代码层面变更盘点 + 任务卡创作）
- 目标：对照需求文档与技术设计（一套），盘点**代码层面变更清单**：**新增**哪些接口/功能/文件、**修改**哪些（精确到模块/函数）、**删除**哪些。
- 同时做：工作流划分 + 工作量预估（从技术设计移入本阶段）。
- 产物：decomposition.md（变更清单）+ 任务卡创作（每卡四要素：做什么/怎么做[实施卡 W5]/可证伪验收标准/依赖）。
- 出口：人工门——拆分确认（确认任务粒度与实施卡质量；防"批了 A 落库 B"由这道已有门负责）。
- 禁止：薄卡落库；与技术设计矛盾 → **退回 planning 改设计**，不在拆分阶段二次创作。

#### 实施 implementing（用户裁定：文档驱动执行）
- **开工先写实施文档**：基于需求文档 + 技术设计一套 + 拆分文档，产出 implementation.md（步骤、顺序、每步验证方式）。
- 执行：agent **看文档执行任务卡**（开工送达任务卡全文），每任务完工 task_report 汇报。
- 收尾：全部任务完成 → **生成验收文档**（验收单内容）→ 自动进验收（R2）。
- 禁止：批量关任务；无凭证 done；范围蔓延（超实施卡声明文件 → 警告进验收单）。

#### 验收 accepting（用户裁定：逐项弹框 + 断点续验）
- 活动：ask_user_question **逐项**弹框请用户验收（每项：验收标准+证据，通过/不通过+意见）；看板勾选为并行通道。
- **断点续验**：发现问题可挂起修复（小修当场改、大修打回实施），修复后从断点继续，已过项不重验（详见 W6.4）。
- 出口：全过 → 人工门 → 归档。

#### 归档 archived
- 活动：archive_submit 补材料（目录/清单/合并去向/索引/说明书更新点）；merged_into **真实写入**对应项目文档。
- 禁止：只挪目录不合并内容。

#### 工具与提示词配套
- plan_submit 任务表改可选（技术设计只交一套设计文档）；decompose 承担任务卡创作。
- STAGE_PROMPTS 按上述职责重写（brainstorming 从纪律清单升级为方法论检查表）。
- 存量兼容：本需求自身仍按现行工具走，W7 落地后新需求按新边界执行。

### W8 文档演进与留痕（用户 2026-09-17 裁定：文档是活的，变更必须留痕）

**原则**：需求文档在推进过程中会发现问题、解决问题——**文档会变，且每次变都要留痕**。文档是唯一事实源：agent 换窗口/上下文压缩后靠文档续命，"口头改了文档没改"是事故源头。

1. **变更必回写**：任何阶段讨论/验收中产生的新要求、范围调整、设计修改，必须同步更新对应文档（requirement.md / 技术设计一套 / decomposition.md / implementation.md）。
2. **留痕**：文档内设 changelog 段（版本/时间/窗口编码/变更原因/变更点）；台账 artifact 记录版本号。
3. **变更传播**：上游文档变更 → 下游文档自动标"⏳ 待同步"（需求改了 → 技术设计/拆分文档待同步；技术设计改了 → 拆分/实施文档待同步）；同步完成后销标；带"待同步"标记的需求在推进/验收时给出警告。
4. **影响评估**：上游变更时列出受影响的下游任务/验收项，写进时间线。

## 4. 验收标准

- 弹框点确认后节点立即推进（ask_confirm 一次调用完成落章+move），点"需修改"不推进
- 阶段产物登记后超时未确认 → 绑定窗口收到 capture-hook 主动提醒（注入留痕可查）
- 文字确认经核验后有效：evidence 引用伪造/找不到原文/语义不明的"用户确认"被 confirm_artifact 拒绝；引用真实用户消息原文则正常落章
- 防死锁：agent 未发起弹框时，看板确认按钮仍可完成落章推进（用户实测走通）
- 25ms 速通任务被 done 凭证门拒绝；无 task_report 不得转 done
- 重复 decompose 被拒绝并返回已有任务清单
- plan_submit 拒绝含前向引用/不存在依赖的任务表（提交时即报，不留到落库时炸）
- 幽灵任务存在时 verify_submit 返回显式 blockers
- 写入 docs/requirements/<REQ>/ 的新文件无需手工登记即出现在详情页文档记录区
- 页面插件任务在 lib/client.js 陈旧时转 done 被拒
- decompose 落库的任务卡均含实施方案段（薄卡被拒）
- 全部任务 done 后需求自动进入 accepting，verify_submit 产出逐项验收单
- 验收单挂起后状态持久化，修复后从断点继续弹框验收，已过项不重弹
- 验收单某项不通过 → 需求打回 implementing 且自动生成关联返工任务；修复后 v2 验收单只含未过项
- 阶段职责规范生效：brainstorming 提示词为方法论检查表（上下文探索→范围评估→逐个提问→方案对比→分节确认→文档→自查→审阅）；技术设计产物为一套代码层面设计文档；拆分产物含新增/修改/删除变更清单
- 文档变更留痕：requirement.md 修改后 changelog 段有新条目；上游变更后下游文档带"待同步"标记，同步后销标

## 5. 风险与依赖

- reqboard_ask_confirm 经 ctx.userQuestions 服务接缝调用弹框（已查证存在）；subagent/owned child 无权发问（DELEGATED_CALLER）→ 捕获降级提示看板通道。
- done 凭证门对存量 in_progress 任务不设追溯（只约束新转移）。
- 验收单逐项确认在看板侧需要 UI 配合（勾选列表 + 意见输入 + 挂起状态）；会话侧 ask_user_question 逐项弹框为主通道。
- 文档留痕依赖 agent 遵守"变更必回写"——changelog 段由工具在产物登记/重登记时强制要求填写（硬门），不靠自觉。
- 全部改动在 dsh-pmboard 插件内部，不动内核。
