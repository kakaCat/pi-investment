## 1. 产品定义

**产品**：pmboard（项目看板）**内容门禁的可执行性**——已经存在或已经承诺的门禁，必须真的会在执行链上拦人。

一个门禁要成立，三件事必须同时为真，缺一件就等于不存在：

| 环节 | 是什么 | 今天的状态 |
|------|--------|-----------|
| **① 契约** | 提示词告诉执行者「缺了会被 `task_card_incomplete` 拦下」 | ✅ 已有（implementing 轻重两档 overrides 都写了） |
| **② 实现** | 判定逻辑是纯函数、有单测 | ⚠️ 一半：三要素判定完整；编号跳号与重复两处**结构性失效** |
| **③ 接线** | 执行链上真的有调用点、真的用该 code 拒绝 | ❌ 缺：三要素门禁**零调用方**，两处编号门禁**永不触发** |

**一句话**：**门禁的价值等于它被触发的次数，不等于它被实现的次数。**

**为什么现在做**：REQ-99b58f 的 FR-4 审计里，三处失效的表现完全一致——文档与提示词写得很硬，
代码里却永远走不到那一行。这类失效**不报错、不告警、测试全绿**，比没写更危险：
它让人误以为这块已经被保护了。

**为什么不是「随手改一下」**：编号两处是确定性缺陷（可单测证伪），三要素是**已实现的
未接线**（需要选调用点、定跳过规则、防存量误伤），改动跨越 domain / application / tools 三层，
并牵连 T-9 改卡通道与两条建卡路径，值得留痕与验收。

## 2. 用户与角色

| 角色 | 是谁 | 他要什么 | 今天被什么卡住 |
|------|------|----------|---------------|
| **需求方 / 验收人** | 用户 | 看得懂卡在做什么；能相信「门禁说了会拦就真的会拦」 | 承诺过的门禁没生效，但看板与提示词看起来一切正常 |

## 4. 要解决的问题

### P1 三要素门禁从未被接线（主问题）

`checkTaskCardTriad`（content-gates.ts）实现完整、单测齐全，但**没有任何生产调用方**；
`GateFailure` 的 code 联合类型里早就预留了 `task_card_incomplete`，全仓无处产出它。
同时卡骨架**根本不产出三要素节**——即使接上线，每张卡都会被拦下。
承诺、门禁、产出三方各说各话。

### P2 编号跳号门禁的判据失效

连续性判定的正则把 `\d+` 写成 `d+`（字面字符 d），实测 `re.exec('FR-1')` 恒为 `null`，
分组表恒空 → 函数恒返回「无跳号」。这条门禁**从上线起一次都没生效过**。

### P3 编号重复门禁结构上不可能触发

重复判定的输入来自「条款定义提取」，而后者返回前已用 `Set` 去重 →
每个编号的计数恒为 1 → 判定恒返回空。这是**结构性死代码**，不是阈值问题。

### P4 失效无任何报警（元问题）

P1–P3 的共同放大项：三处失效都不报错、不告警、测试全绿。
仓库里没有任何机制回答「这条门禁最近一次拦下过什么」。
本需求**不建**这套观测能力（见 §8），但要求三处修复都带**反向验证**用例：
把判据改坏，用例必须变红。

## 5. 用户场景

### 场景 1｜拆分产出新卡（今天翻车的地方）
窗口调 `reqboard_decompose` → 每张卡的骨架**直接含三要素节**（在做什么 / 解决什么问题 /
得到什么结果），内容取自计划的 title / context / acceptance → 人打开卡就能读懂，
不需要追问「这张卡到底在干什么」。

### 场景 2｜卡读不懂就想开工
窗口调 `reqboard_move` 从 `decomposing` 进 `implementing` → 插件在**离开拆分态之前**
逐卡核对三要素 → 有卡缺节或节为空 → **推进被拒**，消息指出是哪张卡的哪一节。
（门禁在**开工前**生效，不是等交付后才发现卡看不懂。）

### 场景 3｜单卡结单
窗口调 `reqboard_task_move(to=done)` → 同比对卡文件；齐备放行，缺节则拒并指路
（补三要素后重试）。防止卡在拆分后被手改坏、被覆盖。

### 场景 4｜需求文档编号自查
窗口写需求文档时跳号（`FR-1` 之后直接 `FR-3`）或把同一条款定义写了两遍 →
**提交被拒**并指出缺哪个编号 / 哪条重复。门禁**在提交的那一刻**生效，
而不是等到下游拆分才发现编号对不上。

### 场景 5｜接手存量卡
新窗口接手一张已归档的旧卡（只有 `## 目标` / `## 验收标准`，无三要素节）→
不被新门禁拦下（存量豁免），需要改验收标准时 T-9 改卡通道**仍然定位得到那一节**。

## 6. 功能点

> 编号规则：根编号 = `FR-<n>`（功能点），验收标准 = `AC<n>`；每条 AC 都可证伪（跑什么、看到什么算过）。

### 模块 A｜把门禁接上执行链

**FR-1 三要素门禁接线**：`task_card_incomplete` 必须有真实产出路径，且只在「卡该被判定」的时刻判定。
- AC1：需求出口拦——`decomposing→implementing` 时若任一卡缺三要素节，`reqboard_move` 被拒，
  code=`task_card_incomplete`，消息列出是哪几张卡的哪些节。
- AC2：单卡结单拦——`reqboard_task_move(to=done)` 时同判；三节齐备的卡放行（不阻断正常流程）。
- AC3：不误伤——卡文件不存在、任务不属于本窗口绑定需求、`to` 不是被守卫的目标态 → 一律不判。

**FR-2 拆分骨架直出三要素**：两条建卡路径产出的卡都含 `## 在做什么` / `## 解决什么问题` /
`## 得到什么结果` 三节且各节正文非空。
- AC1：`reqboard_decompose` 落库后读卡文件，三节均在；`context` 为空时该节为**显式兜底文案**而非空行。
- AC2：`reqboard_task_report` 在卡文件缺失时自造的骨架头同样含三节（两条路径同构、不各说各话）。
- AC3：反向回归——把骨架里任一节改回旧标题（`## 目标`），对应出口门禁必须拒（证 `task_card_incomplete` 真在跑）。

### 模块 B｜让失效的编号门禁复活

**FR-3 编号跳号门禁复活**：`FR-1` 与 `FR-3` 之间的缺失编号必须被检出并拒绝。
- AC1：构造跳号的需求文档（`FR-1` + `FR-3`）→ 提交被拒，code=`requirement_clause_sequence_gap`，消息含 `FR-2`。
- AC2：连号文档（`FR-1` 到 `FR-5`）→ 通过；多前缀各自独立连续（如同时有 `FR-1` 与 `NFR-1`）→ 通过。

**FR-4 编号重复门禁复活**：同一条款定义出现两次必须被检出并拒绝。
- AC1：同一编号的**定义行**在文档里出现两次 → 提交被拒，code=`requirement_clause_duplicates`，
  消息含 `FR-1（出现2次）`。
- AC2：反向回归——把判定改回「喂去重后的清单」，该用例必须变红（证明判据真的依赖未去重来源）。

### 模块 C｜不误伤、不掉链

**FR-5 存量兼容与既有通道不失效**：
- AC1：T-9 改卡通道对新旧标题都命中——旧卡（`## 验收标准`）与新卡（`## 得到什么结果`）
  各构造一例，改卡后该节正文被整段替换。
- AC2：存量豁免——台账里 10 条非终态需求 / 19 张在途卡在新门禁下**零误伤**（实测记录留痕）。
- AC3：提示词侧零改动——`prompt-baseline` 与 `stage-prompts` 基线用例保持全绿（本次只让实现追上已有承诺）。

## 7. 非功能需求

| 项 | 要求 |
|----|------|
| **向后兼容** | 旧标题卡仍可被改卡通道定位；存量需求（无产物 / 已过出口）不被新门禁拦下 |
| **不改状态机** | reqboard 六态与既有闸门（产物确认 / 人工确认 / 计划批准）语义**不变**，只**新增调用点** |
| **分层不破** | 判定仍是零 IO 纯函数（content-gates），文件读取只在 wiring 层，工具壳只负责调用与拒绝 |
| **可回滚** | 移除两个调用点即恢复今天行为；wiring 函数不写台账、无副作用 |
| **规模** | 出口门禁多读 N 张卡（N ≤ 20），单次开销 < 200ms |

## 8. 边界（本轮不做）

- ❌ **不回溯改写存量卡**：已归档 / 已验收的 19 张卡保持原样（归档事实不重写），只在重新打开结单时受新门禁约束。
- ❌ **不改 `support.ts` 的同步结单证据校验**：新门禁只走工具壳的异步预检（沿用既有薄壳路线），不动另一窗口正在占用的文件。
- ❌ **不新增门禁类型、不改提示词片段**：本次只让实现追上已有承诺（`task_card_incomplete` 已在提示词里）。
- ❌ **不做文风评判**：标题像工程名词堆叠只产生建议级 warnings，不阻断（保持既有取向，避免形式主义）。
- ❌ **不建门禁观测面**（「这条门禁最近拦下过什么」的统计）——P4 提出的元问题本轮只记录，不实施。

## 9. 优先级与版本切分

| 批次 | 内容 | 理由 |
|------|------|------|
| **批次 1** | FR-3、FR-4（两处编号门禁复活） | 纯函数、零接线风险、可独立单测证伪；先做能把回归基线立起来 |
| **批次 2** | FR-2（拆分骨架直出三要素） | 接线的**前置**——骨架不产出三要素节，接上线就会把所有新卡拦死 |
| **批次 3** | FR-1（两个调用点接线）、FR-5（兼容与通道回归） | 依赖批次 2；接线后必须跑存量零误伤与 T-9 通道回归 |

**依赖关系**：FR-1 **依赖** FR-2（顺序不可颠倒）；FR-5 与 FR-1 同批（接线同时验证兼容）。

## 10. 测试策略

| 层级 | 数量（估） | 覆盖 |
|------|-----------|------|
| 单元 | ~6 | 跳号判定（跳号 / 连号 / 多前缀 / 不可解析 id）、重复判定（重复 / 唯一）、三要素判定（缺失 / 空） |

| **E2E** | **≥1** | 需求文档 → 拆分产出卡 → 出口门禁拦截/放行 全链路 |

**反向验证（必做，对齐 P4）**：把三处判据各改坏一次（骨架改回旧标题 / 重复判定喂去重清单 /
跳号正则改回 `d+`），对应用例必须变红；只测成功路径不算测过。

**明确不覆盖**：前端渲染（本轮不动 `src/client`，也不需要重建客户端产物）。
