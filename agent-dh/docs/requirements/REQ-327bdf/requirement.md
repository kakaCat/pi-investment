## 1. 产品定义

**产品**：**用 DSH 原生 Workflow 执行任务**——不再维护自己的状态机（pending → in_progress → testing → done），而是把任务执行定义为 DSH Workflow，让用户可以看到实时进度、每个阶段的 agent 输出、失败重试机制。

### 当前问题（为什么要重构）

| 维度 | 当前实现 | 问题 |
|------|---------|------|
| **状态管理** | 自己维护状态机（TaskStatus 类型 + reqboard_task_move） | 重复造轮子，DSH 已有 Workflow 系统 |
| **可见性** | 只能看到"任务状态=in_progress"，看不到内部在做什么 | **Agent 是黑盒**（用户核心痛点） |
| **并发** | 任务按依赖顺序串行执行 | 前后端任务可以并发，但当前无法表达 |
| **失败处理** | 手动调用 reqboard_task_move 返工到 in_progress | 无自动重试，无失败回滚 |
| **监控** | 无实时进度，只有最终汇报 | 用户不知道 agent 卡在哪一步 |
| **可视化** | 无，只有文本汇报 | DSH 有现成的 workflow 可视化 UI |

### 目标状态

**任务不再是"YAML 状态机 + 静态 Markdown"，而是"DSH todo_write + Agent 动态拆解 + Subagent 执行 + 实时更新 Markdown"**

**用户看到的**：
- ✅ 实时进度：当前在"编码"阶段，已完成 "创建 Controller"
- ✅ 每个 agent 的输出：看到 agent 创建了哪些文件、运行了什么测试
- ✅ 可视化：Markdown 任务卡实时更新进度（✅/⏳标记）
- ✅ 失败重试：某阶段失败可以重新运行该阶段

## 2. 用户与角色

| 角色 | 是谁 | 他要什么 | 今天被什么卡住 |
|------|------|----------|---------------|
| **用户（监督者）** | 用户 | **观察 agent 要做什么，不让 agent 是黑盒**——实时看到 agent 在哪个阶段、做了什么、输出了什么 | 只能看到"任务状态=in_progress"，看不到内部进展 |
| **执行窗口 / Agent** | 执行任务的 agent 窗口 | Agent 动态拆解 + Subagent 执行，失败时记录断点可重试 | 手动管理状态转移，无自动重试机制 |
| **接手窗口 / 未来的自己** | 中途接手任务的其他窗口或未来回看 | 看到完整的执行进度（Markdown 任务卡实时更新） | 只有最终汇报，看不到中间过程 |
| **前后端开发者（人工）** | 需要与后端联调的前端开发者 | 前后端任务可以并发执行，联调阶段自动等待 | 只能串行执行，无法表达并发 |

## 4. 要解决的问题

### P1 Agent 是黑盒（用户核心痛点）

**现象**：
- 用户看到"t-001: in_progress"，但不知道 agent 在做什么
- agent 卡住了（等待 API 响应、思考时间过长），用户无法判断
- 只有任务完成后才看到汇报，中间过程不可见

**根因**：
- 当前状态机只有 6 个粗粒度状态（pending/in_progress/integrating/in_review/testing/done）
- 状态转移是离散的（从 in_progress 跳到 testing），中间没有进度

**影响**：
- 用户无法监督 agent，不知道 agent 是否在做正确的事
- 无法判断 agent 是卡住了还是正常运行

### P2 重复造轮子

**现象**：
- reqboard 自己实现了状态机（TaskStatus 类型 + task 文件的 status 字段）
- 自己实现了状态转移逻辑（reqboard_task_move）
- DSH 已有的工具：subagent（子 Agent）、todo_write（任务状态）、job 系列（后台任务）

**根因**：
- reqboard 开发时不知道 DSH 有 workflow 能力，或者当时 DSH workflow 还不成熟

**影响**：
- 维护成本高（自己维护状态机代码）
- 无法享受 DSH workflow 的能力（可视化、重试、并发）

### P3 无法表达并发

**现象**：
- 前端任务和后端任务可以并发开发（编码阶段）
- 当前只能按 depends_on 串行执行

**根因**：
- 状态机是线性的（一个任务只有一个状态）
- 无法表达"前端和后端同时进行，联调时汇合"

**影响**：
- 效率低，本可并发的任务被迫串行

### P4 失败处理手动

**现象**：
- 测试失败后，需要手动调用 reqboard_task_move(to='in_progress') 返工
- 无自动重试机制
- 无失败回滚（如编码阶段创建了文件，测试失败后文件还在）

**根因**：
- 自己实现的状态机没有重试逻辑
- 没有事务回滚机制

**影响**：
- 失败处理繁琐，需要人工介入

## 5. 功能需求

### FR-1：用 DSH todo_write 替代 YAML
- 拆分任务时调用 todo_write 持久化
- 不再生成 tasks.yml 文件
- Agent 可以用 DSH todo 工具查询和更新任务状态

### FR-2：Agent 二次拆解 + Subagent 执行
- 任务开工时，Agent 根据任务信息动态生成 6 阶段详细计划
- 逐个阶段调用 DSH subagent 执行
- 实时更新 Markdown 任务卡进度

### FR-3：支持并发执行
- 可以用 Promise.all 并发执行多个粗粒度任务
- 前后端任务可以并发开发

### FR-4：失败处理与重试
- Sub-task 失败时记录失败阶段
- 可以从指定阶段重新执行
- 不需要从头开始
