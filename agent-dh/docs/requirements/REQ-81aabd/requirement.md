# REQ-81aabd 需求流水线节点名称统一（设计/拆分）+ 设计文档建模

| 项 | 值 |
|----|-----|
| 类型 | feature |
| 提出 | 用户（会话 w-45748eec） |
| 分析 | investor / w-45748eec |
| 触发实证 | 用户："planing 和技术设计名字，不合适，代码整体都修改了"；"设计节点展示设计所有的文档了吗" |

> **本文档只回答「做什么」。** 分层实现、字段建模、渲染契约属于「怎么做」，在 `design/*.md`；
> 落地步骤在拆分计划 `plan.md`。

## 1. 问题

需求流水线（reqboard）的节点名与产出物名在**三个层面**同时错位，且已固化进代码、UI、文档与提示词分片：

1. **节点名错位（中英两套语义）**：节点 3 的英文键是 `planning`（计划），中文却叫「技术设计」；
   `decomposing` 节点显示「拆分」，但语义边界与用户心智相反——
   用户的心智是「**拆分才是计划**（做哪些步骤），**设计就设计**（怎么做）」。
   实测旧 UI 文案把 `plan`（计划）挂在"设计"节点上，导致"计划批准"这一人工门看起来像在批准设计文档。
   **且中文改成「设计」后，英文键仍叫 `planning`——中英两套语义，同一错误换个语言又犯一次。**
2. **产出物名错位**：设计阶段的计划文档 `plan.md` 在文档与提示词里被称作「**实施计划**」，
   而"实施"是下一个节点（`implementing`）的动作——同一份文档的名字与它所在节点互相矛盾。
3. **设计产物不可见**：设计节点只显示分类模板要求的**文件名清单**（`CATEGORY_DELTAS.requiredDesignDocs`），
   从不显示需求目录里**实际已提交**的 `design/*.md`；已提交的设计文件被自动发现成 `kind=notes`。
   结果是"产出无人消费"——用户问"设计节点展示设计所有的文档了吗"，答案是**没有**。

## 2. 产品定义

**产品**：需求流水线（reqboard 项目看板）的**阶段命名体系**与**设计阶段产物呈现**。

- 命名体系是**公共坐标**：节点中文名 / 英文键 / 产出物名三者必须一一对齐，否则人在看板上批准的
  东西与系统落库的东西会错位。
- 设计阶段的呈现要回答一个具体问题：**"这套设计文档交齐了没有？"**——逐份给 已交/未交，
  而不是只列模板要求的名字。

交付后用户应能：在看板上看到与心智一致的节点名（设计 = 怎么做；拆分 = 做的步骤），
并在设计节点一眼看出四份设计文档哪份交了、哪份没交。

## 3. 用户与角色

| 角色 | 关心什么 | 本需求给他什么 |
|------|----------|----------------|
| 需求提出人（用户） | 我在批准什么？节点名与我的说法一致吗？ | 节点名 = 设计/拆分/实施；设计文档逐份 已交/未交 |
| 执行窗口（本窗口/其他窗口） | 提交的东西落在哪个节点、叫什么 | 统一后的 ZH/EN 命名表 + 唯一事实源文档 |
| 半年后的复盘者 | 当时的 `design/*.md` 到底交了没有 | 台账里 `kind=design` 的产物条目 + 面板上的交付状态 |

## 4. 功能点

### FR-1: 设计节点改名并唯一化（键 `planning` → `design`，中文「技术设计」→「设计」，英文 Design）

把节点 3 的**英文键**从 `planning` 改为 `design`、显示名从「技术设计」统一为「**设计**」；
代码、UI、提示词分片、文档四处用同一组名字（代码里用英文键、UI 显示中文、注释写「中文（英文）」）。
契约版本 `REQBOARD_SCHEMA_VERSION` 6 → 7；运行时读路径保持**零兼容**（不做读时自动归一），
旧台账由 FR-7 的一次性版本化迁移修好。

### FR-2: 拆分节点与拆分计划命名收口（`decomposing` = 拆分，`plan.md` = 拆分计划）

`design` 阶段产出的 `plan.md` 由「实施计划」更名为「**拆分计划**」；`decomposing` 节点中文名
「拆分」保持不变但英文/文档表述统一为 `decomposing`。全仓不再出现旧名「实施计划」指代 `plan.md`。

### FR-3: 设计文档种类建模（`design` kind + `design/*.md` 归位规则）

产物种类新增 `design`（设计文档）：`design/*.md` 经 `kindForRelPath` 归为 `design`、归因到
`design` 阶段；非 `.md`（如 `design/*.html`）仍归 `notes`。**该种类是展示种类，
不进入任何闸门与必备产物清单**——六类需求里有四类不要求设计文档，塞进必备清单会误伤它们。

### FR-4: 设计节点逐份显示设计文档交付状态（已交/未交）

设计节点面板按分类模板要求的文件逐份渲染，标出 ✅ 已交 / ⬜ 未交（含真实路径），
业主可直接追问"哪份没交"；本类型不要求设计文档时显示「无（本类型跳过设计文档）」。
**只加呈现：提交闸门、必备产物、计划批准门不变。**

### FR-5: 旧产物条目种类回填（规则升级后不停留在 notes）

`syncReqArtifacts` 扫描时，对 `autoDiscovered: true` 的旧条目按**当前**规则重算种类并回填
（`notes` → `design`），保证规则升级后历史需求不需要手工重登；人工登记的条目不被覆盖。

### FR-6: 全仓旧名清理与客户端产物重建

src（含提示词分片源）、docs、测试基线中不再残留旧名「技术设计 / 实施计划 / 头脑风暴」；
客户端 `lib/client.js`、`lib/client.cjs` 重建并通过构建门禁。

### FR-7: 旧台账键名迁移（`planning` → `design`，schema v6 → v7）

存量台账（`requirements[].status`、`statusHistory[].status`、`artifacts[].stage`）里的旧键名
`planning` 由 `scripts/migrate-ledger.ts` 一次性迁移为 `design`：幂等（`schemaVersion=7` 时早退）、
白名单外零差异、备份原文件、原子替换、`--verify` 能独立复核。**只改状态类字段，不改正文**
（评论/证据/验收标准里的历史 `planning` 措辞原样保留）。

## 5. 边界

- **不做**：不把 `design` 加入 `STAGE_ARTIFACT_REQUIREMENTS`、`ARTIFACT_CONFIRM_GATES` 或任何推进条件
  （选项 A，用户已确认）；不改验收单 / 归档门。
- **不做**：不调整 `plan.md` 的登记阶段（仍由 `design` 阶段登记 `kind=plan`）——
  用户提出的"拆分才是计划"在**命名层**收口；登记阶段迁移属于下一轮，需单独立项。
- **不做**：不为已有历史需求补写设计文档（只回填种类，不造文件）。
- **不做**：不为历史 `planning` 正文措辞做改写（评论区、证据、验收标准里的历史用语保留原样）。
- **做**：台账 JSON 契约版本 6 → 7（FR-7），仅状态类字段归一 + 版本号 bump，不含其它结构变更。
