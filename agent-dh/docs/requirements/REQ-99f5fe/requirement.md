## 1. 产品定义

**产品**：pmboard 的**业务 hook 领域**——一句话：
**把"宿主事件到达 → 触发业务行为"的判定与动作收成一个领域：判定纯函数化、动作单点化、过程可查、接线可门禁。**

**为什么现在做（实证触发，不是"应该做"）**：
① 用户报告注入文案失效；② 本窗口实证：注入文案每回合都在（系统提示词可见），却**一次弹框都没有**；
③ 排查时发现同类静默故障还有两处（悬空接线、半接线——后者已被 REQ-e3b6a0 接手）；④ 业务 hook 行为
目前散在 `adapters/CaptureHook.ts`（判定）与 `src/index.ts`（5 个闭包动作）两处，**没有一个地方能回答
"这个插件的 hook 到底会做哪些事"**。

### 1.1 "业务的 hook 机制"清单（本需求的范围）

业务的 hook = 宿主事件到达后**触发业务行为**的那一层。现状清点（2026-09-20 实测）：

| # | 业务行为 | 触发事件 | 现状位置 |
|---|---------|---------|---------|
| B1 | 立项捕获登记（待立项评估候选） | `user/message`（未绑定窗口） | `CaptureHook.ts` |
| B2 | 承接推进（draft → brainstorming） | `user/message`（已绑定窗口） | 判定在 CaptureHook，动作在 `index.ts` 闭包 |
| B3 | 阶段纪律提示词注入 + 注入留痕 | `user/message`（绑定 + 节点可注入） | 同上 |
| B4 | 里程碑超时提醒（产物登记 30 分钟未确认） | `user/message`（绑定 + 超时） | 同上 |
| B5 | 节点结算 → 上下文隔离 | `turn/end`（本回合登记过结算） | 同上 + `node-settlement.ts` |
| B6 | 待捕获清除（防跨回合重复 nag） | `turn/end` | `CaptureHook.ts` |
| B7 | 工具痕迹跟踪（done 凭证门判定"开工以来有无干活"） | `tool/call`（非忽略会话） | `CaptureHook.ts` |
| B8 | 近期用户消息缓冲（文字确认防伪造核验） | `user/message`（清洗后非空） | `CaptureHook.ts` |
| B9 | 捕获引导段注入（未绑定→立项引导；已绑定→推进纪律） | systemPrompt 组装 | `capture-section.ts` + `index.ts` 段注册 |
| B10 | 闸门确认后置链（推进 / 压缩 / 注入 / 唤醒 / 留痕） | 弹框作答（声明 `gate`） | **REQ-e3b6a0 的 gate 链（进行中），本需求只对齐不重建** |

**明确不收（注册型 plumbing，不是业务 hook，本轮一律不动）**：

- 工具注册（`tools.register` ×11）、HTTP 路由注册（`webServer.register`）、服务惰性注入（`ctx.inject` ×6）；
- systemPrompt 段的**注册机制**本身（B9 收的是"注入什么内容"的判定，不是"怎么注册段"）；
- 手工 `disposers.push`、SSE 推送通道、工具 `render` 展示回调；
- 客户端全部挂载（slots / 自定义事件 / 定时器 / 样式注入 / `window.__*` / sessionStorage / page-kit 壳）；
- 台账订阅管道（`repo.subscribe`）的机制本身。

> 理由：这些是"怎么向宿主注册"的基础设施，不是"事件到了做什么业务动作"。混进来会让领域变成
> "插件全量重构"，范围失控。若以后要治理注册面，另立需求。

## 4. 要解决的问题

### P1 注入文案使立项门失效（用户报告的直接现象）

**现象**：注入文案每回合都在（系统提示词可见，且引用当轮消息原文），但 LLM 全程不弹框。
**证据**：本窗口 15+ 轮方案讨论，`reqboard_status` 始终 unbound；台账（`agent-dh/.dsh-data/dsh-reqboard.json`）
中该窗口 `sourceSessionId` 的 open 需求数 = 0。
**根因**（三处硬伤）：① 写成「请先**判断**该输入是否属于这类工作」——建议句而非指令句；
② 豁免项含「**继续之前话题** → 正常回复即可」，使多轮讨论中的每次追问都能被放行；
③ 文案说「**两问**确认」而 `reqboard_create` 工具契约要求「必须先弹**三问**确认」。
**影响**：立项门形同虚设；用户对系统失去信任。
**关联**：REQ-e3b6a0 §7.3.1/§7.3.2 独立发现了同一根因（同一门三处口径矛盾 + "何时弹"缺口）——
两侧结论一致，本条款与其对齐（谁先做谁做，不重复）。

### P2 业务 hook 判定与动作散落两处

**现象**：B1–B8 的"判定"在 `adapters/CaptureHook.ts`，"动作"全在 `index.ts` 的闭包里
（经 `CaptureHookDeps` 的 5 个回调绕回组合根）。
**证据**：`CaptureHookDeps` 声明 `onBoundWindowActivity` / `onStagePrompt` / `onNodeSettled` 等回调，实现在 `index.ts`。
**根因**：hook 按"哪里需要就在哪里接一根线"长出来，从未定义登记处。
**影响**：改一条行为要同时改两处；新人/新窗口无法一次读懂。

### P3 悬空接线（实证）

**现象**：`index.ts` 曾残留 `onAskUserQuestionAnswered`，而 `CaptureHookDeps` 并不声明该字段。
**证据**：`npx tsc --noEmit` 报 5 个错误（`src/index.ts(257,5)` TS2353 等）；且该残留正是用户已明令禁止的能力
（"ask_user_question 不能有这个能力，会混乱的"）。
**根因**：没有"声明—注册"一致性门禁；类型错误只是"碰巧"暴露（若字段可选则完全静默）。
**影响**：禁用能力可能悄悄复活；类型门禁长期红着，真错误被淹没。

### P4 半接线（实证；当前状态已变化，需重新对齐）

**现象**：本会话早前误加的"业务弹框自动继续"能力曾处于一半状态（端口声明与适配器实现存在，
用例与组合根未接线，运行时永不触发，而单测 6/6 绿）。
**证据**：当时 `use-cases/` 零命中 `autoContinue`、`index.ts` 仅传 `resolve`。
**现状（2026-09-20 复核）**：该桩已被 REQ-e3b6a0 t7 **删除**，替换为 `gate` 声明 + `GateAwareQuestions`
装饰器 + `GatePostChain` 责任链。
**根因**：单测直接 `new UserQuestionsAdapter(resolve, spy)` 注入回调，**绕过组合根**，于是全绿假象。
**影响**："源码级测试绿 ≠ 线上生效"的又一次复现；本需求据此立门禁（RF-7），并明确与 e3b6a0 的边界（RF-5）。

### P5 不可观测

**现象**：被问"为什么没触发"时，系统内没有任何地方能回答。
**证据**：本次排查只能靠"读代码 + 在自身系统提示词里碰巧看到注入文本"倒推，耗时整个会话。
**根因**：hook 执行过程无留痕（对比：阶段提示词注入有 `injection_log`，hook 决策没有对应物）。
**影响**：每次排查从零开始；无法回归验证"触发率是否真的提升"。

## 6. 重构条款（RF-#）

### RF-1: 注入文案可驱动立项弹框（本需求唯一显式行为变更）

需求分析阶段的注入文案（针对性提示 + 未绑定静态引导）必须让 LLM 在本回合弹出立项确认框：
改为指令句、给出必立触发清单（含"已产出方案后用户任何回应"）、豁免收窄为纯寒暄 / 纯状态查询 /
纯知识问答、显式声明"继续之前话题"不是豁免，并与 `reqboard_create` 的三问契约统一口径。

- AC1：`capturePromptForMessage` / `captureGuidanceText` 渲染结果**包含**「本回合」「必须」「三问」，
  且**不包含**「两问」；`npx vitest run tests/capture.test.ts` 通过。
- AC2：构造"用户追问已给出的方案"场景，两段文案均命中「已产出方案 → 立项信号」分支（断言包含该分句）。
- AC3：文案不含 `{{变量}}` 占位符（断言 `not.toContain('{{')`）。
- AC4：与 REQ-e3b6a0 的 CaptureRequirement（pm 专有立项弹框）**不冲突**：若其已上线，文案改指向
  其工具而非 `ask_user_question`（以 design 阶段的边界定案为准，见 §14）。

### RF-2: 业务 hook 判定聚合成单一领域

B1–B9 的判定收进**一个领域目录**，提供规则类型、规则表、跑批器与单一动作出口；
`adapters/CaptureHook.ts` 退化为"规范化 + 执行"的薄适配器，`index.ts` 不再持有散落回调。

- AC1：`grep -rn "onBoundWindowActivity\|onStagePrompt\|onNodeSettled" src/index.ts` **无命中**。
- AC2：`grep -rln "shouldCaptureWindow" src/adapters/CaptureHook.ts` **无命中**（判定已迁出）。
- AC3：规则表导出为一个数组常量，长度 = 9（B1–B9 全部登记；B10 由 REQ-e3b6a0 的链承载，不入本表）。
- AC4：每条规则的判定是纯函数：可单独单测，不依赖 `ctx` / 网络 / fs。

### RF-3: 新增 hook 不改组合根

新增一条业务 hook 只允许改"规则表 + 测试"两处；`src/index.ts` 不因新增行为而改动。

- AC1：一次演示提交中 `git diff --stat src/index.ts` 对该新增**为空**，而规则表文件有改动。
- AC2：新增条目后相应单测通过（证明无需额外接线）。

### RF-4: 悬空接线与禁止项机械可查

- AC1：`npx tsc --noEmit -p tsconfig.json` 对 hook 相关代码 **0 错误**。
- AC2：往组合根故意加回一个未声明的回调字段 → 门禁测试**失败**。
- AC3：禁止项断言：任何 hook/续跑机制的白名单**不包含** `ask_user_question`（用户裁定）。

### RF-5: 闸门作答后置与 REQ-e3b6a0 对齐（不重建）

pmboard 里"弹框作答后要做的事"必须以 REQ-e3b6a0 的 `GatePostChain` 为**唯一织入点**；
本需求不另建续跑机制，只在边界上对齐与补缺口。

- AC1：`grep -rn "autoContinue\|onAnswered" src/` **无命中**（旧桩不得复活）。
- AC2：`grep -c "autoContinue" src/application/use-cases/AskConfirm.ts` **= 0**（范式①内联完成的弹框禁止叠加异步续跑）。
- AC3：核验 REQ-e3b6a0 的链是否覆盖 `reqboard_accept_sheet` 多批续跑（作答后自动发起下一批直至 `pending=0`）：
  覆盖则本条款仅留验证记录；不覆盖则在其链上补 handler，**不绕开链另造机制**。
- AC4：反向证明：对 `reqboard_ask_confirm` 作答后断言**没有**注入任何"继续"消息（防双重推进）。

### RF-6: hook 决策留痕与只读查询

每次宿主事件经领域跑批后留下决策记录（规则 id / 事件 / 窗口 / verdict / 原因 / 动作 / 耗时），
提供有界 ring buffer（容量上限常量）与只读查询入口。

- AC1：跑一次规则，决策记录含 `ruleId` / `verdict` / `event` / `windowKey` 四字段。
- AC2：写入超过容量上限后，记录条数 **= 容量上限**（有界）。
- AC3：只读查询能按窗口过滤，返回命中与跳过记录。

### RF-7: 接线门禁 G1–G5 落地且可故障注入

- AC1：门禁测试含 G1–G5 五组断言，`npx vitest run` 全绿。
- AC2：故障注入：临时注入悬空接线 → G1 红；临时让规则表与注册不一致 → G2 红；
  临时把 `ask_user_question` 加入续跑白名单 → G5 红（逐一验证后还原）。

### RF-8: 既有 hook 行为不变式

- AC1：`npx vitest run tests/capture.test.ts tests/capture-hook.test.ts tests/isolate-node-context.test.ts`
  **全绿**，且这三个文件断言**逐条未被修改**（`git diff` 对它们为空）。
- AC2：领域目录内无 `node:` / `@deepseek-ai/*` / `fs` 导入（`layer-boundary` 门禁通过）。

## 7. 行为不变式（refactor 必填）

| # | 不变式 | 判定方式 |
|---|--------|---------|
| INV-1 | 既有 hook 行为的可观测结果不变 | `capture.test.ts`(22) / `capture-hook.test.ts`(27) / `isolate-node-context.test.ts` 逐条不变且全绿 |
| INV-2 | 判定层纯函数：禁 `node:` / `@deepseek-ai/*` / `fs`，禁 `Date.now()` | `layer-boundary` 门禁 + 规则单测（注入 now） |
| INV-3 | 监听器内不做会话写操作（D-17） | 动作用途经异步边界；沿用 `node-settlement` 的可注入 `schedule` |
| INV-4 | 失败隔离：任一规则抛错只告警，不打断其他规则与流水线 | 故障注入单测 |
| INV-5 | `ask_user_question` 永不进入任何续跑/自动继续白名单 | 门禁 G5 |
| INV-6 | 搬迁不夹带改行为 | 纯搬迁步的回归逐条不变 |
| INV-7 | **不叠加续跑**：范式①（同步内联完成）的弹框不得叠加异步注入续跑 | 门禁：`AskConfirm.ts` 的 `autoContinue` 命中数恒为 0；端到端断言无多余 followup |

## 8. 非功能需求

| 项 | 要求 |
|----|------|
| 向后兼容 | 迁移期间不改变 hook 对外可观测行为；`CaptureHookDeps` 既有字段在迁移步内保持可用 |
| 不改动什么 | 不改需求状态机与人工闸门语义；不改 token / 提示词分片口径；不改 `userQuestions` 服务本身；**客户端一行不动** |
| 可回滚 | 分步迁移，每步独立 revert；任一步回归变红即停并回退该步 |
| 规模 / 性能 | hook 全程同步无网络；判定复杂度 O(规则数 × 台账规模)；决策日志 ring buffer 有界 |

## 9. 边界（本轮不做）

- ❌ **注册型 plumbing 一律不动**：工具注册 / HTTP 路由注册 / 服务惰性注入 / systemPrompt 段注册机制 /
  `disposers` 清理机制 / SSE 通道 / 工具 render 回调 / 台账订阅管道（见 §1.1 不收清单）；
- ❌ **客户端一行不动**（slots / 事件 / 定时器 / 样式 / 全局挂载 / 持久化 / page-kit 壳）；
- ❌ 不重建闸门后置链（REQ-e3b6a0 已做，本需求只对齐）；
- ❌ 不引入任务依赖调度器 / DAG（另立需求）；
- ❌ 不回填、不伪造历史台账数据；
- ❌ 不改 `ask_user_question` 本体行为；
- ❌ 不把"验证文档存在"当作"功能已接线"。

## 12. 迁移与回滚（refactor 必填）

- **分步迁移**，每步独立可验证、独立可回滚（单步 revert 不牵连其他步）；
- 顺序：清悬空（本次会话已做，待门禁固化）→ 抽规则表（纯搬迁）→ 加决策留痕 → 迁 B1–B9 九条行为 →
  与 REQ-e3b6a0 链对齐核验 → 门禁；
- **双向校验**：规则表建立期，用"现有行为集合 vs 规则表集合"的差集证明无遗漏（差集为空才进下一步）；
- **回滚点**：任一步回归变红即停止并回退该步，不带病推进。

---

## 13. 性能基线（refactor 必填）

- 现状基线：单次 `user/message` 处理为纯内存判定（规则数 × 台账规模），无网络、无 fs；
- 目标：迁移后**判定耗时 P95 不劣于现状**；由决策日志 `ms` 字段采集并回归对比；
- 决策日志写入不得阻塞事件派发（同步入内存 ring buffer，落盘异步/有界）。
