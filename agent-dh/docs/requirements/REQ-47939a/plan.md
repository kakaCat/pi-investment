# REQ-47939a 实施计划 · reqboard 分层重构

> 阶段：technical design（planning）· 窗口 w-41e7e4cd
> 需求文档：`requirement.md` · 设计一套：`design/architecture.md`、`design/domain-model.md`、`design/migration.md`、`design/test-cases.md`

## 1. 目标（一段话）

把 15,413 行的 dsh-pmboard 插件按 DDD 拆成 `domain`（纯规则）/ `application`（用例）/ `adapters`（I/O）/ `tools`+`http`（薄适配）四层，让**每条领域规则全仓只有一处实现**；顺带把 13 个工具收敛为 9 个、把账本从 v4 无损迁移到 v5，并删掉迁移后不再需要的兼容代码。目的不是"好看"，是把"改一处漏三处"和"规则无法独立单测"这两个真实故障源去掉。

## 2. 做法（人话版）

1. **先立骨架再搬代码**：先建 `domain/` 与 `application/ports.ts`，把规则**按现有实现语义**搬进去（注释一起搬），暂不改行为。
2. **strangler-fig 逐用例切换**：新用例与旧实现并存，一个动作一个动作地切；每切一个跑一次全量测试，红了就退回上一步。
3. **工具壳最后换**：9 个工具的入参/返回体逐一对照现状；`reqboard_submit(kind)` 用**分派表 + 4 个独立用例**实现，不写大 if。
4. **routes 只做协议转换**：删掉 `routes.ts` 里重复实现的状态校验（:285/:347/:355），改调用例。
5. **迁移在最后做**：代码删除收益（别名表、backfill 兜底）依赖迁移完成，所以迁移排在 P0 尾部，脚本 + 报告一起交付。
6. **客户端放 P1**：`view.ts`/`styles.ts` 按视图区机械拆分，DOM 结构与类名不变。

## 4. 设计与实施纪律（硬约束）

1. **零行为变更**：除"工具入口 13→9"与"账本 v5"两处**已获用户批准**的变更外，任何可观察行为不得改变（拒绝条件、错误码、消息、台账语义、DOM 结构）。
2. **每步回归**：任一批次结束必须 `npx vitest run` 全绿；契约测试与层边界测试是硬门。
3. **构建门**：涉及客户端时 `pnpm build:client` + `verify-client-build.mjs` 哨兵必须过（历史事故：改了 src 未构建，页面无变化）。
4. **注释随代码搬**，不重写、不删"为什么"型注释（事故出处是本仓最贵的资产）。
5. **不新建平行实现**：搬完后旧文件必须删除，禁止"新旧两份都在跑"长期共存（strangler-fig 是过程不是终态）。
6. **测试只增不删**：实现测试可重写但须列出"原断言 → 新断言"对照，总数不减少。

## 8. 为什么本阶段不交任务表（W7 边界）

技术设计回答"代码层面怎么做"；**任务卡（含实施方案与可证伪验收标准）在拆分阶段创作**，由 `reqboard_decompose` 落库。本计划给出的是可据以拆分的结构与纪律，不预设任务粒度——避免"批次顺序"在拆分阶段被计划表绑架。
