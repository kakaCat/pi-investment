## ⚠️ T3 复诊结论：T2 的「apply() 未执行」判定是**观测面错误**，予以推翻

### T2 误诊的三重观测错误

T2 依据「日志里找不到 capture hook registered / NODE-1」判定 pmboard 插件 apply()
未执行。T3 逐项复核后发现，这是**日志观测面全面失效**导致的误判，真实情况是
日志根本不在被检查的地方：

| # | T2 检查的观测面 | 实际情况 |
|---|----------------|---------|
| 1 | `~/Library/Logs/com.pi-investment.dsh/launchd.out.log` | **路径错误**。launchd plist 配置的 StandardOutPath 实为 `agent-dh/.dsh-data/state/launchd.out.log`，该目录从未有日志写入 |
| 2 | `.dsh-data/state/launchd.out.log`（配置路径） | **停更于 09-19 18:59**。此后所有重启都由外部 shell 手工 `start.sh` 拉起，未经 launchd，故不写该文件 |
| 3 | 当前进程 stdout | **死管道**。当时进程由另一个 Claude Code 会话的 `./scripts/start.sh --no-open 2>&1 \| tail -5` 拉起，tail 退出后 stdout 指向无读者的管道，console.log/logger.info 全部蒸发（`lsof -p <pid> -d 1,2` 显示 PIPE，对端无进程） |

### 反证（apply() 其实一直在正常执行）

- reqboard 工具全部可用（reqboard_status / task_move 等均正常返回）——它们与 Hook 订阅在同一个 apply() 里注册；
- 本窗口（bound）的 systemPrompt 里持续注入「项目看板（reqboard · 本窗口已绑定需求）」段——该段由 registerCaptureGuidance 注册，与 capture 引导段同一装配点；
- dist/index.mjs 与 node_modules 是符号链接且 inode 相同（排除硬链接副本过期假设）。

### 教训（已沉淀为本次修复的一部分）

**诊断日志必须落文件，禁止只依赖 stdout**。stdout 在以下常见情形全部不可读：
launchd 未接管、外部 shell 管道拉起、tail/tee 提前退出。
