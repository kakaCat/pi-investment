## 1. 背景：痛点与现状核查

### 1.1 用户痛点（立项原话）

任务卡太粗，一个任务包含设计+实现+测试+文档全部工作量时，agent 执行到后半程质量显著下滑（"任务太长 agent 就不好好完成任务"）。用户要求：**任务再拆成子任务，子任务由 workflow 管理**。

## 2. 产品定义

### 2.1 目标（做完之后世界有什么不同）

1. 任务卡之下新增**子任务层**：按任务类型的**固定模板**落子卡，每张子卡是看板上可认领、可独立凭证推进的真实卡片；
2. 子卡执行统一走 **DSH Workflow**：一张子卡 = 一次独立 workflow run（子代理干活），产出回写子卡；
3. 父卡由子卡**自动收尾**：全部子卡 done → 汇总产出 → 父卡过凭证门 → 需求 rollup；
4. 单次执行单元（一张子卡）的工作量小到一个子代理可靠完成 —— 直接对症"任务太长做不好"。

## 3. 用户与角色

| 角色 | 是谁 | 职责 |
|---|---|---|
| 发起人（人） | 用户 | 提出工作意图；做关键决策（需求文档确认 / 批准计划 / 异常处置 / 验收裁决）；**不必进看板** |
| 执行窗口（agent） | 立项窗口（如本窗口） | 写需求·设计·计划；批准后触发首个推进事件；异常时被弹框请处置 |
| 执行器（system actor） | 插件宿主自动链（非任何窗口） | 以 system 身份推进任务状态、写凭证、收尾与 rollup；不代表窗口 |
| 子代理（workflow 叶子） | 每张子卡启动一次 | 干活；**无台账写权限**，产出经宿主回写 |
| 审阅者（人） | 用户 | 验收单逐项裁决（既有能力，不变） |

## 4. 功能点（FR，供拆分阶段 requirement_refs 引用）

- **FR-1: 按卡类型落子卡集合**（映射表覆盖 feature/refactor/bug/doc/chore/spike/research/data/ops/review-only，未知类型回退两卡）
- **FR-1b: 显式 stages 逃生舱口**（拆分计划可为单张卡声明 stages 覆盖映射表，枚举受控、验收仍须可证伪）
- **FR-2: TaskRecord 子卡字段**（parentId / stageKind / attempt，全部可缺省、向后兼容）
- **FR-3: 父卡开工懒展开子卡**（task_move→in_progress 同事务落子卡 + 留痕）
- **FR-4: reqboard_task_run 逐卡执行**（一次调用执行当前 ready 的一张子卡 = 一次独立 workflow run）
- **FR-5: 子卡状态收紧四态**（todo→in_progress→done（+canceled），不进 integrating/testing/in_review）
- **FR-6: 子卡完工凭证**（workflow run 证据 + 文件 mtime 证据，豁免窗口活动检查）
- **FR-7: 失败即暂停并留痕**（子卡退回 + attempt+1 + 失败评论 + revisions 记录；链停在该卡、不自动重试、不由自动链代劳决策）
- **FR-8: 父卡自动收尾与需求 rollup**（全部子卡 done → 汇总汇报 → 父卡凭证门 → 父卡 done）
- **FR-9: 父卡分层并行与并发上限**（父卡层由 depends_on 可并行；同需求同时 in_progress ≤3）
- **FR-10: 并发写冲突纪律**（拆分阶段改动面重叠即拒 + 运行期 mtime 跨卡覆盖兜底）
- **FR-11: 事件链自动驱动**（批准计划 → 自动拆分/开工/展开/逐卡执行/收尾/rollup；每步完成自动触发下一步，全程无需人工触发）
- **FR-12: 自动化控制面**（需求级 autoRun 开关、进度可见、暂停/继续/终止、连续失败熔断告警）
- **FR-16: 会话内弹框交互**（人工确认以弹框/对话形式完成；除关键决策外节点推进全自动，不需要人到需求看板点节点）
- **FR-13: 失败暂停与人工介入**（不自动重试；失败即暂停 + 会话内弹框（唯一交互面，见 §8 #17）+ 人三处置：重跑/退回上游/取消）
- **FR-14: 返工回上游**（新增 `implementing → design` 人工闸门转移，重新描述需求后重走设计→计划→拆分→实施）
- **FR-15: 卡片修订留痕**（返工就地更新旧卡 + 卡片修订记录；回滚类动作同样留痕；done 卡受影响时人工重开）

## 5. 边界（明确不做，防范围蔓延）

- ❌ 不引入动态拆分（默认集合由映射表确定，不由 LLM 临场发挥；仅允许计划**显式声明** stages 覆盖，见 FR-1b）
- ❌ 不做后台全自动跑链（由窗口循环调用驱动；取消/跳过的裁决权保留给人）
- ❌ 不做存量任务卡迁移（无 parentId 的存量卡行为完全不变）
- ❌ 不重做看板视觉（子卡按普通卡展示 + 阶段徽标即可）
- ❌ 不恢复/不依赖被禁用的 `tool-workflow`（直接消费已在位的 workflow 引擎）

**父卡状态机收敛（本设计的直接后果）**：新式父卡只走 `todo → in_progress → done`（中段由子卡链承载，父卡不动）；原五段状态机中的 integrating/testing/in_review **保留给存量卡**（双模共存），新式父卡不再进入。

```
存量卡：todo→in_progress→integrating→testing→in_review→done（原样，不改）
```

### 6.2 自动驱动：推进事件链（"可控的自动化"核心）

**机制一句话**：不是"一条传送带一直转"，而是"推倒第一张骨牌，它自己撞倒下一张"——**每完成一步，就自动触发下一步**。

```
批准计划 ──👉【事件1】自动拆分 + 自动开工 + 展开子卡链
                              │ 完成后自动触发
                              ▼
                        【事件2】跑子卡①  ─┐
                        【事件3】跑子卡②   │ 每步 = 一次独立 workflow run
                        【事件4】跑子卡③   │ 每步完成即自动触发下一步
                        【事件5】跑子卡④  ─┘
                              │ 链完
                              ▼
                        【事件6】父卡自动收尾 ──→ 下一张父卡 或 需求 rollup
                              │
                              ▼
                        需求进入 accepting ──■ 停下（验收是人的事）
```

**每一步（推进事件）的四个性质 = "可控"的来源**：

| 性质 | 含义 | 带来的控制力 |
|---|---|---|
| **小** | 一次只推进一张子卡（一次 workflow run） | 不会撞 10 分钟工具超时，不会长时间黑箱 |
| **幂等** | 同一步重复触发不会重复干活（"子卡已 done"是事实） | 进程崩溃/重启后，重新触发一次即接着走 |
| **可中断** | 不触发下一步，链即停住 | **暂停 = 不推下一张牌**；终止 = 关掉开关 |
| **留痕** | 每步写台账 + 事件日志 | 看板可见"走到哪一步 / 上一步干了什么 / 为何停" |

**交互面原则（FR-16，2026-09-20 用户裁定）**：人工交互一律以会话内弹框/对话完成——弹框是友好的设计，但"进需求看板点节点推进"不该是必经路径。据此：
- **保留弹框**：需求文档确认、计划批准、失败处置、验收（这些是人真正要做决策的点）；
- **去掉重复弹框**：「确认拆分清单」这道门并入「批准计划」——批准的计划里已含完整任务表，落库只是把它写进台账；批准弹框内写明"批准后自动拆分并开跑，中途不再打断"；
- **节点推进全自动**：除上述关键决策点外，实施链的每一步都不需要人操作，也不需要进看板点击（看板是"观察与控制面"，不是"必经的推进入口"）。

**可控性控制面（人可随时介入，但不是必须介入）**：
- **进度可见**：需求卡显示 父卡 x/y、子卡 x/y、当前在跑的卡与阶段；
- **暂停/继续**：需求级 `autoRun` 开关——关掉即"不推下一张牌"，已有状态不丢；打开并触发一次事件即续跑；
- **终止**：同开关 + 可手动取消任务（取消是人工闸门，取消后自动链跳过该卡）；
- **熔断**：同一需求连续 N 次失败自动暂停并以会话内弹框告知（唯一交互面，防无人值守时无限重试烧 token）；
- **无需人工的常态路径**：批准 → … → 需求进入 accepting 全程无人工介入；人工只在异常（熔断/告警）时被请上场。

### 6.3 子卡映射表（按卡类型，固定默认 + 显式逃生舱口）

| 父卡类型 | 子卡集合（stageKind，默认串行顺序） |
|---|---|
| feature / refactor | dev（研发）→ integrate（联调）→ review（复核）→ test（测试） |
| bug | repro（复现）→ fix（修复）→ review（复核）→ regress（回归测试） |
| doc | dev（文档撰写）→ review |
| chore | dev → review |
| spike | probe（探针）→ review |
| research / analysis（策略研究、取数调研） | collect（取数/调研）→ analyze（分析）→ review |
| data（数据修复/数据作业） | prepare（方案/脚本改动）→ run（执行）→ verify（数据校验）→ review |
| ops（部署/运维/配置） | change（变更）→ dryrun（试运行）→ apply（实施）→ verify（验证）→ review |
| review-only（纯复核卡） | review |
| **未映射/未知类型** | dev → review（保守两卡回退） |

- **映射表是数据化配置**（不改代码即可扩类型）：新增卡类型 = 加一行映射
- **逃生舱口（FR-1b）**：拆分计划里可为单张卡显式声明 `stages`（覆盖映射表），用于映射表盖不住的新流程；声明必须取自受控 stageKind 枚举（不允许自由文本），且每张子卡仍须有可证伪验收标准
- **默认仍不由 LLM 临场发挥**：不动 `stages` 时集合完全确定（守住第 1 问"固定模板"的可预测性）
- 联调卡（integrate）沿用既有 `skipIntegration` 语义可跳过（其余卡不允许跳过）
- **顺序口径（2026-09-20 用户裁定）**：**review 在前、测试在后** —— 先复核设计与实现是否对齐（早发现偏离、改完再测不浪费），测试作为链尾放行门；无测试段的类型以 review 收尾
- 子卡 acceptance 由映射表模板生成（必须可证伪）；implementation 由父卡 implementation + 阶段提示组合成

### 6.4 数据契约（TaskRecord 扩展，全部可缺省、向后兼容）

| 字段 | 类型 | 必填 | 语义 |
|---|---|---|---|
| `parentId` | string? | 否 | 有值 = 子卡；无值 = 普通/父卡（存量卡行为不变） |
| `stageKind` | enum? | 子卡必填 | `dev`/ `integrate`/ `test`/ `review`/ `repro`/ `fix`/ `regress`/ `probe` |
| `attempt` | number | 否（默认 0） | 失败重跑次数 |

- 子卡继承父卡 `requirementId` / `side`；链内 `dependsOn` = 前一张子卡；首卡依赖父卡原有外部依赖
- 父卡**不存**子卡 id 列表（由 parentId 反查派生，单一事实源，避免双写不一致）
- 子卡状态收紧为四态：`todo → in_progress → done（+ canceled）`，**不进** integrating/testing/in_review（避免"联调卡自己还要联调"的递归语义）；`assertTaskTransition` 增"卡片角色"入参以收紧子卡转移表
- 无需 bump schemaVersion（纯加字段）

### 6.5 接口

**变更**：`reqboard_task_move(to=in_progress)` 作用于普通卡时触发懒展开（同事务落子卡 + 留痕）。理由：计划批准的是任务表，拆分时偷落子卡会变成"批了 A 落库 B"；懒展开让子卡在开工时出现于看板。

**新增**：`reqboard_task_run(task_id)`

```
入参：{ task_id: string }                      // 父卡 id
出参：{
  subtask_executed: { id, stageKind, status } | null,
  next_ready:       { id, stageKind } | null,      // null = 链完或停链
  chain:            { done: number, total: number },
  blocked:          { subtaskId, reason } | null,  // 停链原因
  parent_status:    string
}
错误语义：
  · 父卡不存在 / 不属于本窗口绑定需求 → 拒绝（沿用现有错误码）
  · 父卡未 in_progress → 提示先开工，不执行任何卡
  · 链已全部 done（重入）→ 幂等返回 chain.done === chain.total
  · 存在失败未仲裁的子卡 → 直接返回 blocked，不执行任何卡
```

**执行实现**：每张子卡 = `ctx.workflowEngine.start()` 一次 run（直接消费已加载引擎，不经被禁用的 tool-workflow）；脚本只用官方五个 hook（`agent/parallel/pipeline/phase/log`），不得出现 `ctx.*` 或工具名。

### 6.6 失败、暂停与返工（全自动下的人工介入）

**失败处理（不自动重试）**：
- 子卡失败（子代理跑挂 / 产出不合格 / 凭证门不过）→ 子卡退回 `todo` + `attempt+1` + 写失败评论；**不自动重试**；
- 立即**暂停该需求自动链**（关 `autoRun`）+ **以会话内弹框请人处置**（含失败卡、原因、建议）——**唯一的人工交互面就是这道弹框**（2026-09-21 用户裁定，见 §8 #17）；同一文本落宿主日志**仅作排障留痕**，**不另做告警通道、不发飞书**；需求停在 `implementing`，**不进验收**；
- 理由（用户裁定）：失败常见根因是"需求本身没描述对"，自动重试解决不了描述错误，只会烧 token 并掩盖真因。

**人工三处置**（收到告警后择一）：
1. **重跑该卡**：开启 `autoRun` 并触发一次推进事件；
2. **退回上游重新描述需求**（本需求新增能力，见下）；
3. **取消任务/需求**（人工闸门，现有能力）。

**告警即弹框、且只有弹框**（FR-16 友好交互）：失败暂停后的**唯一人工交互面 = 会话内弹框**（选项：重跑该卡 / 退回上游重新描述需求 / 取消），人点选即完成处置，不需要进看板找入口；**不另做告警通道、不发飞书、不接通知面**；同一文本落宿主日志仅作排障留痕。

**弹框的达成机制（2026-09-21 用户裁定 v2，见 §8 #18）**：后台执行器无会话回合、不能直接向用户弹框，故失败告警投递给来源窗口的不是原始告警正文，而是**弹框指令壳**——指挥来源窗口 LLM 收到后立即调弹框工具（题干 ≤80 字说清"哪条需求、停在哪张卡、为什么停"，选项固定三处置，用户点选即执行对应动作）。指令壳复用里程碑超时提醒（REQ-2e9473 t09）同款"到时触发"机制；宿主日志仍记原始告警正文供排障。

**返工回上游（本需求新增的状态机能力）**：
- 现状缺口（实读 `src/domain/requirement/RequirementStatus.ts:61`）：`implementing: ['accepting', 'canceled']` —— **没有退回上游的路径**，"需求描述不对"时无处可退；
- 新增转移：`implementing → design`（回上游重新描述/设计），**人工闸门**（破坏性：会触发卡片修订）；退回后重走 design → 批准计划 → decomposing → implementing（均为既有路径）；
- 验收退回返工路径已存在（`accepting → implementing`，`RequirementStatus.ts:63`），无需新增。

**返工时的卡片处理（用户裁定：更新旧卡 + 卡片留痕，与测试回滚同口径）**：
- **就地更新而非作废重建**：重新批准计划后，对受影响的既有父卡**更新**（title/description/implementation/acceptance/dependsOn），不新增重复卡、不置 canceled；
- **卡片修订记录（revision log）**：每次修订在卡上追加一条——时点 / 触发原因（哪次失败、哪条需求描述变更）/ 字段变更摘要 / 操作者；**回滚类动作同样留痕**（子卡失败回退、done 卡被重开），形成可回溯时间线；
- **done 卡只在受影响时才重开**：已被新需求描述推翻的 done 卡 → 人工闸门**重开**（`done → in_progress`；现有状态机 `done: []` 为终态，需新增该转移）；重开后 rollup 重新计算，需求若已进 accepting 则沿既有 `accepting → implementing` 退回；
- **不做**：自动重开 done 卡——自动链只推进未完成卡，不擅自推翻已完成结论。

**跳过**：仅联调卡可走既有 skipIntegration 语义；其他卡不允许自动跳过（取消是人工闸门）。

**工具级回滚**：撤下自动驱动开关即回手动模式；已生成的子卡仍可手动 `task_move` 推进，不阻塞交付。

### 6.7 子卡完工凭证（关键技术点）

现有 done 凭证门（`application/internal/support.ts:92` `assertDoneEvidence`）含"本窗口工具活动"检查，而干活子代理在**别的会话**，该检查对子卡恒不成立。子卡凭证口径改为：

1. 子卡有非空 report（由调度器从 workflow 产出生成，含 filesChanged）；
2. filesChanged 至少一个文件真实存在且 mtime ≥ 子卡开工时间（与窗口无关的文件系统证据）；
3. workflow run 的 stopReason 为 completed 且阶段产出非空。

父卡凭证：汇总 report（由子卡产出合成）+ 全部子卡 done。

### 6.8 父卡并行与并发纪律（2026-09-20 用户补问后新增）

**层职责划分**：
- **父卡层**：并行度由父卡 `dependsOn` 控制（现有语义，无需新机制）。互不依赖的父卡可同时处于 `in_progress`；
- **子卡层**：只在自己父卡内部串行（链内 dependsOn）；**子卡依赖不跨父卡** —— 跨父卡的先后顺序一律由父卡层依赖表达，避免两套依赖语义打架；
- **驱动**：执行器每次只推进**一张子卡**（单次时长可控、不撞 10 分钟超时）；不同父卡的子卡链由执行器同时推进（无需窗口在场），互不阻塞。

**并发上限**：
- 同一需求下同时 `in_progress` 的父卡数默认 **≤ 3**（常量化到 `domain/limits.ts`，可配）；
- 超限时 `reqboard_task_move(to=in_progress)` 拒绝并提示"先完成已在跑的父卡"（拒绝发生在开工动作，而不是 task_run）。

**并发写冲突纪律**（两张卡的研发子卡同时改同一文件会互相覆盖）：
- **拆分阶段拦（主防线）**：同一需求下**互无依赖**的父卡，若 `implementation` 声明的改动文件路径集合有交集 → `reqboard_decompose` 拒绝，要求重划范围；
- **运行期兜底（次防线）**：子卡完成后若其 filesChanged 中某文件的 mtime 落在**同需求另一张在跑父卡**的子卡执行窗口内 → 判定跨卡覆盖，子卡标记失败并停链，交窗口仲裁；
- **诚实边界**：文件 mtime 只能证明"文件被改过"，不能证明"内容正确"；本纪律防的是**静默覆盖**，不替代人工 review。

**收尾互不干扰**：父卡收尾只改自己与子卡的状态；需求 rollup 仍按"全需求任务 done"推进（`applyTaskRollup` 现有语义不变）。

## 7. 验收标准（可跑）

### 7.1 单元测试

- 子卡模板映射表：4 种父卡类型 → 正确卡集合（含 unknown/legacy 类型回退到两卡）
- ready 选择：仅"todo 且链上前卡 done"的子卡被选中
- 失败停链：注入子卡失败 → 断言 `task_run` 返回 blocked、不执行后续卡、子卡回 todo 且 attempt+1
- 父卡收尾：全部子卡 done → 父卡 report 生成 + 父卡 done
- 子卡状态机收紧：子卡尝试 →integrating 被拒
- 父卡并发上限：同一需求第 4 张父卡 →in_progress 被拒（上限 3）
- 拆分期冲突拦截：两张互无依赖父卡的 implementation 声明同一文件 → decompose 拒绝
- 非研发映射：research/data/ops/review-only 卡各自落到正确子卡集合；未映射类型回退 dev→review
- 逃生舱口：计划为单卡声明 `stages:[collect, analyze, review]` → 断言实际落库子卡按声明顺序；声明非法 stageKind 时拒绝建卡
- 运行期冲突兜底：构造某文件 mtime 落在另一张在跑父卡的子卡窗口内 → 该子卡判失败并停链

### 7.2 集成验证

- 建测试需求 → 落一张 feature 父卡 → 自动链跑完 → 断言：4 张子卡按 dev→integrate→review→test 顺序全 done、父卡 done、需求自动进 accepting
- 脚本契约门禁：生成的 workflow 脚本静态扫描**只含** hook 白名单，出现 `ctx.`/`subagent`/工具名即失败（替代现有"grep 字符串"式测试）
- 父卡并行：两张互不依赖的父卡由执行器同时推进 → 两条子卡链独立推进、互不阻塞；两张都跑完后需求 rollup 正常进 accepting
- 全自动链：批准计划后**不调用任何人工工具** → 断言需求一路自动推进到 accepting（含父卡收尾与 rollup），中途无任何弹框/看板点击
- 门合并：批准计划 → 断言需求自动 design→decomposing→implementing（不再出现"确认拆分清单"弹框），且落库任务表与已批准计划 key 一致
- 失败暂停：注入子卡失败 → 断言 autoRun 关闭 + 会话内弹框抛出（唯一交互面）+ 需求停在 implementing（不进验收）
- 返工回上游：implementing → design（人工闸门）→ 重新批准计划 → 断言既有父卡被**更新**（卡数不变）且卡上新增修订记录
- done 卡重开：人工重开受影响 done 卡 → 断言状态回 in_progress、留痕写入、rollup 重算

### 7.3 工程边界

- 新增字段不破坏旧台账读取（用现有台账样本跑一遍读取 + 看板渲染）
- `pnpm vitest run`（dsh-pmboard 包）全绿；工具 schema 过冒烟测试
