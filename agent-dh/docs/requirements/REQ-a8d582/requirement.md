> 相关：[REQ-2e9473](../REQ-2e9473/requirement.md)（验收单逐项裁决 / 关键确认三通道）· [REQ-9f4a44](../REQ-9f4a44/requirement.md)（验收通过即归档）

## 0. 档位：重档（轻档 L3 单向升级）

轻档 L3 定的升级信号是「出现第二个未定决策 / 要动架构 / 要改数据模型」。本条在追加「不合格也展示按钮」后同时命中两条：待定决策不止一个（返工任务生成的时机、覆盖留痕写哪一层），且要动台账字段（数据契约）。按规则**停手升级，不得反向降级**。

## 1. 背景

**用户原话**（本窗口收到的直接消息）：

1. 「本阶段操作」
2. 「未提交验收材料：先 reqboard_submit(kind=verification) 交材料，操作条才会出现「验收通过」」
3. 「这个修改成点击「验收通过」弹框，说有不合格的是否通过，可以吗」
4. 「不合格也展示按钮 这个添加上」

**用户订正（确认弹框中给出，取代我对第 2 句的误读）**：

> 「未提交验收材料：先 reqboard_submit(kind=verification) 交材料，操作条才会出现「验收通过」**这个你理解错了，是验收阶段按钮就展示**」

即：判据是**需求处于验收阶段**，不是"窗口已交验收材料"。现有那行提示把显示条件写成了后者，它本身就是被要求改掉的对象。

**现状实测**（2026-09-20 读工作区源码；起草时笔误写 09-16，此处订正）：

| # | 事实 | 位置 |
|---|---|---|
| 1 | 看板的「验收通过」是**一键直达归档、没有任何确认** | board-mount.ts:451-457 → api.ts:78 → POST /req/verify/pass |
| 2 | 后端这个端点**完全不看验收单**，只查"状态=验收态 / 材料存在 / 产物已登记" | verdicts.ts:34-82 handleVerifyDecision |
| 3 | 其它两条通道反而都有闸门：逐项裁决出现不通过会自动打回并生成返工任务；agent 侧弹框在全部通过时会弹最终确认 | verdicts.ts:128-175、AcceptSheet.ts:48-118 |
| 4 | 验收态但未交材料时，操作条**不铺按钮**，只给一行提示（把"验收阶段"错当成"已交材料"） | stage-detail.ts:258-260 |
| 5 | 提交含"不通过"的裁决后，需求被打回实施，**「验收通过」按钮随之消失** | verdicts.ts:130-167 |

第 3 条是动机：**看板按钮是唯一一条没有把验收情况摆到人眼前的路**。第 4、5 条是用户要求修掉的两处"按钮消失"。

## 2. 产品定义

项目看板（pmboard）的**验收环节**：窗口 agent 交付后提交验收材料，由人看着材料与逐项验收单决定"通过（即归档）"或"退回返工"。

本需求改的是这一环的**交互与裁决语义**：按钮的可见性要跟"处于验收阶段"一致，点击前必须把"不通过 / 未裁决"摆到人眼前；裁决动作与需求状态解耦（不再自动打回）；人确认"带不合格也通过"时，系统必须留下一笔可查的覆盖记录。**验收通过仍是人工门**，agent 不可代办。

## 3. 用户与角色

| 角色 | 在本需求里的位置 | 能做什么 / 不能做什么 |
|---|---|---|
| **人（审核者）** | 唯一有权操作验收裁决的角色 | 看验收材料与验收单 → 点「验收通过」（可带覆盖）或「退回返工」；**本次要保证他点之前先看到不合格项** |
| **窗口 agent（交付方）** | 提交验收材料、维护任务 | 调 reqboard_submit(kind=verification) 交材料；**不能**代替人点通过/退回，也不能绕过覆盖提示 |
| **看板插件（系统）** | 载体 | 决定按钮可见性、装配确认文案、把覆盖写进台账与留痕面 |

## 4. 功能点

### FR-1: 点「验收通过」先弹不合格项确认框

点按钮时先弹确认框，列出验收单里"不通过 / 未裁决"的条数与摘要，明确问"存在不合格项，是否仍要通过（通过即归档）"，人确认后才真正提交。

- 确认来源：立项弹框（用户选择「看板『验收通过』加不合格项二次确认弹框」）。

### FR-2: 有不合格项时不自动打回

提交含"不通过"的裁决后，需求**留在验收态**、不合格项留在验收单上，「验收通过」与「退回返工」两个按钮都在；由人自己选"通过"还是"退回返工"。退回时才回实施并生成返工任务。

- 确认来源：追问弹框选「①②都要」。
- 现状对照：现在只要有一项不通过就自动打回实施（verdicts.ts:130-167），按钮随之消失。

### FR-3: 进入验收阶段即展示「验收通过」按钮

只要需求进入验收阶段，操作条就展示「验收通过」，**显示条件只看阶段，不看是否已交验收材料**；现有"未提交验收材料：…才会出现「验收通过」"的提示文案随之移除。

- 确认来源：用户订正（见 §1）。
- 现状对照：现在未交材料时该位置只有提示文字、没有按钮（stage-detail.ts:258-260）。

### FR-4: 无材料时通过须显式覆盖并留痕

FR-3 的配套语义：验收阶段尚未交材料时点「验收通过」，弹框必须先讲清"尚无验收材料/证据"，人确认后才通过，且该次通过按**显式覆盖**处理（台账记录操作人 / 时间 / 原因，并进评论与状态事件）；不允许静默通过。

- 确认来源：追问弹框选「①②都要」；用户订正后本条的显示部分收窄为 FR-3（已获批准）。
- 备选口径：FR-4 也可改为"无材料时点击弹框只作说明并引导先补材料，仍不允许通过"——该口径未获采纳。

**"弹框"的载体**：看板是浏览器侧的 HTML 插件，沿用同文件既有交互（退回返工/退回理由已用 window.prompt），不新建弹框组件。

## 5. 接口与数据契约（细节见 design/interfaces.md、design/data-model.md）

- `POST /req/verify/pass` 增可选 `confirm_override`：有不合格项或无验收材料时必填，缺失返回结构化错误（错误码 `verify_override_required`）。
- 台账 `verification.override`（可选）：记录操作人 / 时间 / 覆盖说明 / 当时的不通过与未裁决计数；旧记录缺省即"无覆盖"。

## 6. 边界（明确不做）

1. **不改验收单逐项裁决规则**：不通过仍必填意见、返工续版仍只含未过项与未裁决项。
2. **不放宽人工门**：验收通过与退回返工仍只有人能操作，agent 不可代办。
3. **不改归档门**：归档材料要求与合并去向校验维持现状。
4. **不引入"自动通过"**：任何情况下都不存在无人确认的通过路径。

## 8. 验收标准（可证伪）

1. **不回归**：验收单全部为"通过"且材料齐全时，点「验收通过」不出现"不合格"字样，能正常进入归档态且不要求覆盖参数。
2. **有不合格项**：弹框可见，且文案含未通过/未裁决的**计数**；选"取消"→ 不发起任何请求，需求状态与验收单逐项状态不变。
3. **不自动打回**：提交含 1 项"不通过"的裁决后，需求**仍在验收态**、操作条同时有「验收通过」与「退回返工」；点「退回返工」才回实施，且生成的返工任务数 = 不通过项数。
4. **按钮只认阶段**：需求进入验收态、**尚未交任何验收材料**时，操作条就已出现「验收通过」（并断言旧提示文案不再出现）。
5. **覆盖留痕**：带覆盖的通过能在台账 `verification.override`、需求评论与状态事件三处查到原因原文；不带覆盖的同类调用被拒绝且状态不变。
6. **命令级**：`npx vitest run`（packages/pages/dsh-pmboard）全绿。

## 9. 风险与待决（已归位）

- **风险 1**：FR-4 放宽"必须有验收材料"= 允许无证据归档，兜底为"弹框警示 + 必须显式覆盖 + 双处留痕"。
- **风险 2**：取消自动打回后不合格项可能长期挂在验收态，兜底为看板显式标记（只要求可见）。
- **待决（已在设计中定）**：返工任务生成时机 → 随「退回返工」生成；覆盖留痕字段落点 → `verification.override`。
