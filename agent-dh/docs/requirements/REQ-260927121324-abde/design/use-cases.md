# 用户场景（REQ-260927121324-abde）

**一句话**：无论需求是靠窗口 agent 推进、人在看板点按钮推进，还是自动链无人值守推进，
Token tab 都要**要么给出可信数字，要么明确说「这段不可算」**——不再出现节点空白却显示正常。

| 场景 | 谁 | 走哪条写路径 | 关联功能点 |
|---|---|---|---|
| UC-1 看节点有数或如实空白 | 看板使用者 | 读路径 | FR-7 |
| UC-2 窗口 agent 推进 | 会话窗口 | 需求迁移 + 任务执行 | FR-1, FR-4, FR-5 |

## UC-1 看板使用者看到真实数字或诚实的「无快照」 <!-- serves: FR-7 -->

**触发**：打开需求详情 → 「🪙 Token」tab。

**期望**：
- 有快照的节点显示数字，任务明细列出每张卡的开销；
- 真缺快照的节点显示「无快照」，顶部出现「部分节点/执行无快照」提示（`degraded=true`）；
- 不出现「节点空白、明细为空，却显示一切正常」。

**现状对照**：REQ-260927100007-b8ba 的 `implementing` 既无 `buckets` 也无 `executions`，
`degraded` 却是 `false`。修复后 `degraded` 变 `true`，缺口在页面上可见。

## UC-2 窗口 agent 推进任务/需求时自动落账 <!-- serves: FR-1, FR-4, FR-5 -->

**触发**：窗口 agent 调 `reqboard_task_move`（todo→in_progress→done）、`reqboard_task_report`、`reqboard_move`。

**期望**：
- 开工写 `tokenUsage.start`（该会话累计四桶投影）；
- 完工 / 中途汇报写 `end`，仅当两端同会话且均为 projection 时产出 `delta`；
- 需求迁移带进入快照，离开节点结算进 `byStage`；
- agent 无需额外动作，也不需要理解快照机制。

**现状对照**：`beginExecutionToken` 是死代码，任务执行只有运行区间、没有消耗。

## UC-3 看板操作者点按钮推进也落账 <!-- serves: FR-1, FR-2, FR-3, FR-6 -->

**触发**：人在看板点「移动」/「确认产物即推进」/「验收通过 / 退回返工」/「逐项裁决」。

**期望**：
- 从看板走的每条路径同样把快照落账（带 `sessionId` 时）；
- 取不到会话上下文时诚实不传，该段显示「无快照」，不伪造；
- 批准计划 → 实施（拆分→实施跨越）后，`decomposing` 与 `implementing` 两个节点都消失的问题不再出现。

**现状对照**：`req/move` 与 `verify/*` 两处直接给 `req.status` 赋值，绕过迁移收敛点；
`confirm-settle.ts` 批准计划的两条分支都不带快照。

## UC-4 自动链无人值守跑完一张父卡 <!-- serves: FR-4, FR-5, FR-6 -->

**触发**：需求 `autoRun=true`，自动链依次开父卡、跑子卡、收尾、rollup 进验收。

**期望**：
- 父卡开工与子卡执行都写 `start`，收尾写 `end`（自动链驱动会话可解析时）；
- 纯 `system`、无会话的历史对账路径诚实不传，不产生伪造快照；
- 由任务完成触发的 `implementing → accepting` 派生推进，`implementing` 节点在 `byStage` 中有值。

## UC-5 维护者新增一条写路径时漏写快照会被拦下 <!-- serves: FR-8, FR-9 -->

**触发**：未来开发者新增一个任务执行产生点，或新增一条需求迁移路径。

**期望**：
- 任务执行快照只有一个写入口（`token-usage.ts` 的执行助手）；绕过它 → 源码扫描单测红灯；
- 需求迁移只能经 `transitionRequirement`；直接赋值 → 源码扫描单测红灯；
- 既有 token 单测全绿，并包含「漏快照即红灯」的回归断言。

## UC-6 翻历史需求时如实标注 <!-- serves: FR-7 -->

**触发**：打开修复前创建的、当时没写快照的需求。

**期望**：
- 继续显示「无快照 / 部分数据不可用」，不因修复而伪造历史数字；
- 总量与任务明细不自相矛盾（无快照节点的执行差值可按既有兜底口径合计）。
