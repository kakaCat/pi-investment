> —— 该设计稿已经用户多轮评审定稿（列表→泳道、折叠框、去统计、去顶栏底栏、锚定式弹框均逐条确认），本需求是它的落地实现。

## 产品定义

一句话：把 pmboard 会话流程节点的详情弹框重做成"点节点就地展开的结构化面板"——**基础信息**看这一步交付了什么，**执行流程**核对 agent 这一步是否按规定的流程执行（规定 vs 实际逐条对照）。设计基线见顶部链接（stage-modals-alpine.html）。

## 用户与角色（目标用户与使用场景） <!-- serves: FR-1 -->

- **谁用**：在 DSH 会话里跑需求流水线的窗口（Agent）与盯流程的人（用户）。
- **什么场景用**：一个需求跑到一半，人回到会话，想知道「这一步做到哪了、这一步交了哪些东西、**这一步背后到底发生了什么**」——鼠标移到会话标题栏的流程图，点其中一个节点。
- **解决什么痛点**：
  1. 现有节点弹框是纯文字流水账，节点之间信息结构不同质，"这一步交了哪些文档"要在文字里翻；
  2. **这一步的"隐藏动作"看不见**：站在页面上只看到需求往前走了一格，看不到背后注入了哪份提示词、调用了哪些工具、上下文是怎么被压缩与传递的——出问题时无从复盘；
  3. 长文档路径内联在面板里，既挤又不好点；面板还会盖住整页（居中大弹框），打断看会话正文。

### FR-1: 点节点就地下拉详情

用户在会话标题栏的流程图上点任一节点，详情**贴着流程条下方右侧**展开（不是盖住整页的居中弹框）；点面板外面或右上角 × 收起。

**验收标准**：打开任意绑定需求的会话 → 点「拆分」节点 → 面板出现在流程条正下方、右边缘与流程条右边缘对齐（间隙 8px），页面上没有全屏遮罩；点面板外部 → 面板消失。

### FR-2: 面板头说清"哪个需求、这一步什么状态"

第一行是需求编号胶囊 + 需求标题；第二行是节点状态胶囊（已立项/已分析/已设计/已拆分/实施中/待验收/已归档）+ 该节点一句话进展 + 最近动态时间。

**验收标准**：点「实施」节点 → 第一行看到 `REQ-xxxxxxx` 胶囊与需求标题；第二行看到「实施中」胶囊、一句话进展（如「7/12 完成 · 剩 5 个 · 进行中 t-xxxx」）与相对时间（如「12 分钟前」）。

### FR-3: 「基础信息」折叠框（默认展开）

装这一步交付了什么、这一步有哪些关键信息；框内所有文档都是可点的条目，点击在右侧栏打开全文。

**验收标准**：点「需求分析」节点 → 看到标题为「ℹ️ 基础信息」的框（已展开），框内列出该节点已登记的产物文档条目；点击任一条目 → 右侧栏打开该文档。

### FR-4: 各节点的基础信息各不相同

- 立项 = 需求描述 / 分类 / 文档位置 / 来源窗口 / 创建时间
- 需求分析 = 产物文档清单
- 设计 = 设计文档清单（逐份标已交/未交）
- 拆分 = 拆分计划文档 + 📊 DAG 层级（按依赖分层，节点可点开任务卡）
- 验收 = 验收材料 + 验收单统计（共 N 项 / 通过 / 不通过 / 待裁决）
- 归档 = 归档时间徽标 + 归档文档清单 + 合并到项目清单 + 一句话结论

**验收标准**：逐个点开 6 个节点（立项/需求分析/设计/拆分/验收/归档）→ 每个节点的「基础信息」框内出现上表对应内容；点「归档」→ 看到「✅ 已归档 · 时间」徽标与「🔗 合并到项目」清单。

### FR-5: 实施节点不摆「基础信息」，直接给 [流程图][泳道]

实施这一步要的是"任务怎么走"，所以不设基础信息框，直接给两个视图切换，默认流程图。

**验收标准**：点「实施」节点 → 面板内**看不到**「基础信息」框；看到「流程图 / 泳道」两个切换按钮，默认停在「流程图」并显示按依赖分层的任务节点。

### FR-6: 「执行流程」= 核对 agent 这一步是否按规定的流程执行

**目的**（2026-09-23 用户裁定）：让人一眼看出"agent 这一步有没有按规定的流程来执行"——是**规定 vs 实际**的合规对照，不是流水账。默认收起，点开才看。

三段构成：

- 📝 **提示词注入 = 规定本身**：这一步发给 agent 的阶段纪律（提示词片段）是哪份——它是"规定的流程"的原文，逐条可点开读。
- ⚙️ **执行动作对照 = 规定 vs 实际**：把该阶段纪律要求的关键动作逐条列出，**每条右侧给实际履行状态**（✅ 台账有记录 / ⬜ 未见记录）与出处（哪份产物/哪条时间线/哪个任务）。
- 🗜️ **上下文管理 = 规定的压缩传递 vs 实际隔离**：节点上下文怎么结算（规定）对照隔离留痕里的真实结果（实际）。

**「规定」的真实来源**：该阶段的提示词片段原文（`src/domain/prompt/fragments/<stage>/**` 里的纪律清单，如 `accepting/light.md` 明文写着"提交验收材料 reqboard_submit(kind=verification) / 请人审核 reqboard_accept_sheet / 下一步 archived"）。对照表的"规定"条目必须**逐字来自这些片段**——新增守护断言：对照表引用的动作名必须能在该阶段片段语料里找到，提示词改了纪律而面板没跟上时测试变红。

**「实际」的真实来源（不是文案，是留痕）**：

- 📝 **提示词注入** ← 注入留痕 `state/prompt-injection-log.json`（经 `GET /dashboard/api/reqboard/injection-log?window=<session>` 读取，接口已存在）：显示这一步**实际**命中的 `routeKey`、命中层级、`fragmentIds`（逐条可点开 → `src/domain/prompt/fragments/**` 真实文件）、字符数、是否被裁剪、难度判定理由、时间。片段 id 里有一部分是**路由壳**（无独立文件、只有 include 列表）——这类显示「路由壳 → 含 N 个子片段」，不假装有文件。
- ⚙️ **执行动作对照的"实际"一侧** ← 该节点**真实台账记录**：产物登记/人工确认（`artifacts`：登记了没有、人确认了没有）、状态推进（`timeline`：谁 · 何时 · 为什么）、任务流转（`tasks.executions`：每个任务真实的开工/完工/失败记录）。**不声称**是"窗口工具调用日志"——PTC 模式下内部调用统一呈现为 `run_code`，进程内 toolTrace 不落库、不按节点切分，做不到；台账记录是可核、持久、按节点切分的。
- 🗜️ **上下文管理** ← 节点隔离留痕 `state/node-isolation-log.json`：这一步节点结算时**有没有遗弃上下文**（status=replaced/skipped/rejected/fallback）、替换了 surface 的哪一段（range）、节点输入包多大（packageChars）、为什么（reason）。数据已在代码里建模（`application/internal/isolation-trace.ts` + `adapters/IsolationTraceFile.ts`），本期补一个与 `injection-log` 同款的**只读**端点把它读出来。

**验收标准**：点任一节点的「🔄 执行流程」→ 三段显示；「⚙️ 执行动作对照」里每条规定动作右侧带 ✅/⬜ 与出处（点出处可跳到对应产物/任务文档）；抽查 3 个节点 → 每条 ✅ 都能在该节点 artifacts/timeline/tasks 里找到记录、每条 ⬜ 确实无记录（不冤枉 agent）；点「提示词注入」片段条目 → 右侧栏打开真实提示词文件（路由壳显示「含 N 个子片段」，无留痕显示空态）；「上下文管理」显示真实隔离结果（状态/替换区间/输入包字符数/原因）。

### FR-7: 泳道视图

切到「泳道」后，任务按状态分列（待办/研发/联调/测试/Review/完成），6 列看板排开；每列列头是状态名 + 数量胶囊，列内卡片竖向堆叠、卡片多了列内纵向滚动；点卡片打开任务卡。

**验收标准**：点「实施」→ 切「泳道」→ 看到 6 条状态列（列头状态名 + 数量胶囊，列内任务卡片竖排）；窗口调窄后 6 列仍等宽排布、列内卡片纵向滚动，**没有卡片被裁切**。

### FR-8: 简约高级的苹果风视觉

浅灰底折叠头、胶囊标签、细分隔线、白底文档列表、无粗重投影；面板最宽 720px、超过 68vh 内部滚动。

**验收标准**：打开任一节点面板 → 面板为白底细边小圆角（10px）、最大宽度 720px；文档列表为白底圆角卡片逐行分隔；宽屏下与流程条右对齐，窄屏（1000px）下面板左边缘不越出窗口。

面板不再有「打开项目看板 / 打开需求看板 / 收起」三条按钮；收起改用右上角 × 与点面板外部（设计稿形态）；原「打开项目看板」入口仍在侧边栏与看板页。

**验收标准**：打开任一节点面板 → 面板底部**没有**按钮行；右上角有 × ；点 × 面板收起。

### FR-10: 消除「模板与门禁互相矛盾」

**问题**（2026-09-23 本需求实测踩出）：brainstorming 六类型注入模板（`templates/brainstorming/*.md`）的功能点/条款章节从未给出门禁唯一认得的定义形态（行首 `**<前缀>-N: 名称**` 或标题 `### <前缀>-N: 名称`；门禁正则 `DEF_LINE_RE`，`src/application/internal/doc-parse.ts:52`）。照模板写的文档在该需求登记过任意产物后会被提交门禁拒绝（`requirement_missing_clauses`）——本需求第一版就是这样被拦的（首次提交靠 legacy 放行分支漏过）。且 bug 模板把「目标」表编号写成 G1/G2，与五道人工闸门 G0–G4 撞名。仓内既有需求文档形态五花八门（bold/heading/table/三无并存）也印证了"没人能从模板推导出门禁要的样子"。

**做法**（修模板一侧，门禁代码与既有需求文档不动——门禁形态本身是合理的定义约定）：

1. 六份模板（feature/bug/doc/refactor/spike/chore）的条款章节补上门禁形态要求与示范定义行，前缀按类型：FR/BUG/RF/SP/DOC/CH；feature 保留三列表（给人看的速览）+ 定义行（给门禁的硬要求），其余五份照各自章节骨架补；
2. bug 模板的 G1/G2 目标表编号改掉（与闸门 G0–G4 撞名），条款一律 `BUG-x`；
3. **feature 模板与文档集策略对齐**（同一矛盾的第二个面，2026-09-23 实测）：`CATEGORY_DELTAS.feature.rootSectionsDelta` 要求根文档必有「产品定义 / 用户与角色 / 功能点」节，而 feature 模板写的是「目标用户与使用场景」且没有「产品定义」——照模板写的文档会在 G2 被 `missingCategoryDocs` 拦下。模板章节名与策略对齐（模板用「用户与角色（目标用户与使用场景）」双名过渡，并补「产品定义」节）；
4. 新增守护单测 `tests/template-clause-gate.test.ts`：① 每份模板的示范定义行能被 `DEF_LINE_RE` 认出且前缀正确；② feature 模板章节名覆盖 `requiredRootSectionsFor('feature')` 的全部必填节——模板与策略再漂移即变红，矛盾不能复发。

**验收标准**：① `pnpm vitest run tests/template-clause-gate.test.ts` 全绿（六份模板逐份断言示范定义行可解析 + 前缀正确 + feature 模板章节覆盖文档集策略必填节）；② 用改后的 feature 模板照写的样例文档喂给 `extractClauseDefinitions`（门禁同源函数）→ 解析出连续条款 FR-1…（单测断言）；③ `grep -c 'G[12]' templates/brainstorming/bug.md` 目标表编号处为 0；④ 本需求文档自身过 G2 的 `missingCategoryDocs` 核验（实测：设计阶段推进时无「requirement.md 缺必填节」）。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不改看板其他页面**：需求详情页、泳道看板页、工具定制卡片、Token 页的现有外观一律不动——新样式全部作用在节点面板根节点之下，不改既有全局选择器。理由：本次设计稿只覆盖节点详情弹框；改全局会波及与本次无关的页面。
- **不内联长文档全文**：面板内不渲染文档正文，一律「点开在右侧栏看」。理由：面板是索引不是阅读器（用户已明确）。
- **不重做会话顶部流程图本身**：流程条（节点/连线/token）已符合设计稿，本次不动。
- **不做移动端专项适配**：沿用现有 `min(720px, 100vw - 130px)` 的收敛策略，不单独设计手机布局。
