# 确认弹框新增"需要补充内容"选项

## 用户反馈
"新增内容那，现在支持吗"

## 问题分析

### 之前的 4 个选项
```
1. 确认推进
2. 需要澄清（有疑问，但不一定要改）
3. 需要修改
4. 暂停
```

**缺少的场景**：
- ❌ 用户想说："整体方向对，但需要**补充** XX 内容"
- ❌ "新增内容" ≠ "修改现有内容"
- ❌ "需要补充" ≠ "需要改错"

### "新增内容"的典型场景

#### 场景 1：漏了功能点
**用户反馈**：
> "需求文档只写了 FR-1 到 FR-4，但还漏了一个重要功能 FR-5：用户权限管理，需要加上"

**特征**：
- ✅ FR-1~FR-4 是对的（不需要修改）
- ✅ 但不够完整（需要补充 FR-5）
- ✅ 范围扩展（可能影响工作量）

---

#### 场景 2：技术方案不完整
**用户反馈**：
> "设计里有架构图和接口定义，但缺少数据库迁移方案，需要补充"

**特征**：
- ✅ 现有章节内容是对的
- ✅ 但缺少某个必要章节
- ✅ 需要新增而非修改

---

#### 场景 3：边界条件遗漏
**用户反馈**：
> "需求文档的边界部分没有提到并发限制，需要补充：单用户 QPS ≤ 100"

**特征**：
- ✅ 现有边界是对的
- ✅ 但遗漏了某个重要边界
- ✅ 需要追加而非修改

---

## 解决方案

### 新的 5 个选项

```typescript
export const DEFAULT_CONFIRM_OPTIONS = [
  '确认，推进到下一阶段 (Recommended)',
  '需要澄清（有疑问，但不一定要改）',
  '需要补充内容（现有内容对，但不够完整）',  // ✨ 新增
  '需要修改',
  '暂停',
] as const
```

---

## 三种"不满意"的区分

| 维度 | 需要澄清 | 需要补充内容 | 需要修改 |
|------|---------|-------------|---------|
| **问题类型** | 理解层面 | **完整性** | 准确性 |
| **现有内容** | 可能没问题 | **没问题，但不完整** | 有问题 |
| **操作** | 解释 | **追加/扩展** | 改正/改写 |
| **范围变化** | 无 | **可能增加工作量** | 通常不变 |
| **用户心态** | "我不懂" | **"漏了XX"** | "这个错了" |

## 实际案例对比

### 案例 1：选"需要补充内容"
**用户反馈**：
> "需求文档漏了 FR-5：导出报表功能。需要补充这个功能点"

**Agent 行为**：
```typescript
if (result.user_choice === '需要补充内容（现有内容对，但不够完整）') {

  await appendToRequirementDoc({
    section: '功能点',
    newClause: 'FR-5',
    content: '导出报表功能：支持导出 Excel/PDF 格式...'
  })
  // 重新提交确认
  await tools.reqboard_ask_confirm(...)
}
```

if (result.user_choice === '需要澄清（有疑问，但不一定要改）') {
  // 先解释

## 为什么需要区分"补充"和"修改"？

### 1. Agent 行为不同
- **"补充"** → `append()` 追加新内容
- **"修改"** → `update()` 改现有内容

### 2. 用户心理负担不同
- **"补充"**：心理更轻松，"只是漏了点东西"
- **"修改"**：心理更重，"写错了，要改"

### 3. 工作量评估不同
- **"补充"**：可能增加工作量（新功能点）
- **"修改"**：通常不增加工作量（改准确）

### 4. 沟通更精确
用户说"需要补充内容"时：
- ✅ Agent 知道：现有的别动，追加就好
- ✅ 用户知道：我不是说你写错了，只是不完整

用户说"需要修改"时：
- ✅ Agent 知道：现有内容有问题，要改
- ✅ 用户知道：这个确实写错了
