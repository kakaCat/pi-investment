# 确认弹框选项细化：理解差异 ≠ 需要修改

## 问题背景

**用户反馈**："理解差异不一定需要修改，这个你需要补充了"

**当前问题**：
- ❌ 原选项只有 3 个：`['确认推进', '需要修改', '暂停']`
- ❌ **"需要修改"太重**：用户可能只是有疑问、需要澄清、想换个角度理解
- ❌ **理解差异 ≠ 一定要改文档**：用户犹豫要不要点"需要修改"
- ❌ 缺少中间态：确认 vs 修改之间没有"讨论/澄清"的空间

## 解决方案

### 新增"需要澄清"选项

**修改文件**: `packages/pages/dsh-pmboard/src/domain/text/labels.ts`

**原选项**（3 个）:
```typescript
export const DEFAULT_CONFIRM_OPTIONS = [
  '确认，推进到下一阶段 (Recommended)',
  '需要修改',
  '暂停',
] as const
```

**新选项**（4 个）:
```typescript
export const DEFAULT_CONFIRM_OPTIONS = [
  '确认，推进到下一阶段 (Recommended)',
  '需要澄清（有疑问，但不一定要改）',  // ✨ 新增
  '需要修改',
  '暂停',
] as const
```

## 场景区分

### 场景 1：需要澄清（新选项）
**用户心态**：
- "我不太理解 FR-3 是什么意思，能解释一下吗？"
- "这个技术方案为什么选 A 而不是 B？"
- "这部分逻辑有点绕，能换个角度说说吗？"

**Agent 行为**：
- 读取 `user_feedback`
- **先解释/澄清，不立即改文档**
- 解释清楚后，可能不需要改文档
- 或者：解释完发现确实需要改，再改

**关键差异**：
- ✅ **理解层面的问题**（沟通问题）
- ✅ 文档可能是对的，只是用户还没理解
- ✅ 需要对话，不需要立即修改

---

### 场景 2：需要修改（原选项）
**用户心态**：
- "FR-3 的验收标准不够具体，必须补充"
- "技术方案漏了数据库迁移步骤，必须加上"
- "这个边界条件写错了，必须改"

**Agent 行为**：
- 读取 `user_feedback`
- **直接修改文档**
- 重新提交确认

**关键差异**：
- ✅ **内容层面的问题**（文档缺陷）
- ✅ 文档确实有问题，必须改
- ✅ 直接改，不需要讨论

---

### 场景 3：确认推进（肯定项）
**用户心态**：
- "没问题，可以推进了"

**Agent 行为**：
- 落章（confirmedAt）
- 自动推进到下一阶段

---

### 场景 4：暂停
**用户心态**：
- "暂时不处理这个需求"
- "等其他事情完成后再来"

**Agent 行为**：
- 不落章、不推进
- 等待用户重新发起

## 实际案例

### 案例 1：理解差异 → 选"需要澄清"
**用户反馈**：
> "FR-3 说的'实时同步'是什么意思？是 WebSocket 还是轮询？"

**Agent 后续**：
```typescript
if (result.user_choice === '需要澄清（有疑问，但不一定要改）') {
  // 先解释
  await tools.ask_user_question({
    questions: [{
      id: 'clarify',
      question: 'FR-3 的实时同步采用 WebSocket 推送，延迟在 100ms 内。需要我在文档中把这个明确写出来吗？'
    }]
  })
  // 根据用户回答决定是否修改文档
}
```

---

### 案例 2：内容错误 → 选"需要修改"
**用户反馈**：
> "FR-3 的验收标准不够具体，必须补充'同步成功率 ≥ 99.9%'"

**Agent 后续**：
```typescript
if (result.user_choice === '需要修改') {
  // 直接改文档
  await modifyRequirementDoc({
    clause: 'FR-3',
    update: '验收标准：同步成功率 ≥ 99.9%，延迟 ≤ 100ms'
  })
  // 重新提交确认
  await tools.reqboard_ask_confirm(...)
}
```

## 设计原则

### 1. 用户心智负担最小化
- ✅ **"需要澄清"** 是低成本选项：用户不用担心"点了就一定要改"
- ✅ **"需要修改"** 是高确定性选项：文档确实有问题才点

### 2. Agent 行为可区分
- ✅ 收到"需要澄清" → 先解释，再决定是否改
- ✅ 收到"需要修改" → 直接改

### 3. 理解差异 vs 内容差异
| 维度 | 需要澄清 | 需要修改 |
|------|---------|---------|
| **问题类型** | 理解层面 | 内容层面 |
| **文档质量** | 可能没问题 | 确实有问题 |
| **下一步** | 解释 → 可能不改 | 直接改 |
| **用户心态** | "我不太懂" | "这个写错了" |

## 技术实现

### 文案单点原则
所有确认弹框选项**统一在 `domain/text/labels.ts` 定义**：
- ✅ Host 判定与 Client 渲染引用同一常量
- ✅ 改文案只改一处，不会漂移
- ✅ 新增选项自动在所有 `reqboard_ask_confirm` 调用中生效

### 向后兼容
- ✅ 旧代码不传 `options` → 自动用新的 4 选项
- ✅ 旧代码显式传 `options` → 按传入的用（不受影响）
- ✅ 用户选任何选项 → `user_choice` 和 `user_feedback` 都会返回
