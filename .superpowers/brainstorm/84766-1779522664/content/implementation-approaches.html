实施方案：3 种方案对比

为 React Dashboard 补充接口的不同实现路径

🎯 目标

为 React Dashboard 补充 3-5 个 API 端点，使其能够展示完整的投资组合数据（总资产、持仓、净值走势等），达到生产可用标准。

方案对比

根据实现复杂度和数据完整性，提供 3 种方案

A

🚀 方案 A：最小化实现（推荐）

策略：只添加 3 个核心 API，使用现有数据表，快速上线

新增接口：
  • GET /api/portfolio/summary - 从 account_balance 表获取最新记录
  • GET /api/portfolio/history - 从 account_balance 表查询历史数据
  • GET /api/portfolio/holdings - 从 portfolio_holdings 表 + 最新价格计算
调整接口：
  • /api/signals - 添加 date 参数支持今日筛选
  • /api/backtest/results - 添加 limit 参数

优点

  • 实现快速（1-2 小时）
  • 利用现有数据表和 Repository
  • 代码改动最小
  • 风险低，易测试

缺点

  • 依赖 account_balance 表有数据
  • 如果表为空，需要先初始化数据
  • 持仓盈亏计算需要实时价格
✅ 推荐理由：

数据表已完备，Repository 已实现，只需添加 API 路由。如果 account_balance 表为空，可以先写入初始数据或实时计算。

B

⚙️ 方案 B：实时计算方案

策略：不依赖 account_balance 表，所有数据实时计算

实现方式：
  • /api/portfolio/summary - 实时查询 portfolio_holdings + 最新价格计算
  • /api/portfolio/history - 从 trades 表回溯计算历史净值
  • /api/portfolio/holdings - 同方案 A
计算逻辑： 
总资产 = Σ(持仓数量 × 最新价格) + 现金余额
今日涨跌 = 今日总资产 - 昨日总资产
盈亏 = 当前市值 - 成本

优点

  • 不依赖 account_balance 表
  • 数据永远是最新的
  • 适合初期没有历史数据的情况

缺点

  • 实时计算性能开销大
  • 历史净值计算复杂（需要回溯交易）
  • 实现时间较长（3-4 小时）
  • 需要处理价格缺失的情况
⚠️ 适用场景：

如果 account_balance 表完全为空且短期内无法填充数据，可以选择此方案作为临时方案。

C

🏗️ 方案 C：完整重构方案

策略：建立完整的数据同步机制，定时更新 account_balance 表

实现内容：
  • 创建定时任务，每日收盘后计算并写入 account_balance
  • 创建 portfolio_snapshots 表存储持仓快照
  • 实现完整的资产计算引擎
  • 添加数据回填脚本，补充历史数据
  • API 端点从预计算的表中读取（性能最优）
架构： 
定时任务 (每日收盘)
  ↓
计算引擎 (持仓 + 价格 + 交易)
  ↓
写入 account_balance 表
  ↓
API 直接读取预计算结果

优点

  • 性能最优（预计算）
  • 数据一致性好
  • 支持完整的历史回溯
  • 架构最完善

缺点

  • 实现时间长（1-2 天）
  • 需要设计定时任务机制
  • 需要数据回填脚本
  • 初期上线慢
💡 长期方案：

这是最理想的架构，但不适合快速上线。建议先用方案 A 快速上线，后续再逐步迁移到方案 C。

✅ 我的推荐：方案 A（最小化实现）

推荐理由：
  • 数据表和 Repository 已完备，只需添加 API 路由
  • 实现快速（1-2 小时），风险低
  • 性能优秀（直接读表）
  • 如果 account_balance 表为空，可以先写入初始数据或用方案 B 临时补充
实施步骤：
  1. 检查 account_balance 表是否有数据
  2. 如果有数据：直接实现 3 个 API 端点
  3. 如果没有数据：先写入初始数据（或用方案 B 实时计算作为临时方案）
  4. 调整 /api/signals 和 /api/backtest/results 接口
  5. 前端集成测试
后续优化：

上线后，可以逐步实施方案 C 的定时任务机制，建立完整的数据同步架构。
