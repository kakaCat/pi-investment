## 做对的三件事

1. **删前先取基线**（非记忆端点 200 与体积、测试总数 6565、分层违规 322）——删完才有「没删坏」的对照物，而不是靠感觉。
2. **三条判据互相独立**：端点 404（行为面）+ 符号 grep 0（代码面）+ 启动日志无 memory 注册（装配面）。
   其中「不留宽容导入分支」是刻意的：让「删干净」这件事**可以被日志证伪**。
3. **提交被拒期间的兜底**：索引有未合并条目时 `git commit` 被 git 拒绝，先做了带 sha256 的补丁+tar 恢复包（后来确认落进提交才作废）。

## 做错 / 被迫绕弯的四件事

1. **先干活后建卡**：t1 的代码在工作开始时就做完了，而台账里没有对应的活卡——后面子卡凭证门（要求改动文件晚于子卡开工）因此卡住，
   只能用「本需求真正产出的持久文档」作为凭证落点。**教训：卡先落地，再动手。**
2. **计划里的依赖图漏了一条**：`t2`（摘注册点）一落地端点就没了，它必须和 `t3` 一样排在迁移之后——首版计划只卡了 `t3`。
   计划评审时应该逐条问「这张卡落地后，对外可观察行为变了没有」。
3. **本仓 ESM 模块 mock 不可靠**：`jest.unstable_mockModule` 动态 import 会拿到缓存模块，失败信息还是空的；改用
   「纯函数单测 + 假 CLI 脚本」两条确定路才把测试写绿。
4. **撞了两个插件缺陷**（业务动作成功、回执被丢）：`reqboard_submit` 的 `doc_sync_pending` 带未声明字段被判无效；
   本窗口弹验收单被 `REQBOARD_PROJECT_ROOT_MISMATCH` 拦住（记录根 = quantsys-v2，写盘根 = dsh-pmboard）。
   **两条都值得另立需求修**。
