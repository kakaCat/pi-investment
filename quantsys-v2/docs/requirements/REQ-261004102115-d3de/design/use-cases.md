# 使用场景（REQ-261004102115-d3de）

## 角色与关注点（serves: FR-1, FR-2, FR-3, FR-4）

- **项目所有者（人类）**：休市期间不该收到"K 线滞后"；告警只在**真断供**时出现。
- **本窗口 / 后续 agent**：只认一个"应有交易日"入口，不再各自写 `weekday()`。
- **探针自身**：必须继续"不依赖被监控进程"——它现在多依赖了一个**日历表**与一个**外部 provider**，
  两者都必须在不可用时安静降级并留痕。
- **告警接收方（值班视角）**：降级态要能一眼看出"这条判定可信度更低"。

## 场景 1：国庆/中秋休市巡检（serves: FR-2）

**现状**：2026-10-04 10:18 报 `K线最新 2026-09-30 / 应有 2026-10-02，滞后 2 天`，每 5 分钟一次。

**期望**：`expected=2026-09-30`、`lag_days=0`、`healthy=true`、退出码 `0`，**不发送任何告警**；
下一个交易日在 10-08 收盘后（`expected=2026-10-08`）若数据仍未到，才应当报警。

## 场景 2：真断供（serves: FR-2, FR-3）

**触发**：交易日收盘后 K 线迟迟不到（本仓已发生三次静默停摆）。

**期望**：行为与现状**一致且更强**——`expected` 是当天的真实交易日，`lag_days` 为正即报警
（`--max-lag-days 1` 的容差保持不变）；探针与 `freshness_guard` 给出**同一个** `expected`，
不再出现"探针说滞后 2 天、契约说已达标"的两套答案。

## 场景 3：日历源不可用（serves: FR-1）

**触发**：`quant.trading_calendar` 为空/不可读，且 provider 断网或返回空。

**期望**：**不报错、不静默**——降级为周一至周五口径，`expected_source='weekday_fallback'`、
`expected_degraded=true`，探针 JSON **与告警正文**都带出这一事实；
探针退出码仍按"被监控对象是否异常"给（`0`/`2`），**不因日历故障给 3**。

## 场景 4：下一个节日（春节 / 中秋）再来一次（serves: FR-4）

**触发**：2027 年春节休市 9 天（连续 7 个工作日）。

**期望**：无需改代码——日历表/provider 天然排除；且用例 1~6 已把"休市工作日不得当交易日"钉死，
若有人把口径改回 `weekday()`，回归锁当场变红。

## 场景 5：表被填上之后的管道行为（serves: FR-1）

**触发**：执行一次 `tools/refresh_trading_calendar.py` 回填。

**期望**：`load_trading_calendar_from_db(exchange)` 从"空表 → 回退 K 线 + error 日志"
变为"直接读表"（这正是该函数注释要求的方向）；回退路径与异常处理保持不变，
日志里 `trading_calendar_empty_fallback_to_klines` 不再出现即视为生效。
