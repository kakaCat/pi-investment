# 使用场景（REQ-261003150739-b98d）

## 角色与关注点（serves: FR-3）

- **本仓开发者 / 后续 agent**：跑测试时不应产生任何对外副作用；漏桩应立刻看到，而不是靠人提醒。
- **CI / 本地全量跑**：必须能证明"零真实外发"，而不是"大概没发"。
- **项目所有者（人）**：收件箱里不该出现假任务卡片——一次都不该。
- **测试作者**：仍要能断言"我这条路径确实调用了通知"（只是不许真的发出去）。

## 场景 1：开发者跑测试（serves: FR-3）

**现状**：跑 `tests/test_false_success_guard.py` → 真实渠道收到 4 张 `fake_job` 卡片；
跑 e2e 手动触发用例 → 再收到 2 张 `watch_rule_health` 卡片，且在测试库里真跑了生产 handler。

**期望**：跑完后收件箱**零新增**；守卫输出 `intercepted=0 egress=0`（这两条用例的桩已在更上游拦住一切）。
若某用例确实调用了通知，守卫按"拦截+记账"处理，测试照常通过，**不改变被测判定**。

## 场景 2：有人再次打错桩（serves: FR-4）

**触发**：下一次模块拆分 / 符号搬家后，有人把桩打到转发壳或来源模块（历史已发生三次）。

**期望**：该用例**当场失败**，失败信息给出"本用例真实外发 N 次 + 目标 URL + 打桩点规则"；
同时真实渠道**依然收不到消息**（拦截在先）。即：漂移的代价是"一条红的用例"，
不再是一封发给用户的假卡片。

## 场景 3：需要断言"通知确实被调用"的用例（serves: FR-3）

**触发**：如 `tests/test_freshness_guard.py`——它打桩 `pipeline._send_feishu` 并断言告警文本。

**期望**：不受影响。守卫在**传输层**而非门面层，这类"在更上游打桩并断言"的用例照旧通过；
只有当调用**真的走到出网那一步**时，守卫才介入。
