# REQ-261006163444-8e4f · 设计：使用场景（Use Cases）

> 每个场景都是"人看得到的事实"：谁在什么条件下看到什么、系统的动作是什么。
> 数据基线：2026-10-06，全市场 5686 只，可交易域 5280 / 观察中 3 / 存量 403。

## 1. 场景 A：域内健康（常态）（serves: FR-2, FR-4）

**条件**：可交易域 5280 只，均值评分 90.84（阈值 88.0），D级 3 只（阈值 20），末日 09-30 齐全。

**系统动作**：不发任何域内阈值告警；只发 1 项「本期掉出可交易域 2 只」warning。

**人看到**：

```
📊 数据质量告警（1 项）
时间: 2026-10-06 13:54:21
口径: 可交易域（最后交易日 2026-09-30）｜统计 5280/5280 只

检查域: 可交易 5280 ｜ 观察中 3 ｜ 存量 403
本期掉出可交易域: 2 只
  002813 路畅科技, 603183 建研院
域内指标: 评分 90.84（阈值 88.0）｜覆盖率 98.54%（信息项）｜D级 3 只（阈值 20）
```

**判据**：正文与 `result['domain']` 一致；`alert_count == 1`。
**对比现状**：今日真实发出的是 3 项（D级 806 / 评分 86.28 / 失败率 71.4%）——全部消失。

## 2. 场景 B：域内真的退化（serves: FR-2, FR-4）

**条件**：某日域内 D级 = 26 只（> 20），或域内均值 = 87.2（< 88.0）。

**系统动作**：发对应 warning 项；正文照旧打印三层计数与掉出名单，便于定位。
**人看到**：`问题清单` 里出现「⚠️ D级股票数量过多: 26只 (阈值: 20)」或「⚠️ 数据质量评分偏低: 87.20 (阈值: 88.0)」。
**判据**：阈值边界用例 T9/T10 双向（20/21、88.0/87.9）。
**要点**：新口径下这两条**只在真退化时**出现——这才是告警的价值。

## 3. 场景 C：采集漏批 / 管道断流（新口径的核心保护）（serves: FR-3）

**条件**：某日 `kline_update` 漏采了一批（例如 120 只标的没有当日 K 线），而它们并非停牌。

**系统动作**：这 120 只 `gap == 1` ⇒ 进 `dropped_new` ⇒ 正文「本期掉出可交易域: 120 只」+ 前 20 只名单（warning）。

**人看到**：一个数量级明显异常的掉出数（平日 2 只 → 今日 120 只），点开名单即可判断是漏采还是集体停牌。

**判据**：用例 T11；基线对照 E12（正常日 2 只）。
**设计要点**：这就是"为什么不能把无数据标的静默移出分母"——移出是对的，但**必须同时留下掉出的痕迹**（D-4）。
**盲区**：若整个管道停摆导致 `D_last` 本身滞后，本哨兵测不到（architecture.md §8），
但正文打印 `最后交易日`，人一眼可辨。

## 4. 场景 D：标的退市 / 长停（存量）（serves: FR-1, FR-3）

**条件**：某标的连续 5 个交易日无 K 线（真退市或长停）。

**系统动作**：
- 第 1–4 个交易日：在观察中，逐日进「本期掉出」名单（warning）；
- 第 5 个交易日起：转存量，正文只报数（`存量 403 只`），**不再点名**。

**人看到**：一只票退市时最多吵 4 天，之后安静；它不占 D 级配额、不参与均值、不被回填。
**判据**：用例 T2（gap 4/5 边界）、T4（无上期）。
**设计要点**：不需要"已通知过"状态——`gap` 单调递增，天然只亮相 4 天（architecture.md §2.1）。

## 5. 场景 E：自动回填（serves: FR-4）

**条件**：检查发现域内有 30 只标的缺日数据，本次额度 50 只、剩余预算充足。

**系统动作**：候选集 = `per_symbol` 里"有缺失天"且**在可交易域内**的标的，按缺失天数降序取前 30；
逐只回填；失败率仅在 `分母 >= 10` 时判定。

**人看到**：`回填: 目标 30 只（域内）｜失败 9 只 → 失败率 30.0%`（不告警）；
若某日失败率 60%（n=30），则是**真的数据源故障** → error 告警。

**判据**：用例 T12（样本门槛）、T13（域内选取）。
**对比现状**：今日 7 只目标里 5 只已退市（E10），失败率 71.4% 与"数据源健康度"无关——
修后这类目标根本不进候选集（`All data providers failed` 应归零）。

## 6. 场景 F：同一天跑多次（serves: FR-2）

**条件**：00:00 cron 跑一次（自动），13:48 因排障又手动跑一次（今日真实情形，E2）。

**系统动作**：两次各自基于**本次 run 的 `per_symbol`** 统计；`count_by_grade_on` 按 distinct 标的计。
**人看到**：两次告警正文的 D级 都是 **3 只**（域内），不再变成 806。
**判据**：用例 T15 / 反例锁 L1；SQL 交叉核对 3.2（`rows=806` 但 `syms=404`，代码必须返回 404 量级而非 806）。

## 7. 场景 G：分域不可用（响亮失败，不静默跳步）（serves: FR-1, FR-3）

**条件**：`daily_klines` 查不到交易日（空表/库异常），或上游返回的 `quality_result` 里没有 `per_symbol`（旧替身）。

**系统动作**：`alert_scope="degraded"`；发 **error** 项「⚠️ 分域不可用，本次未做域内判定（reason=…）」；
**不回退**到 `count_by_grade_on`，也不静默跳过阈值判定。
**人看到**：一条明确的 error，而不是"今天一切正常"。
**判据**：用例 T5、T17。
**设计要点**：这正是本仓反复踩的"失败伪装成正常"的形态（与 REQ-261006133733-1fdf 同族），
新代码不得再制造一次。

## 8. 场景 H：回滚（serves: FR-2, FR-4）

**条件**：上线后发现新口径不符合预期，需要回到旧行为。

**系统动作**：还原提交 + 把 `quant.scheduler_tasks` id=232 的 `quality_threshold` 改回 `95.0`。
**人看到**：告警回到"死标的入域 + 同日多跑翻倍"的旧红（3 项）。
**判据**：回滚说明里写明旧值（95.0）与两条部分回滚路径（architecture.md §5）。
**备注**：无表结构变更 ⇒ 无数据回滚动作；`kline_data_quality` 新写入的 `original_count` 非 0，
回滚后仍保留（旧代码不会再写，但也不会读错）。

## 9. 场景 I：阈值重标定（上线后必做）（serves: FR-4）

**条件**：新口径累计运行 ≥10 个交易日。

**系统动作**：取域内 `mean_score` / `d_grade` 的实测分布，重新标定阈值并回写需求文档 FR-4 ③。
**人看到**：阈值从"锚定单日"变为"锚定 10 日分布"，误报/漏报同时下降。
**判据**：FR-4 ③ 的重标定条款；今日基线（90.84 / 3 只 / 98.54%）是标定起点。
**为什么必须做**：本仓只有 2 次全市场运行（E13），当前阈值是**临时锚定值**，不得当成长期真理。

## 10. 裁定对照（每个场景服务哪条裁定）（serves: FR-1, FR-2, FR-3, FR-4）

| 裁定 | 内容 | 落到哪些场景 / 设计节 |

## 11. 非目标：本需求明确不覆盖的场景（serves: FR-5, FR-6）

1. 修 239 只标的的 `is_delisted`/`is_suspended` 标记（场景 C 靠哨兵替代，不靠标记）。
2. 评分模型与 Z-score 敏感度复盘（域内 P5/P10 = 80.00 的现象属后续线 3）。
3. 整个数据管道停摆的检测（场景 C 盲区，责任方 `freshness_guard`）。
4. 历史 `kline_data_quality` 行 `original_count=0` 的追改。
5. 服务层 `stocks_with_issues[:50]` 截断本身（只解耦统计与它，不扩大到"报告要全量"）。
