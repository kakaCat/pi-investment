# 审计取证架构（REQ-261006010812-cd19）

> 一句话：把「a7cd 的设计文档说了什么」与「这台机器上真在跑什么」**逐条对撞**，
> 每条结论都钉到一个取证面 + 一条证据上；审计自身**不产生任何写入**。

```
   取证面（只读）                     判定                         产物
 +---------------------+        +------------------+      +----------------------+
 | A 设计文档面        |        | 已实现且一致     |      | audit-report.md      |
 |   a7cd/design/*.md  |        | 已实现但语义偏离 |      |  §结论摘要           |
 +---------------------+        | 未实现           |      |  §一致性矩阵         |
 | B 代码面（文件:行） |  --->  | 无法判定(+缺什么) | ---> |  §验收命令复跑       |
 | C 库表面（只读SQL） |        +------------------+      |  §缺口清单           |
 | D 运行面（日志/工具）|                                  |  §改进项             |
 | E 版本面（git 状态）|                                  +----------------------+
 +---------------------+
```

## 0. 目标与判据（serves: FR-1, FR-2, FR-5）

- **serves: FR-1, FR-2, FR-5**
- 目标：产出「设计条目 → 判定 → 证据」的可复核矩阵，并回答「照这份设计继续干有没有坑」。
- 判据（可证伪）：
  1. 矩阵中**每一行**都有 `design.md:行` 与非空证据列；抽查 5 行，证据可复现（见 `test-cases.md` §3）；
  2. 判定只用四档枚举（`interfaces.md` §2），**不得**出现「基本一致」「大致符合」这类连续语气；
  3. 报告五节齐全（`interfaces.md` §1）。

## 1. 取证面分层（serves: FR-1, FR-2, FR-3, FR-4）

- **serves: FR-1, FR-2, FR-3, FR-4**
- 审计只用五个取证面，**每个面各自有强度上限**（强度分级见 `interfaces.md` §3）：

| 面 | 取什么 | 拿它证什么 | 上限 |
|---|---|---|---|
| **A 设计文档面** | `docs/requirements/REQ-261004154902-a7cd/design/*.md`（6 份）与 `requirement.md` | 设计**声明了什么**（这是被审的"应然"） | 只能证"设计说了"，不能证"做到了" |
| **B 代码面** | 被审模块文件的 `路径:行号` 与内容 | 设计条目是否有落点、语义是否一致 | 静态定位，不证运行行为 |
| **C 库表面** | 生产库 `quant.*` 只读 SQL（清单见 `data-model.md` §1） | 数据行改动是否落地、历史事实 | 时间点快照，须记时间戳 |
| **D 运行面** | pytest（写 `quant_test`）、`tools/check_*.py`、日志文件 | 判据是否真能跑、退出码是多少 | 生产进程动作被 D-3 边界禁止 |
| **E 版本面** | `git status` / `git log` / `git check-ignore` / `git ls-files` | 产物是否在版本控制内、回滚路径是否成立 | 只反映本机工作区 |

- **面 A 与面 B~E 的关系是"对撞"**：面 A 出条目，面 B~E 出证据，判定在矩阵里落。
- **不允许单靠面 A 下"已实现"判定**——那是最常见的自证循环。

## 2. 判定链路（serves: FR-2）

- **serves: FR-2**
- 逐条链：`面 A 取条目（design.md:行）` → `在面 B 找落点（grep 符号/接口名）` →
  `有落点则读实现核对语义` → `需要数据事实则查面 C` → `需要行为事实则跑面 D` →
  `产物是否在版本内查面 E` → 落四档判定。
- **"语义偏离"的判据要写清**：设计的字段名/取值/默认值/错误语义/开关名，任一与实现不同即为偏离，
  并在证据列写出两侧取值（如「设计 `reason=pending_expired→failed`，实现 `→success`」）。
- **"未实现"必须给反向证据**：不能只写"没找到"，要写搜索口径（如 `grep -rn "should_have_run" --include='*.py'`）
  与命中数，否则与"我没搜对"无法区分。
- **"无法判定"必须点名缺口**：写清缺哪个面的什么证据、为什么本次拿不到（例：需 `kill -9` 生产进程，被 D-3 禁止）。

## 3. 只读边界与依赖方向（serves: FR-2, FR-3, FR-4）

- **serves: FR-2, FR-3, FR-4**
- 允许：读文件/日志/git 状态；生产库 `SELECT`；跑 pytest（落到 `quant_test`，根 `conftest.py` 有库名守卫）与只读检查器。
- 禁止（D-3 裁定）：`kill` 任意生产进程、触发真实飞书/Agent OS 外发、写任何库表（含生产与测试库的**生产事实**）、
  改动被审代码与文档、重跑 a7cd 的修复动作。
- 依赖方向：审计**单向依赖**被审对象；被审对象不得反向感知审计（不改它、不 import 它之外的新代码）。
- 收工自检：审计前后 `git status --porcelain` 对被审代码文件的输出**必须一致**（`test-cases.md` §4）。

## 4. 产物落点与不做什么（serves: FR-5）

- **serves: FR-5**
- 唯一产物：`docs/requirements/REQ-261006010812-cd19/audit-report.md`（结构契约见 `interfaces.md` §1）。
- **不做**：不修 a7cd 的任何缺陷（发现即进"改进项"，不顺手改）；不改 a7cd 的文档；
  不下"V13 该不该继续跑"的运营结论（那是项目所有者的决定，报告只给证据与风险等级）。

## 5. 仓库边界口径（serves: FR-1, FR-3）

- **serves: FR-1, FR-3**
- 本工作区的 git 根是 `/Users/mac/Documents/ai/pi-investment`（`quantsys-v2/` 是其子目录）。
  所有 git 类命令与 `路径:行号` 引用按此口径书写，否则 `git log -- <path>` 会静默取不到历史。
