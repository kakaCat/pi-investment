# 使用场景（REQ-261006010812-cd19）

> 报告写给"要拿它做决定的人"。下面五个场景就是它必须能顶住的问法。

## 角色与关注点（serves: FR-5）

- **serves: FR-5**
- **项目所有者**：V13 这条链现在能不能信；要不要照 a7cd 的设计继续推进；哪些地方得先补。
- **后续接手者**：按设计文档能不能复现、能不能回滚。
- **值班/运维**：`success` 是不是真成功；「该跑没跑」有没有人管。
- **agent（投资脑）**：还有哪些链路没人守（需不需要人工补位）。

## 场景 1：接手者要按设计回滚（serves: FR-2）

- **serves: FR-2**
- 问法：「`design.md` §11 说回滚是 `git revert` 对应提交 —— 提交在哪？」
- 报告必须给的：把「回滚路径」当**设计条目**进一致性矩阵，证据落面 E
  （`git log -- <path>` / `git status --porcelain`）与面 B（回滚表里点名的数据行原值）。
- 期望结论形态：若实现未提交 → 判 `未实现`（回滚路径不成立），
  进改进项并给判据「被审代码文件在 `git log` 中有提交，或设计改为以"工作区补丁"为回滚载体」。

## 场景 2：怀疑某条设计没落地（serves: FR-2, FR-3）

- **serves: FR-2, FR-3**
- 问法：「`RunOutcome` 那套『失败即 failed』到底接了没有？」
- 报告必须给的：符号搜索口径 + 命中位置 + 实现语义核对 + （若有测试）实跑退出码。
- 期望结论形态：四档之一 + 证据多行；**不得**只凭设计文档里有这段代码片段就当已实现。

## 场景 3：归档需求的覆盖度自相矛盾（serves: FR-1, FR-2）

- **serves: FR-1, FR-2**
- 问法：「a7cd 已归档，可它的条款接收状态表还把 FR-1..FR-10 全标『未被接收』——到底有没有任务承接？」
- 报告必须给的：三个面的证据并列 —— `requirement.md` 的标记块、`rtm-decomposing.yml` 的
  `inputs.requirements`、`decomposition.md` 与 `tasks/` 的实际条数，然后给判定与影响。
- 期望结论形态：判 `已实现但语义偏离` 或 `未实现`（取决于标记是否陈旧），
  影响面写"归档需求的可信度统计是否可被引用"，并进缺口清单。

## 场景 4：验收命令跑不了（serves: FR-3, FR-4）

- **serves: FR-3, FR-4**
- 问法：「设计里写的那条判据命令，为什么跑不了？」
- 报告必须给的：`不可跑` + 原因（文件不存在 / 被 `.gitignore` 排除 / 需生产进程动作）
  + 替代判据（纯函数复刻，标 `L4`）+ 缺口一行。
- 期望结论形态：读者能据此决定"补工具"还是"改设计口径"；不允许静默跳过该条。

## 场景 5：第三方要复核这份报告（serves: FR-5, FR-6）

- **serves: FR-5, FR-6**
- 问法：「你说『未实现』，我怎么知道不是你搜错了？」
- 报告必须给的：矩阵证据列自带搜索命令与命中数；`## 逐条取证附录` 的 5 行抽查结论。
- 期望结论形态：第三方按 `test-cases.md` §3 原样复跑，得到同方向结论。
