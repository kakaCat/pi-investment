# 使用场景（REQ-261004154902-a7cd）

> 总览见同目录 [`design.md`](design.md)。

## 角色与关注点（serves: FR-1, FR-2, FR-3, FR-7, FR-8, FR-9, FR-10）

- **项目所有者（人类）**：要知道"它今天干了什么、成了没有"；不要在休市日收到假成交，
  也不要在系统停摆时一无所知。
- **agent（投资脑）**：需要可判读的状态，而不是只能自己翻库发现"11 天没动作"。
- **看板 / 调度**：`success` 必须真的等于"干成了"。
- **值班视角**：告警要么是真事，要么别发——不接受每天几百条节假日误报。

## 场景 1：国庆休市巡检（2026-10-05 ~ 10-07）（serves: FR-3）

**现状**：`TradingDayGuard` 的"近 7 日有 K 线"启发式把三天都判成交易日 →
① V13 日检在休市日尝试调仓；② orchestrator 9:31 会撮合挂单；
（价格只能取到 9/30 的陈旧价）→ 产生**休市日的假成交**，还记 `success`。

**期望**：三天均判 `False`（`quant.trading_calendar` 无行），
**不调仓、不撮合、不写快照**；日结仍发一条"今天是休市，未执行"的低优先级信号。

## 场景 2：复市首日（2026-10-08）（serves: FR-3）

**现状**：`(10-08 - 09-30).days = 8 > 7` → 判 **False** → 复市第一天被跳过
（当日 K 线要 17:40 才落库，而日检 06:30 就要判断）。

**期望**：判 `True`，正常执行日检与撮合；数据未落库这件事由"日历"承担，不再由 K 线代答。

## 场景 3：调仓失败（serves: FR-1, FR-2, FR-9）

**现状**：`rebalance()` 第 10 步调用一个**缩进在 `if __name__ == '__main__':` 块内**的方法
（`_send_rebalance_notification`）→ 必抛 `AttributeError` → 被 `except` 吞 →
`run_daily_check` 丢弃返回值 → `strategy_service` 记 `success` → **钱已动、通知没发、任务全绿**。

**期望**：①方法回到类体，通知正常发出；②即便通知失败，调仓本身仍记成功但
`detail['notify_error']` 可见；③若交易/存库阶段失败 → `ok=False` +
`scheduler_runs.status='failed'` + 飞书告警。

## 场景 4：挂单搁浅（serves: FR-7）

**现状**：`agent_virtual` 两笔挂单自 `2026-08-24` 起 `updated_at == created_at`
（41 天无人碰）；10-02 09:31 的撮合崩在取数（库缺 `decision_price` 列）→ 只留 ERROR；
另有两笔在 8/21 16:41 被"非交易时段"批量拒绝后永久丢弃。

**期望**：
- 撮合**在交易时段内**运行；非交易时段调用 → 跳过（不改状态、留痕），**不误杀**；
- 单笔异常不中断整批，异常单标 `failed` + `fail_reason`；
- 超过 1 个交易日仍未成交 → `expired` + `fail_reason` + **主动外发**（不再无限搁浅）。
- **存量两笔按同一规则处置**（默认 `expired`；若人选"人工确认后补成交"，则人工执行一次补单）。

## 场景 5：服务重启导致漏跑（serves: FR-4, FR-8）

**现状**：2026-10-02 09:00 起进程，当天 06:30 的 v13 排班**直接丢失**
（`misfire_grace_time_seconds` NULL 被加载器 `or 300` 抹成 300 秒），无人知。

**期望**：①加载器区分 NULL（必补跑）与显式值；②探活新增"关键任务该跑没跑"判据，
按（任务 + 应跑时刻）**去重告警一次**——既不静默，也不重演 3 天 504 条刷屏。

## 场景 6：通知只报喜不报忧（serves: FR-9）

**现状**：`AgentChannel.supports()` 恒真 → 渠道收窄为 `['agent']` → 8080 死 →
`rebalance` / `risk_alert` / `trade_signal` / `verification` 等 7 类 **100% 丢弃**；
日志实证 48 次通知**全是 `system_alert`**。同时用户实际收到约 540 条探针节假日误报。

**期望**：渠道选择"兜底追加"后，全部类型都含 `feishu`；`rebalance` / `risk_alert`
有 formatter 且能送达；"无 formatter""facade 未装配"不再走 `debug` 静默。

## 场景 7：账本对账（serves: FR-10）

**现状**：4 只标的 `ΣSELL > ΣBUY`（300045 买 1000 / 卖 2000 等），虚增现金 ≈ ¥49,425，
账户显示 **+32.99%** 含虚增；`simulation_positions` 与 `simulation_trades` 双源并存是成因。

**期望**：①新增卖出前置校验，超卖当场拦下；②对账器输出"逐标的净额 + 现金重放差额 + 超卖清单"，
超卖清单必须 0 行；③**历史虚增的处置**（回填冲正 / 标记为脏并从统计排除 / 保留不动）
由项目所有者裁定后单独执行——本设计不代替人做账务决定。
