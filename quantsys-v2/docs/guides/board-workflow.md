# 公告板工作流协议

## 概述

本文档定义公告板（Board）的工作流程、状态转换规则、"我来解决"按钮语义及 Agent 行为规范。

---

## 状态机

```
open (悬赏池)
  ↓ claim
claimed (认领)
  ↓ complete / blocked / drop
done / blocked / dropped
  ↓ (blocked 可 claim 恢复)
claimed → done
```

**状态定义**：
- **open**：悬赏池，等待认领
- **claimed**：已认领，执行中
- **blocked**：卡住，需要外部条件（服务重启、特定时间窗口、第三方响应）
- **done**：已完成
- **dropped**：放弃（不做或转派）

---

## "我来解决"按钮语义

### 用户行为
点击"我来解决" = **委托 Agent 立即执行该任务**

### Agent 预期行为（强制，不可偏离）

1. **立即认领**（`board_update(action='claim')`）
2. **立即执行**（不问用户"要继续吗"，不评估"是否适合"）
3. **尽最大努力完成**
4. **结果分类**：
   - ✅ **done**：代码/文档/调查/修复 100% 完成（代码层）
   - ⏰ **blocked**：执行过程中发现需要外部条件，已完成可达部分
   - ❌ **drop**：发现任务描述错误、重复、或完全不可达（罕见，需充分理由）

### 关键特征

#### 1. 无二次确认
- ❌ **禁止**："我先评估一下工作量" → 用户点了就是要你做
- ❌ **禁止**："这个任务需要 X 小时，要继续吗？" → 直接做
- ❌ **禁止**："当前深夜 03:30 不适合执行" → 照做（除非任务明确依赖交易时段）
- ✅ **正确**：claim → 立即开始实施

#### 2. 深夜照做
- 用户深夜点"我来解决" = 用户授权深夜执行
- 不因"已工作 5h"或"深夜 03:30"而拒绝
- 执行后若发现工具不可达/数据不完整，complete 说明部分完成

#### 3. 代码完成 = 已解决
- **代码层修复完成** = done（即使运行时验证需要重启）
- **运行时问题**（模块缓存、服务未重启）→ blocked 说明需要重启，但代码已交付
- **部分完成**（3 项动作完成 1 项）→ complete 说明完成度与待后续

#### 4. Blocked 的合理边界

**✅ 可以 blocked 的情况**：
- 需要服务重启验证（qv2/Agent OS 重启后加载新代码）
- 依赖第三方 API 修复（akshare 数据源维护）
- 需要特定时间窗口（交易日盘中验证、等待下个交易日触发）
- 依赖后端基建（需要新增 API 端点、数据库 schema 变更）

**❌ 不可以 blocked 的情况**：
- "我没时间" → 不应该点"我来解决"
- "我不会" → 应该 drop 转派，不是 blocked
- "需要 X 小时" → 时间不是 blocked 理由
- "深夜不适合" → 用户点了就是授权深夜执行

## 实施规范

### Rule 1：点击即执行，无二次确认
```typescript
// ❌ 错误示例
用户: 点击"我来解决"
Agent: "这个任务需要修改 3 个文件，预计 2h，要继续吗？"

// ✅ 正确示例
用户: 点击"我来解决"
Agent: (claim board) → 立即开始实施 → (完成后 complete)
```

### Rule 2：代码完成 = 交付完成
```typescript
// ✅ 正确判定
- 代码修改完成 + commit → done
- 文档编写完成 + commit → done
- 调查完成 + 结论记录 → done
- 修复完成 + 运行时验证需要重启 → blocked（代码已交付，等待重启验证）

// ❌ 错误判定
- 代码修改完成但模块缓存未清理 → blocked（应该是 done，缓存是运行时问题）
- 修复完成但"需要下个交易日验证" → blocked（正确，时间窗口依赖）
```

### Rule 3：Blocked 必须附详细 note
```typescript
// ✅ 正确 blocked note
board_update({
  action: 'blocked',
  note: `卡因：需要 quantsys-v2 重启加载新 conditions.py（当前进程 PID 88323 运行旧代码）
        代码层已完成：
        - ✅ conditions.py 新增 combined 类型
        - ✅ validate_condition 递归校验
        验证计划：9/8 白天重启 qv2，执行 6 个集成测试，预计 15min`
});

// ❌ 错误 blocked note
board_update({
  action: 'blocked',
  note: "需要更多时间" // 不充分，时间不是 blocked 理由
});
```

### Rule 4：部分完成也是完成
```typescript
// ✅ 正确处理（任务 3 项动作，完成 1 项，2 项需后端支持）
board_update({
  action: 'complete',
  note: `部分完成（1/3）：
        ✅ 动作 1：experience_write 强制 outcome 标注（代码已修改）
        ⚠️ 动作 2：历史 82 条补标需后端 PATCH 接口（agent 工具层不可达）
        ⚠️ 动作 3：信号 5D 回填需排查 signal-perf-verify 任务
        验收：新写入经验 outcome 100%，历史补标待后端支持`
});

// ❌ 错误处理（因为"只完成了 1/3"而 blocked）
board_update({
  action: 'blocked',
  note: "只完成了 1/3，其余需要后端支持" // 应该 complete 说明完成度
});
```

## 状态转换矩阵

| 当前状态 | 允许的操作 | 语义 |
|----------|-----------|------|
| open | claim | 认领任务 |
| claimed | complete | 完成（100% 或部分完成） |
| claimed | blocked | 卡住，需要外部条件 |
| claimed | drop | 放弃（任务错误/重复/不可达） |
| blocked | claim | 恢复执行（外部条件满足） |
| blocked | complete | 直接完成（不再需要外部条件） |
| blocked | drop | 放弃 |

## 典型场景示例

### 场景 1：代码修复 + 运行时验证待重启

**任务**：修复 watch 复合条件支持  
**执行**：
1. 修改 conditions.py + parseCondition → commit
2. 服务已重启，但模块缓存未清理 → 集成测试失败

**判定**：
- ❌ 错误：blocked（"代码完成但测试未通过"）
- ✅ 正确：done（"代码 100% 完成，运行时缓存问题待环境修复"）

**理由**：代码层交付完整，模块缓存是环境配置问题，不影响交付完整性。

---

### 场景 2：3 项动作，1 项可达

**任务**：L4-A 数据清理（经验补标 + 信号回填）  
**执行**：
1. ✅ experience_write 强制 outcome（代码已修改）
2. ⚠️ 历史补标需后端 PATCH 接口（agent 工具不可达）
3. ⚠️ 信号回填需排查定时任务（agent 工具不可达）

**判定**：
- ❌ 错误：blocked（"只完成了 1/3"）
- ✅ 正确：complete（"部分完成 1/3，2/3 待后端支持"）

**理由**：已完成可达部分（动作 1），其余动作需要后端基建，属于任务边界外，不是 blocked。

---

### 场景 3：深夜执行盘后任务

**任务**：盘后数据清理（明确标注"盘后 15:30 可执行"）  
**时间**：深夜 03:30  
**用户行为**：点击"我来解决"

**执行**：
- ❌ 错误：blocked（"任务标注盘后执行，当前深夜不适合"）
- ✅ 正确：立即执行 → 发现部分动作需盘后数据 → complete 说明完成度

**理由**：用户深夜点"我来解决" = 授权深夜执行，不应拒绝。执行后若发现依赖盘后数据，complete 说明实际完成情况。

---

## 与用户的契约

**用户点"我来解决"的预期**：
1. Agent 立即开始执行（不问"要继续吗"）
2. Agent 尽最大努力完成（不因时间/工作量/难度而拒绝）
3. Agent 完成可达部分后交付结果（done 或 blocked + 详细说明）

**Agent 的承诺**：
1. 点击即执行，无二次确认
2. 代码层完成 = 交付完成（done）
3. 运行时问题 = blocked（代码已交付，等待环境修复）
4. 部分完成 = complete（说明完成度与待后续）
