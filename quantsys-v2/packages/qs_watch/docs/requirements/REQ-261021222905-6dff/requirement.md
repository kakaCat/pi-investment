# 需求说明（REQ-261021222905-6dff）

**需求ID**: REQ-261021222905-6dff
**类型**: feature（新子系统，含新包与新数据表）
**作用域**: `quantsys-v2/` 新增 `packages/qs_plan/`；接线 `qs_watch`（编译目标）、
`qs_trading`（成交回执）、`qs_ops`（反思定时器）、`qs_agenthub/evolution`（知识沉淀）、
`agent-ts`（盘前加载与反思会话）
**档位**: expert（新包 + 状态机 + 编译器 + 跨包归因 + 定时反思，五条线并进）

## TL;DR <!-- serves: FR-1 -->

系统没有「交易计划」这个实体：建仓写在 core_plan.json、盘中盯盘写在 watch_rules、
agent 盘前没有「今日计划」可读、改过的规则没人记得为什么改。
本需求把交易计划做成一等公民：计划编译成盯盘规则去执行，agent 终判下单，
盘后定时器驱动 agent 用「修改历史 + 错过机会 + 盈亏」做反思，反思再回头改计划。

## 业务流程图 <!-- serves: FR-1 -->

```
                       ┌────── 执行段（白天，盘中）──────┐
                       │                                │
人/agent ──建计划──▶ qs_plan ──编译──▶ watch_rules（带 plan_id）
                          ▲                │
                          │                ▼
                          │        WatchEngine 触发 → 指令卡 → 待办
                          │                │
                          │                ▼
                          │        agent 终判下单 → 成交回执（带 plan_id）
                          │                │      收敛待办 + 推进计划状态
                          │                ▼
                          │        盘后/周六定时器
                          │        组装四类材料包（计划修改/错过机会/盈利/亏损）
                          │                │
                          │                ▼
                          │        agent 反思（五问作答）→ 反思报告
                          │                │                │
            ┌─────────────┘                │                ▼
            │ 计划更新通道 ◀──── 修改提案 ────┘         进化层沉淀知识
            │ 预览→确认→生效                            （不碰在跑的计划）
            │ 重新编译规则
            │
            └──────── 回到 qs_plan：反思修改交易计划，次日按新计划继续执行
```

闭环读法：计划 → 编译执行 → 成交留痕 → 定时器组材料包 → **agent 反思** →
修改提案 → 更新通道确认生效 → **交易计划被修改** → 重新编译 → 次日继续执行。

## 产品定义 <!-- serves: FR-1 -->

交易计划系统：把一个账户「买什么、什么条件进、什么条件出、盯什么消息、多久看一次」
打包成一个有生命周期、可编译执行、可归因、可反思的实体。
核心价值：从「规则散落各处、改了不知道为什么」到「一个计划看清全部意图，
每次修改有理由、有对照、有复盘」。与现状的区别：core_plan.json 只答「买什么」，
watch_rules 只是执行载体，二者之间没有归属关系——本需求补上中间那层。

### 功能点 FR-1：交易计划实体与生命周期

**FR-1: 交易计划实体与生命周期**
**判据**：POST /api/plans 建计划 → GET 返回 status=draft、version=1；非法迁移 4xx 且 plan_events 零新增；pytest tests/plan/ 状态机用例全绿。

**功能描述**：agent/人建计划后，计划按状态机流转，每次变迁留痕可查。

**详细说明**：
- **使用场景**：agent 盘前规划今日要做的事，或人指定「这个标的按这个思路盯」。
- **操作流程**：
  1. 调创建接口提交计划 spec（标的、入场条件集、退出策略、监控、节奏）→ 计划为 draft；
  2. 激活 → 状态变 active，触发编译（FR-2）；
  3. 成交回执推动 active→holding→closing→closed（FR-4）；人/agent 可 pause/resume；
  4. 关闭后归档 archived，全程 `plan_events` 留痕（谁、何时、为什么、从哪到哪）。
- **预期结果**：
  - 每个计划有唯一 id、当前状态、版本号，任意时刻可查「它现在处于哪一步」；
  - spec 版本化：每次结构性修改 version++，历史版本可回读（复盘能回答「这笔成交发生在哪个版本上」）。
- **边界条件**：
  - 状态机非法迁移（如 draft 直接 closed）→ 拒绝并返回可读原因，不静默改写；
  - spec 缺必填段（无退出策略）→ 创建即 400，不收半成品。

**验收标准**：
1. `POST /api/plans` 建计划 → `GET /api/plans/{id}` 返回 `status=draft`、`version=1`；
2. 非法迁移（如对 draft 调 close）→ 返回 4xx 且状态不变（`plan_events` 零新增）；
3. `pytest tests/plan/` 下生命周期状态机用例全绿（覆盖全部合法边与至少 3 条非法边）。

### 功能点 FR-2：计划编译器

**FR-2: 计划编译器**
**判据**：激活后 watch_rules 出现 plan_id 正确的托管规则；重复激活规则数不变；修改 apply 后 watch_rule_changes 有审计行；pytest tests/plan/ 编译器用例全绿。

**功能描述**：激活计划时把 spec 幂等编译成带 plan_id 的盯盘规则，修改走「预览→确认→生效」。

**详细说明**：
- **使用场景**：计划激活、反思后修改计划、关闭计划时，规则层需要跟着变。
- **操作流程**：
  1. 激活或 apply 修改 → 编译器算 diff（新建/更新/退役哪些规则）；
  2. 修改场景先返回编译预览（不落库）→ 确认后才真正写入；
  3. 编译产物规则带 `plan_id + role`（entry/stop_loss/take_profit/reduce/news），
     同一 `(plan_id, role, symbol)` 重复编译幂等命中，不产生重复规则；
  4. 每次编译写 `watch_rule_changes` 审计（`change_kind='plan_compile'`）。
- **预期结果**：
  - `watch_rules` 里能看到「这条规则属于哪个计划、什么角色」；
  - 编译时按持仓真值直接写规则的 `position_state`（不再靠日频兜底）。
- **边界条件**：
  - 被计划托管的规则不允许绕过编译器直接改（人工 force 通道记 drift 事件）；
  - 编译中途失败 → 整批回滚，不留半编译状态。

**验收标准**：
1. 激活含 1 标的、止损 8%、两批减仓的计划 → `watch_rules` 新增对应规则且 `plan_id` 正确；
2. 同一计划重复激活 → 规则数不变（幂等）；
3. 修改计划阈值后 apply → 规则阈值更新且 `watch_rule_changes` 有带 plan_id 的审计行；
4. 运行 `pytest tests/plan/` 编译器用例全绿（含失败回滚与托管规则直改被拒两条）。

### 功能点 FR-3：今日计划聚合视图

**FR-3: 今日计划聚合视图**
**判据**：GET /api/plans/today 返回激活计划与环境闸 verdict；无计划账户返回 200+空列表；接口冒烟 P95<500ms。

**功能描述**：agent（agent-dh/agent-ts）盘前经 trading_plan 工具调聚合接口，一屏拿到激活计划、条件就绪度、环境闸结论、持仓差额。

**详细说明**：
- **使用场景**：agent（投资脑 agent-dh / fin-agent agent-ts）每日启动/盘前例行，第一步经 trading_plan 工具加载「今天要干什么」。
- **操作流程**：
  1. 经 trading_plan 工具（内部调 `GET /api/plans/today?account=xxx`，账户取自 agents.json，不写死）；
  2. 返回该账户全部 active/holding 计划：每个标的的入场条件与当前距离、
     环境闸当前结论、与持仓的差额、未决待办数；
  3. agent 把它作为当日决策上下文。
- **预期结果**：agent 盘前例行不再零计划可用（现状：agent-ts 对 core_plan 零引用）。
- **边界条件**：
  - 无激活计划 → 返回空列表 + 明确字段 `empty=true`，不返回 5xx 也不编造计划；
  - 环境闸数据缺失 → 对应维度标 `skipped`，不用 0 冒充事实。

**验收标准**：
1. 有 1 个 active 计划时调用 → 返回包含该计划的 targets 与环境闸 verdict 字段；
 2. 无计划账户调用 → 返回 200 + 空列表；
3. 接口冒烟测试全绿（`pytest tests/plan/` 聚合视图用例）。

### 功能点 FR-4：成交归因与状态推进

**FR-4: 成交归因与状态推进**
**判据**：模拟带 plan_id 卖出成交 → 待办 handled+计划状态推进+position_state 翻转；回执重放幂等；pytest tests/plan/ + tests/application/test_fill_sync_service.py 全绿。

**功能描述**：成交回执带 plan_id 回写，自动收敛待办、翻转持仓状态、推进计划状态。

**详细说明**：
- **使用场景**：agent 终判下单成交后，计划层需要知道「这笔计划执行了」。
- **操作流程**：
  1. agent 下单（走既有 `execute_trade`，不新增下单路径）；
  2. `execute_trade` 成交后发出带 plan_id 的成交事件（FillEvent）；
  3. FillSync 收敛对应待办、翻转规则 `position_state`、推进计划状态、记录执行时延。
- **预期结果**：
  - 修复现状断点：agent 走 `/trade` 成交后计划/规则层可感知（现状该路径零回写）；
  - 部分成交只收敛对应批次（减仓计划的第一批卖掉 → 该批标记已执行，计划不收摊）。
- **边界条件**：
  - 不带 plan_id 的成交（手工单）→ 按计划外成交登记，不影响计划状态；
  - 回执重复到达 → 幂等跳过。

**验收标准**：
1. 模拟一笔带 plan_id 的卖出成交 → 对应待办变 handled、计划状态推进、`position_state` 翻转；
2. 同一回执重放 → 不产生第二次收敛；
3. `pytest tests/plan/` + `tests/application/test_fill_sync_service.py` 全绿。

### 功能点 FR-5：定时反思

**FR-5: 定时反思**
**判据**：盘后定时任务触发 → plan_reflections 新增五问齐全报告；agent 超时 → reflection_overdue_count 递增；pytest tests/plan/ 反思用例全绿。

**功能描述**：盘后/周度定时器组装四类材料包唤醒 agent，agent 按固定五问作答并落库反思报告。

**详细说明**：
- **使用场景**：每个交易日收盘后、每周六，agent 被定时器唤起对计划做反思。
- **操作流程**：
  1. 定时任务（qs_ops，盘后 15:30 / 周六）逐激活计划组装材料包：
     计划修改历史、错过机会（被拦信号走势 + 踏空打分）、盈利、亏损（含止损后走势）；
  2. 唤醒 agent，agent 按固定五问（盈亏对质/修改评估/错过对质/逻辑存活/修改决议）作答；
  3. 反思报告落库 `plan_reflections`（verdict、理由、修改提案、材料包快照）；
  4. 报告里的修改提案进入 FR-6 的计划更新通道——反思不停在纸面，闭环到「修改交易计划」。
- **预期结果**：
  - 每个反思周期每个激活计划有一份结构化报告，可回看「agent 当时看到了什么、怎么判的」；
  - 反思缺席（agent 超时未响应）→ 计划标 `reflection_overdue`，连续 3 日进摘要告警。
- **边界条件**：
  - 材料包某项数据缺席 → 报告对应项标 `missing`，不许跳过不问；
  - verdict 为 keep/observe 必须写明维持理由；adjust/close 必须附修改提案。

**验收标准**：
1. 盘后触发反思任务 → `plan_reflections` 新增报告且五问字段齐全；
2. 模拟 agent 超时 → 计划 `reflection_overdue_count` 递增；
3. `pytest tests/plan/` 反思材料包组装与落库用例全绿。

### 功能点 FR-6：反思驱动计划修改

**FR-6: 反思驱动计划修改**
**判据**：观察窗内无说明的反向修改被 4xx 拒；合规修改 version++ 且基线快照落库；pytest tests/plan/ 纪律用例全绿。

**功能描述**：反思产出的修改提案经计划更新通道生效并重新编译规则、次日按新计划执行，带观察窗锁定与防反复横跳纪律。

**详细说明**：
- **使用场景**：反思发现「止损 8% 被噪音打掉」，提案改 10%，需要安全地生效并回到执行闭环。
- **操作流程**：
  1. 反思报告附修改提案 → 走 FR-2 的「预览→确认→apply」通道；
  2. apply 生效 → 计划 version++，编译器立即重编译托管规则（新阈值/新批次落进 watch_rules）；
  3. 下一拍起引擎按新规则执行——「执行→反思→修改→再执行」闭环闭合；
  4. 落地时冻结修改前基线指标 + 观察窗天数；
  5. 观察窗未满时同字段新提案标「无对照组」，需更强证据；
  6. 同字段 N 日内反向修改 → 必须写明「上次判断为什么错了」，写不出则拒。
- **预期结果**：
  - 修改有理由、有对照、有评估期，反思不是「每天改着玩」；
  - 每次反思通过的修改都能在次日执行中观察到效果，并在下个反思周期被「修改评估」审判。
- **边界条件**：
  - 紧急修改（盘中资损风险）走紧急通道直接改、强制附理由，次日反思必须复核；
  - 上次修改效果未评估 → 材料包「修改评估」项显式标出，不许静默跳过。

**验收标准**：
1. 观察窗内提交同字段反向修改且无说明 → 被拒并返回可读原因；
2. 带完整说明的修改 → 生效且版本++、基线快照落库、托管规则按新值重编译（`watch_rules` 读数可见新阈值）；
3. `pytest tests/plan/` 修改纪律用例全绿。

### 功能点 FR-7：反思数据面补全

**FR-7: 反思数据面补全**
**判据**：被拦触发到回填日后统计接口给出 N 日涨跌幅；计划内/外成交分组计数正确；pytest tests/plan/ 全绿。

**功能描述**：被拦信号走势打分聚合、成交 plan_id 归因、修改效果进入下次材料包。

**详细说明**：
- **使用场景**：反思五问中的「错过对质」「修改评估」需要这两类数据答得出来。
- **操作流程**：
  1. 被环境闸/市场门拦掉的归档触发接入走势回填的统计视图（「拦错了没有」可答）；
  2. `simulation_trades` 增加 `plan_id` 归因列（计划内/外成交可区分）；
  3. 每次修改的版本号、冻结基线、到期日自动进下一份材料包。
- **预期结果**：「错过机会」从信号侧扩展到盯盘侧；盈亏按计划可归因。
- **边界条件**：历史成交无 plan_id → 归因视图标「计划外」，不回填历史。

**验收标准**：
1. 一条被环境闸拦截的触发到回填日后 → 统计接口能给出其后 N 日涨跌幅；
2. 计划内/外成交在统计接口分组计数正确；
3. `pytest tests/plan/` 与 watch 回填相关用例全绿。

### 功能点 FR-8：进化层对接

**FR-8: 进化层对接**
**判据**：knowledge_updates → agent_knowledge 落条目且 evidence 完整；结构性检查脚本 grep 进化服务对 plans 写调用为零（退出码 0）。

**功能描述**：qs_agenthub/evolution 消费反思报告沉淀 agent_knowledge，只改知识不碰在跑计划。

**详细说明**：
- **使用场景**：反思验证过的结论（「这类票止损给 10% 起步」）跨计划复用。
- **操作流程**：
  1. 反思报告的 `knowledge_updates` 段由 lesson_generator 消费；
  2. 沉淀进 `agent_knowledge`（domain/confidence/evidence 结构现成）；
  3. 新建计划时默认带上已验证的知识（作为 spec 默认值建议）。
- **预期结果**：习得的经验只影响**下一个**计划，运行中的计划不被进化层触碰。
- **边界条件**：进化层对 active 计划的写操作 → 接口层不存在该路径（结构性不可能）。

**验收标准**：
1. 反思报告含 knowledge_updates → `agent_knowledge` 新增/更新对应条目且 evidence 完整；
2. 全仓 grep 进化服务对 plans 表无任何写调用（结构性检查脚本退出码 0）。

### 功能点 FR-9：core_plan 适配器

**FR-9: core_plan 适配器**
**判据**：对当前批次调适配接口 → 生成等量 draft 计划且预算一致；重复调用幂等。

**功能描述**：建仓计划的批次名单可一键生成交易计划。

**详细说明**：
- **使用场景**：core_plan.json 每批次 N 只标的，逐只手工建计划太繁。
- **操作流程**：调适配接口指定批次 → 为该批每只标的生成 draft 计划 → agent 逐个确认激活。
- **预期结果**：组合层到执行层的上下游打通；生成物一律 draft，不自动激活。
- **边界条件**：core_plan 文件缺失/过期 → 返回明确不可用原因。

**验收标准**：
1. 对当前批次调适配接口 → 生成对应数量的 draft 计划且预算比例一致；
2. 重复调用幂等（不重复生成）。

## 失败与并发路径 <!-- serves: FR-1 -->

- **并发建/改同一计划**：两个会话同时 PATCH 同一计划 → 后到者按 `expected_version` 被拒（409），
  台账零改动；人工修改落地时该计划的 agent 待确认提案自动作废并通知。
- **编译中途失败**：编译器写规则一半进程被杀 → 整批回滚（事务），重跑幂等命中，
  不留半编译规则；
- **成交回执重复/乱序**：同一回执重放 → 幂等跳过；部分成交先于「计划激活确认」到达 →
  登记为计划外成交，不阻塞；
- **反思定时器触发时 agent 不在线**：材料包落库待取，agent 上线后补反思；
  超窗未反思 → `reflection_overdue_count` 递增，连续 3 日进摘要告警；
- **托管规则被人工 force 直改**：放行但记 drift 事件 + 通知计划 owner；
  下次编译 diff 显式呈现「计划值 vs 人工值」，由反思裁定以谁为准；
- **写路径半成品**：计划创建/修改均为单事务（计划行 + 事件行 + 版本行同生共死），
  不存在孤儿版本；
- **状态机非法迁移**：拒绝并返回可读原因（如「closed 计划不能重新激活，请新建」），不静默改写。

## 边界（不做什么） <!-- serves: FR-1 -->

- **不做自动下单**：计划与盯盘都不产生订单；执行 = 指令 → agent 终判 → 回执（D-1，宪法不变）；
- **不做计划内自动反思改单**：反思产出的是提案，生效必须过计划更新通道（预览→确认），
  反思本身不直接落任何计划改动（三层分离，D-3）；
- **不让进化层碰在跑的计划**：进化只写 agent_knowledge 与默认模板（D-3）；
- **不做前端界面**：本期无 Web UI（sides 仅 backend）；计划与反思的消费方是 agent 与 API；
- **不合并 core_plan**：组合层建仓计划保持独立，仅 FR-9（P2）做下游适配；
- **不改既有盯盘引擎骨架**：编译器只生成规则，WatchEngine 的 15 阶段流水线不动；
- **不做跨账户计划**：单计划单账户（与 watch_rules 账户归属口径一致）。

## 非功能需求 <!-- serves: FR-1 -->

- 性能：今日计划聚合接口（FR-3）P95 < 500ms（单账户 ≤20 计划口径，接口冒烟计时）；
- 兼容：既有 watch_rules 无 plan_id 一律视为「非托管」，行为与现状一致（fail-open）；
- 安全：agent 自主修改必须带 `decision_audit_id`（沿用 watch_rule_changes 既有 CHECK 纪律）。

## 验收标准（整体） <!-- serves: FR-1 -->

1. 建一个含入场条件、止损、两批减仓的计划并激活 → watch_rules 出现对应托管规则；
2. agent 盘前调 today 接口 → 拿到该计划与环境闸结论；
3. 模拟条件触发 → agent 收到指令卡（带 plan_id）→ 模拟成交 → 待办收敛、计划状态推进；
4. 盘后定时器触发 → agent 收到材料包 → 反思报告落库（四输入五问齐全）；
5. 反思提案改止损 → 预览 diff → 确认 → 规则按新值重编译、版本++、基线冻结，下一拍引擎按新规则执行；
6. 观察窗内反向修改无说明 → 被拒；全流程 `pytest tests/plan/` 与 watch 既有套件全绿。

## 关键决策与取舍

| 取舍点 | 否掉的方案 | 选了 | 为什么（依据） |
|---|---|---|---|
| 计划放哪 | 塞 qs_watch（使命膨胀）/ 塞 qs_trading（依赖倒挂）/ 留 monolith（再添债） | 独立包 qs_plan | 跨包编排 + 独立生命周期；D-6 |
| 计划怎么执行 | 新建执行引擎 | 编译成 watch_rules，复用 WatchEngine | 引擎 15 阶段流水线已跑通，重造=双份维护 |
| 反思怎么落地 | 反思直接改计划（最快） | 反思出提案、走更新通道确认生效 | 修改必须有对照与审计；D-3 |
| 进化怎么参与 | 进化自动调在跑计划 | 只沉淀知识，影响下一个计划 | 在跑计划的变更权只能有一个入口；D-3 |
| 谁终判下单 | 系统自动执行 | agent 终判 | D-1（宪法） |

## 技术方案与亮点

- 新包 `packages/qs_plan`：domain（计划/退出策略/状态机，纯逻辑）+ application（计划服务/编译器/聚合器/材料包组装器），
  依赖单向 `qs_plan → qs_watch/qs_trading/qs_sourcing/qs_market_data/qs_kernel`（import-linter 强制）；
- 编译器是幂等 diff 引擎（`(plan_id, role, symbol)` 唯一），不是一次性生成器；
- 反思材料包是「证据快照」随报告落库——事后可查 agent 当时看到了什么；
- 与常规做法差异：不新建执行引擎（编译复用）、反思议程模板化（五问必填防散文）、
  修改纪律机械化（观察窗/防横跳由代码强制，不靠自觉）。

## 依赖与约束 <!-- serves: FR-1 -->

- 强依赖：`qs_watch`（编译目标与触发链）、`qs_trading`（成交回执写点 execute_trade）、
  `qs_agenthub/evolution`（知识沉淀）、agent-ts（盘前加载与反思会话）；
- 弱依赖：core_plan（FR-9，P2）、MissedOpportunityService（错过机会信号侧数据源）；
- 约束：不自动下单（D-1）；业务定时任务归 v2 调度（ADR-004）；
  新代码进包不走 monolith 旧路径（S1-S10 包边界纪律）；
  依赖方向不可倒挂（import-linter 守门）。
