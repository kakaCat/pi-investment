# 账户级交易计划统一与数据库化重构需求文档

## TL;DR

当前交易计划主链路为 `core_plan_service → core_plan.json → CorePlanAdapter → qs_plan`，存在两套“计划”、文件交接、单标的限制、自动生成与激活脱节等问题。文件方案缺少事务、并发约束和可靠审计，不能继续作为企业生产链路。

本需求将交易计划统一为 **`qs_plan` 管理的账户级、多标的、每日滚动计划**：组合算法只提供决策输入；计划、版本、标的项、条件、执行状态、规则归因、成交进度、对账和反思全部以数据库为唯一事实源。系统每个交易日幂等生成待审核版本，经审核、激活和就绪检查后进入 WatchEngine 执行；任何数据过期、审核缺失、规则不一致或持仓不明均必须明确 `not_ready`，不得静默交易。

## 1. 背景与问题

### 1.1 当前链路

```text
core_plan_generate（工作日盘前）
  → application/services/core_plan_service.py
  → 写 config/core_plan.json
  → agent 主动读取或调用 /api/core-plan
  → CorePlanAdapter 按批次转换
  → qs_plan 单标的 draft
  → agent 补入场条件、apply、activate
  → watch_rules
```

### 1.2 必须解决的问题

| 问题 | 当前表现 | 业务影响 |
|---|---|---|
| 两套计划概念 | `core_plan` 管组合目标，`qs_plan` 管单标执行 | 没有统一的当日交易计划事实源 |
| 文件作为生产契约 | 计划写入并回读 `core_plan.json` | 无事务、并发控制和可靠恢复，路径或新鲜度处理易出错 |
| 自动链路断开 | 文件生成后依赖 agent 主动转换和激活 | 某天可能只有组合文件，没有可执行交易计划 |
| 单标模型 | `targets` 被限制为恰好一个，主计划状态随单标持仓翻转 | 无法表达一个账户全部持仓和候选的统一计划 |
| 核心状态放入 JSON | 标的、入场、退出和执行语义主要装在 `spec` | 难以建立外键、逐项状态机和精确成交归因 |
| 激活缺少统一事务 | 路由先编译规则再迁移状态，底层写点分别提交 | 失败时可能出现半激活、补偿失败或审计缺失 |
| 就绪状态不明确 | 无激活计划时 today 仅返回空列表 | “正常无计划”和“今天计划没跑起来”无法区分 |
| 历史迁移风险 | 规则、成交和减仓进度已关联旧计划 | 不能直接删表或重置计划，否则会破坏历史与累计口径 |

## 2. 需求决策

以下决策是本需求的强制约束：

- **D-1 唯一事实源**：`quant` 数据库是交易计划唯一生产事实源；`core_plan.json` 退出生产生成、传递和读取链路。
- **D-2 统一领域归属**：组合选股与风险计算可以独立存在，但只是 `PortfolioDecisionProvider`；交易计划的生成、版本、执行、对账和反思统一归 `qs_plan`。
- **D-3 账户级计划**：一个账户一份持续滚动的主计划，包含多个标的计划项；不再以“一标的一份主计划”作为新模型。
- **D-4 每日版本**：每个交易日生成一个新 revision，不每天创建互相割裂的主计划；未完成计划项及其执行状态跨日延续。
- **D-5 关系化核心数据**：计划项、版本、条件关联、执行状态、规则归因和成交归因使用关系表及明确列。JSONB 只允许保存条件参数、证据快照和扩展属性。
- **D-6 审核后激活**：每日任务可以自动生成待审核版本，但不得编造入场条件或绕过授权自动激活。
- **D-7 失败关闭**：数据过期、审核缺失、计划项不完整、规则不一致或持仓对账失败时必须 `not_ready`，不得把失败伪装为空计划或成功。
- **D-8 保留历史**：旧计划、版本、事件、成交和反思不得物理清除；迁移必须保留历史归因和累计减仓基线。
- **D-9 执行边界不变**：`qs_plan` 不直接下单；WatchEngine 负责监控和触发，agent/用户在授权范围内最终决策。
- **D-10 先测试后切换**：测试库验证、生产备份、灰度和回滚方案是生产切换的前置条件，不得直接覆盖生产计划链路。

## 3. 产品定义

交易计划是一个账户在一段时间内的完整决策与执行对象，回答：

- 当前账户的现金、持仓、总风险预算和市场限制是什么。
- 每个标的应当买入、卖出、持有还是回避，依据是什么。
- 每个标的的目标仓位、入场条件、有效期、止损、减仓和失效条件是什么。
- 每个标的当前执行到哪一步，哪些规则和成交属于它。
- 今日计划是否真正具备执行条件；若不具备，具体阻塞原因是什么。
- 盘后执行结果如何进入反思，并如何形成下一交易日的计划版本。

### 3.1 目标业务流程

```text
盘前读取数据库中的账户、持仓、行情与风险事实
  → PortfolioDecisionProvider 产出组合决策
  → qs_plan 幂等生成今日 revision 和全部计划项
  → 审核/补充交易条件
  → CAS 生效 + 同事务激活与规则编译
  → 盘前 readiness 和持仓/规则对账
  → WatchEngine 监控，agent 终判下单
  → 成交按 plan_id + item_id + plan_version 回流
  → 逐项更新执行状态和累计减仓进度
  → 收盘对账与反思
  → 生成下一交易日 revision，延续未完成项
```

## 4. 用户与职责

| 角色 | 职责 | 权限边界 |
|---|---|---|
| 用户 | 查看计划与阻塞原因，执行授权和结构性修改确认 | 最高决策权 |
| 投资脑 / fin-agent | 审核每日计划、补充交易条件、提交反思和修改提案 | 必须携带账户和决策审计身份 |
| 组合决策服务 | 提供标的、权重、分批建议、风险预算和依据 | 不创建执行计划，不写文件，不直接下单 |
| `qs_plan` | 计划生成、版本、状态、编译编排、对账、反思 | 不直接下单 |
| WatchEngine | 执行已编译规则并产生触发 | 不自行改变计划意图 |
| 调度系统 | 触发每日生成、就绪检查、对账与反思 | 不得把部分成功记为整体成功 |
| 运维人员 | 迁移、监控、故障处理和生产切换 | 生产变更需授权、备份和回滚方案 |

## 5. 范围

### 5.1 本需求包含

- 账户级主计划、多标的计划项及逐项执行状态。
- 数据库每日生成、版本管理、审核、激活和跨日滚动。
- 组合算法无文件化改造及进程内 provider 接入。
- 规则、成交、事件和反思的 `item_id` 精确归因。
- 激活和规则编译的统一事务。
- 盘前就绪门、规则对账、持仓对账和运行记录。
- 旧计划与历史数据的可审计迁移。
- 旧 API、调度、策略注册和 agent 消费链路的切换。
- 测试、监控、文档、生产灰度和回滚要求。

### 5.2 本需求不包含

- 不借重构改变现有选股、波动目标、回撤闸和分批策略的投资逻辑。
- 不新增自动下单通道，不绕过 agent/用户终判。
- 不承诺收益、胜率或任何交易结果。
- 不实现一个计划跨多个账户共享持仓。
- 不在本需求中要求前端页面；API 与 agent 工具契约必须完整。
- 不物理删除旧计划、历史成交或历史反思。
- 不在未单独授权时执行生产迁移、生产调度启停、真实下单或真实 agent 唤醒。

## 6. 功能需求

### FR-1 数据库唯一事实源

**优先级：P0**

**需求**

1. 所有新交易计划必须写入数据库，禁止以本地 JSON 文件作为生成结果、任务输入或模块间契约。
2. 服务重启后，必须仅凭数据库恢复计划生成、审核、激活、执行和反思状态。
3. JSONB 不得保存本应由外键或状态字段表达的 `plan_id/item_id/version/state` 核心关联。
4. 如需导出 JSON，只能是只读展示快照，不得回读为生产输入。

**验收**

- 临时移走 `core_plan.json` 后，测试环境每日生成、读取、激活、成交回流和反思仍完整工作。
- 生产代码不再存在写 `config/core_plan.json` 的路径。
- 服务重启后重复执行同一任务，不丢失状态也不重复生成计划。

### FR-2 账户级主计划与多标的计划项

**优先级：P0**

**需求**

1. 一个账户只能有一份当前滚动主计划；主计划包含全部候选和持仓管理项。
2. 每个计划项必须有稳定 `item_id`，并记录 `symbol/action/horizon/target_weight` 等决策。
3. `action` 至少支持 `buy/sell/hold/avoid`。
4. 计划项执行状态至少支持：

   ```text
   planned → ready → entering → holding → reducing → exited
       └──────────────→ cancelled
   ```

5. 单个计划项成交或退出不得直接关闭账户主计划。
6. 新组合目标未覆盖的已有持仓不得被自动解释成卖出；必须形成待审核的持仓管理项。
7. 同一账户同一激活 revision 中，同一标的不得出现互相冲突的未关闭计划项。

**验收**

- 一个含两个买入项、一个持仓项的计划可以生成并激活。
- 其中一个标的清仓后，其他计划项和主计划仍按各自状态运行。
- 清单外已有持仓出现在计划中，但不会仅因缺席组合目标而被自动卖出。

### FR-3 每日计划生成与跨日滚动

**优先级：P0**

**需求**

1. 每个交易日盘前由数据库调度任务调用 `TradingPlanGenerationService.generate(account, trade_date)`。
2. 生成输入至少包括账户、现金、真实持仓、组合目标、数据时点、市场闸、风险预算和决策依据。
3. 同一账户同一交易日的生成必须幂等；并发执行不得生成两份有效草稿或两个当前激活版本。
4. 每次生成在一个数据库事务内写入 revision、计划项版本、条件、执行状态、运行记录和审计事件。
5. 新 revision 初始为待审核状态；数据缺失、数据过期、账户不符或风险输入不完整必须失败并记录原因。
6. 次日滚动必须延续未完成 `item_id` 及其成交和剩余数量，不重置执行进度。
7. 已激活 revision 不可变；修改必须形成新草稿并经过生效流程。

**验收**

- 同一生成请求串行和并发重放均返回相同计划身份，数据库无重复有效版本。
- 任一写入步骤失败时，不出现部分计划项或“已生成”运行记录。
- 次日生成后，持仓项的累计成交和减仓进度与上一日连续。

### FR-4 审核、两步修改与原子激活

**优先级：P0**

**需求**

1. 系统生成后必须进入审核流程；缺少入场条件的 `pending` 项不得激活。
2. agent 自主修改必须携带 `decision_audit_id`，并继续遵守现有修改理由、观察窗和反向修改纪律。
3. PATCH 只修改草稿 revision 并返回结构化 diff；APPLY 通过 CAS 生效，版本冲突必须拒绝。
4. 激活必须由应用服务统一编排，不得由路由分别调用多个独立提交写点。
5. 版本状态、规则创建/更新/退役、规则映射和审计必须处于同一事务；任一步失败全部回滚。
6. 审计写入失败不得返回激活成功。
7. 激活必须遵守账户授权；不得为了每日自动闭环而默认自动激活或自动下单。

**验收**

- 入场条件缺失、审核未完成或版本冲突均无法激活。
- 对规则创建、映射、审计等步骤分别做故障注入，均无半激活计划或孤儿规则。
- 激活后可以从数据库还原使用的确切 revision 和全部规则。

### FR-5 多标的规则编译与精确归因

**优先级：P0**

**需求**

1. 编译器以 `(item_id, role, batch)` 为期望规则幂等键。
2. 新托管规则和规则映射必须携带 `plan_id/item_id/plan_version`。
3. 入场、止损和分批减仓规则由对应计划项版本生成，不允许跨 item 复用或按 symbol 猜测归属。
4. 重复编译不得产生重复规则；版本变化必须正确增改退役。
5. 计划项退出只退役该 item 对应批次或规则，不影响同账户其他 item。
6. 被托管规则发生计划外修改时必须形成 drift，并进入对账结果。

**验收**

- 多标计划激活后，每条规则均可精确反查计划项和版本。
- 同一 item 多批减仓按累计成交逐批退役，其他 item 规则不变。
- 编译重放、修改和失败回滚测试全部通过。

### FR-6 成交回流与连续执行状态

**优先级：P0**

**需求**

1. 新执行链路的成交必须携带 `plan_id + item_id + plan_version`；缺少 item 归因不得推进新计划。
2. 历史成交允许 `item_id` 为空，但只能通过明确的旧计划迁移映射读取，不得按 symbol 临时猜测。
3. 成交按 `trade_id` 幂等；重复回执不得重复更新数量、状态或退役规则。
4. 买入、部分卖出、清仓只更新对应 item 的执行状态。
5. 累计减仓采用“迁移基线 + 当前 item 累计成交”口径，跨日和迁移后不得清零。
6. 持仓或成交读取失败时必须显式降级并进入对账，不得臆造清仓或卖出比例。
7. 计划外手工成交仍按现有规则登记，不得篡改计划项决策；如造成未管理持仓，必须使 readiness 失败。

**验收**

- 两个 item 同时运行时，各自成交只推进各自状态。
- 重复成交、跨日成交和旧计划迁移后的减仓结果连续且正确。
- 缺失 item 的新成交会报警并显示阻塞原因，不会错误推进同标的其他计划。

### FR-7 盘前就绪门与持续对账

**优先级：P0**

**需求**

1. 系统必须提供统一的 readiness 判定，至少检查：
   - 今日 revision 是否存在且数据新鲜；
   - 审核和授权是否完成；
   - 所有计划项的入场、退出、权重和有效期是否完整；
   - 当前激活版本与规则是否一致；
   - 是否存在缺失、孤儿或错误版本规则；
   - 是否存在未管理持仓或持仓数量异常；
   - 是否存在未解决的生成、迁移、成交或对账错误。
2. 检查结果必须是 `ready` 或 `not_ready`，并附机器可读原因、涉及 item 和检查时间。
3. 交易日盘前没有计划不得再仅表示为正常 `empty`；必须说明“尚未生成”或“生成失败”。
4. readiness 失败必须阻止新计划进入执行，并产生运行记录与告警。
5. 对账任务可重复执行，结果持久化，服务重启后仍可查询。
6. 就绪检查不能伪造行情、持仓、审核或规则事实。

**验收**

- 分别注入无计划、过期行情、未审核、缺规则和未管理持仓，返回对应 `not_ready` 原因。
- 全部条件满足时 `/api/plans/today` 返回当前 revision、全部 item 和 `ready=true`。
- 对账修复前重复运行不会把错误自动清除。

### FR-8 对账、反思与次日闭环

**优先级：P1**

**需求**

1. 收盘后必须对计划、规则、成交和实际持仓进行对账；无成交也应有明确结果。
2. 反思材料包按账户 revision 聚合，并保留 item 级盈亏、规则触发、修改和成交归因。
3. 反思修改必须进入新草稿 revision，不能直接覆盖已激活版本。
4. 唤醒失败不得推进反思到期时间；漏反思继续保留 overdue。
5. 知识沉淀只读反思，不得直接修改正在运行的计划。
6. 次日生成必须能读取前一日反思和对账结果。

**验收**

- 可完成“生成→审核→激活→成交→对账→反思→次日 revision”全链路。
- 无成交交易日也留下计划、对账和反思记录。
- 反思中的调整经审核生效后，新规则归属新的 revision。

### FR-9 旧链路迁移与退出

**优先级：P0**

**需求**

1. 必须通过新增增量迁移实施，不得修改旧迁移文件来冒充生产已升级。
2. 旧计划、版本、事件、成交和反思必须保留并可查询。
3. 旧计划迁移按账户分组形成新主计划和计划项，使用 `legacy_plan_id` 保留来源。
4. 历史成交的原始归属不得改写；仍需运行的托管规则可迁移到新计划项，并记录审计。
5. 必须根据旧成交和真实持仓初始化执行基线，保证累计减仓连续。
6. 有持仓但数量无法核实的账户不得自动迁移，必须进入人工异常清单。
7. `/api/core-plan` 在兼容期只能读取新数据库计划并标记 deprecated，不得回读文件。
8. 所有调用方完成切换后，删除 `/api/plans/from-core-plan`、`CorePlanAdapter` 和旧文件生成注册。
9. 策略注册、候选任务和 agent 例行任务必须改用 `qs_plan`，不得继续引用 `plan_file`。
10. 生产旧调度禁用和新调度启用必须进入同一授权变更窗口，避免双跑或空窗。

**验收**

- 迁移 dry-run 能报告账户、计划项、规则、成交基线和异常数量。
- 测试库首次迁移成功、重复执行零重复变更。
- 旧历史仍可查询，新规则和新成交使用新归因。
- 全部生产消费者迁移后，代码与配置不再依赖 `core_plan.json`。

### FR-10 审计、运行记录与可观测性

**优先级：P1**

**需求**

1. 持久记录生成、审核、readiness、对账和迁移运行，包括状态、幂等键、错误和关联版本。
2. 所有状态变化必须记录操作者、时间、原因和决策审计编号（适用时）。
3. 至少提供以下指标或等价查询：
   - 每日生成成功/失败；
   - ready/not_ready 及原因；
   - 审核超时；
   - 规则对账差异和孤儿规则；
   - 未管理持仓；
   - 成交归因与推进失败；
   - 反思 overdue。
4. 部分步骤失败不得把整日任务报告为成功。
5. 错误响应不得泄露数据库凭据、账户敏感配置或内部连接串。

**验收**

- 任一日期的失败均可从数据库或监控接口定位到具体步骤和原因。
- 重试后保留完整运行历史，不覆盖首次失败事实。

## 7. 数据要求

### 7.1 逻辑模型

| 数据对象 | 核心职责 |
|---|---|
| `trading_plans` | 账户级持续主计划、当前版本指针和生命周期 |
| `trading_plan_versions` | 每日/修改 revision、数据时点、风险预算、审核和激活状态 |
| `trading_plan_items` | 跨 revision 稳定的计划项身份及旧计划来源 |
| `trading_plan_item_versions` | 每个 revision 中计划项的不可变决策 |
| `trading_plan_item_states` | 当前执行状态、成交数量、剩余数量、迁移基线和乐观锁 |
| `trading_plan_conditions` | 计划项版本的入场、止损和减仓条件 |
| `trading_plan_rules` | 计划项到 WatchEngine 规则的映射 |
| `trading_plan_runs` | 生成、审核、readiness、对账和迁移运行记录 |
| `trading_plan_events` | 计划与计划项的完整时间线 |
| `plan_reflections` | 账户和 item 归因的反思与材料快照 |

### 7.2 数据约束

1. 核心关联使用外键；核心数量、比例和状态使用明确列及必要 CHECK。
2. 同账户只能有一个当前滚动主计划和一个当前激活 revision。
3. 草稿生成以 `account + trade_date` 幂等；版本以 `plan_id + version` 唯一。
4. 已激活 revision 和其 item 决策不可原地更新。
5. 执行状态与不可变决策分表，禁止覆盖历史版本来表示最新成交进度。
6. 旧字段在兼容期可保留用于审计，但新执行链路不得继续依赖旧 `spec/draft_spec`。
7. 所有新时间必须明确时区；`trade_date` 与 `data_as_of` 分开，不能用生成时间冒充行情时点。

## 8. 接口与任务要求

### 8.1 API

| 接口 | 要求 |
|---|---|
| `POST /api/plans/generate` | 幂等生成指定账户、交易日的草稿 revision |
| `GET /api/plans/today?account=...` | 返回今日 revision、items、states、环境闸和 readiness |
| `GET /api/plans/{id}` | 返回主计划、版本、计划项、执行状态、事件和迁移来源 |
| `PATCH /api/plans/{id}` | 修改草稿项并返回结构化 diff，不直接生效 |
| `POST /api/plans/{id}/apply` | CAS 生效草稿，保留修改纪律 |
| `POST /api/plans/{id}/activate` | 同事务完成激活、规则编译、映射和审计 |
| `POST /api/plans/{id}/readiness` | 重新执行就绪与对账检查并持久记录 |
| 现有 pause/resume/close/reflections | 切到账户主计划和 item 语义，保持授权与审计 |

新增错误码至少覆盖：

- `PLAN_DATA_STALE`
- `PLAN_REVIEW_REQUIRED`
- `PLAN_NOT_READY`
- `PLAN_ITEM_ATTRIBUTION_REQUIRED`
- `PLAN_RECONCILE_FAILED`
- `PLAN_MIGRATION_REQUIRED`
- 继续复用 `VERSION_CONFLICT`、`PLAN_STATE_ILLEGAL` 和 `DECISION_AUDIT_REQUIRED`

### 8.2 调度

- 新增交易日盘前 `trading_plan_generate_daily`。
- 新增盘前 readiness/对账任务和盘中/收盘对账任务；具体频率在设计阶段依据现有调度能力确定。
- 复用并改造现有盘后、周度反思任务。
- 所有任务以数据库为恢复依据，重复执行安全。
- 新任务测试验证完成前，不得直接替换生产 `core_plan_generate`。

### 8.3 agent 契约

- `trading_plan.today` 必须返回账户级多标计划和 readiness。
- 审核、修改、激活和反思接口必须携带账户、版本和必要的 item 身份。
- agent-dh、agent-ts 的工具和例行任务提示必须同步迁移。
- 外部配置不在本仓时，必须形成部署协同项；未实际修改和验证前不得宣称外部链路完成。

## 9. 非功能要求

### 9.1 事务与并发

- 每日生成、版本生效、激活和成交推进必须具备明确事务边界。
- 多调度实例并发执行不得产生重复计划、重复激活或重复成交推进。
- 所有可重试操作必须有幂等键或等价数据库约束。

### 9.2 可恢复性

- 不允许依赖进程内存保存待审核、待唤醒、待对账或失败状态。
- 服务重启后能从数据库继续执行或安全重试。
- 生产切换前必须完成备份和回滚演练。

### 9.3 可审计性

- 任意交易日可还原“为什么制定、谁审核、激活了哪些规则、发生哪些成交、如何反思”。
- 历史 revision 不可被后续执行状态覆盖。
- 迁移本身也必须有来源映射和事件记录。

### 9.4 性能与可用性

- 今日视图必须按账户和日期使用索引查询，不得扫描全部历史计划。
- 多标编译和对账应批量读取，避免按 item 重复查询账户或全库规则。
- 行情、持仓等外部数据异常必须显示具体降级状态，不得阻塞无关历史查询。

## 10. 迁移与发布要求

1. **离线契约**：检查 DDL、约束、索引、默认 dry-run 和写开关。
2. **测试库迁移**：仅在 `quant_test` 执行首次迁移、重跑和数据迁移验证。
3. **双链路静态核查**：确认没有新代码继续写文件，没有消费者仍把旧文件作为生产事实源。
4. **完整回归**：覆盖计划、组合决策、规则、成交、调度、反思、策略注册和 agent 契约。
5. **生产准备**：备份、数据异常清单、灰度账户、切换步骤、回滚条件和监控读数齐全。
6. **授权切换**：生产迁移与调度启停单独授权，避免旧新任务双跑。
7. **切换后核查**：今日计划、激活规则、持仓对账、成交归因和反思均有真实只读证据。
8. **退出兼容层**：确认所有消费者迁移后，再删除兼容 API 和文件产物；历史研究快照不属于生产事实源。

## 11. 总体验收场景

### UC-1 正常每日闭环

```text
给定账户有现金、两个候选和一个已有持仓
当盘前生成任务运行两次
则只存在一个有效草稿 revision
并且包含两个候选项和一个持仓管理项
审核并激活后，规则均有正确 item_id 和 plan_version
其中一个标的成交只推进该 item
收盘完成对账和反思
次日 revision 延续全部未完成项和执行进度
```

### UC-2 数据或审核不就绪

```text
给定行情数据过期或入场条件未补齐
当生成/激活/readiness 执行
则系统返回明确失败原因
并且计划不激活、不产生可执行入场规则、不自动下单
```

### UC-3 并发与故障恢复

```text
给定两个调度实例同时生成同一账户同日计划
则数据库约束和幂等逻辑只保留一个有效结果
当规则映射或审计写入失败
则整个激活事务回滚
服务重启后可从数据库安全重试
```

### UC-4 旧计划迁移

```text
给定同账户多个旧单标计划，其中包含历史减仓和当前持仓
当执行迁移
则形成一个账户主计划和多个带 legacy_plan_id 的 item
历史成交仍属旧计划
新规则归属新 item
累计减仓基线连续
无法核实持仓的账户进入异常清单而非自动切换
```

### UC-5 文件退出

```text
给定 core_plan.json 不存在
当执行每日生成、today、规则编译、成交回流和反思
则全流程正常
并且所有生产消费者读取数据库，无文件回读或补写
```

## 12. 完成定义（Definition of Done）

本需求只有同时满足以下条件才算完成：

- [ ] 数据库可完整还原任意交易日的计划、版本、计划项、条件、审核、规则、成交、对账和反思。
- [ ] 账户级多标模型和逐项状态机已取代新链路的单标 `spec` 执行模型。
- [ ] 每日生成幂等，并发和重试不会产生重复计划或重复激活。
- [ ] 激活与规则编译具备统一事务和故障回滚证据。
- [ ] 成交按 item 精确归因，跨日及迁移后的累计减仓连续。
- [ ] 所有异常均明确 `not_ready`，不会静默执行或伪造事实。
- [ ] 服务重启后仅凭数据库即可恢复整个闭环。
- [ ] `core_plan.json` 已退出全部生产链路，旧调用方和 agent 契约均已迁移。
- [ ] 旧计划、成交和反思历史保持可查，迁移和对账证据完整。
- [ ] 测试库相关回归全部通过，生产切换有独立授权、备份、灰度、回滚和只读验证证据。
