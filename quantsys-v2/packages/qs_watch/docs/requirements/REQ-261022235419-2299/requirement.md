# 盯盘引擎 V2 —— 持仓驱动重写 需求文档

**TL;DR**：按「持仓驱动」重写盯盘主流程——先统一取实时价、再按持仓分两类模块各自判定、作废范围覆盖全部激活票；触发按 10 次一循环路由（当天盘中）：循环首发对应账户 agent 判断（改/执行/哪个账户买），agent 判断后发盯盘群；第 2~9 次不处理；第 10 次直通群并归零；每日收盘定时任务清零，次日首轮仍 agent 先处理；止损必达。得到：顺序正确的盯盘引擎，未持仓票也有作废范围，建仓不再需要接棒补丁，通知有 agent 判断层。

## 摘要

- **要解决什么**：盯盘主流程按「持仓驱动」模型重写——查所有激活规则 → 统一取实时数据 → 按持仓分两类 → 各自判定逻辑，作废范围覆盖全部激活票，触发按10次循环路由（首发agent判断、中段不处理、第10次直通群）。
- **来源与证据强度**：用户直接裁定（2026-10-22 全天对话逐轮给出模型与多次纠正顺序）；证据为生产实测（39 次触发只 1 条送达、作废范围对未持仓票不生效、建仓要接棒建新规则）。
- **本轮结论**：进 PRD 11 条（R-1~R-8、R-10~R-12）；已拒 1 条（R-9 程序写死环境/情绪过滤，已拒并已在 V1 移除）；延期 0 条。

## 待解问题

| 问题 | 证据 | 影响 | 谁受影响 |
|---|---|---|---|
| V1 是意图驱动（规则带固定 intent，持仓门匹配），与持仓驱动模型顺序相反 | 用户 2026-10-22 裁定「应该查实时持仓和盯盘匹配，然后找意图」 | 持仓翻转后规则 intent 失效，逼出「建仓接棒建新规则」补丁 | 用户、agent |
| 取价排在过滤之后，被过滤的票没有实时价 | 代码实测：`engine.tick()` 取价在持仓门/到期门之后 | 未持仓/被跳过票无法做失效判定 | 用户 |
| 作废范围对未持仓票不生效 | 实测：exit+空仓规则被持仓门整条跳过，走不到失效判定 | 清仓后的规则永远僵在 active，既不作废也不触发 | 用户 |
| 程序曾写死判断并静默吞信号 | 实测：环境闸拿 51 只样本假涨跌比拦 6 条信号；2026-09-11 用户裁定不许机器过滤 | 盯盘不发消息（本需求起点） | 用户 |
| 触发通知直达用户、缺 agent 判断层 | 用户 2026-10-22 裁定「第一次触发都要发给agent，让agent判断……agent再发盯盘群里通知」 | 用户看到的是未判断的原始信号，无法回答「改规则还是执行、哪个账户买」 | 用户 |

## 边界

**做**：重写盯盘主流程编排（加载→统一取价→持仓分类→判定→失效→路由→投递）；持仓/非持仓两独立判定模块；失效判定独立覆盖全部激活票；10 次循环路由 + 每日收盘重置；发 agent 与发飞书两独立通道文件 + 提示词/模板两独立文案文件（按持仓×判定类型）。

**不做**：不改条件 DSL 求值器（复用）；不改通知渠道本身（复用 facade）；不改规则表结构（今日已落字段直接复用，V2 只加 trigger_channel/process_state/cycle_count 三列）；不做前端 UI；不做持仓双面规则（开放问题留后续）；不读懂 V1 代码（黑盒复用接口）。

## 产品定义

盯盘引擎 V2 是「持仓驱动」的实时盯盘主流程：以票为中心，先统一取实时数据，再按持仓状态分两类（持仓管理 / 建仓关注），各自走对应判定逻辑，失效判定独立覆盖全部激活票。程序只做机械判定（取数、比对、分类、送达），失效线等阈值由 agent 设定，一切裁决（失效改/删、执行、建仓接棒）归 agent/用户。触发按 10 次循环路由：循环首发 agent 判断，中段不处理，第 10 次直通盯盘群，每日收盘重置。

## 需求明细

#### R-1 激活规则加载

**描述**

每拍判定前查询 `quant.watch_rules` 中 `rule_state='active'` 的全部规则；invalid/archived 不进判定集合。

**来源与证据**

用户 2026-10-22：「查出所有盯盘的股票」；三分支字段今日已落库（迁移 20261022_watch_rules_state）。

**验收判据**

`psql -c "select count(*) from quant.watch_rules where rule_state='active'"` 返回 52（2026-10-22 现状）；引擎日志记录激活规则数且与库一致。

**优先级理由**

这是全流程的输入集，错了后面全错。

#### R-2 统一实时取价前置

**描述**

对全部激活规则覆盖的 symbol（去重）统一取实时行情，取价在任何过滤（失效/到期/持仓）**之前**——过滤是对比时的维度，不是取价前置条件。

**来源与证据**

用户 2026-10-22：「不是查出所有盯盘的股票，然后再查股票实时数据和规则对比吗」；实测 V1 取价在持仓门/到期门之后。

**验收判据**

代码断言取价输入集合 == 全部激活规则 symbol 集合；任一激活票的 quote 在分类与判定阶段可用；单测覆盖「被持仓门跳过的票也有实时价」。

**优先级理由**

取价前置是「作废范围覆盖所有票」与「持仓作对比维度」的前提。

#### R-3 持仓分类模块

**描述**

取到实时价后按 position_state（holding/none）分两类：持仓走 `position_engine` 模块、非持仓走 `unpositioned_engine` 模块，各一个独立文件。

**来源与证据**

用户 2026-10-22：「判断盯盘是持仓还是非持仓，持仓写一个文件，非持仓写一个文件」。

**验收判据**

两模块文件各自存在且可 import；holding 规则只进 position_engine、none 规则只进 unpositioned_engine（单测覆盖）。

**优先级理由**

这是「持仓驱动」的骨架，两个模块是各自逻辑的载体。

#### R-4 持仓类判定

**描述**

持仓票四操作：增仓（add_position）、止盈（exit_take_profit）、止损（exit_stop）、减仓（exit_reduce）。止损宪法级：任何情况必达，持仓状态滞后（空仓显示）时也 fail-open 照常判定并留痕。

**来源与证据**

用户 2026-10-22：「持仓的看止盈止损减仓增仓」。

**验收判据**

单测：持仓票 × 四 intent 各产生对应通知/待办；止损 + 空仓状态仍触发（fail-open + state_mismatch 留痕）。

**优先级理由**

持仓管理是盯盘的第一价值（风控）。

#### R-5 非持仓类判定

**描述**

未持仓票两操作：买入范围（entry 买点价触发提醒）、观察（trend_observe）。

**来源与证据**

用户 2026-10-22：「未持仓看到买入范围等级」。

**验收判据**

单测：空仓票 + entry 规则，到买点价触发通知，未到不触发。

**优先级理由**

建仓机会发现是非持仓票存在的意义。

#### R-6 失效判定独立覆盖全部激活票

**描述**

对每条激活规则（不管持仓与否、不管是否触发、不管是否到期）用实时价算偏离：`|现价−触发价|/触发价 > rule.invalidation_threshold_pct`（agent 必填）→ 标 invalid + 留痕 + **经 ⑦ notify_agent 投递 agent**（发 agent 统一走这一个模块，与触发首发同一通道）。

**按操作类型分场景**（持仓类同样适用）：止损（exit_stop）豁免——止损线是保护线，穿越是资损事实（触发），永不作废；止盈/减仓/增仓是目标线——价格跑远目标过时（如止盈 250 现价 300、增仓 220 现价 280），偏离超失效线即判失效交 agent 重定价。

**来源与证据**

用户 2026-10-22：「盯盘要设定涨多少或者跌多少这个规矩就作废的能力」「失效线交 agent 输入，不是写死」「未持仓看作废范围」。

**验收判据**

单测：空仓票 + 偏离超线的 exit 规则 → 标 invalid 且投递；持仓/未持仓/未到期三类票同覆盖；同一规则标后不重复投递。

**优先级理由**

作废范围覆盖未持仓票是用户明确纠正的核心点。

#### R-7 信号直发用户

**描述**

所有命中通知直发盯盘群；程序不按环境/情绪等写死条件过滤（环境闸已 2026-10-22 移除，开关 WATCH_ENV_GATE_ENABLED 可回滚）。

**来源与证据**

用户 2026-09-11：「通知是给用户看的事实，不该由机器替用户过滤」；实测环境闸吞 6 条信号。

**验收判据**

构造环境偏冷（情绪 20/涨跌比 0.27）场景，触发信号仍 notified=true 送达。

**优先级理由**

这是本需求的起点（盯盘不发信息）。

#### R-7 触发路由与通知（10 次一循环：循环首发 agent，循环内其余不处理）

**描述**

**触发路由按「10 次一循环」**：每条规则带循环计数——每循环**第 1 次触发 → 发对应账户 agent 处理**（notify_agent；agent 判断：规则是否修改 / 是否执行规则 / 应由哪个账户购买 → 判断后发盯盘群通知用户）；**第 2~9 次触发 → agent 不处理**（循环内无新事不重复劳动）；**第 10 次触发 → 引擎直通盯盘群**（notify_feishu，不等 agent），随后计数归零进入下一循环（下循环第 1 次再发 agent）。跨天延续：次日循环第一次仍 agent 先处理。无每日定时任务。止损宪法级必达——「必达」只保**不被预算/降噪/状态滞后吞掉**（该发必发），止损与其他规则一样走 10 次循环，无「永远走 agent」特权。

**两条通道文件级分离（D-13）**：发 agent 一个文件（`notify_agent`：触发→agent 判断通道），发飞书盯盘群一个文件（`notify_feishu`：→用户通知通道）。两个文件各自独立实现，互不内嵌——每次触发只走 notify_agent；agent 判断后由 agent 侧走 notify_feishu 发群；循环第 10 次触发时引擎直接走 notify_feishu 发群（随后归零）。

**来源与证据**

用户 2026-10-22/23 原话：「信号直发用户（盯盘群）——程序不过滤；止损宪法级必达 这个不对。第一次触发都要发给agent，让agent判断（规则是否修改还是执行规则，应该那个账户购买）agent再发盯盘群里通知，后面重复发10次内agent不处理，直接发群里」「同一规则第一次agent（盯盘添加一个状态，agent处理修改这个状态）处理了后面9次不处理。所有都要发给agent」。

**验收判据**

单测：每循环第 1 次触发 → 投递对应 agent（notify_agent）；第 2~9 次触发 → agent 不处理（零投递）；第 10 次触发 → notify_feishu 直通盯盘群且计数归零；第 11 次（新循环第 1 次）→ 重新投递 agent；跨天日期变更不影响循环连续性；止损触发在预算耗尽/抑噪下仍 notified=true（必达=不被吞）。

**优先级理由**

「先 agent 判断再通知用户」是本需求对通知路径的核心裁定——agent 是判断层，用户看到的是 agent 判断后的结论。

#### R-8 失效投递 agent 裁决闭环

**描述**

标 invalid 的规则投递 agent 裁决：改阈值回 active（清失效标记）/ 退役归 archived；滞留超 24h 升级提醒用户推进。

**来源与证据**

用户 2026-10-22：「失效投递给agent，让agent判断是否修改规则，还是直接把规则改成删除」。

**验收判据**

单测：invalid 投递带 adjust_threshold/retire 建议；PATCH rule_state=active 自动清失效标记回盯盘；PATCH archived 退出一切处理。

**优先级理由**

失效不是终态是待裁决，这是「决策归 agent」的落点。

#### R-9 程序按环境/情绪写死阈值过滤信号（已拒）

**描述**

曾实现为全局环境闸：指数/板块/情绪三维写死阈值，环境不达标时个股信号全部只归档不发送。

**来源与证据**

实测事故：2026-10-22 该闸拿 51 只样本的假涨跌家数比（API 自标 degraded=true）拦截 6 条信号（含真买点伏击确认），完全静默。用户 2026-09-11 裁定「通知是给用户看的事实，不该由机器替用户过滤」，2026-10-22 进一步裁定「这个是 agent 来判断的不应该的程序写死」并指令删除该逻辑。

**验收判据**

该逻辑已于 2026-10-22 从 V1 移除（开关 WATCH_ENV_GATE_ENABLED=false 默认关闭，可回滚）；V2 不再引入任何形式的程序写死过滤。环境数据若需呈现，只能作为通知标注（事实），不得作为拦截条件（决策）。

**优先级理由**

被拒理由：机器过滤信号与用户「事实直发」原则冲突，且写死阈值在数据降级时制造假拦截。不做的代价是零——删除后用户能及时看到全部信号，判断由人/agent 做。

#### R-10 账户绑定路由

**描述**

每条规则绑定账户（`account` 字段），触发信号路由到**该账户对应的 agent**（账户→agent 映射表，现有 `WATCH_ACCOUNT_AGENT_MAP`）处理——不同账户的盯盘信号由各自 agent 负责判断与执行。

**来源与证据**

用户 2026-10-22 原话：「盯盘还要和账户绑定，那个账户要发对应的agent让对应agent处理信息」。

**验收判据**

单测：账户 A 的规则触发 → 通知/待办路由到映射表里的 agent-A，不到 agent-B；账户缺失的规则触发 → 按数据缺陷处理（留痕提醒补归属，不静默丢）。

**优先级理由**

多账户并存时，发错 agent = 判断权和资金账户错配，是资损级错配。

#### R-11 消息模板按判定类型区分

**描述**

不同判定类型（增仓/止盈/止损/减仓/买入范围/失效裁决…）各有专用文案，且**两个通道分开**：
- `feishu_templates`（独立文件）：飞书盯盘群的消息模板，按判定类型各一张（字段、建议动作、时效提示）
- `agent_prompts`（独立文件）：发 agent 的提示词，按判定类型各一份（判断任务说明、上下文结构、期望输出）

两个文件各自独立维护，notify_feishu / notify_agent 分别读取，互不内嵌。

**持仓与非持仓方案不同（D-21）**：文案按「持仓状态 × 判定类型」组织——持仓类（增仓/止盈/止损/减仓）一套方案（含成本、浮盈浮亏、可卖量、建议仓位），非持仓类（买入范围/观察）另一套方案（买点价、失效线、建议试探仓位）；两类的提示词与模板各自独立。

**来源与证据**

用户 2026-10-22 原话：「不同类型的判定，有不同的消息模板。」

**验收判据**

单测：六种判定类型在 feishu_templates 各渲染出关键字段（止损含浮亏与建议卖出量；买入含买点价与失效线）、在 agent_prompts 各产出对应提示词；两个文件各自可 import 且注册表逐类型可查。

**优先级理由**

模板混用会让用户拿到卡不知道怎么操作（今天实测反馈过「建议动作缺失」）。

#### R-12 触发通道字段与每日翻转

**描述**

每条盯盘规则带「是否触发agent」字段（默认**触发 agent**）+ **独立的循环计数**（同一规则 10 次一轮，各规则互不影响），并配**两套并存机制**：

- **当天盘中：10 次一循环**——循环第 1 次触发发 agent 处理；第 2~9 次不处理；第 10 次触发直通盯盘群并计数归零，进入下一循环。
- **跨天：每日收盘定时任务**——把全部规则的循环计数与处理状态清零，次日开盘后所有规则从「循环第 1 次（agent 先处理）」重新开始。

两者分工：循环管当天节奏（同一天内不重复打扰 agent），定时任务管跨天重置（每天重新审视一遍）。

**来源与证据**

用户 2026-10-23 原话：「盯盘添加一个字段是否触发agent（默认agent触发），添加一个定时任务，每天结束了，再把触发agent改成触发」。

**验收判据**

单测：新建规则默认「触发agent」且循环计数=0；循环第1次触发→投递 notify_agent；第2~9次→零投递；第10次→notify_feishu 直通群且归零；第11次（新循环首发）→重新投递 notify_agent；每日收盘任务执行后全部规则计数=0、处理状态='待处理'；次日（任务后）首次触发→投递 notify_agent；两条规则各自独立计数——A 规则循环到第 5 次不影响 B 规则的计数。

**优先级理由**

agent 判断是稀缺资源（token 成本）：新规则首日要 agent 把关，次日直发——这条把「判断的稀缺性」和「通知的及时性」用时间维度分开。

## 失败与并发路径

- **依赖失败（取数/行情源）**：单 symbol 取价失败只让该票本轮失明（隔离，不影响其他票）；上游全部熔断冷却 → 本轮整体跳过且**不计入停牌/退市计数**（非标的故障）。失效判定对无报价的票跳过（不误标 invalid）。
- **超时**：行情提供方调用有超时与熔断；判定模块本身纯计算无外部超时面。通知发送失败 → trigger 落库 notified=false，下拍经补发短路重发同一条（不新建不双发）。
- **数据畸形**：持仓状态读不出/非法值 → fail-open 照常求值并留 state_mismatch 事件（宁可多判不漏判）；条件缺阈值 → 该条件跳过失效判定。
- **并发与重复**：同 tick 同 symbol 共享同一实时价（去重取价，天然一致）；同一规则标 invalid 后退出 active 集合，下拍不再加载——天然幂等防重复投递；持仓状态在读取与写入间翻转时以 fill 实时同步为准、日频对账纠偏。
- **状态机非法迁移**：rule_state 只许 active→invalid→archived 与 invalid→active（裁决回写）；PATCH 非法值 400；启用→停用跳变触发级联归档名下未收敛待办（防死工单）。
- **写路径半成品**：规则创建/更新走仓储白名单 + 守卫（无账户买卖规则拒、宪法止损裸停用拒）；失效投递失败时规则已标 invalid（先落库后投递，投递失败不丢规则状态）。

**与 V1 的关系（替换策略）**：V2 新模块（position_engine / unpositioned_engine）与 V1 的 15 阶段管道并行构建；V1 主循环保留至 V2 验收通过。验收后 V1 主流程下线（开关切换 + 归档）。灰度：先影子模式（V2 只记录不发）对比 V1/V2 判定一致性，再切换。
