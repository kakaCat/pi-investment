## 摘要  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **问题**：成交后没人回写、消息命中不投递、不执行无联动、超时口径失真——四条断点都落在具体文件的具体函数上。
- **方案**：交易包出一个中立成交端口并在真实成交落库后发事件；盯盘包补消息桥、待办关闭联动、执行期限巡检与 sidecar 盘后段；宿主侧加一列证据与一个只读统计端点。
- **影响面**：新建 3 个文件（端口、消息桥、迁移），修改 14 个文件，删除 0 个；不新增外部依赖、不新增服务、不改既有表语义。

## 背景与问题  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

### 需求来源  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

### 现状与代价  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- `AccountTradingService.execute_trade` 是唯一成交写点（订单、成交、持仓、资金在同一事务提交），但它提交之后**没有任何一行业务回调**；唯一填报点是模拟撮合引擎的 `_notify_fill`，agent 走真实成交接口时链路断开。
- `FillSyncService` 的收敛逻辑已存在（买卖两向、幂等、时延落账），缺的只是**事件源**与「卖出清仓后收敛执行待办」的完整挂钩。
- `sla_job` 已有时区偏移导致误报的历史（生产 3 分钟连发 3 张超时卡）；`WATCH_EXEC_SLA_MIN` 在构造指令时被读，但巡检侧零消费。
- `RuleChangeLinkage` 已实现四类动作与审计溯源，全仓仅测试引用，零生产调用。
- `engine._run_sidecar` 在入口处用「交易日 + 交易时段」双门守卫，导致消息扫描服务内部的 08:00–22:00 窗口永远到不了盘后段。

### 为什么是现在  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

改造点全在既有模块内部、全部可开关降级；越晚做，「未执行止损被记成已收敛」污染的历史样本越多。先定实现顺序（端口 → 事件源 → 收敛 → 消息 → 关闭 → 超时 → 统计），可按里程碑逐段验证。

## 目标与非目标  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

### 目标  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **T1**：成交落库到盯盘收敛完成，P95 额外耗时小于 50ms，且回调异常不影响成交返回值。
- **T2**：同一成交号重复投递只收敛一次、只写一次时延。
- **T3**：消息 critical 命中持仓标的或板块时建 1 条 P1 待办并唤醒 1 次；soft 建 0 条；窗口内同标的不重复。
- **T4**：关闭为已忽略并带结构化动作时，规则字段真实变化且审计恰好 1 行（触发溯源非空）；重复关闭返回 409。
- **T5**：期限前 1 分钟不发超时回执、期限后 1 分钟发 1 次、重复巡检仍 1 次；执行待办终态保持未收敛。
- **T6**：统计端点三态计数与待办台账逐项相等，时延 p50/p95 可读，空数据返回 0。
- **T7**：缺列库、未注册监听、未注入消息桥、未装配联动四种降级态下，行为与今天逐字一致。

### 非目标  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **不做 v2 侧自动下单**（D-1）：本设计不新增任何下单调用；成交端口只发事实，不产生意图。
- **不引入事件总线或消息队列**：为一条进程内业务回调引入 pub/sub 会多出异步、顺序、丢失三类语义，收益为零。
- **不动既有表结构与状态机枚举**：只加一列可空证据与一个部分索引；三态沿用已处理/已忽略/已过期。
- **不重构引擎调度骨架**：`_run_sidecar` 只做段落拆分与时间门调整，不引入新线程、不改 tick 主循环。
- **不补齐历史数据**：历史待办证据保持空、历史触发执行明细保持空（空即「无记录」，回填只能造假）。

## 方案总览  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

**一句话方案**：在三处断点上各接一根短线——交易服务多一句 `notify_fill`、盯盘多一个消息桥与一次关闭联动、巡检多一个期限分支；其余全部复用既有收敛器、待办状态机与审计表。

### 成交回写时序（FR-1、FR-2）  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

```text
agent ──POST 交易接口──▶ AccountTradingService.execute_trade
  │ ① 同一事务：订单 + 成交 + 持仓 + 资金 → commit
  │ ② _auto_record_decision → decision_audit_id（拿不到则 None，不虚报）
  └ ③ notify_fill(FillEvent)            ← 提交之后，外层 try/except
        │
        ▼
  fill_listener.notify_fill（qs_trading 中立端口）
        ├─ 未注册监听者 → 返回 False（一行空操作 = 旧行为）
        └─ 已注册 → listener.on_fill(event)；异常被捕获记 fill_listener_error
              │
              ▼
  FillSyncService.on_fill（qs_watch，唯一消费方）
        1) 幂等：trade_id 已在本进程处理过 → 直接返回
        2) 读持仓真值：simulation_positions.shares_total（读失败 → 不猜，保持原状态并记降级）
        3) 状态：>0 → holding；=0 → none（作用于该 account+symbol 的全部规则）
        4) 收敛：sell 且剩余为 0 → 未收敛 P0 执行待办 close(handled, action_kind='trade')
        5) 触发：disposition='handled'，detail.exec 合并 {trade_id, price, latency_sec}
        6) 退役：exit_* 规则 enabled=False + lifecycle_stage='closed'（复用既有退役语义）
```

### 待办关闭时序（FR-5）  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

```text
agent ──POST /api/watch/todos/{id}/close（+ rule_change）──▶ TodoService.close
  ├─ ① 校验：终态合法 → ignored 必填 next_condition → 待办存在 → 未终态 → L3 动作需审计号
  ├─ ② 仓储条件关闭（WHERE terminal IS NULL）：影响 0 行 → 409 已收敛
  └─ ③ 带 rule_change 时调 RuleChangeLinkage.apply(reason, trigger_id 必填, params)
         ├─ 守卫先行：宪法级止损停用/退役必须给理由（写库之前拒绝）
         ├─ rule_repo.update_fields（真实字段变更 + 规则注记追加）
         └─ change_repo.record（watch_rule_changes，含 trigger_id / todo_id / 前后值）
         └─ 两步同一事务：任一步失败整体回滚，不留「规则改了但没审计」
```

### 消息投递与超时时序（FR-3、FR-4、FR-6）  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

```text
sidecar（30s 一拍）
  ├─ 盘中段：摘要门 / 元复核 / 持仓联动 / 板块映射 / 回填 / 池对账（各每日一次，语义不变）
  └─ 盘后段：交易日且 08:00–22:00 → 消息扫描 → 分级命中
        ├─ critical 且命中持仓标的或持仓板块 → news_todo_bridge.dispatch
        │     ├─ 窗口内同标的已有未收敛消息待办 → 跳过
        │     ├─ TodoService.create(level='P1', action_kind='rule_change', evidence=…)
        │     └─ 按归属路由唤醒 agent（失败只记日志，不影响已建待办）
        └─ soft / 未命中 → 维持发卡

sla_job.run_once（既有节奏）
  └─ 执行期限分支：P0 + 交易类 + 未收敛 + 可执行
        ├─ 统一时间基准后比较 now > deadline_at
        ├─ 发 kind='timeout' 回执（一次）→ 唤醒 owner → flow_state='L3' → escalate_count+1
        └─ 期限周期幂等键（todo_id + deadline_at）：重复巡检不再发；不写 expired
```

**关键概念**：成交事实（落库后的投影，不含下单意图）；证据（待办附带的只读载荷，只增不改）；期限周期（同一待办同一期限只催一次，重新建单或延期才进入下一周期）。

## 架构与依赖  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

### 模块划分  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **交易包中立端口**（`qs_trading/application/ports/fill_listener.py`）：只有 `FillEvent`、监听协议、模块级注册位与 `notify_fill` 出口；不 import 任何消费方。
- **交易包成交写点**（`account_trading_service`）：唯一发事件的地方；端口异常不得影响成交返回。
- **盯盘收敛器**（`fill_sync_service`）：唯一消费方；读持仓 → 写状态 → 收敛待办 → 退役规则 → 写证据。
- **消息桥**（`news_todo_bridge`）：消息扫描与待办服务之间唯一的桥；只建待办与唤醒，不碰交易。
- **待办服务与联动**（`todo_service` + `disposition_engine.RuleChangeLinkage`）：关闭是唯一入口，联动负责落地规则变更与审计。
- **巡检**（`sla_job`）：提醒升级节奏与执行期限两个时钟正交，互不改写。
- **组合根**（`factory`）：唯一装配点，负责把桥、联动、监听接上；未装配即降级。

### 依赖方向  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- `qs_watch → qs_trading` 是已声明的单向依赖；交易包只依赖自己的端口，**不知道**盯盘实现，反向 import 会被 import-linter 拦下。
- 端口通过「组合根写入模块级注册位」装配，不引入进程内事件总线、不走 HTTP、不新增包依赖。
- 宿主路由只调应用服务与仓储，不直接碰 ORM 会话；消息桥只在盯盘包内，不新增跨包依赖。

### 外部依赖与降级  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **成交监听未注册**：`notify_fill` 一行空操作 + 返回 False，成交路径与今天逐字一致。
- **消息桥未注入**：两个扫描服务维持只发卡；日志 warn 一次，不重复刷。
- **规则联动未装配**：关闭只收敛待办，不写规则与审计（回滚态）。
- **持仓读失败**：不写状态、不收敛，保持未收敛并记降级——读失败不等于空仓。
- **证据列缺失**（未跑迁移）：读路径返回空、写路径忽略该字段并 warn，建单照常。

## 数据模型  serves: FR-3, FR-6, FR-7

- **唯一变更**：`quant.watch_todos` 新增可空 `evidence jsonb`；新增部分索引 `(symbol, action_kind) WHERE terminal IS NULL`（索引名 `idx_watch_todos_open_symbol_action`）。其余表结构与语义不动：执行时延仍以触发证据里的执行明细为唯一事实源，规则变更仍写既有审计表，超时回执仍用既有回执表。
- **证据形状**（读侧按字典容错，缺键即「无」）：来源（新闻/政策）、级别、告警 id、标题摘要、命中词、扫描时刻。
- **不变量**：证据只增不改；终态一旦写入不再改写；成交号是成交证据的幂等键；未收敛执行待办一标的一账户至多一条。
- **迁移**：`infrastructure/persistence/migrations/20261021_watch_todos_evidence.py`，默认 dry-run 打印语句与预估行数，`--apply` 才写库，`--dsn` 可覆盖连接串；两条语句均带 IF NOT EXISTS，重跑零行变更。
- **迁移与回滚**：不回填历史（空即无证据）；回滚只需保留列与索引——旧代码不读该列，部分索引只影响未收敛行的查询计划，删列会丢证据但不动业务；生产回滚优先「停用读写」而非删列。
- **生命周期**：随待办归档保留；三日自动过期只改终态、不删行，证据随之保留。

#### IF-1 成交回调协议  serves: FR-1, FR-2, FR-3, FR-5, FR-6, FR-7

**语义**

定义「成交之后系统还能知道什么」：账户、标的、方向、数量、价格、成交号、订单号、决策审计号、成交时刻、来源。它是**事实投影**，不含下单意图；实现方只做收敛动作（写状态、关待办、退役规则、写证据），不产生新订单、不改成交结果。端口刻意放在交易包内，因为盯盘已声明依赖交易包、反向不存在；交易包不 import 任何消费方。

**错误码**

无错误码，无返回值约定。实现方必须自吞异常；出口再包一层 try/except，记录 `fill_listener_error` 并带成交号，便于按成交号反查。调用方（交易服务）在两种情况下都不改变已提交的成交、不回滚、不重试成交。

**兼容性**

新增协议，旧代码无引用。`application/trading/paper_trading_engine.py` 继续导出同名符号（转发到新端口），旧 import 路径不破。未注册监听者时为零开销空操作。

**幂等与重试**

调用方不重试。实现方按成交号幂等：重复事件不二次收敛、不二次写时延；部分成交只记进度、不收敛待办。

#### IF-2 成交通知函数  serves: FR-1, FR-2, FR-3, FR-5, FR-6, FR-7

**语义**

进程内唯一出口：读模块级注册位，有监听者就同步调用一次并返回是否被消费。注册/注销各一个函数，注册时只做结构校验（有 `on_fill` 可调用），不 import 实现方。这个函数的语义是「尽力而为的通知」，不是「必须成功的事务分支」。

**错误码**

函数本身不抛错：监听者异常被捕获、记日志、返回 False；未注册返回 False 且不告警（那是正常降级态，不是故障）。

**兼容性**

新增函数。原模拟撮合引擎的成交回调改为调用它，撮合侧外部行为不变；旧调用方继续用转发符号。

**幂等与重试**

不自动重试：重试会把一次成交变成多次收敛风险，收益为零而代价是双写。丢一次回写由巡检与日频对账兜底，不靠重放。

#### IF-3 待办关闭（扩展）  serves: FR-1, FR-2, FR-3, FR-5, FR-6, FR-7

**语义**

一次调用做两件事：给待办终态，以及把「为什么不执行、下次按什么条件动作」落成规则的真实变更。终态为已忽略时必须给下次条件（既有约束）。只有携带结构化动作且终态为已忽略时才触发联动，动作词表固定四类：调阈值（把价格线调出噪音带）、延期（把到期与复核时间往后推）、停用（关规则、保留生命周期阶段）、退役（关规则并终结生命周期）。联动 = 规则字段更新 + 一条审计（含触发溯源、待办溯源、理由、前后值）+ 规则注记追加，三者同一事务；审计写入的动作名沿用既有变更词表，不新造名字。

**错误码**

| 情形 | 码 | 调用方应如何处理 |
|---|---|---|
| 终态非法，或已忽略缺下次条件 | 400 | 修正入参后重试 |
| 待办不存在 | 404 | 放弃，核对 id |
| 待办已收敛（含并发后到者） | 409 | 不重试；读终态确认结局 |
| 动作非法：未知动作、缺参数、缺理由、缺触发溯源 | 422 | 去掉结构化动作或补全后重试 |
| 规则或审计写库失败 | 422 + 可读原因 | 事务已回滚，修正后重试一次 |
| 宪法级止损停用/退役无理由 | 422 | 补理由；这是守卫拦截，不是权限问题 |

**兼容性**

结构化动作与响应里的规则变更结果都是 additive：旧调用方不传时行为逐字不变，旧消费方忽略新增字段即兼容。审计沿用既有表（已有触发溯源列），不加列、不改约束。

**幂等与重试**

重复关闭由仓储条件更新兜住：`WHERE terminal IS NULL` 影响 0 行即 409，台账零改动。联动不做「先查再写」的乐观分支，避免并发下双写规则。

#### IF-4 执行闭环统计  serves: FR-1, FR-2, FR-3, FR-5, FR-6, FR-7

**语义**

只读聚合，回答「止损到底执行没有」：已执行、未执行、未收敛、超时四项计数，加「触发→成交」时延的 p50/p95（秒）。判定口径：已执行 = 终态已处理且动作为交易类；未执行 = 终态已忽略且带结构化动作；未收敛 = 未终态且属执行类；超时 = 已有超时类回执的执行类待办数。治理类待办（规则重叠、元复核）不进分母；空数据返回 0 而不报错。刻意不挂既有预判命中率端点：那是触发后 5/10/20 个交易日方向命中率，混用会同时做坏两个指标。

**错误码**

| 情形 | 码 | 调用方应如何处理 |
|---|---|---|
| 时间窗无法解析或结束早于开始 | 400 | 修正入参 |
| 聚合查询异常 | 500 | 稍后重试；不返回半份数字 |

**兼容性**

新增端点，无版本变更；字段名一次定死，后续只增不改。旧端点返回结构不变。

**幂等与重试**

纯读、天然幂等，可自由重试。

#### IF-5 消息→待办桥  serves: FR-1, FR-2, FR-3, FR-5, FR-6, FR-7

**语义**

把已分级的消息命中变成 agent 看得见的待办：仅 critical 且命中持仓标的或持仓板块才建 P1 待办（动作类型为规则变更类），证据写消息来源、标题摘要、命中词、级别、板块与扫描时刻，并按账户归属唤醒 agent；soft 直接跳过。去重口径：同一标的在同一窗口内已有未收敛的消息待办时跳过，不新增。它是消息扫描与待办服务之间唯一的桥，不产生交易动作、不改规则。

**错误码**

方法不抛错，返回新建、跳过、错误三类结果：单条建单失败只进错误项并记日志（带标的与原因），不中断整轮扫描；扫描任务按错误计数告警。重复命中返回「跳过」而不是错误。

**兼容性**

新增方法，两个扫描服务未注入桥时行为与现状一致（只发卡）。待办证据是新增可空列，旧数据读出为空即「无证据」。

**幂等与重试**

同一轮内按标的去重；跨轮靠「同标的未收敛消息待办是否存在」判定。不自动重试建单（重试会造重复待办），下一轮扫描自然会再命中。

### 错误处理策略  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **分层**：成交主链路 > 回写 > 待办/规则 > 通知。上层绝不为下层失败回滚已提交的业务事实。
- **成交侧**：回写全部包在 try/except，只记日志与计数；不重试、不回滚成交、不改返回值。
- **回写侧**：单笔成交内逐段隔离（读持仓 → 写状态 → 收敛待办 → 退役规则 → 写证据），某段失败只跳过该段并在结果里记错误项，不中断其它段。
- **消息桥**：单条建单失败进错误项，整轮继续；唤醒失败只记日志（待办已建，agent 下一拍仍能从待办列表看到）。
- **关闭联动**：规则更新与审计同事务，任一失败整体回滚并向调用方返回 422 + 原因；不吞错、不留半成品。
- **巡检**：单条待办处理失败不中断整批，统计里记失败计数。
- **重试纪律**：写路径不自动重试（幂等键在数据库层兜住）；读路径（统计）可自由重试；迁移失败按幂等语句重跑。

### 回滚演练与不可逆动作  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

| 性能与容量 | 对成交主链路影响远小于 50ms | 同步进程内调用、无网络、单表更新；消息侧每轮持仓标的数有限，每标的每轮最多一条待办 |
| 文档与支持 | 值班手册补三条处置 | 「回写失败怎么按成交号反查」「超时误报怎么关」「规则被改坏怎么按审计回退」；实施者随里程碑交付 |

### 性能与并发注意点  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

- **成交路径**：回写在提交之后同步执行，读持仓 1 次 + 未收敛待办查询 1 次（走部分索引，命中索引前缀 `symbol + action_kind`，条件 `terminal IS NULL`）+ 更新若干（不超过该标的规则数）。压测口径：本地库单笔回写 P95 小于 50ms；不引入任何外呼。
- **索引**：部分索引只覆盖未收敛行，写放大与索引膨胀都可控；查询条件必须写成「标的 + 动作类型 + 终态为空」才能命中，禁止在 SQL 里对该列做函数包覆。
- **并发**：同一成交号并发重复投递由「终态已写 → 条件更新影响 0 行」兜住，表现为幂等跳过而不是报错；不同成交并发收敛同一标的时，先到者改状态与规则，后到者读到的持仓已是新真值，结果一致。
- **锁顺序**：先读持仓（只读）→ 再关待办（单表单行条件更新）→ 再改规则（同表批量）→ 最后写证据；不跨表长事务，每段短事务并在段间归还会话，避免盯盘线程长期 idle in transaction。
- **巡检**：单线程串行、30 秒一拍；执行期限分支只处理未收敛可执行待办，按到期时间排序并限批，避免一次拉全表。
- **sidecar**：盘后段与盘中段串行执行同一线程，不并发；消息扫描内部 15 分钟节流，盘后段每拍调用不会放大外呼次数。
- **消息桥**：一轮按持仓标的数线性，每标的每轮最多一条待办；去重查询走部分索引，随待办增长不退化为全表扫。

## 常见问题  serves: FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8

| 问题 | 回答 |
|---|---|
| 端口为什么不放盯盘包？ | 反向依赖会被 import-linter 拦下；盯盘已声明依赖交易包，端口只能在交易侧。 |
| 为什么不用事件总线或消息队列？ | 单进程、单消费方、低频业务回调；引入 pub/sub 会多出异步、顺序、丢失三类语义，收益为零。 |
| 回调同步执行会不会把成交拖死？ | 回写在提交之后，异常两层兜住，最坏是没回写；压测口径 P95 小于 50ms。 |
| 重复投递靠什么幂等？ | 靠成交号 + 待办条件更新：终态已写时条件更新影响 0 行，表现为跳过而不是报错。 |
| 回写失败要不要重试？ | 不自动重试。重放会把一次成交变成多次收敛风险；丢一次由巡检与日频对账兜底。 |
| 交易量涨 10 倍先坏在哪？ | 先坏在收敛器逐标的读写与巡检批量的查询频次，不是索引；缓解手段是限批与把证据写入延后到同事务外。 |
| 谁半夜被叫起来、手上有什么？ | 值班；手上有按成交号可搜的日志、按待办 id 的回执计数、按规则 id 的审计前后值，以及四个降级开关。 |
| 数据错了怎么修？ | 状态错：关状态门后按持仓表修正；规则错：按审计前后值反向应用；证据错：证据只增不改，追加新证据不覆盖旧值。 |
| 这个决定错了多久能发现？ | 一天：执行证据非空率、超时回执数、状态对账差值三项日频对账，任一异常当天可见。 |
