# 盯盘执行闭环三接缝 需求池（REQ-261021194640-69b8）

> 本文是 PRD 的上游：回答「这些诉求成立吗、凭什么排前面、哪些决定不做」。
> 本期范围由用户裁定：只补三条接缝——成交回写、消息投递、待办闭环。

## 摘要

**TL;DR**：盯盘能发指令、agent 能下单，但成交后没人回写——待办悬空、持仓状态失真、统计撒谎。
本期只补三条接缝：成交回写、消息投递、待办闭环。
做完后每条触发都有可追踪结局，止损执行没执行能被统计和复盘看见。

- **要解决什么**：盯盘能发指令，但 agent 成交之后没人回写；待办不关、持仓状态滞留、止损是否执行说不清。
- **来源与证据强度**：代码审计逐行定位 + 生产台账对账（`watch_triggers.detail` 含执行明细 0 行、P0 待办 #107 悬空）+ 用户两次直接裁定。
- **本轮结论**：8 条需求全部进 PRD（R-1～R-8）；被明确排除的 6 项见「边界（不做什么）」；无被拒需求，2 条延后。

## 业务流程图

```
交易日
  │
  ├─ 盯盘引擎（60s / 10s）──触发──▶ 指令卡 ──▶ 待办 + 唤醒 agent
  │                                              │
  │                                              ▼
  │                                      agent 做最后判断
  │                                       │             │
  │                                    执行卖出       不执行
  │                                       │             │
  │                                       ▼             ▼
  │                                下单 /trade     close(ignored)+next_condition
  │                                       │             │
  │                                       ▼             ▼
  │                            成交回写（FillEvent）  规则变更 + 审计(trigger_id)
  │                                       │
  │                                       ▼
  │                        待办 handled / exit 规则退役 / 状态→none
  │
  ├─ 消息扫描（盘中 + 盘后）──critical 命中持仓──▶ P1 待办 + 唤醒 agent
  │
  └─ 日频 ──▶ 闭环统计可读（exec/stats）与人读日报
```

- **收集方式**：对 `packages/qs_watch`、`packages/qs_trading`、宿主路由做逐节点审计（4 路并发、全部带 file:line 证据），再用生产库与日志做二次对账。时间范围 2026-10-21 19:00–19:45。
- **样本**：盯盘引擎 15 阶段流水线、执行指令卡/待办/SLA、成交写点、消息监控与政策通道、复盘回填；生产侧 `watch_triggers` 2336 条、`watch_todos` 107 条、`watch_outcome_checks` 2058 行。

## 产品定义

盯盘执行闭环的「最后一公里」：把 agent 的真实成交、消息判断与「决定不执行」，回写成系统可追踪的终态。
核心价值：从「喊了止损但不知道卖没卖」变成「每条触发都有结局，且结局可统计、可复盘」。
与现状的区别：现状通知一到待办就断链——成交不回写、消息不投递、不执行没有规则联动。

## 干系人与角色

| 角色 | 关注点 | 影响程度 | 决策权 |
|---|---|---|---|
| agent（自主交易员） | 成交后系统能不能立刻知道；会不会反复喊建仓 | 高 | 执行者（下单与最终判断） |
| 投资人 | 止损到底执行没有；消息有没有人跟 | 高 | 决策（范围与验收） |
| 运维/复盘 | 超时是否误报；统计口径是否可信 | 中 | 建议 |
| 交易服务 | 回写会不会拖慢或影响成交 | 中 | 建议（接口约束） |

| 角色 | 什么场景用 | 痛点 |

## 需求明细

#### R-1 卖出成交回写并收敛待办

**描述**

agent 经交易接口卖出成交后，系统在成交落库后把成交事实通知盯盘；盯盘收敛该标的未收敛的执行待办（终态已处理）、退役退出类规则、把持仓状态翻为无持仓，并把成交价、数量与「触发→成交」时延写入证据。非盯盘来源的卖出同样收敛，来源写进证据。

**来源与证据**

代码审计：成交回调只在模拟撮合引擎发生（`application/trading/paper_trading_engine.py` 的 `_notify_fill`），真实成交写点 `account_trading_service.execute_trade` 零通知；生产 `watch_triggers.detail` 含执行明细 0 行，P0 待办 #107 仍 open。

**验收判据**

端到端用例：触发 → 建待办 → 模拟卖出成交 → 断言待办终态已处理、触发处置已处理、退出规则退役、状态无持仓、证据含成交号与成交价与时延，退出码 0；同一成交号重复投递只收敛一次。

**优先级理由**

这是唯一会造成「未执行止损被统计成已收敛」的资损口径问题；不做则待办永远悬空，SLA 与统计全部失真。

**依赖与假设**

依赖交易服务成交唯一写点；依赖既有成交回调端口与待办状态机。

#### R-2 买入成交后状态秒级转持有

**描述**

agent 买入成交后，系统立即把该标的（含账户）的规则持仓状态改为持有；下一拍起入场类规则不再对该标的求值，退出类规则开始生效。

**来源与证据**

审计发现持仓状态唯一写点是成交回执与一次性迁移回填，日频对账不写该字段；买入后入场规则按空仓继续求值，会重复喊建仓。

**验收判据**

用例：买入成交 → 规则状态为持有 → 下一拍入场规则被状态门跳过且止损规则照常求值，退出码 0；生产抽查 1 例，成交后秒级与持仓表一致。

**优先级理由**

与 R-1 互为反向，缺一半就会出现「买了还喊建仓」或「卖了还喊止损」，直接制造错误信号。

#### R-3 消息 critical 命中持仓 → P1 待办 + 唤醒

**描述**

公告/政策达到 critical 且命中持仓标的或持仓板块时，系统建 P1 待办（附消息摘要与命中依据），按责任归属唤醒 agent；soft 级别维持发卡、不建待办。同一消息/标的在去重窗口内不重复建单。

**来源与证据**

审计：消息命中只进回执发送（`watch_channels` 的 `news_alert`），不建待办、不唤醒；政策通道同款。用户 2026-10-21 选择该口径（D-3）。

**验收判据**

用例：critical 命中持仓 → 待办 1 条 + 唤醒 1 次；soft 命中 → 待办 0 条；同一消息重复扫描 → 待办数不增。退出码 0。

**优先级理由**

没有这一步，「消息破坏交易逻辑→提前离场」在系统里根本不会发生（agent 不知道有这条消息）。

**依赖与假设**

依赖既有待办创建与 owner 路由；依赖消息分级结果可信。

#### R-4 盘后消息可扫

**描述**

交易日 15:00–22:00 的消息扫描照常执行，盘后公告不再漏扫；其它日频任务节奏保持不变。

**来源与证据**

审计：sidecar 在非交易时段直接返回，消息服务内部的 08:00–22:00 窗口因此永远到不了；生产日志今日最后一轮扫描 14:52。

**验收判据**

用例：时钟设为交易日 16:30 → 消息扫描执行，回填/生命周期等日频任务不重复执行，退出码 0；生产日志核查 15:00 后存在扫描轮次。

**优先级理由**

盘后公告是消息面最主要的风险来源；不做则 R-3 只在盘中有效，夜间隔夜风险失察。

#### R-5 不执行 → 改规则联动

**描述**

agent 对待办选择不执行并给出下一次条件时，系统把处置卡的动作项落成规则变更（阈值/冷却/停用/退役之一），并写一条带触发溯源的规则变更审计；重复关闭返回冲突而非重复改。

**来源与证据**

审计：`RuleChangeLinkage` 已实现但全仓仅测试引用，零生产调用；规则更新接口也不写审计。

**验收判据**

用例：关闭为已忽略 → 规则字段变化 + 审计 1 条（含触发 id），退出码 0；未接线时该用例失败（先红后绿）。

**优先级理由**

不做则「不执行」只是一句口头结论，规则照旧，下次同样触发——闭环只剩一半。

#### R-6 执行期限与超时收敛

**描述**

执行待办到真实期限仍未收敛时，系统发一次超时回执并升级催办；同一期限周期只发一次；未执行不得被记成已收敛。

**来源与证据**

审计：执行期限环境变量全仓零消费；`sla_job` 时区 +8h 导致生产 3 分钟连发 3 张超时卡；3 天后被过期归档并计为已收敛。

**验收判据**

时区矩阵单测（带时区/裸时间/跨日）通过；用例：期限前 1 分钟不发、期限后 1 分钟发 1 次、重复 tick 不重发，退出码 0。

**优先级理由**

超时是「执行/不执行」之外唯一兜底；口径错则保护失效且统计撒谎。

#### R-7 闭环统计可读

**描述**

人/agent 能查询执行闭环三态（已执行/未执行/超时）计数与处理时延分位；空数据返回 0 而不是报错；治理类待办不计入分母。

**来源与证据**

审计：执行统计端点不存在；现有触发统计先取 200 行再过滤，今日 232 条必截断；交易绩效无盯盘归因。

**验收判据**

接口用例：构造三类样本 → 计数分别命中、分位可读，退出码 0；与待办台账同口径查询一致。

**优先级理由**

没有统计就无法回答「止损到底执行没有」，也无法验收前六条。

#### R-8 自动补挂规则带持仓状态

**描述**

日频持仓联动为新持仓补挂止盈/减仓规则时，创建即写入持有状态，保证下一拍可被求值；旧规则不回填，缺列库按旧行为放行。

**来源与证据**

审计：补挂时未传状态，DB 默认无持仓；状态门对退出族 + 无持仓直接跳过——新持仓止盈永不触发（当前库无实例，属潜在漏保护）。

**验收判据**

用例：模拟补挂 → 规则状态为持有 → 下一拍参与求值，退出码 0；不写状态时该用例失败（可复现）。

**优先级理由**

这是状态机改造留下的反向缺陷，代价是「悄悄没有止盈保护」，必须与 R-1/R-2 同批修。

## 失败与并发路径

- **成交回调失败**：成交已落库，回调异常只记日志并重试一次；不回滚成交，不把待办误判为已收敛。
- **重复成交事件**：同一成交号重复投递只收敛一次，时延只写一次（幂等键 = 成交号）。
- **部分成交**：不收敛待办，保持未收敛；剩余仓位成交或清仓后收敛。
- **消息重复命中**：同一窗口内同一标的/同一消息只建一条待办；重复扫描不新增。
- **并发关闭同一待办**：后到者返回冲突（400 系），台账零改动。
- **超时与关闭竞态**：先关闭者生效；超时巡检发现已收敛则跳过，不发回执。
- **状态机**：待办 未收敛 → 升级 → 已处理/已忽略/已过期；非法迁移拒绝并给可读原因；执行超时不是终态。
- **写路径半成品**：规则变更与审计同事务；任一步失败整体回滚，不留「规则改了但没审计」。

## 边界（不做什么）

- 不做 v2 侧自动下单：下单与最后判断永远是 agent 的事（D-1）。
- 不做一等公民「交易计划」实体与开机一屏：留待下一期。
- 不做盘中实时指数与板块/大盘资金流：数据面属另一条线。
- 不做减仓数量化：指令仍为清仓口径，分批减仓由 agent 自行裁量。
- 不改自动兜底止损（30 分钟百分比）行为：保留作为最后防线。
- 不做消息语义自动判定「是否破坏逻辑」：判断在 agent，本期只保证消息送到。
