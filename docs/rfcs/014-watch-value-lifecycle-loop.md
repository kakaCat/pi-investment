## 1. v1 错在哪（自我修正）

| v1（错） | v2（对） |
|---|---|
| 把闭环设计成**工程调参回路**：响了→判→改阈值→更准 | 闭环是**投资生命周期**：盯盘服务于 agent 的价值判断，触发只是 agent 的**检查点** |
| 退出 = 清理僵尸规则（零触发/漂移就退役） | 退出 = **价值证伪**（不买了）或**交易完成**（卖完了）；生命周期自然终点，不是卫生打扫 |
| 反馈边 = 调阈值/调分级 | 反馈边 = **agent 对价值的再判断**；改规则只是它的产出之一 |
| 触发即动作 | **触发 ≠ 执行**：买卖节点必须 agent 介入做最终判断 |

## 2. 三条铁律

1. **触发 ≠ 执行**——买卖节点只唤醒 agent，最终判断由 agent 做（这是 L2 行动态的定义）
2. **每条规则必须挂在某个意图上**（为什么盯它、触发后要做什么）——**无主规则＝烂账**（2026-09-11 清掉的那些正是无主意向）
3. **回路没有终点**——清仓后回到「发现价值」，不是结束
4. **规则不能无限期盯下去**——每条规则必须有复核周期，到期必须被 agent 看一次；
   规则反复触发或长期静默都要回到 agent 重新判断（见 §13），不允许一条规则钉在那里自动跑


## 2.5 定位：盯盘是「紧盯市场情况」的工具（2026-09-11 用户定位）

**盯盘首先是 agent 的市场感知工具（眼睛），不是只服务持仓的监控器。**
前面的 v1/v2 框架都隐含把盯盘绑在「价值→买入→持仓→卖出」上，这是窄化。
正确的定位是：**agent 用它持续感知市场，持仓只是其中一个用途。**

### 观察对象分三层（scope）

| 层 | 看什么 | 典型规则 |
|---|---|---|
| **市场级** | 指数关键位、板块资金与轮动、涨停家数与连板高度、量能、情绪分、异动 | 指数跌破/站上关键位、板块资金异动、涨停家数骤降、情绪转极端 |
| **标的级** | 个股趋势/结构/关键位/量价异动（无论是否持有） | 趋势观察、突破/破位、放量异动、回踩确认 |
| **持仓级** | 买卖节点（止损/止盈/减仓/加仓/做T） | 卖出规则族、加仓规则、做T区间 |

### 感知产出的三种去向（多数不是交易）

1. **更新 agent 对市场的认识**（绝大多数）→ 落 `auto_observed`，**不产生任何动作**，但进了 agent 的上下文
2. **触发价值发现** → 从「市场级/标的级观察」升级为「买入跟踪」
3. **触发交易判断** → 买卖节点（持仓级）

> 推论：**`auto_observed` 是主力状态而不是异常状态**。「盯盘响了但不用做事」是常态，
> 只有极少数触发才应该走到 `handled`（有动作）。这也解释了为什么 token 预算必须与触发数解耦。

### 工程缺口（要做到「紧盯市场」必须补）

现 WatchEngine **只支持个股**：`tick()` 走 `quote_service.get_realtime_quote(rule.symbol)`，
`symbol` 是个股代码。要做到市场级盯盘，需要：

| 缺口 | 说明 |
|---|---|
| 标的类型 | rules 增加 `scope`（market/sector/symbol/position）与 `target`（如指数代码、板块名、市场指标名） |
| 取数通道 | 指数行情、板块行情、市场情绪/量能/涨停家数需要 tick 级取数（现有工具是准实时但非 tick） |
| 判定器 | 指数/板块/指标类条件的求值（现在 conditions 只认个股 quote） |
| 汇总形态 | 市场级感知**按固定节拍汇总成「市场状态」**，不逐条打扰（与元触发共用摘要机制） |

## 3. 盯盘的三类用途（规则族）

| 族 | intent | 触发后 agent 要回答 |
|---|---|---|
| **趋势观察** | `trend_observe` | 趋势/结构变了吗？继续观察 / 升级为买入跟踪 / 取消盯盘 |
| **买入跟踪** | `entry` | 买不买、买多少？（买则同时给出卖出规则） |
| **持仓管理** | `exit_stop` / `exit_take_profit` / `exit_reduce` / `add_position` / `t_trade` | 卖多少 / 加多少 / 做T区间怎么定？ |

> 盯盘不只为买卖点——**趋势观察本身就是一个正当用途**（无交易意图）。

## 4. 生命周期（规则随价值状态走）

```
①发现价值 ──→ ②跟踪价值 ──→ ③买点触发 ──→ ④agent 判 ──→ ⑤买入
                  │                                    │
                  │ 判"没价值"                          │ 同时给出：
                  ▼                                    ├─ 卖出规则（止损/止盈/减仓）
              取消盯盘                                  ├─ 加仓规则
              （回到①）                                 └─ 做T规则（围绕底仓区间）
                                                        │
                                       ⑥ 持仓：卖出规则族持续盯 ──→ ⑦卖点触发
                                                        │
                                                  ⑧agent 判 ──→ ⑨减/清
                                                        │
                                        ⑩卖完 → 取消卖出规则族
                                                        │
                                     ⑪回到①：agent 再判断还有没有值得跟踪的价值
```

**卖出侧同理**：卖点触发 → agent 判断 → 改规则继续盯 / 执行卖出 / 卖完收摊或转回观察。

## 5. agent 在每个检查点的输出 = 一次「规则重配置」（可含动作）

| 选项 | 说明 |
|---|---|
| 改规则继续跟踪 | 调阈值/换方向/续期（价值还在，但条件不再合适） |
| 执行买入 + 挂卖出规则 | 买点确认：买入并立即给出止损/止盈档 |
| 执行买入 + 加仓规则 | 分批建仓场景 |
| 执行买入 + 做T规则 | 设定区间高抛低吸（围绕底仓，用可卖数量） |
| 减仓 / 清仓 | 卖点确认；清仓后**取消卖出规则族** |
| 清仓 + 转观察 | 还想继续看趋势 → 转 `trend_observe` |
| 判不动 | 保留规则 + 必须写 **NEXT 条件**（下次什么情况下才动） |

## 6. 层级 = agent 的状态（双向可达）

| 状态 | 含义 | 是否唤醒 LLM |
|---|---|---|
| **L0** | 纯信息 | 否 |
| **L1** | 观察态（含趋势观察、买入跟踪的日常） | 日终汇总 1 次 |
| **L2** | 行动态：**买卖节点**，agent 必须终判 | 摘要批量 |
| **L3** | 交接态：超授权/涉资金/不可逆 → 交人 | 生成决策请求 |

**双向**：L1→L3、L2→L3 成立；**L3→L2 / L3→L1 同样成立**（用户答完回到执行或继续观察）。

## 7. 通道（飞书只通知，不承载决策）

- **飞书**：单向事实广播；**一律不含"等你确认"语义**
- **决策请求**：走交互会话的 `ask_user_question`（用户 2026-09-11 选定通道 A）
- L3 待决策项入**待决策队列**；非交互场景（定时唤醒）**不得替用户决策**

## 8. 底层机制（已实现，继续用——这是"运输层"）

去重合并（同标的同向 60s）｜分级 L0/L1/L2｜摘要式批量唤醒（唤醒次数与触发数解耦）｜
处置状态机（pending/auto_observed/deduped/escalated/handled/ignored/expired）｜处置 API 与留痕｜
周度卫生审计。**这些不因模型修正而废弃**——它们负责把信号准确、便宜地送到 agent 面前。

## 9. 数据模型要补的（本 RFC 的核心新增）

`quant.watch_rules` 增列：

| 列 | 含义 |
|---|---|
| `intent` | 规则意图：`trend_observe` / `entry` / `add_position` / `t_trade` / `exit_stop` / `exit_take_profit` / `exit_reduce` |
| `lifecycle_stage` | `discovered` / `tracking` / `entry_triggered` / `holding` / `exit_triggered` / `closed` |
| `linked_account` | 关联账户（买入/卖出归属哪个盘） |
| `created_from` | 溯源：哪次触发/哪次判断生成了这条规则（无源规则＝可疑） |
| `next_action_hint` | 触发后 agent 该做什么（与预案 `context` 配合） |

**规则重配置 API**：批量 create / update / retire + 强制审计（每次重配置写 `decision_audit`，关联触发 id）。

## 10. 退出（按价值生命周期，不是按"僵尸"）

| 场景 | 动作 |
|---|---|
| 跟踪期判「无价值」 | **取消盯盘**（回到发现） |
| 买点触发但判「不买」 | 改规则继续跟踪，或取消盯盘 |
| 清仓完成 | **卖出规则族全部退役**；转 `trend_observe` 或彻底收摊 |
| 逻辑证伪 / 结构破坏 / 事件过期 | 取消盯盘 |
| 非交易日 / 数据源降级 / 熔断期 | **暂停**（可恢复，不算退出）：降级期只记录不行动 |
| 交接等待 | 超时保持原状，**绝不"没人管就自动执行"** |


## 13. 元触发：频次与超时必须回到 agent（2026-09-11 用户补充）

价格触发之外，**规则自身的健康度**也要触发 agent 介入——因为一条规则如果永远挂着，
它就会退化成 2026-09-11 清掉的那批「无主烂账」。

| 元触发 | 判定条件 | agent 必须处理什么 | 默认分级 |
|---|---|---|---|
| **频次超限（一直响）** | 同一规则在 1 个交易日内触发 ≥ N 次（实测：#105 单日 10 次、#119 单日 25 次） | 阈值是否已失真？该转阶段（买入跟踪→持仓）？还是该**取消盯盘**？ | L1 提请（**不逐条通知**，一次汇总提出） |
| **静默超时（一直不响）** | 距创建/上次复核 ≥ T 且零触发 | 价值还在吗？续期 / 调整条件 / 取消盯盘 | L1 进日终与周度复核 |
| **阶段滞留** | lifecycle_stage 停留 ≥ T_stage | 卡在哪一环？推进（买/卖）还是回退（重估） | L1 |
| **规则到期** | expires_at 临近 | 续期还是收摊 | L1 |

**与「去重」的区别（互补，别混）**：
- 去重解决「**同一次**跌穿不要响多次」（60 秒窗内合并）
- 元触发解决「**同一条规则长期反复响 / 长期不响** → 规则本身需要重新评估」

**机制**：元触发与价格触发**走同一个摘要唤醒**（一次唤醒批量处理），不额外增加唤醒成本。

**数据模型补充**：

| 列 | 含义 |
|---|---|
| last_reviewed_at | 上次被 agent 复核的时间 |
| review_interval_days | 复核周期（按意图默认：entry 7 天 / holding 3 天 / trend_observe 14 天） |
| review_due_at | 下次复核到期（**到期必被 agent 看一次**） |
| burst_count_window | 窗口内触发计数（频次超限判定用） |

## 11. Token 预算（与触发数解耦）

微循环 0 ｜ L1 日终 ≤1 ｜ L2 摘要 ≤4 ｜ 宏观（价值复核/规则重配置）≤2 ｜ 合计 **≤8 次 LLM/日**，不随触发数增长。

## 12. 实施顺序（先定稿、后动代码）

| 阶段 | 内容 | 验收 |
|---|---|---|

## 14. 核心判据：agent 何时介入 · 盯盘何时退出（2026-09-11 用户定调）

> 用户原话：「核心是 agent 何时介入、盯盘何时退出，要认真设计。所有都让 agent 介入，
> token 消耗承受不起，会导致利润和成本不一致。**你的目标就是挣高额利润。**」

### 14.1 先把成本算清楚：token 不是大头

以当前账户（总资产 105,120 元、持仓 13,444 元、现金 91,676 元）为例：

| 成本项 | 量级 | 性质 |
|---|---|---|
| 直接 token 成本 | 一次摘要唤醒 ≈ 数千 tokens ≈ **0.0x 元** | 可控、可预测、可优化 |
| **判断错误成本** | 一次错误动作 ≈ **数百元**（单标的 5–8k 仓位 × 5–10%） | **不可控，才是大头** |
| 注意力 / 信噪比 | 噪声淹没真机会 —— 今天实测：单日 42 次触发里真正值得动作的极少 | 隐性但致命 |

**结论**：把不必要介入砍掉，理由**不是省钱，而是减少犯错机会、保住信噪比**——
方向对，但要按"利润"而不是按"token"来算账。

### 14.2 介入判据：五道门必须同时过，否则机械归档（零 LLM）

| 门 | 内容 | 建议阈值 |
|---|---|---|
| ① **意图门** | 该规则有明确交易意图（entry / exit_* / add_position / t_trade），且我有仓位或明确买入意向 | **趋势观察类不介入**（只归档） |
| ② **金额门** | 该动作影响 ≥ 账户的 X% | 建议 **1% ≈ 1,050 元**（低于此，做对了也不值得一次介入） |
| ③ **增量门** | 同一标的、同一议题在冷却窗内未被介入过 | 建议 **4 小时 / 标的** |
| ④ **节点/异常门** | 计划内买卖节点，或显著偏离预期（异常） | 计划节点必介入；异常另设阈值 |
| ⑤ **经济门** | 期望收益 × 命中率 > k × 介入成本 | k ≈ 3（含错误风险成本，不只 token） |

**不满足 → `auto_observed`（零 LLM）**，进日终汇总；满足 → 进摘要队列，按节拍批量唤醒。
（趋势观察类触发永远走第 1 类去向：**只更新认识，不介入**。）

### 14.3 退出判据：规则的价值账本

每条规则维护 4 个计数：

| 字段 | 含义 |
|---|---|
| `valuable_actions` | 带来**有价值动作**的次数（买了/卖了/有效调整） |
| `interventions` | 被 agent 介入（唤醒处理）的次数 |
| `noise_triggers` | 只响不办事的次数（触发但结论是"不动"） |
| `last_value_at` | 最近一次产生有价值动作的时间 |

**退出（退役：disable + 归档，不物理删）——任一成立**：
1. **价值证伪**：建规则的论据被推翻
2. **交易完成**：买入完成 → 买点规则退；清仓完成 → 卖出规则族退
3. **边际价值归零**：`valuable_actions = 0` 且（龄 ≥ T 或触发 ≥ N）
4. **成本 > 收益**：`interventions × 单次介入成本 > 该规则贡献的收益`
5. **信息枯竭**：长期停牌 / 退市 / 无波动
6. **被替代**：被更完整的规则吸收（如今天 601600 六条 → 一条三档缓冲带）

### 14.4 北极星指标（衡量"是否在挣钱的方向上进化"）

**单位唤醒产出 = 有价值动作数 ÷ LLM 唤醒次数**

要优化的就是这个比值——不是"唤醒了多少次"，也不是"规则有多少条"。
配合：触发→处置率、平均规则寿命、噪声比（noise_triggers ÷ 总触发）。
