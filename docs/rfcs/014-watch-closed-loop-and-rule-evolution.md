- **作者/窗口**：investor / w-c8cae280
- **日期**：2026-09-11
- **上游**：[RFC 013 处置状态机](./013-watch-trigger-disposition-state-machine.md)（Phase 1 已实现）

## 1. 为什么需要本 RFC（对 RFC 013 的自我修正）

RFC 013 把处置设计成**有终态的一次性状态机**——这是错的。用户评审指出：

> "没有把 L1/L2/L3 的闭环流程设计出来；agent 还可以改规则；**不是结束，是一个一直循环的能力**；
> 在哪些场景退出要设计。"

正确的模型是**永续控制回路**：

- **单条触发**确有终态（handled/ignored/expired）——013 只对到这一层
- **规则与回路没有终态**，它们是循环：触发 → 处置 → **归因** → **改规则** → 新触发
- 013 缺失三条边：①分层各自的回路与节拍 ②**反馈边（agent 反改规则）** ③**退出/暂停边**

### 现有设施缺口（实测，2026-09-11）

| 能力 | 现状 |
|---|---|
| 触发→处置 | ✅ Phase 1 已交付 |
| 规则生命周期（退役/TTL/复核） | ❌ **完全缺失**——只有手动 `DELETE /api/watch/rules/{id}`，无任何清理任务 |
| 规则字段修改 | ⚠️ 仅 `enabled` 可改（`update_fields` 白名单不含 conditions/action_hint/expires_at/account） |
| 规则卫生 | 53 条 / 33 启用；**6 条无过期时间**；**13 条 `escalation_policy` 为空**；1 条 `action_hint` 空；同标的重复最高 601600×6、600887×4 |
| 自动建规则入口 | `opportunity_to_watch_rule_service`（L1/observe + 默认 TTL），是回路的"创建边" |
| 治理节拍 | 无日终/周度的规则复核任务 |

## 2. 回路总览：三层嵌套循环

```
┌─ 宏循环（日 / 周）──────────────────────────────────────────────┐
│  归因 → 规则演化（调阈值 / 调分级 / 新建 / 合并 / 退役）→ 退出检查  │
│    ▲                                                    │        │
│    │ 证据（触发序列+处置结果+盈亏归因）                    ▼        │
│  ┌─ 中循环（日内）──────────────────────────────────────┐ │        │
│  │  触发簇汇总 → 判断（结构变没变）→ 动作 → 结果回填      │ │        │
│  │    ▲                                        │        │ │        │
│  │    │                                        ▼        │ │        │
│  │  ┌─ 微循环（实时 tick）──────────────────────────┐   │ │        │
│  │  │ 条件判定 → 去重 → 通知 / 落库（零 LLM 为主）  │   │ │        │
│  │  └──────────────────────────────────────────────┘   │ │        │
│  └─────────────────────────────────────────────────────┘ │        │
└─────────────────────────────────────────────────────────────┘
        ▲                                                     │
        └──────────── 规则变更（收紧自动 / 放松需人工）──────────┘
```

## 3. 分层闭环（L0 / L1 / L2 / L3）

> 说明：现有实现只有 **L0/L1/L2**（`TriggerLevel`）。用户提到 L3——本 RFC 提出 **L3 = 人机交接层**
> （不是"更自动的层"，而是"必须由人决定"的场景），见 3.5 与第 8 节待确认问题。

### 3.1 L0 信息层（零 LLM）

| 项 | 设计 |
|---|---|
| 触发 | 事件/公告/纯信息类条件 |
| 回路 | 通知 → 落库(`auto_observed`) → **周期价值复核**（周度：这条信息有人看吗/还有效吗） |
| 节拍 | 实时通知；周度复核 |
| 反馈边 | 有价值 → **升级为 L1**；连续 N 天无人查看且无升级 → **静音/退役** |
| 退出 | 事件已过（`expires_at`）/ 无价值退役 / 标的归档 |

### 3.2 L1 观察层（零 LLM，日终一次汇总）

| 项 | 设计 |
|---|---|
| 触发 | 价格/量能观察类（`action_on_trigger=observe`） |
| 回路 | 实时触发（直发飞书、去重、落 `auto_observed`）→ **日终把这批触发打包成一次汇总**给 agent → agent 判断"结构是否变化" |
| 日终三选一 | ①维持观察（重新武装，回微循环）②**升 L2**（进入行动层，需证据）③**调参**（阈值不合理→调宽/调窄）或**降级 L0** |
| 节拍 | 实时 + 日终 1 次 |
| 退出 | 价格反向穿越（回未触发态，正常循环）/ 结构证伪 → 退役 / 连续 N 日触发但无结构变化（噪声）→ 调宽或降级 |

### 3.3 L2 行动层（摘要唤醒 agent）

| 项 | 设计 |
|---|---|
| 触发 | `trigger_level=L2` 或 escalation_policy 命中 |
| 回路 | 触发 → 进摘要队列 → **批量唤醒**（盘中定时 + 盘后）→ agent 决策（不动/减/清/加，走 R-001~R-009）→ 执行或挂单 → **结果回填** → 归因 → **驱动规则演化** |
| 唤醒成本 | **与触发数解耦**：队列空则不唤醒；单日上限见第 6 节 |
| 反馈边 | 动作完成 → 规则使命可能结束（退役/转反向）；判"不动" → 必须写 **NEXT 条件**（下次什么情况下才动），否则视为无效处置（`ignored` 必须有 reason + next_condition） |
| 退出 | ①动作完成（清仓/减半/加仓完毕）②连续 N 次 escalated 均判"不动" → 阈值不合理 → 自动提案调参或降级 ③持仓归零且无观察理由 → 退役 |

### 3.4 L3 人机交接层（新增，需确认）

**定位**：不是"更高级的自动化"，而是**回路必须停等人类决策**的场景。停等 ≠ 退出。

| 场景 | 为什么必须人定 | 停等期行为 |
|---|---|---|
| 资金变动（出入金、大额调仓） | 超出 agent 授权 | 保持原状 + 记录，不擅自行动 |
| 策略级规则改动（放松保护、批量退役） | 见第 4 节非对称护栏 | 出提案等确认；超时保持原状 |
| 熔断后重开交易 | 宪法级风控 | 只读，禁止新开仓 |
| 单笔超限 / 跨账户冲突 | 账户治理 | 挂起该触发，通知用户 |
| 数据源降级期产生的行动触发 | R-011/R-013 精神 | 降级为"待复核"，不下单 |

**超时策略**：超过 N 小时未获人工答复 → 保持原状 + 写入未处置清单（**绝不"因为没人管所以自动执行"**）。

## 4. 反馈边：agent 改规则的能力与护栏

### 4.1 能力清单（回路输出）

| # | 能力 | 触发场景（回路信号） | 当前可实现性 |
|---|---|---|---|
| 1 | **调阈值** | 阈值被反复穿越但无结构变化（噪声）/ 阈值过远从不触发 | 需扩展 PATCH rules |
| 2 | **调分级**（L0↔L1↔L2） | L2 连续 N 次判"不动"→ 降 L1；L1 结构转强 → 升 L2 | 需扩展 PATCH rules |
| 3 | **改有效期** | 催化未到 → 续期；催化已过 → 缩短/退役 | `expires_at` 已存在，需开放修改 |
| 4 | **改条件类型/方向** | 下破改上破（结构反转）、加量能确认（假突破多） | 需扩展 PATCH rules |
| 5 | **新建规则** | 发现新的关键位/观察点 | ✅ 已有 create + 自动建规则服务 |
| 6 | **退役规则** | 见第 5 节退出场景 | 需新增（disable+归档，**不物理删除**） |
| 7 | **合并重复规则** | 同标的同向多规则（601600×6） | 需新增（合并为一条多档） |
| 8 | **改归属账户** | 规则跟账户走（清仓后换绑） | 需扩展 |
| 9 | 改池 / 调仓 | 战术层调整 | 已有工具；**调仓需人确认（R-001~R-009）** |

### 4.2 非对称护栏（本设计最关键的约束）

> 原则：**收紧保护可自动，放松保护必须人工确认。** 因为 agent 有"减少自己被唤醒次数"的自利倾向
> （放宽阈值 → 触发变少 → 显得清净，但风险敞口变大）。

| 变更方向 | 例子 | 授权 |
|---|---|---|
| **加保护** | 新建规则、收紧阈值、升 L2、缩短有效期、加量能确认 | agent 可自动执行 + 留痕 |
| **减保护** | 删/退役规则、降 L0/L1、放宽阈值、取消止损类条件、延长有效期 | **必须人工确认**（人工闸门）+ 证据包 |
| **等效** | 改条件类型但保护强度不变 | agent 可自动 + 留痕 |

**通用护栏**：①交易时段禁改（宪法）②单规则单日改动上限 1 次（防震荡）③每次改动写
`decision_audit` 并关联触发 id/归因证据 ④退役 = `enabled=false` + 归档标记，**不物理删除**
（保留历史可回溯）⑤变更后进入观察期，跟踪其触发频率与有效性变化。

### 4.3 回路学习的落地链条

```
触发 → 处置(handled/ignored) → 结果回填(价格/盈亏) → 归因(选股/择时/阈值/分级 哪一环错)
   → 提案(改什么/证据/预期) → [非对称护栏] → 执行 → 观察期跟踪 → 经验沉淀(experience)
```

## 5. 退出场景矩阵（用户明确要求）

### 5.1 触发级退出（微循环，单条触发的收敛）

| 退出态 | 判定 | 处置者 | 留痕要求 |
|---|---|---|---|
| `handled` | 已执行动作 | agent/人 | 动作 + 结果回填 |
| `ignored` | 知悉但不动作 | agent/人 | **必须写 reason + NEXT 条件**（下次何时才动） |
| `expired` | 超期未处置（盘后清单兜底） | 系统 | 自动收敛 + 计入未处置统计 |
| `superseded` | 被同一标的更新的触发取代 | 系统 | 指向新触发 id |

### 5.2 规则级退出（宏循环，规则何时结束）

| 场景 | 判定条件 | 授权 | 动作 |
|---|---|---|---|
| 目标达成 | 止盈/清仓/建仓完成 | agent 自动 | 退役（转观察或删除条件） |
| **逻辑证伪** | 建规则时的论据被推翻（事件反转/基本面变坏/政策转向） | 需证据 | 退役 + 经验沉淀 |
| 结构破坏 | 价格结构失效（支撑/趋势破坏） | agent 自动 | 退役或改条件类型 |
| 账户清仓 | 持仓归零且无观察理由 | agent 自动 | 退役；有观察理由 → 降 L0/L1 |
| 长期未触发 | 超 TTL / 连续 N 日未触发 | 系统提案 | 进入周度复核清单（**人工确认后**退役） |
| 被合并 | 同标的同向重复规则 | agent 提案 | 合并为一条多档（保留最严阈值） |
| 事件过期 | 催化已发生/已失效（`expires_at`） | 系统 | 退役 |
| 噪声超标 | 触发频率高但无信息量（N 次触发 0 次有价值处置） | agent 提案 | 调参或降级 |
| 分级重判 | L2 连续 N 次判"不动" | agent 提案 | 降 L1（**需人工确认**，属减保护） |

### 5.3 标的级退出（何时停止盯这个标的）

池子剔除 / 账户清仓且无观察理由 / 连续 N 次触发零信息量 / 长期停牌或退市风险 →
**停盯 + 归档**（保留历史规则与触发，便于复盘）。

### 5.4 回路级暂停（不是退出，是可恢复的挂起）

| 场景 | 行为 |
|---|---|
| 非交易日 / 非交易时段 | 引擎不 tick（已有） |
| 数据源降级 / 数据冻结 | 只记录不行动（R-011/R-013 精神）：降级期触发的行动类降为"待复核" |
| 熔断期 | 只保留风控类规则（止损/减仓），暂停机会类 |
| 维护窗口 / 用户冻结 | 全局静默，触发只落库不通知 |

### 5.5 交接级退出（L3 停等）

等人工决策；超时 → 保持原状 + 进未处置清单 + 升级提醒；**绝不自动执行**。

## 6. 节拍与 Token 预算（与触发数解耦）

| 循环 | 节拍 | LLM 唤醒/日 |
|---|---|---|
| 微循环（tick） | 实时（60s / fast 10s） | **0** |
| L1 日终汇总 | 每日 1 次（仅当当日有 L1 触发） | ≤1 |
| L2 摘要 | 盘中定时（队列非空）+ 盘后 1 次 | ≤4 |
| 宏循环（规则演化） | 日终 1 次 + 周度复盘 1 次 | ≤2 |
| 退出检查 | 日终（机械可判，仅异常时唤醒） | ≈0 |
| **合计** | — | **≤8 次/日，与触发数无关** |

## 7. 失败模式与对策

| 失败模式 | 对策 |
|---|---|
| 规则震荡（反复改阈值） | 单规则单日改动上限 1 次 + 观察期 |
| 过度退役（丢历史） | 只 disable + 归档，不物理删除 |
| 假退出（催化未过就删） | 退出必须带证据包 + 事件日历校验 |
| agent 自利（放阈值减少唤醒） | 非对称护栏：减保护一律人工闸门 |
| 汇总漏项（未处置清单没人看） | 盘后清单必须闭环；连续 N 日有未处置 → 告警 |
| 回路空转（改了但没效果） | 变更后跟踪触发频率/有效性，无改善则回滚 |

## 8. 待用户确认的问题（设计决策点）

1. **L3 的定义**：按本 RFC 取"人机交接层"？还是你想要的是"组合/系统层"（行业暴露、账户级共振）？
2. **"减保护"是否一律走人工闸门**（我建议是；这是防 agent 自利的关键）？
3. **节拍**是否接受（盘中定时 + 盘后 + 日终 + 周度，合计 ≤8 次 LLM/日）？
4. **退役**是否允许物理删除（我建议 disable+归档，永不物理删）？
5. **规则治理的授权边界**：agent 能否自行"新建规则"（增量保护）而不必每次问人？

## 9. 实施路线

| 阶段 | 内容 | 交付判据 |
|---|---|---|
| **Phase 2** 回路（本 RFC 3.1–3.3） | 摘要式批量唤醒 + L1 日终汇总 + 盘后未处置清单接入 19:30 例程 | agent 唤醒 ≤8/日且与触发数解耦；未处置清单日清 |
| **Phase 3** 演化（第 4 节） | PATCH rules 扩展（conditions/action_hint/expires_at/account）+ 非对称护栏 + 日终演化提案 | 每条规则变更可追溯 + 减保护全走人工 |
| **Phase 4** 退出与治理（第 5 节） | TTL/静默退役 + 重复合并 + 标的级停盯 + 治理指标 | 无过期规则数=0；同标的重复≤1；规则存活率可测 |

**治理指标**：规则存活率、演化接受率、平均规则寿命、触发→处置率、单位唤醒产出（有价值处置/LLM 唤醒次数）。
