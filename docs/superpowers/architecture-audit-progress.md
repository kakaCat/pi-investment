## 架构原则

### 六边形架构（Hexagonal Architecture）

```
┌─────────────────────────────────────────────┐
│         Adapters (Inbound)                  │
│  ┌──────────────────────────────────────┐   │
│  │      Application Services            │   │
│  │  ┌───────────────────────────────┐   │   │
│  │  │      Domain (Core)            │   │   │
│  │  │  • Entities                   │   │   │
│  │  │  • Value Objects              │   │   │
│  │  │  • Domain Services            │   │   │
│  │  │  • Ports (Interfaces)         │   │   │
│  │  └───────────────────────────────┘   │   │
│  └──────────────────────────────────────┘   │
│         Adapters (Outbound)                 │
│  • Repositories • DataSources • External    │
└─────────────────────────────────────────────┘
```

### 依赖规则

1. **依赖方向**: 外层 → 内层（单向）
   - ✅ Adapters → Application → Domain
   - ❌ Domain → Application
   - ❌ Application → Adapters

2. **接口隔离**: 内层定义接口，外层实现
   - ✅ Domain 定义 `IRepository` 接口
   - ✅ Adapters 实现 `Repository` 类
   - ✅ Application 依赖 `IRepository` 接口

3. **领域纯净**: Domain 不依赖任何框架
   - ❌ Domain 不导入 SQLAlchemy
   - ❌ Domain 不导入 Flask
   - ✅ Domain 只包含纯 Python 业务逻辑

## 决策记录

### ADR-001: 采用六边形架构
- **日期**: 2026-08-15
- **决策**: 重构为六边形架构（端口和适配器模式）
- **理由**: 
  - 提高可测试性
  - 降低耦合度
  - 便于替换技术栈

### ADR-002: 接口优先的 Repository 模式
- **日期**: 2026-08-15
- **决策**: 所有 Repository 必须定义接口
- **理由**:
  - 支持依赖倒置原则（DIP）
  - 便于单元测试 mock
  - 解耦应用层和数据访问层
