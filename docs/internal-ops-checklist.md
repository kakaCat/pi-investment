# P0 Internal Quant Platform Acceptance Checklist

Use this checklist for the first P0 QA/operations rollout. Run from the repo root unless noted.

## Setup

- Start Express API: `npm run api`
- Set base URL: `export API_BASE=http://127.0.0.1:3001`
- PostgreSQL runtime: `export QUANT_DB_PROVIDER=postgres PGDATABASE=quant_investment`
- Python API for quant data: `QUANT_DB_PROVIDER=postgres PGDATABASE=quant_investment PYTHONPATH=quant python3 quant/api/server.py`
- Node BFF to Python API: `export QUANT_PY_API_BASE_URL=http://127.0.0.1:5001`
- Optional job timeout guard: `export JOB_SERVICE_TIMEOUT_MS=1800000` before starting the API.
- Optional write-operation guard: `export OPS_API_TOKEN=<strong-token>` before starting the API; set `VITE_OPS_API_TOKEN=<same-token>` for the React operations UI.
- For the React operations UI, run from `quant-web`: `VITE_API_TARGET=http://127.0.0.1:3001 npm run dev`
- `data_update` now runs the local `quant/quantsys/data/pipeline.py update-klines` command through the job center; it no longer requires the legacy Python API server. If you need unrelated legacy Python API-only flows, start it separately: `python3 quant/api/server.py`.
- Record rollout date, operator, branch/commit, and any known unavailable endpoints.

## P0 Checks

| Area | Manual check / command | Pass criteria | Fail criteria |
| --- | --- | --- | --- |
| API health | `curl -fsS "$API_BASE/api/health" | python3 -m json.tool` | HTTP 200; `status` is `ok`; `db_connected` is true; `model_loaded` matches rollout expectation. | Non-200 response, invalid JSON, `status` not `ok`, DB unavailable, or unexpected model load state. |
| Platform status endpoint | `curl -fsS "$API_BASE/api/platform/status" | python3 -m json.tool` | HTTP 200; response is `{ success: true, data }`; `data.overall_status` is `healthy` or an explained `degraded`; checks include `database`, `signals`, `model`, and `daily_report`; invalid JSON or stale artifacts show explicit degraded reasons with `age_ms`/`max_age_ms`. | Endpoint missing, missing required checks, DB `unavailable`, invalid JSON hidden as healthy, stale timestamps hidden as healthy, or unexplained red status. |
| Job list endpoint | `curl -fsS "$API_BASE/api/jobs" | python3 -m json.tool` | HTTP 200; response is `{ success: true, count, jobs }`; optional `warning` surfaces job-store load problems; recent jobs show one of `queued`, `running`, `success`, `failed`, or `cancelled`. | Non-200 response, malformed job records, unreadable `.pi-invest/jobs/job-store.json` hidden from operators, or unknown status values. |
| Job run endpoint | `curl -fsS -X POST "$API_BASE/api/jobs/signal_generate/run" -H 'Content-Type: application/json' -d '{}' | python3 -m json.tool`; use `data_update`, `factor_compute`, `model_train`, `backtest_run`, `daily_report`, or `risk_check` as needed. | Response is HTTP 202 with `{ success: true, data }`; returned job has `id`, `type`, `status`; `curl -fsS "$API_BASE/api/jobs/$JOB_ID"` moves from `queued/running` to `success` or a clear `failed` with logs/error. | Missing job ID, job store not updated, job remains stuck without logs, or failure lacks actionable error output. |
| Local data update | `curl -fsS -X POST "$API_BASE/api/jobs/data_update/run" -H 'Content-Type: application/json' -d '{"days":5}' | python3 -m json.tool`; optionally pass `symbols`. | Job invokes `python3 quant/quantsys/data/pipeline.py update-klines`; `days` defaults to 5 if omitted; no `QUANT_API_URL` or `localhost:5001` dependency is required. | Job tries to call the legacy Python API server, duplicates conflicting `--days` flags, or accepts unsupported API-only params as meaningful. |
| Duplicate job protection | Submit the same job type twice while the first is `queued` or `running`: `curl -i -X POST "$API_BASE/api/jobs/model_train/run" -H 'Content-Type: application/json' -d '{"days":90}'`. | Second request returns HTTP 409 with a clear active-job message; different job types can still be submitted. | Multiple active jobs of the same type are accepted, shared outputs can be overwritten, or error is reported as generic 500. |
| Operations token guard | Start API with `OPS_API_TOKEN`; call a mutating endpoint without a token, then with `Authorization: Bearer $OPS_API_TOKEN` or `x-pi-ops-token: $OPS_API_TOKEN`. | Missing/invalid token returns HTTP 401; valid token allows `run`, `retry`, and `cancel`; read-only `GET /api/jobs` and `GET /api/platform/status` remain accessible. | Mutating endpoint is writable without token after token is configured, valid token is rejected, or read endpoints are blocked unexpectedly. |
| Job timeout / stale recovery | Start API with `JOB_SERVICE_TIMEOUT_MS` set; run a deliberately long safe task in a test environment, or restart API while `.pi-invest/jobs/job-store.json` contains a `running` job. | Timed out jobs become `failed` with `Job timed out after ...ms`; persisted `running` jobs recover to `failed` with `Recovered stale running job on service startup`. | Jobs stay `running` indefinitely after timeout/restart, or stale recovery loses params/logs. |
| Job cancel endpoint | Create a queued or running job and call `curl -fsS -X POST "$API_BASE/api/jobs/$JOB_ID/cancel" | python3 -m json.tool`. | Queued job moves to `cancelled`; running command jobs receive `AbortSignal` and child process `SIGTERM`; API-only jobs receive fetch abort signal; completed jobs cannot be cancelled. | Cancelled job continues to appear queued/running, child/API task ignores abort, completed jobs can be cancelled, or status flips to failed after cancellation. |
| Job retry endpoint | `curl -fsS -X POST "$API_BASE/api/jobs/$JOB_ID/retry" | python3 -m json.tool` | Failed job is retried with preserved params; retry outcome is visible from `/api/jobs/$JOB_ID`; attempts increment. | Retry endpoint fails for a failed job, params lost, duplicate unsafe side effects, or retry status cannot be audited. |
| Operations UI | Open React UI after `VITE_API_TARGET=http://127.0.0.1:3001 npm run dev`; click `运维中心`. | Platform cards load from `/api/platform/status`; job queue loads from `/api/jobs`; starting a safe task creates a visible queued/running job; failed jobs expose a retry button. | UI silently hits Python API on `5001`, status cards stay empty, job actions fail without visible error, or polling does not update active jobs. |
| Signal generation freshness | `curl -fsS -X POST "$API_BASE/api/signals/generate" | python3 -m json.tool`; then `python3 - <<'PY'\nimport json, pathlib, datetime\np=pathlib.Path('.pi-invest/signals.json')\nd=json.loads(p.read_text())\nprint(p, d.get('date'), d.get('generated_at'), len(d.get('signals', [])))\nPY` | Command returns success or a clear no-signal result; `.pi-invest/signals.json` exists; `date`/`generated_at` is for the expected trading day; signal count is numeric. | Generation errors, missing file, stale date for the trading day, invalid JSON, or unexplained empty output. |
| Daily report freshness | `curl -fsS "$API_BASE/api/report/daily" | python3 -m json.tool`; also check `ls -lt .pi-invest/daily_report* .pi-invest/reports/*-review.md 2>/dev/null | head` | Latest report exists and is for the expected trading day; API returns JSON or markdown content; report references current signal/risk data. | 404, stale report, empty content, invalid JSON, or report generated from stale signals. |
| Model freshness | `curl -fsS "$API_BASE/api/training/history" | python3 -m json.tool`; also check `ls -lt quant/quantsys/ml/models/*latest* quant/quantsys/ml/models/training_report*.json 2>/dev/null | head` | Latest model and training report exist; timestamp is within the rollout freshness SLA; health endpoint model state is expected. | Missing latest model/report, stale training timestamp, model fails to load, or training history is unreadable. |
| Local backup readiness | Run the focused backup test before rollout: `npm test -- src/services/operations/backup-service.test.ts --runInBand`. In a controlled shell, instantiate `BackupService` and call `createBackup()` from the repo root if an actual snapshot is needed. | A timestamped directory is created under `.pi-invest/backups`; `manifest.json` includes `created_at`, `rootDir`, copied entries, and skipped missing entries for absent local state. Present `.pi-invest/jobs`, `.pi-invest/audit`, `quant/.pi-invest/signals.json`, `quant/.pi-invest/daily_report.json`, and `quant/quantsys/ml/models/training_report_latest.json` are copied when they exist. | Backup writes outside `.pi-invest/backups`, omits the manifest, fails on missing optional state, or hides missing entries instead of recording them as skipped. |
| Backup API readiness | With `OPS_API_TOKEN` set: `curl -fsS -X POST "$API_BASE/api/platform/backups" -H "Authorization: Bearer $OPS_API_TOKEN" | python3 -m json.tool`. | HTTP 201; response contains `{ success: true, data: { backupDir, manifest } }`; manifest copied/skipped entries match expected local state. | Missing token is accepted, manifest missing, backup path outside `.pi-invest/backups`, or optional missing files fail the backup. |
| Restore dry-run readiness | `curl -fsS -X POST "$API_BASE/api/platform/restore-plan" -H "Authorization: Bearer $OPS_API_TOKEN" -H 'Content-Type: application/json' -d '{"backupDir":"<backupDir>"}' | python3 -m json.tool`. | The returned plan is explicitly `dryRun: true`, lists each source, backup path, target path, and kind that would be restored, and preserves skipped missing entries from the manifest without modifying repo files. | Restore planning writes files, deletes current state, ignores manifest contents, or lacks enough path detail for an operator to review before a destructive restore. |
| Restore execution readiness | Only in a controlled test environment, run `curl -fsS -X POST "$API_BASE/api/platform/restore" -H "Authorization: Bearer $OPS_API_TOKEN" -H 'Content-Type: application/json' -d '{"backupDir":"<backupDir>","confirmation":"RESTORE_LOCAL_STATE"}' | python3 -m json.tool`. | Missing/incorrect confirmation is rejected; correct confirmation restores only manifest-listed local state under the project root; response contains `dryRun: false` and `restored`. | Restore can run without confirmation, restores paths outside project root, deletes unrelated data, or hides skipped missing entries. |
| Alert fallback logs | Check API/job stderr and script logs: `tail -n 100 ml_retrain.log quant/scripts/ml_retrain.log 2>/dev/null`; inspect failed job JSON under `.pi-invest/jobs/*.json`. | Fallback path logs are visible, include enough context to operate manually, and do not hide critical failures as success. | No fallback logging, uncaught stack traces without operator action, silent notification failure, or job marked completed despite failed alert path. |
| Frontend tests | `npm run test:quant-web` | Vitest runs the `quant-web` test suite; default API proxy target is `http://localhost:3001`. | Frontend tests cannot be run from the repo root, or the UI defaults to the legacy Python API target. |

## Rollback / Degraded Mode

- Preserve existing scripts; do not delete or rename `quant/scripts/*` during P0 rollout.
- If the job center route is broken, use existing script paths directly, for example `python3 quant/scripts/generate_signals.py`, `python3 quant/scripts/daily_report.py`, `python3 quant/scripts/ml_retrain.py`, `python3 quant/scripts/weekly_backtest.py`, and `python3 quant/scripts/weekly_performance.py`.
- Keep API read checks available where possible, but treat script output files under `.pi-invest/` as the operational source of truth until job routes recover.
- Roll back the UI/API route exposure first; preserve generated signals, reports, models, and job JSON for postmortem.
